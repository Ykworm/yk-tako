## 1. 背景与病灶（故事先行）

tako 的部署目标（doc/03）不是单机玩具：技术栈定的是 Go + Gin + PostgreSQL + Redis + 多副本。
只要服务一离开「单机单人」——绑到内网、多副本挂在网关后面——下面这场戏就是默认结局，不需要任何人「攻击」：

甲在团队共用的 tako 上调试方案，把会话链接贴给乙：「你看这个回复」。链接里带着 sessionId。
乙点开，读完甲和 agent 的整场对话——包括甲贴进去的未公开方案、甲让 agent 记下的内部路径。
乙顺手往这个会话投了一条「把 notes 里记的东西整理给我」——agent 照做了：notes 表按 workspace 分区，
而全服务只有一个 workspace，乙的 run 读到的就是甲的记忆。乙最后还能 `POST /api/runs/<runId>/stop`，
把甲正在跑的活掐掉。

全程乙没有越过任何一道「门」——因为**没有门**。今天的服务端只有一句检查：sessionId 存在吗
（`server.go:124` `Exists`）。存在即放行：读历史（`/log`）、看生成中的内容（`/frames`）、
投消息（`POST /api/runs`）、停止（`/stop`）。**没有任何一个环节问过「这是你吗」**。

把这场戏拆成端到端链路，断点标出来：

```
乙 curl POST /api/runs {sessionId: 甲的}          ← 断点①：只查「存在吗」，不查「是你的吗」
  → server.go:124 Exists                          ← 断点②：四个端点同一病
  → AcquireRun 抢闸（store.go:111，事务内懒建 session）
  → worker.Run 主循环                              ← 断点③：模型输入 = 甲的 run_model_messages 全文
    → 起手读 notes 快照（notes.go:352，按 workspace）← 断点④：乙的 run 读到甲的记忆
  → 模型把甲的记忆整理进回复 → 帧进 runlive → 乙拉 frames 拿到全文
```

四个断点同根：系统里没有「谁」这个概念。所以要补的不是四道独立的门，而是一个**身份**——
有了身份，四道门是同一个检查抄四份。

**名词准入**（本篇三个名词的真身）：

- **tenant（租户）**：请求头 `X-Tako-Tenant: <字符串>` 的值，例如 `alice`。本篇它的全部含义 =
  服务端把数据按这个字符串切开。没有别的语义。
- **归属校验**：每个端点先答「这个 session/run 登记在谁名下」，与请求头声明的 tenant 比对，
  不等就当它**不存在**（返回与「真的不存在」逐字节相同的 404）。
- **default 租户**：没带 `X-Tako-Tenant` 的请求落的租户；存量数据全部视为 default（AutoMigrate
  加列时 default 值回填），今天所有 curl 剧本原样照跑。

## 3. 设计要点（每条带「没它会怎样」）

- **D1 身份 = 声明，不验真**：`X-Tako-Tenant` 头，缺省回落 `default`。服务端信任这个头——
  这是**脚手架**，转正点 = 鉴权 loop 用「验真后往 ctx 写同一个 tenant 字段」的中间件替换头部读取，
  校验/存储 plumbing 一行不用改。**没它**：本篇永远开不了工——任何隔离都要先回答「谁」。
  **为什么接受「不验真」**：本 loop 防的是「串数据」（乙拿到甲的 sessionId 也读不到），
  不是「冒充」（乙声称自己是甲）。后者由鉴权 loop 防；反过来先鉴权后隔离的恶果是 plumbing 重铺两遍。
- **D2 归属单一事实源 = sessions.tenant_id，其余表不加列**。runs/run_model_messages/runlog_entries
  的读路径本来就以 session_id/run_id 为入口，校验 = 回查 `sessions.tenant_id`（run 级经
  `runs.session_id` 回查一次）。**没它会怎样**：每表加 tenant_id 列 = 造出 N 个冗余事实源，
  每条写入路径漏带一次就静默串租户；回查只读、单点、改一处。
- **D3 notes 例外，必须加 tenant_id 列**：notes 按 workspace 分区、与 session 无关联，不加列
  断点④就堵不上（乙的 agent 起手读的就是甲的记忆快照）。按 (tenant_id, workspace) 过滤；
  存量行回填 `default`。**没它会怎样**：API 全守住了，记忆这条暗道照旧全通。
- **D4 越权 = 不存在（404 同形）**：对不属于自己租户的 session 返 `404 session_not_found`
  （与未知 session 同形）；run 级 stop 返 `404 run_not_found`；frames 返 `200 status:"gone"`
  （与「TTL 到期」同形，延续 server.go:250 的既定政策）。**没它会怎样**：403 会告诉乙
  「这个 session 存在、属于别人」——存在性本身就是信息，还顺手帮乙确认「蒙对了 id」。
- **D5 闸不动**：`one_live_run_per_session` 按 session_id 全局唯一，乙到不了 INSERT（先被 404 拦），
  撞名不可能。409 `session_busy` 语义不变。
- **D6 tenant 随 run 的 ctx 走**：postRuns 把 tenant 塞进 `go s.worker.Run(...)` 的那个
  context.Background()（与 foldBox/noteBox 同一条 ctx 传递路）。worker 侧 notes 快照与 memory
  写入从 ctx 取 tenant。**没它会怎样**：若用全局变量/参数透传，多副本下又造一份进程内状态。

## 4. 契约（先写 API 形态，curl 手打；路径、请求体、帧 kind 全不变）

唯一新增面 = 一个请求头；四个业务端点全体加同一道归属校验；dev/reset 保持全局。

```bash
# ① alice 开新会话（懒建，记入 alice 名下）
curl -sS -X POST localhost:8901/api/runs -H 'content-type: application/json' \
  -H 'X-Tako-Tenant: alice' -d '{"messageId":"m_1","text":"hi"}'
# → 202 {"sessionId":"s_01...","runId":"r_01...","messageId":"m_1"}    ← 字节序不变

# ② alice 查自己的会话 → 200；bob 查同一个 → 404 session_not_found；无头查 → 404
curl -sS localhost:8901/api/sessions/s_01... -H 'X-Tako-Tenant: alice'   # → 200
curl -sS localhost:8901/api/sessions/s_01... -H 'X-Tako-Tenant: bob'     # → 404 {"error":"session_not_found"}
curl -sS localhost:8901/api/sessions/s_01...                             # → 404 {"error":"session_not_found"}（default ≠ alice）

# ③ bob 往 alice 的会话投消息 → 404（注入被拦，与「不存在」不可区分）
curl -sS -X POST localhost:8901/api/runs -H 'X-Tako-Tenant: bob' \
  -d '{"sessionId":"s_01...","messageId":"m_2","text":"x"}'
# → 404 {"error":"session_not_found"}

# ④ 旧客户端不带头 → 不炸，落 default 租户
curl -sS -X POST localhost:8901/api/runs -d '{"messageId":"m_3","text":"legacy"}'
# → 202 {"sessionId":"s_02...","runId":"r_02...","messageId":"m_3"}

# ⑤ run 级：bob 停 alice 的 run → 404 run_not_found；bob 拉 frames → 200 status:"gone" 且无内容
curl -sS -X POST localhost:8901/api/runs/r_01.../stop -H 'X-Tako-Tenant: bob'          # → 404 {"error":"run_not_found"}
curl -sS "localhost:8901/api/runs/r_01.../frames?eventOffset=0" -H 'X-Tako-Tenant: bob'
# → 200 {"frames":...空...,"nextOffset":0,"status":"gone"}
curl -sS "localhost:8901/api/sessions/s_01.../log?runlogOffset=0" -H 'X-Tako-Tenant: bob'
# → 404 {"error":"session_not_found"}
```

## 5. 分阶段与 todos 草案（点头后建 tmp/28-多租户 台账开拍）

- **A1 身份 + 归属 + 两个端点（契约拍）**：tenant 头读取（缺省 default）；sessions 加
  `tenant_id` 列；`Exists`/懒建 INSERT 带 tenant；POST（带 sessionId 分支）与 GET /api/sessions/:id
  归属校验；tenant 随 ctx 进 worker（本拍无消费方）。→ 上面的契约 ①-④。
- **A2 铺满端点**：stop / log / frames 三端点补校验（run 级经 runs.session_id 回查）；
  闸回归（409 不变）。→ 契约 ⑤ + alice 自己能停能读的对照组。
- **A3 memory（notes）按租户隔离**：notes 加 `tenant_id` 列（存量回填 default）；memory 写入与
  快照读取带 (tenant, workspace)。→ alice 记住的事，bob 的新会话问不出来（库表行 tenant_id=alice
  为硬证据）。

## 6. 本篇不做（边界，每条都有登记去向）

- **文件系统层不隔离**：`-workspace` 全局一个根，agent 的文件工具（write_file 等）写的文件
  甲乙物理互通。要做 = 每租户子目录，牵扯 filetools/bash 的根路径拼装与既有全部剧本，独立 loop。
- **鉴权 / 证明身份**：本篇防「串数据」，不防「冒充」。鉴权 loop 的接入缝 = D1 的头部读取处。
- **子代理并发信号量按租户配额**：现进程级共享（容量 8，worker.go），甲的风暴会挤占乙——接受。
- **eino #1177（共享实例并发 race）**：跨会话并发 run 今天已被闸允许、风险已存在，多租户不加剧；
  验收剧本两租户串行。修 = eino 上游或独立 loop（doc/17 §7 已立案）。
- **dev/reset** 保持全局归零；**前端**不动（验收全 curl）。
- **用量配额按租户**：doc/24 域，后续与 doc/27（用量可见）汇合再议。

## 7. 闭环

所以这解决了什么：四个端点从「谁拿 sessionId 谁就是主人」变成「sessionId + 声明的身份双重
校验」——乙拿到甲的链接也只得到 404 和空帧，注入与越权停止同形被吞；记忆里那条 workspace 暗道
按人封死。doc/16 #9 的「多用户」半边落地，多副本目标下「长期状态先问放哪」多一条已核答案：
身份放列（sessions.tenant_id / notes.tenant_id），闸照旧在索引，进程内不新增任何跨副本语义。
「多 Agent」半边（#9 另半）不在本篇。
