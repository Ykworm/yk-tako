## 0. 大白话版

**tako 要做的是什么。** 不是“单机聊天工具”，是**多租户 agent 运行时 + 会话**：一个部署里有很多租户，每个租户有自己的用户、会话、agent、记忆、文件和配额；租户之间不能互相看见。

**四层关系，一句话：**

```
平台（platform）
  └─ 租户 tenant（隔离 + 计费 + 配额）
       ├─ 成员 tenant_members（user + role + status）
       ├─ 会话 sessions（tenant_id + user_id + visibility）
       │    └─ run（一次执行）
       ├─ agent（租户级资源，creator + visibility）
       ├─ notes（tenant 共享 / user 私有）
       └─ workspace / files / sandbox（租户级隔离）
```

**团队功能已拍支持，怎么做。** 每个用户注册时自动得到一个**个人 tenant**（单成员）；团队是**多成员 tenant**。
A6 做团队后端 API（创建、邀请、成员/角色、团队 agent/notes）；团队前端页面是独立 loop，但 A6 契约要够前端直接用。
用户可以在多个 tenant 之间切换，个人数据不搬家。

**Alice 的一天。**

```
Alice 注册
  → 自动建 personal tenant t_alice，Alice 是 owner
Alice 建 session s1（private）
  → s1.tenant_id=t_alice, s1.user_id=alice
Bob 和 Alice 在同一个团队 Acme（另一个 tenant）
  → Bob GET s1：404（private，不是他的）
Carol 在另一个 tenant
  → Carol GET s1：404（跨租户）
Alice 加入 Acme
  → 只多一条 tenant_members(t_acme, alice, member)
  → 她切到 Acme，看到 Acme 的 agent/notes；s1 仍在个人 tenant
Acme owner 邀请 Bob
  → Bob 接受后成为 member；团队共享 agent/notes，但 session 仍默认私有
```

**五个关键决定。**

1. **tenant 是一等公民**：所有资源带 `tenant_id`；不搞“个人资源 + 可空 team_id”的双路径。
2. **个人 tenant 先行，团队 tenant A6 后端落地**：个人 tenant 现在就能用；团队后端 A6 做，团队前端页面独立 loop；表结构、token、切租户 API 从 A0 起按多租户做。
3. **session 默认私有**：同租户普通成员也读不到别人的会话；团队共享要显式 `visibility=tenant`。
4. **notes 分 scope**：`user` 私有、`tenant` 共享；模型默认只写个人记忆，团队记忆由 owner/admin 管。
5. **文件/沙箱/配额是 P0**：多租户 agent 运行时不能共用一个全局 workspace，也不能让一个租户占满所有并发。

**分几步走。**

- **A0 身份与个人 tenant**：users/tenants/members、注册登录、refresh、切租户、system admin；个人 tenant 自动建。
- **A1 会话归属**：`sessions.tenant_id/user_id/visibility`；建/读/停/拉 log/frames 全部按身份校验；store 层同事务守。
- **A2 角色与后台**：owner/admin/member/viewer、成员管理、最后一个 owner、system admin 路由、审计。
- **A3 记忆**：notes 的 `tenant/user` scope；快照、写入、定位、删除全部按 scope；个人记忆不串。
- **A4 工作区与文件**：每 tenant 一个 workspace 根；file tools/bash 按 tenant 解析；多副本共享存储。
- **A5 并发与配额**：按租户限并发/子代理/token/存储；eino #1177 的决策；两租户并发验收。
- **A6 团队**：创建团队、邀请、角色、切换、团队 agent/notes；session 仍默认私有。
- **A7 以后**：API key、组织/跨租户共享、SSO、账单。

**故意不做。** 不做公开注册以外的账号体系；不做 OIDC/SSO；不做组织/跨租户共享；不做 API key capability；不做计费；不做团队嵌套/部门树；不做“管理员默认读所有会话”。这些都留了缝，但不在本方案施工。

**所以这解决了什么。** tako 从“谁有 sessionId 谁就是主人”变成“tenant + user + role + 会话归属”四重边界；个人用户今天就能用，团队以后只是多一条 membership，不用搬 session/notes/files；后台管理有平台管理员和租户角色两条轴，不会把“空间管理员”和“平台管理员”混成一个 role。

### 1.2 病灶：四个具体的失败故事

**故事一：跨租户读会话。** Alice 在 tenant A 建了 session `s_1`，把链接贴给 Bob。Bob 在 tenant B，直接 `GET /api/sessions/s_1`。今天服务端只问“s_1 存在吗”，存在就返回 200；Bob 读到 Alice 和 agent 的整场对话，还能 `POST /api/runs` 往会话里投消息、`POST /stop` 停掉 Alice 的 run。

**故事二：笔记暗道。** Alice 让 agent 记下“deck 在 output/deck.html，不要重建”。Bob 在 tenant B 开自己的 run，agent 起手读 notes 快照——notes 按全局 workspace 分区，Bob 读到的是 Alice 的记忆，并在回答里把路径说出来。API 全守住了，记忆这条暗道照旧全通。

**故事三：文件暗道。** 文件工具和 bash 共用一个 `-workspace` 根。Bob 不需要碰 Alice 的 session：自己开一个 run，让 agent `cat` 共享目录里的文件，就能读到 Alice 的方案、代码、上传的文档。

**故事四：配额与并发。** tenant A 开了 50 个会话、每会话一个 run，把模型配额和子代理的 8 个槽位占满；tenant B 的 run 排队等不到子代理。更糟的是，所有租户共用同一个 eino agent 实例，doc/17 的 #1177 共享实例并发 race 从“同一个人多标签页”升级成“两个租户并发可能互相取消/串状态”。

**四个故事同根：系统里没有“tenant/user/role”这三个概念。** 只加一个 `tenant_id` 列不够：session 还需要 owner，notes 需要 scope，文件需要租户根，后台需要角色，并发需要配额。这是数据模型变更，不是加一个 middleware。

### 1.3 为什么“先不做团队，以后加 team_id”会返工

如果今天做成“资源归 user，`team_id` 可空”，以后加团队会遇到：

- 每个查询都要分“个人资源”和“团队资源”两条路径；
- session/notes/files/usage 从个人转团队，要改 owner、改路径、改审计；
- “分享”是改 `team_id`，“取消分享”是改回去，权限和配额都跟着抖；
- 团队里“这个 session 是谁的”和“这个 session 属于哪个团队”两套语义。

**本方案选：tenant 从第一天就在；个人只是单成员 tenant。** 以后加团队，只是 `tenant_members` 多一行，资源不搬家。

### 1.4 WeKnora 的可借鉴与不可借鉴

WeKnora 的权限模型值得看，但它是“多租户知识库 + 跨租户共享”，tako 是“agent 运行时 + 会话”，不能照抄。

## 2. 目标与非目标

### 2.1 目标

1. **tenant 隔离**：session/run/log/frames/notes/files/usage/audit 不跨租户。
2. **个人 tenant 先行**：注册即用；不需要先建团队。
3. **团队功能**：团队 = 多成员 tenant；A6 做创建/邀请/成员/角色/团队 agent/notes 后端；用户可属于多个 tenant；切租户不搬数据。
4. **角色与后台**：平台 system admin + 租户 owner/admin/member/viewer；成员管理、审计、最后一个 owner 保护。
5. **会话隐私**：默认 private；团队共享显式开启；管理员默认不看内容。
6. **记忆分 scope**：个人记忆 / 团队记忆分开，写入和快照都不串。
7. **文件隔离**：每 tenant 一个 workspace 根；多副本共享存储。
8. **配额与公平**：按租户限并发、子代理、token、存储；不被一个租户拖垮。
9. **多副本**：身份、角色、refresh、配额都不放进程内。

### 2.2 非目标 / 后续 loop

- 团队前端页面（创建/邀请/成员页的交互）——独立 frontend loop；A6 后端 API 在本篇，契约要够前端直接用；
- 组织/跨租户共享（共享 agent、共享 KB）——以后；
- API key capability / 机器 principal——以后；
- OIDC/SSO、账单/席位、审计导出——以后；
- 团队嵌套/部门树——明确不做，用扁平 tenant + project 代替；
- 管理员默认读所有会话——不做；support access 单独设计。

### 2.3 信任模型与上线闸门

**假设租户里的 agent 会跑 bash、写文件，默认按“不可信代码”设计。** 只做路径隔离不够：`bash` 可以 `cat /etc/passwd`、读别的租户的绝对路径、访问网络。真正的隔离需要 per-tenant 沙箱（容器/命名空间/受限命令集 + 资源限制）。

因此设两道闸：

- **A4 完成前**：只允许个人 tenant、单用户/本地开发；不开放多租户。文件工具仍用全局 workspace，但部署只绑 loopback。
- **A5 完成前**：不开放外部团队；A4 的 per-tenant workspace 必须已完成，A5 还要有配额 + eino 并发决策；如果租户不可信，还要有沙箱。

这一版的沙箱不是容器，也不是「把工作目录当成牢笼」。本机的 `sandbox-exec` 要真正 apply 成功，生产 run 里的 bash 和 `-dev` 探针才套同一份配置：默认拒绝，只允许读写当前会话目录，并显式拒绝读 `/etc/passwd` 和 `/private/etc/passwd`。命令的 cwd 只决定它启动时站在哪个目录，挡不住绝对路径。binary 不在，或者系统拒绝 apply 时，bash 直接拒绝，不退回去跑一条裸命令，dev 探针也不报 `sandboxed: true`。时长帽到点后，工具结果写成「bash 超时」，父 run 不因此失败。2026-10-18 在这台 Mac 上打过：`cat /etc/passwd` 得到 Operation not permitted，`pwd` 和写会话根里的文件仍然成功。那次 apply 是被允许的。后来同一台机器上 apply 会被拒绝，这种时候不能把「退出码」当成已经隔离。

## 3. 核心模型与不变量

### 3.1 名词

- **platform**：整个部署。平台管理员 `is_system_admin` 管全局设置、所有租户、平台审计，不等于任何租户的 owner。
- **tenant**：隔离、计费、配额的单位。`kind=personal`（单成员）或 `team`（多成员）。个人 tenant 在注册时自动创建；团队 tenant 由用户创建/邀请加入。
- **user**：全局身份。一个 user 可以属于多个 tenant；角色在每个 tenant 不同。
- **membership**：`tenant_members(tenant_id, user_id, role, status)`。这是角色唯一真源；`active` 才参与鉴权。
- **session**：tenant 内的会话资源；`tenant_id` 必填，`user_id` 是 owner，`visibility=private|tenant`。
- **run**：session 的一次执行。`runs.session_id` 指向 session；tenant/user 经 session 派生。
- **agent**：tenant 级 agent 定义；`created_by`、`visibility`、`is_builtin`。
- **note**：tenant 级记忆；`scope=user|tenant`。两档都写 `user_id`。`scope=tenant` 写的是创建者，列是 `not null default ''`，不是 NULL。
- **workspace**：tenant 的文件根；`<root>/tenants/<tenant_id>/...`。
- **api key**：机器身份，后续 loop；不混入人类角色。

### 3.2 不变量

1. **每个资源都有 `tenant_id`**：session/agent/note/file/usage/audit 直接有；run/message/runlog 经 session 回查。
2. **角色只从 `tenant_members` 来**；JWT 里不带 role，降级立即生效。
3. **session 默认 private**；同 tenant 非 owner 也 404；`visibility=tenant` 才可读，写/stop 仍归 owner。
4. **notes 的 scope 写入时定死**；个人记忆不会因为加入团队变成团队可见。
5. **归属校验在 store 的同一笔事务里**，不只在 handler；handler 的 404 是快路径，不是唯一防线。
6. **不跨 tenant 引用**：session 不能引用别的 tenant 的 agent；agent 不能引用别的 tenant 的 model/MCP；要共享就复制/导入，不做跨租户指针。
7. **身份/角色/refresh/配额不放进程内**；多副本共享 PG/Redis。
8. **个人 tenant 自动建；团队是另一个 tenant**；资源不搬家。
9. **平台管理员与租户角色正交**；平台管理员不自动是 tenant owner。
10. **认证失败 401，授权失败 403，资源不可见 404**；不用 403 泄露存在性。

## 4. 数据模型

### 4.1 表

> ID 沿用现有 `s_`/`r_` 前缀风格：`u_`/`t_`/`a_`/`n_` + ULID。所有表在 PG；dev 清库重来，不做旧数据兼容。

```sql
users(
  id            text primary key,          -- u_<ULID>
  email         text not null unique,
  password_hash text not null,             -- bcrypt/argon2id
  is_system_admin boolean not null default false,
  disabled      boolean not null default false,
  token_version int not null default 0,    -- 改密/禁用时递增，旧 AT 失效
  default_tenant_id text,                  -- UX 偏好，不是授权真源
  created_at    timestamptz not null
)

tenants(
  id         text primary key,             -- t_<ULID>
  kind       text not null,                -- personal | team
  name       text not null,
  status     text not null default 'active', -- active | suspended | deleted
  plan       text not null default 'free',
  created_by text not null,
  created_at timestamptz not null,
  max_concurrent_runs int not null default 8,
  max_subagents       int not null default 8,
  daily_tokens        bigint not null default 0, -- 0 = 不限制
  max_storage_bytes   bigint not null default 0  -- 0 = 不限制
)

tenant_members(
```

### 4.3 为什么 run/message/runlog 不加 tenant_id

读它们本来就从 session/run 进；`tenant_id` 只在 session 上，回查一次就够。每表加 tenant_id 会造多个事实源，写入路径漏一次就串。**但 store 层的每个入口必须在同一笔事务里回查 session 的 tenant/user/visibility**；不能只在 handler 查。

### 4.4 为什么 notes 必须加 tenant_id + scope

notes 按 workspace 分区、与 session 无关；不加 tenant_id 堵不住“Bob 的 run 读 Alice 记忆”。`scope` 决定它是个人记忆还是团队记忆：

- `scope=user`：`user_id` 是本人，只有本人读写；
- `scope=tenant`：`user_id` 写创建者，不是 NULL。全租户可读，只有 owner/admin 能写（模型默认不能写）。

快照读取 `tenant` 共享 + 本人 `user` 私有；帽子和 advisory lock 按 `(tenant_id, scope, user_id, workspace)` 分开。

### 4.5 迁移与存量

- 当前未上线：**dev 库直接 wipe**，不做旧数据兼容；`dev/reset` 仍是 dev-only 全局归零。
- 如果一定要保留 dev 数据：建一个 bootstrap tenant + bootstrap user，把旧 session/notes 归到它；**不要**造一个公开的 `default` tenant。
- `sessions.tenant_id/user_id`、`notes.tenant_id/scope/user_id` 都 `NOT NULL`。`notes.user_id` 默认空串；`scope=tenant` 仍写入创建者，不写 NULL。
- `agentsDir` 现在全局；A0-A3 **不落 agents 表**，继续用全局内置 agent（`sessions.agent_id=NULL` 表示默认）；A6 起每个 tenant seed built-in agent，再开放租户自定义 agent，`agents.tenant_id` 才非空。
- `-workspace` 现在全局；A4 改成 `-workspace-root` + per-tenant 根；A4 完成前不开放多用户。

## 5. 身份、登录与租户上下文

### 5.1 Token

- **Access token**：JWT，15 分钟；claims：`sub`（user_id）、`tid`（active tenant_id）、`jti`、`ver`、`iat`、`exp`、`iss`、`aud`。
- **Refresh token**：随机 256-bit opaque，30 天；PG 只存 SHA-256；刷新时旋转（旧 token revoked，新 token 同 family）；旧 token 再用 → 撤销 family。
- **不在 JWT 里放 role**：角色每次从 `tenant_members` 解析；降级/移除立即生效。
- 签名密钥从环境变量加载；启动缺失 fail fast；多副本共享；校验算法白名单。
- 改密/禁用/移除成员：递增 `users.token_version` 或撤销 refresh + 校验 membership；旧 AT 最多活 15 分钟，必要时加 denylist。

### 5.2 注册、登录、刷新、切租户、登出

```
POST /api/auth/signup    {email,password}
  → 201 {user, activeTenant, memberships, accessToken, refreshToken}
  → 同一笔事务：users + tenants(personal) + tenant_members(owner)

POST /api/auth/login     {email,password}
  → 200 同上

POST /api/auth/refresh   {refreshToken}
  → 200 {accessToken, refreshToken}
  → 旧 refresh 旋转/撤销；active tenant 按最后一次选择/默认 personal 重新解析

POST /api/auth/switch-tenant {tenantId, refreshToken?}
  → 200 新 token 对，active tenant 切换
  → 必须是 active membership；旧 refresh 撤销；更新 last active

POST /api/auth/logout
  → 204；撤销当前 refresh（或该用户全部 refresh，按产品选择）

GET  /api/auth/me
  → 200 {user, activeTenant, role, memberships}
```

登录响应里的 `memberships`（tenant_id、name、role）是给前端工作区切换器/按钮显隐用的；**后端每个路由仍自己查角色**，不信前端。

### 5.3 中间件与租户上下文

```
请求 → Auth middleware
  → 白名单（signup/login/refresh/健康检查）放行
  → Bearer AT：验签/exp/ver → user（disabled？）
  → 取 tid；查 tenant_members(tenant_id=tid,user_id=sub,status=active)
      ├─ 没有：403 tenant_forbidden（token 有效，但已不属于该 tenant）
      ├─ 有：Identity{UserID, TenantID, Role, SystemAdmin}
      └─ tenant 路由且 tid 为空：409 TENANT_REQUIRED
  → 注入 request.Context
```

- `Identity` 里的 `Role` 来自 membership，缺失/非法时默认 `viewer`（fail-closed）。
- `SystemAdmin` 来自 `users.is_system_admin`，与 tenant role 正交。
- `Caller`（授权身份）与 `execution tenant`（数据作用域）分开；如果以后做共享资源，切换执行 tenant 不能改 Caller。
- 不再使用 `X-Tako-Tenant`；active tenant 在 token 里，切租户走 `/auth/switch-tenant`。API key 以后单独绑 tenant。

### 5.4 错误语义

`/api/auth` 的成功和失败用同一套信封，字段顺序 `code` → `message` → `data`：

```json
{"code":0,"message":"","data":{"accessToken":"…","tokenType":"Bearer","expiresIn":900}}
```

```json
{"code":111101,"message":"邮箱或密码不正确","data":null}
```

前端拦截器只认这一套。`code` 是业务码，数字，`0` 表示成功。`message` 是弹窗文案，成功时为空字符串，前端只在 `code` 不是 `0` 时弹出。`data` 是具体内容：成功时放原来的业务体，失败且没有额外细节时为 `null`。你记得的 `body` 就是这个位置，现在常见的字段名是 `data`。

HTTP 状态照旧返回 400/401/403/404/409/429/500，不把所有失败都收成 HTTP 200。状态告诉网关这一类请求怎么样，业务码告诉页面具体哪一种。

业务码 6 位。前两位是模块：`11` 身份，`12` 会话与运行，`13` 配额。身份模块里 `1110xx` 是参数，`1111xx` 是登录与 token，`1112xx` 是权限，`1114xx` 是冲突，`1119xx` 是这一模块里的内部失败。

| 情况 | HTTP | code | message |
|---|---|---|---|
| 成功 | 200/201 | `0` | 空。204 没有 body |
| 请求体不是合法 JSON | 400 | `111001` | 请求格式不对 |
| 邮箱或密码不符合要求 | 400 | `111002` | 邮箱或密码不符合要求 |
| 工作区名称是空的 | 400 | `111003` | 请填写工作区名称 |
| 登录失败（含账号停用，不透露哪一个错） | 401 | `111101` | 邮箱或密码不正确 |
| 没带 token | 401 | `111102` | 请先登录 |
| token 签名错或被改过 | 401 | `111103` | 登录已失效，请重新登录 |
| access token 过期 | 401 | `111104` | 登录已过期，请重新登录 |
| refresh 不存在、过期或已撤销 | 401 | `111105` | 登录已失效，请重新登录 |
| 不是该工作区的有效成员 | 403 | `111201` | 你不是这个工作区的成员 |
| 角色不够 | 403 | `111203` | 没有权限做这件事 |
| 看得到会话但不是本人，尝试写或停止 | 403 | `111204` | 只有本人能修改 |
| 邮箱已注册 | 409 | `111401` | 这个邮箱已经注册 |
| 邀请无效/过期/已撤销 | 404 | `111405` | 邀请无效或已过期 |
| 已经是该工作区成员 | 409 | `111406` | 已经是这个工作区的成员 |
| 邀请不能授予 owner | 400 | `111407` | 邀请不能授予所有者 |
| 模型未配置，或 ref 解析失败 | 409 | `111408` | 这个工作区的模型还不可用 |
| 工具名不在池里，或租户子代理的 allow 超出根助手 | 400 | `111409` | 工具策略里有不认识的工具；子代理越权时是「子代理不能使用根助手没有的工具」 |
| MCP 密钥没配，或环境里直接放了密文 | 400 | `111410` | 有一项 MCP 密钥还没配；密文直放时是「MCP 环境不能直接放密文」 |
| 自定义 MCP 连不上 | 503 | `111411` | 自定义 MCP 连不上 |
| 同名助手已经有租户配置 | 409 | `111412` | 这个名字已经有一份配置 |
| 需要工作区但 token 里没有 | 409 | `111402` | 请先选择工作区 |
| 会变成最后一个 owner | 409 | `111403` | 至少要留一个所有者 |
| 会变成最后一个平台管理员 | 409 | `111404` | 至少要留一个平台管理员 |
| 会话不可见 | 404 | `112001` | 找不到这场会话 |
| run 不可见 | 404 | `112002` | 找不到这次运行 |
| agent 不可见 | 404 | `112003` | 找不到这个 agent |
| 配额超限 | 429 | `113001` | 这个工作区的额度用完了 |
| 登录或刷新太频繁 | 429 | `113002` | 操作太频繁，请稍后再试 |
| 身份模块内部失败 | 500 | `111901` | 服务暂时不可用，请再试一次 |

## 6. 角色与权限

### 6.1 平台管理员

`users.is_system_admin`：

- 管全局模型/provider、系统设置、所有租户（列表/暂停/配额）、平台审计、runtime 队列；
- `/api/system/admin/*` 全部 `RequireSystemAdmin`；这些路由是 **tenant-optional**：只校验 `is_system_admin`，不要求 active tenant，平台管理员可以是无 tenant 的账号；
- 不能自动读租户会话内容；需要 support access 时单独走审计；
- 最后一个 system admin 不能撤销；
- 与 tenant role 无关：平台管理员在某个 tenant 里可能只是 viewer。

### 6.2 租户角色

| 角色 | 能做什么 |
|---|---|
| **owner** | 租户生命周期、成员、所有权转移、配额/账单、租户 API key、删除租户 |
| **admin** | 模型/provider、MCP、沙箱、工具、agent 配置、成员日常管理；不能删租户/改 owner |
| **member** | 建/跑自己的 session，建自己的 agent，上传文件；用团队共享 agent；只看自己的 session |
| **viewer** | 只读团队共享的 agent/资源；不能跑、不能建 |

`tenant_members.role` 是唯一角色源；一个 user 可以在 A 是 owner、在 B 是 member。

### 6.3 资源可见性

| 资源 | 读 | 写/管理 |
|---|---|---|
| **session private** | owner | owner |
| **session tenant-visible** | 同 tenant 所有 active member | owner（多人协作以后再加 `session_members`） |
| **session metadata（列表/用量）** | owner；tenant admin 可看元数据 | 不改内容 |
| **agent private** | creator | creator |
| **agent tenant-visible** | 同 tenant member | creator/admin |
| **agent builtin** | 同 tenant member | tenant admin |
| **notes user** | 本人 | 本人 |
| **notes tenant** | 同 tenant member | owner/admin（模型默认不能写） |
| **workspace/files** | tenant 内按 session/agent 规则 | tenant 内按角色 |

**管理员默认不看会话内容。** 需要支持排查时，走 `support_access`：填原因、限时、审计、通知用户；不要用 `role >= admin` 直接放开。

### 6.4 守卫原语与判定顺序

- `RequireSystemAdmin`：平台管理员；始终生效。
- `RequireTenantRole(min)`：owner/admin/member/viewer 阶梯；tenant role 来自 membership。
- `RequireOwnershipOrRole(min, lookup)`：资源 creator 或 min 角色；用于 agent 等有 creator 的资源。
- `RequireSessionAccess(action, lookup)`：owner / tenant-visible / admin metadata；session 专用。
- `RequireTenantMatch`：URL 里的 tenant id 必须等于 active tenant（如果 URL 有 tenant）。
- `APIKeyGate`：以后；机器身份单独 default-deny。

Ownership 判定顺序（照 WeKnora 的教训）：

1. role >= min → 放行，**不查库**；
2. 不够 → 查资源归属；
3. 资源不存在/不可见 → 交给 handler 出 404；
4. 查库故障 → 503，不伪装 403；
5. creator 匹配 → 放行；
6. 其他 → 403。

### 6.5 最后一个 owner / 最后一个 system admin

- 降级/移除 owner 必须在事务里锁住该 tenant 的其他 active owner；若会是最后一个 → `409 last_owner`；不能靠“先 count 再 update”。
- 撤销 system admin 同理：最后一个 → `409 last_system_admin`。
- 移除成员时撤销该成员在该 tenant 的 refresh/token（不是他在其他 tenant 的登录）。
- 所有成员/角色变更写 `audit_log`。

### 6.6 后台管理端点（草案）


## 7. 会话与运行

### 7.1 会话 API 的访问规则

| 端点 | 规则 |
|---|---|
| `POST /api/runs` 不带 sessionId | 在 active tenant 建 private session，owner=当前 user |
| `GET /api/sessions` | 只列自己的；tenant admin 的“元数据列表”另开，不含正文 |
| `GET /api/sessions/:id` | owner；tenant-visible 可读；其他 404 |
| `GET /api/sessions/:id/log` | 同上 |
| `GET /api/runs/:id/frames` | run→session→同上；无权 200 `gone`，不泄露 |
| `POST /api/runs` 带 sessionId | owner 才能投；tenant-visible 非 owner 403；跨 tenant 404 |
| `POST /api/runs/:id/stop` | owner；tenant-visible 非 owner 403；跨 tenant 404 |
| `PATCH /api/sessions/:id` visibility | owner；改成 tenant 需 owner/admin 确认（产品） |
| `DELETE /api/sessions/:id` | owner/admin；软删；保留审计 |

**现有端点不止四个。** A1 不是“只守 runs/sessions”，而是给下面这张表的每一行定归属；没有归属模型的端点先保守收紧，不能默认放行：

| 端点 | 数据 | A1 先怎么守 | 什么时候开 |
|---|---|---|---|
| `/api/runs` POST/stop/resume、`/api/runs/:id`、`frames`、`stream` | session/run | 按 session owner/visibility；跨 tenant 404；无权 frames/stream 200 gone | A1 |
| `/api/sessions/:id`、`/log` | session | 按 session owner/visibility | A1 |
| `/api/mcp/servers` | 全局 `mcp.json` | 先只允许 `system_admin`；普通用户 403 | A6 改成租户级 MCP 配置后再开 admin/member |
| `/api/media` | 全局 media 根 | 先只允许 `system_admin`（或 dev-only）；没有 owner 元数据前不对普通用户开 | A4 按 tenant/session 路径落盘后再开 |
| `/api/memory/items`、`jobs`、`dialogue`、`recall` | 全局 memory | 先只允许 `system_admin`；recall 也不对普通用户开 | A3 按 tenant/user scope 后再开 |
| `/api/dev/*` | dev 全局 | 保持 dev-only；`-dev=false` 不注册；只绑 loopback | — |

“先只允许 system_admin”不是最终产品语义，是**没有归属模型时的保守闸**；A3/A4/A6 把它们各自做正。**不允许**“先加 auth 中间件、这些端点先放所有人”——那等于把全局 media/memory/mcp 暴露给任意登录用户。


### 7.2 store 层守卫

`AcquireRun` 改成带身份：

```go
type Identity struct {
    UserID      string
    TenantID    string
    Role        TenantRole
    SystemAdmin bool
}

func (s *Store) AcquireRun(ctx context.Context, id Identity, sessionID SessionID, runID RunID, user Row) (bool, error)
```

事务内：

1. `sessionID == ""`：`INSERT sessions(tenant_id,user_id,visibility='private')` + `INSERT runs`。
2. `sessionID != ""`：`SELECT tenant_id,user_id,visibility FROM sessions WHERE id=? FOR UPDATE`；
   - 无行 / tenant 不符 → not found（handler 404）；
   - `visibility=private` 且 user 不符 → not found；
   - `visibility=tenant` 且 user 不符 → forbidden（handler 403，因为可见已不泄露）；
   - 通过 → `INSERT runs`。
3. 抢闸失败 → 409 `session_busy`；整笔回滚。

其他读/写入口同理：

| 方法 | 现在 | 改成 |
|---|---|---|
| `Exists` | id only | 保留内部存在性；新增 `SessionVisibleTo(id, identity)` |
| `SessionStatus` | id only | 查 session 的 tenant/user/visibility；无权 404 |
| `ReadLog` | `Exists(id)` | `SessionVisibleTo`；无权 404 |
| `ReadFrames` | runId only | 先 `RunSession(runID)`，再 `SessionVisibleTo`；无权 200 gone |
| `StopRun` | runId only | 先 `RunSession`，owner 校验；无权 404/403 |
| `writeNote` | workspace | `identity + scope`；user scope owner，tenant scope admin |
| `listLiveNotes` | workspace | `tenant + scope + user` |
| `Reset` | 全局 | 保持 dev-only 全局 |

**预检顺序**：`postRuns` 的 tenant/owner 检查必须在 `AdmitText` 之前；`stopRun` 的 owner 检查必须在 `StopRun` 之前。否则 bob 用超长 text 打 alice 的 session 会拿到 413、或者 404 是在 run 已被停掉之后才返回——响应绿了，副作用已经发生。验收必须验“404 之后 alice 的 run 仍在跑 / 没有新 run 行”。

### 7.3 run ctx 与 worker

- `postRuns` 把 `Identity` 放进 `worker.Run` 的 ctx（**不是** `c.Request.Context()`，run 生命周期不属于请求）。
- worker 从 ctx 取 `tenant_id/user_id`，传给 notes 快照、memory 工具、workspace 解析、usage 记录。
- `runCancels` 仍是进程内注册表；跨副本 stop 靠 lease watchdog 收敛（现有机制，不新增跨副本语义）。
- `one_live_run_per_session` 闸不变：session_id 全局唯一，tenancy 不改变它。

### 7.4 共享会话（以后）

`visibility=tenant` 第一版只读共享：同 tenant member 可读 log/frames；写/stop 仍归 owner。多人协作（多写、评论、协同停止）以后用 `session_members` 表，不用角色硬套。

## 8. 记忆（notes）

### 8.1 scope 语义

- `scope=user`：个人记忆；`user_id` 是本人；只有本人读写；快照里只出现本人的。

## 9. 工作区、文件与沙箱

### 9.1 路径

```
<workspace-root>/
  tenants/<tenant_id>/
    shared/                  # 团队共享文件
    sessions/<session_id>/   # 会话文件
    agents/<agent_id>/       # agent 文件
    .tako/search/            # 检索落盘
```

- 个人 tenant 也是这个结构，只是只有一个成员。
- 这一版真正建出来的目录是 `<workspace>/tenants/<tenant_id>/sessions/<session_id>/`。图里的 `shared/` 和 `agents/<agent_id>/` 还没有单独创建。
- 文件工具和 bash 每次从 ctx 里的 `WorkspaceRef` 取会话根。没有身份的单测才回落到启动时捕获的根。
- `bash` 的 cwd 是这个会话根；环境白名单保留。cwd 不是安全边界，读宿主文件靠第 9.4 节的沙箱拒绝。

### 9.2 工具改造

[worker.go:163](yk-tako-eino/internal/runengine/worker.go#L163) 现在把 `workspace` 传进 `NewWorker`，[worker.go:179](yk-tako-eino/internal/runengine/worker.go#L179) 的文件工具和 [worker.go:191](yk-tako-eino/internal/runengine/worker.go#L191) 的 bash 都捕获它。改成：

- 构造工具时不再吃固定路径；工具执行时从 ctx 取 `WorkspaceRef`；
- `worker.Run` 在 ctx 里放 `Identity` + `WorkspaceRef`；
- `memory`/`search_history` 的落盘也用同一个解析器；
- 所有路径 `resolveInWorkspace` 后再检查是否仍在 tenant 根内；防 `..`/symlink。

### 9.3 多副本存储

本地磁盘的 workspace 在多副本下不共享。A4 必须选：

- 共享 POSIX 卷（NFS/EFS）挂到同一路径；或
- 对象存储 + 文件服务适配层；或
- 按 tenant/session 粘到某个副本（不推荐，复杂度高）。

第一版建议共享卷；对象存储以后再说。否则多副本部署后，A 副本写的文件 B 副本读不到。

### 9.4 bash/sandbox

路径隔离挡不住 `cat /etc/passwd`、绝对路径、网络访问。多租户 agent 运行时默认按不可信代码设计：

- A4 做的是 per-tenant 根和路径检查，包括 `..` 和符号链接。这不是安全边界。
- A5 在 macOS 上用 `sandbox-exec`：默认拒绝，会话目录可读写，显式拒绝 `/etc/passwd` 和 `/private/etc/passwd`。binary 不在，或者 `sandbox_apply` 被拒绝，都拒绝执行，不把 cwd 当成隔离，也不把失败写成普通退出码。容器或命名空间不在这一版。Linux 上通常没有 `sandbox-exec`，生产 bash 同样拒绝。
- 外部团队仍然不要只凭这条沙箱就放开。它挡的是本机绝对路径和默认网络，不是一套完整的多租户运行时隔离。

### 9.5 验收

A4 加 dev-only workspace 探针（读文件/列目录），否则无法用 curl 证明隔离：

```bash
# alice 写 /tenants/t_alice/shared/a.txt
# bob（t_bob）读同路径 → 404
# alice 读 → 200
# bob 的 bash `cat /tenants/t_alice/shared/a.txt` → 拒绝/不可见
```

## 10. 并发与配额

### 10.1 每租户限额

`tenants` 或 `tenant_quotas` 加：

- `max_concurrent_runs`（默认 4/8）
- `max_subagents`（默认 2/4）
- `daily_tokens`（默认按 plan）
- `max_storage_bytes`
- `max_sessions`

执行点：

- `POST /api/runs`：查该 tenant 正在跑的 run 数；超 → 429 `tenant_quota_exceeded`。
- 子代理委派：按 tenant 计数；超 → 工具结果返回“配额不足”，父 run 不崩。
- 模型调用后：`usage` 落库 + Redis 日计数；超预算 → 后续调用拒绝。
- 文件写入：按 tenant 存储配额。
- 管理后台：owner/admin 看用量；platform admin 改配额。

### 10.2 当前进程级信号量的问题

[agents.go:258](yk-tako-eino/internal/runengine/agents.go#L258) 的 `sem` 是进程内 channel，容量 8，所有租户共享：

- 一个租户可以占满 8 个槽，别的租户饿死；
- 多副本下每个副本各自 8 个，配额不可控；
- 进程重启丢状态。

改成 per-tenant 配额 + 全局公平队列；计数放 Redis/DB，不用进程内 channel。

### 10.3 eino #1177

所有 run 共用 `w.agent` 一个 eino 实例；doc/17:217 的共享实例并发 race 在多租户下是跨租户风险（互相取消/串状态）。A5 必须做决策：

1. 修上游 #1177；
2. 每 run 一个 agent 实例（安全但贵）；
3. 每 tenant 一个实例 + 修 race（仍解决不了同 tenant 并发）；
4. 暂时串行（影响吞吐，不能作为长期）。

在决策前，验收不能只跑“两租户串行”；必须加两租户并发用例。

## 13. 验收原则

1. **curl + 期望字节**，不写“页面上看到 X”。
2. 每个否定用例都要验**无副作用**：bob 的 404 之后，alice 的 run 仍在、runlogOffset 不变；bob 的删除失败后，alice 的笔记仍在。
3. 401/403/404 按第 5.4 节；跨 tenant/private 一律 404。
4. 角色：owner/admin/member/viewer 各跑一遍正向 + 反向。
5. 最后 owner / 最后 system admin：409。
6. 配额：A 429 时 B 202。
7. 并发：两租户同时跑，不串 session、不互相取消。
8. `kill -9`：run 租约到期后 session 解锁；配额/refresh 不丢。
9. 多副本：至少手动起两个进程，验证共享 PG/Redis/workspace。
10. dev-only 探针（notes/workspace）登记转正点，A6 后删。
