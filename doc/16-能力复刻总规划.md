## 0. 定位与边界

**tako 是什么**：从 pi 式 agent 循环长出来的 **AI 工作伙伴**，单入口产品（`cmd/yktako`）。核心是"一个能自主干活、带任务看板、带工具安全、能长时间跑任务的 agent"。

**tako 不是什么**：不是知识库 / RAG 产品。RAG、记忆这些能力会被借鉴进来，但只作为**支撑 agent 干活的横切能力**，绝不反客为主把 tako 变成"以文档检索为中心"的系统。这条边界是本文所有取舍的总闸（见 §4 护栏）。

**技术栈**：Go + Eino（CloudWeGo）。主线在 `yk-tako-eino/`。

## 3. 当前重心：子代理（#5）

> **2026-10-20 状态**：本节是立项时的思路留档。子代理已落地（doc/17 §6、doc/25、doc/26）；「下一步动作」里的 doc/17 已产出，施工真源由 doc/25 取代。当前未做项见 §2 的 ⬜/🔶 行。

**要解决的问题**：某些 tool 会把主 agent 上下文撑爆（疯狂刷 tool 输出、读大文档、翻一堆文件）。

**Octop 的答案（=要什么）**：
- 子代理 = 一个 Markdown + YAML frontmatter 规格文件（name/id/description/tools/model/skills，正文即 system_prompt），运行时被框架包成一个 **`task` 工具**挂到主 agent 上——"tool 变子代理"。
- **上下文隔离**：调用方只能看到子代理**最终那条 assistant 消息**，中间 tool 调用不回传。子代理有自己独立的上下文窗口。
- **大文档三招**：`read(offset, limit)` 按行分页读；正本存 workspace 文件系统（外部存储），上下文只放路径/占位；需要通篇理解时派子代理读完回摘要。

**tako 怎么做（=Eino 落地，待出实施计划）**：
- 难点不在抄谁，而在：**Eino 里怎么让一个子 `ChatModelAgent` 以 tool 形态挂到主 agent 上，并做到上下文隔离**（子 agent 独立 message 历史，只把最终文本返回）。
- 子代理规格怎么定义/注册/发现（是否也走 Markdown+frontmatter，还是 Go 结构体）。
- 与已有能力的接缝：子代理是否继承 guard 三件套？（Octop 里子代理**不继承**父 middleware、剥离 ask_user）；子代理产出如何进 taskboard / event_log。

**下一步动作**：去 `harness-pkg/harness-agent` + Eino ADK 摸清"子 agent 以 tool 挂载 + 上下文隔离"的落地方式，出 `doc/17-子代理实施计划.md`。

## 4. 借鉴 WeKnora 的护栏（对话 → RAG / 记忆）

用户明确：想把 WeKnora 偏"通用 agent"的能力借鉴过来（例如把对话内容存进 RAG 供后续召回），**但不想让 tako 变成 WeKnora 那种以 RAG 为定位的项目**。护栏如下：

1. **正本永远是结构化存储**（event_log / messages 表），向量库只是**可重建的派生副本**——用于语义模糊召回，不用于精确回放/审计/恢复。（依据：WeKnora 里 embedding 模型一旦索引不可换、需重建，删会话时两侧同步清理）
2. **双写是手段不是目的**：结构化表管"精确、按序、可恢复"，向量库管"语义召回"，两种查询模式互不替代，所以才双写（承 §Q：为什么双写）。tako 引入 RAG 时沿用这个分工，**但只在"agent 需要回忆历史"这一场景服务 agent**，不做面向用户的知识库检索产品。
3. **召回结果进 agent 上下文，不进 UI 主流程**：RAG 是 agent 的一个 tool / 中间件（"记忆召回"），产出喂给模型，而不是把 tako 的界面改成"搜索框 + 文档列表"。
4. **可延后、可关**：RAG / 记忆属于 #6、#10，排在子代理之后。没落地前 tako 已是完整可用的 agent；落地后也应能通过配置关闭，退回纯结构化存储。
