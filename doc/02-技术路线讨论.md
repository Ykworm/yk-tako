# 02 - 技术路线讨论：T-Mem 整合 & 移植 Octop（LangGraph.js vs Eino）

> 日期：2026-09-23
> 背景：发现腾讯 Octop（WorkBuddy 同系/同源项目）的 Agent 层基于 LangGraph Python 版本，
> 新思路：**直接一步步把 Octop 移植/改造为目标技术栈**。项目名不再使用 einora（待定新名）。

## 1. 关键事实确认

### Octop 实际架构（github.com/TencentCloud/Octop）

```
Next.js 前端  ──►  Go 统一后端  ──gRPC/WebSocket──►  Python 智能体微服务
                                                    （LangGraph + DeepAgents）
                        │
                PostgreSQL + Redis
```

- 已有能力：飞书/企微/QQ 机器人、定时任务、心跳、记忆系统、沙箱、CLI、技能体系
- **Agent 核心逻辑在 Python 微服务里**，这正是要移植的部分

### T-Mem 是什么（arXiv:2606.15405，腾讯 + 港科广）

- 定位：对话式 Agent 的**长时记忆架构**，LoCoMo / LoCoMo-Plus 双基准 SOTA
- 核心思想："**记忆应当预判，而非归档**"——写入时由 LLM 为每条记忆预演两类触发器：
  - 描述性触发器（措辞/实体相似就能召回）
  - 联想性触发器（与记忆无表面特征重叠、靠潜在语义弧关联的查询也能召回）
- 结构：Scene → Topic → Item 三层图 + 级联检索（RRF 融合 BM25 + 稠密向量 + 硬余弦门控）
- 参考实现：Python（github.com/Sherlockwz/T-Mem），构建期 LLM 调用密集

## 2. 问题一：是否整合 T-Mem？

**结论：值得，但不要第一天就整合——把它藏在 Memory 接口后面，分两期走。**

| 阶段 | 方案 | 理由 |
|---|---|---|
| 一期（MVP） | pgvector + 简单情景记忆表（session 摘要 + 事实抽取） | 先跑通 Agent 主循环，记忆接口先行 |
| 二期 | 实现 T-Mem 算法 | 触发器预演 + 三层级联检索是算法层面的东西，**不绑定 Python**，完全可以用目标语言重写；也可先跑其 Python 参考实现做 sidecar 验证效果 |

注意点：
- T-Mem 写入成本高（每段对话多次 LLM 调用：边界判定、主题分配、触发器实例化），需要异步写入管线（可借鉴 WeKnora 的 asynq 任务队列）
- WeKnora 已有"跨会话长时记忆"实现，可对照参考
- Octop 自带记忆系统较简单，T-Mem 是差异化竞争力

## 3. 问题二：移植 Octop，用 LangGraph.js 还是 Eino？

### 对比分析

| 维度 | LangGraph.js (Node/TS) | Eino (Go) |
|---|---|---|
| 移植工作量 | ⭐ API 与 Python LangGraph 几乎一一对应，接近"逐行翻译" | 概念一一对应（Graph/Node/Edge/State/Checkpoint），但 API 需重写 |
| 与 Octop 现有后端 | 引入第 3 种运行时（Go + Python + Node），或被迫砍掉 Go 后端 | ⭐ **与 Octop 的 Go 后端统一为单一语言**，最终可去掉 gRPC 边界、合并单进程 |
| DeepAgents 对应物 | deepagents 有 JS 版，生态跟随紧密 | Eino ADK（多智能体/supervisor），较新但在快速迭代 |
| 桌面 Agent 形态 | Node 守护进程部署重 | ⭐ Go 单二进制，天然适合 WorkBuddy 式本地数字员工 |
| MCP / 流式 | LangChain 生态成熟 | Eino 官方支持 MCP，流式基于 callback 机制完善 |
| 与你的技术资产一致性 | 新增 TS 栈 | ⭐ 与 WeKnora（Go）一脉相承，架构经验直接复用 |

### 结论：**选 Eino**

决定性理由不是"Eino 比 LangGraph.js 强"，而是**系统拓扑**：

1. Octop 本来就是 Go 后端 + Python Agent 的**双语双进程**结构，用 LangGraph.js 移植只是换一种"双语"（Go + Node），复杂度没降下来；用 Eino 移植则收敛为**纯 Go 单语言**，gRPC 边界最终可以整个删掉
2. 目标是 WorkBuddy 式本地 Agent，Go 单二进制部署是硬优势
3. 你已有的参考系（WeKnora）全是 Go，遇到问题时有两个大型 Go 项目（WeKnora + Eino 自身 examples）可抄

代价：移植不是"翻译"而是"重写"，需要先建立 LangGraph → Eino 的概念映射表（见下）。

### LangGraph → Eino 概念映射（移植手册大纲）

| LangGraph (Python) | Eino (Go) |
|---|---|
| `StateGraph` | `compose.Graph` / `compose.NewChain` |
| `add_node` / `add_edge` | `AddNode` / `AddEdge` |
| 条件边 `add_conditional_edges` | `AddBranch`（`GraphBranch`） |
| State（TypedDict + reducer） | 泛型 State + `WithStatePostHandler` / GenLocalState |
| `Checkpointer`（PostgresSaver） | Checkpoint 接口，需自实现 PostgreSQL 存储（可复用同一张库） |
| `interrupt` / 人机协同 | Eino Interrupt & Resume |
| ReAct Agent（prebuilt） | `react.Agent`（Eino 内置）/ ADK |
| 多智能体 supervisor | Eino ADK Supervisor 模式 |
| 工具节点 ToolNode | `ToolsNode` + MCP 工具适配 |
| 流式 `astream_events` | Callbacks + StreamReader |

## 4. 建议的渐进式移植路线（"一步步改"）

```
阶段 0  原样跑通 Octop（Docker Compose），通读 Python agent 服务的 graph 定义
阶段 1  盘点清单：列出所有 graph / node / tool / state schema / checkpointer 用法
阶段 2  Go 侧起 Eino Agent 骨架，实现与 Python 服务相同的 gRPC 契约（契约不变）
阶段 3  逐图移植：先移植最简单的 chat/ReAct 主循环，用 feature flag 切换 Py/Go 实现
阶段 4  状态与检查点迁移：Eino checkpoint 落到同一个 PostgreSQL
阶段 5  记忆模块接口化（先简版），二期接入 T-Mem 算法
阶段 6  Python 服务下线，删除 gRPC 边界，合并进 Go 后端单进程
```

关键技巧：**gRPC 契约不动**是整个渐进迁移的保险绳——前端、Go 后端都无感知，
每个 graph 独立切换、可灰度、可回滚。

## 6. 补充修正：LangGraph.js 路线 ≠ "Go 后端 + Node Agent"

> 讨论修正（2026-09-23）：此前分析默认保留 Octop 的 Go 后端。
> 实际上 LangGraph.js 路线完全可以**全栈 TypeScript**：
> Next.js 前端 + Node 后端（NestJS/Hono）+ LangGraph.js Agent，一种语言到底。

### 修正后的真实对比

| | A. 全 TS（LangGraph.js） | B. 全 Go（Eino） |
|---|---|---|
| Agent 移植 | ⭐ 近乎逐行翻译，成本最低 | 概念重写，成本中等 |
| Octop Go 后端 | ✗ 需重写（IM 渠道、定时调度、WS 网关、鉴权，代码量大） | ⭐ 原样保留 |
| 语言统一性 | ⭐ 前端+后端+Agent 全 TS | ⭐ 全 Go |
| 部署形态 | Node 运行时（Bun 可打单文件，有所缓解） | ⭐ 单二进制 |
| 生态 | ⭐ LangChain/LangGraph 生态最大，deepagents JS 版，LangSmith | Eino 较新，MCP/ADK 官方支持快速补齐 |
| 技术资产复用 | WeKnora Go 经验只能部分复用 | ⭐ WeKnora 可直接对照 |

### 权衡的本质：重写成本付在哪一边？

- Octop Python Agent 服务 ≈ 几个 graph + 工具，规模**小**
- Octop Go 后端 ≈ 渠道/调度/网关/存储，规模**大**

全 TS = 便宜翻译小头 + 昂贵重写大头；Eino = 大头白拿 + 只付小头重写费。

### 决策框架

- **学习 LangGraph 生态优先**（或团队 TS 远强于 Go、想跟随 LangChain 玩法）→ 全 TS + LangGraph.js
- **产品最快落地优先** → 全 Go + Eino（保留 Octop 后端，只换 Agent 层）

> 最终决策：待定（⚠️ 本节的"保留 Go 后端"论据已被第 7 节实地验证推翻，以第 7 节为准）

## 7. 实地验证（2026-09-23）：clone Octop 源码后的重大修正

> ⚠️ 此前第 3、4、6 节基于一份 fork 仓库的 DESIGN.md（描述 Next.js + Go 后端），
> **与上游真实架构不符**。以下以 `TencentCloud/Octop` 实际代码（v0.9.33）为准。

### Octop 真实技术栈

| 层级 | 实际技术 | 证据 |
|---|---|---|
| 主进程 | **Python 3.12+ 单进程**（FastAPI + uvicorn），src 约 **13.1 万行** | `pyproject.toml`、`src/octop/` |
| Agent 运行时 | `orcakit-harness-agent`（外部 pip 包），基于 **LangGraph + LangChain + deepagents** | `uv.lock` 依赖清单 |
| IM 桥接 | `harness-gateway`（外部包）：飞书/钉钉/QQ/Telegram/企微 | 同上 |
| 记忆 | `harness-memory`（外部包），可随工作区迁移 | 同上 |
| 存储 | SQLite(WAL) 默认 / PostgreSQL 可选（控制平面） | 同上 |
| 调度 | APScheduler | 同上 |
| 前端 | **React 18 + TS + Vite + AntD**（`dashboard/`，非 Next.js） | `dashboard/package.json` |
| Go | **仅 `desktop/` 桌面外壳**（托盘/便携升级，~2.6k 行） | 全仓库仅 30 个 Go 文件 |

### 修正后的局面

1. **不存在"可保留的 Go 后端"**——两条路线（全 TS / 全 Go）都是全量重写，谁也不占存量便宜
2. **Agent 核心不在本仓库**：graph 逻辑在 `orcakit-harness-agent` pip 包里，
   "一步步改"的第一步是读该包源码，而非翻译 13 万行应用层代码
   （且其中 voice/mobile/backup 等大量模块 MVP 不需要）
3. **可复用资产重新洗牌**：
   - `dashboard/`（React）——两条路线均可用
   - `desktop/`（Go 外壳）——仅 Eino 路线可自然融合
   - WeKnora（Go，IM 渠道/RAG/调度/MCP 现成实现）——仅助益 Eino 路线
4. **TS 路线的新优势**：agent 核心翻译最直接（langgraph→langgraph.js、deepagents JS 版）、
   与 dashboard 同语言、LangSmith 可观测性；弱点：QQ/企微 TS SDK 生态弱、无单二进制

### 修正后的结论（势均力敌，按目标拍板）

- **忠实复刻 + 跟随 LangChain 生态** → 全 TS（LangGraph.js）
- **单二进制自托管 + 复用 WeKnora Go 资产** → 全 Go（Eino）

> ✅ **最终决策（2026-09-23）：全栈 TypeScript**
> 依据：owner 曾用 TS 和 Go 各复刻过一遍 pi agent（双语言对照实验），
> 实测体感 TS 更适合；生长式路线下学习连续性权重最高；
> 且 harness-agent 的中间件矩阵在 JS 版 deepagents 上有官方对应物，翻译最直接。
> 技术栈定案：LangGraph.js + deepagents(JS) + Node 后端 + React dashboard（复用 Octop 的）

### 共同的第一步（与选型无关）

1. `pip download orcakit-harness-agent` 拉取 agent 核心源码，读懂其 graph 设计
2. 盘点 Octop 应用层真正需要的模块清单（砍到 MVP 范围）
3. 跑通 `octop run` 建立感性认识
