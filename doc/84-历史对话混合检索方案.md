# 84 · 历史对话混合检索方案（ES + Milvus）

> 性质：**方案（待点头）**。
> 状态：⬜ 未施工；本文与 `tmp/84-历史对话混合检索/施工包.md` 交审后才允许 coding。
> 日期：2026-11-19。
> 代码落点：—（未施工；预计落点见施工包 §3）。
> 边界：只改历史对话原文的派生索引与召回，不改 `memory_items`、resident 常驻指令、active 记忆判重或 supersede 历史链。

## 0. 一句话与完成线

给 `dialogue_chunks` 增加一套可重建的 **Elasticsearch 词法索引 + Milvus 向量索引**：用户换个说法问历史对话时，两路各取候选，按名次融合，回 PostgreSQL 取原文并复核权限，再注入当前 run。

完成线不是“两个服务能连上”，而是下面这条业务链真实跑通：

```text
会话 A 说「发布窗口改到周六凌晨」
  → runlog 形成对话块
  → ES 与 Milvus 都完成索引
  → 同项目会话 B 问「周末什么时候上线？」
  → 词法臂与语义臂都返回候选，RRF 合并
  → PG 复核后把会话 A 的原文注入本轮
  → 另一个项目、另一个租户都取不到这段原文
  → 删除项目后，ES 与 Milvus 中对应记录也消失
  → 消费者崩溃并重启后，索引最终补齐且不产生重复文档
```

同时保留当前 `pg_search` 路径。新模式名为 `hybrid`，只有显式启用才接 ES、Milvus 和 embedding 服务；它不可用时不得静默退成单臂并冒称混合检索成功。

## 1. 背景：不能把两类“记忆”混为一谈

当前有三种不同的读取需求：

| 读取对象 | 当前做法 | 为什么不能用同一种“全量视野”替代 |
|---|---|---|
| resident 硬性指令与用户偏好 | 每场全量进 system prompt，当场冻结 | 它本来就不需要检索；改成 Top-K 反而可能丢掉必须遵守的约束 |
| active 长期记忆的写入判重、改口与历史链 | 程序列出可见域全部 active 行，按 token 分批交给判决模型 | 这是有明确状态与归属的当前记忆集合，不是全部历史对话 |
| `dialogue_chunks` 历史对话原文 | 每个 run 一块，BM25 取少量相关片段注入 | run 持续增长，不能全部塞给模型；必须靠检索先缩小范围 |

本方案只处理第三行。它要解决的失败故事是：会话 A 说“发布窗口改到周六凌晨”，几周后会话 B 问“周末什么时候上线”。原话里的“周六”和问句里的“周末”词面不同，当前 BM25 可能漏掉；但用户需要的是当时那段原话，不是让系统重新发明一条 active 记忆。

因此，active 记忆“全量候选视野”是否成功，与历史对话是否需要 embedding 是两个独立问题。本方案不推翻 doc/65 的任何状态机、判重逻辑或硬性指令注入方式。

## 2. 范围与非目标

### 2.1 本期做

- 延续 `runlog_entries → dialogue_chunks` 的现有派生链，一段 run 仍只对应一个对话块。
- 新增加 External Retrieval 派生层：ES 词法索引、Milvus 向量索引，以及 embedding 生成与索引任务状态。
- 查询时两路各取至多 10 个候选，使用 RRF（Reciprocal Rank Fusion，按名次而非原始分数）合并，最终最多注入 3 段，与现有 `dialogueRecallItemsMax` 一致。
- 项目内跨 session 查询；租户、用户、项目三层可见性过滤；命中后回 PG 再校验。
- 新增、修改、项目删除的索引同步；幂等、多副本领取、崩溃补建、全量重建。
- 保留现有 `GET /api/memory/recall` 响应形状，新增 `-dev` 诊断端点观察两臂与索引任务。
- 单元测试、真实 ES/Milvus/embedding 活体验收、双副本与 `kill -9` 场景。

### 2.2 明确不做

- 不改 `memory_items`、resident 快照、`search_memory` 的 active 记忆语义、`valid_from` / `superseded_by` 等历史链。
- 不把全部 runlog 交给模型，不为 active 记忆增加每回合固定 embedding 成本。
- 不用 ES 替换 active 记忆的 `pg_search`，不做三引擎同时查询。
- 不做租户级 embedding 厂商管理面；第一期 embedding 配置是实例级。
- 不做在线即时 reranker 模型、知识图谱、文档知识库产品、额外 chunking 算法。
- 不承诺 ES 与 Milvus 和 PG 的跨系统事务；采用“PG 真源 + 持久索引任务 + 最终一致 + 命中复核”。
- 不在 hybrid 故障时静默退回 `pg_search` 或单臂结果。
- 不引入新的强制 MQ 依赖。沿用现有对话索引反查循环，索引任务表只记录外部索引是否完成及崩溃恢复依据。

## 3. 端到端业务链

```text
run 完成
  → runlog_entries（永久正本）
  → 现有 RunDialogueIndexer 生成/更新 dialogue_chunks
  → 同一笔 PG 事务登记对话索引任务（ES 与向量各自记录完成位置）
  → 后台消费者按租约领取
       ├─ ES：upsert 词法文档
       └─ embedding：生成向量 → Milvus：upsert 向量与可见性字段
  → 任务两侧都完成后记 done；失败按 1/5/30 分钟退避并对账重试

新用户消息
  → Worker.recallBlock
  → hybrid retrieval
       ├─ ES BM25 Top-10
       └─ 查询文本 embedding → Milvus COSINE Top-10
  → RRF 合并名次
  → 按 run_id 回 PG 读取 dialogue_chunks
  → 复核：当前行存在、正文哈希一致、tenant/user/workspace 可见
  → 取前 3 段渲染 <dialogue-context>
  → 追加到本轮 user 消息并写回 mh
  → 现有折叠与模型输入链继续处理
```

这里每一步的输入都来自上一步：索引任务来自 PG 对话块，embedding 来自对话块文本，候选来自两个外部索引，最终正文不直接信外部索引而回 PG 取。这样即使旧文档尚未被清理，也不会把旧正文或越权正文交给模型。

## 4. 已拍定的设计选择

### 4.1 PG 是正本，外部索引都可重建

- `runlog_entries` 是永久原文；`dialogue_chunks` 是可重建的检索块。
- ES 与 Milvus 都只是派生索引，不参与运行状态、权限或删除事实的裁决。
- 文档主键统一为 `run_id`，一场 run 在 ES 和 Milvus 中各至多一条当前记录。
- 同时计算两个哈希：
  - `source_hash = SHA256(passage)`：命中后判断外部候选是否仍对应 PG 当前正文；
  - `index_hash = SHA256(schemaVersion + maskedPassage + embeddingModel)`：判断索引任务是否需要重做。PII 规则或 embedding 模型变化时递增 `schemaVersion` 或更换模型名，避免新旧向量混用。

### 4.2 词法与语义按名次融合，不直接加原始分

两路各取 10 个候选，名次从 1 开始：

```text
RRF(run) = Σ 1 / (60 + rank)
```

同一 run 在两路都出现时累加。BM25 与向量相似度只用于各自排序，不跨引擎比较数值。合并后取前 3；这解决量纲不同和“某一臂原始分虚高”的问题，但不证明内容正确，内容仍须回 PG 核对并保留来源。

### 4.3 混合模式是显式、实例级配置

```text
TAKO_DIALOGUE_RETRIEVAL=pg_search | hybrid
```

- 缺省仍为 `pg_search`，现有部署行为不变。
- `hybrid` 需要完整 ES、Milvus、embedding 配置；`TAKO_RAG=off` 时不启动任何对话索引与召回。
- 启动时真实调用 ES  mapping、Milvus collection/schema 与最小 embedding 请求。缺配置、版本不兼容或维度不一致，启动失败，不降级。
- 运行中任一臂报错，召回按现有辅助能力的失败语义返回错误：worker 记日志并不注入召回块，run 继续；不得把另一臂单独的结果冒充 hybrid 成功。
- 一臂合法地零命中不是故障，另一臂可以正常提供候选。

### 4.4 项目与权限以真实 ID 为准

- 新索引写入时从 `sessions` 行取得 `tenant_id`、`user_id`、`workspace_id`，不把全局 `MemoryConfig.Workspace` 或文件根目录当项目 ID。
- run 内查询从 `WorkspaceRef.WorkspaceID` 取当前项目；开发诊断端点必须显式传 `workspaceId` 并调用 `VisibleWorkspace` 校验。
- 普通用户：`tenant_id + workspace_id + user_id` 过滤。
- owner/admin 的 `scope=tenant` 预览：按 `tenant_id + workspace_id` 过滤，不按单个 `user_id` 过滤；跨租户 `tenantId` 只有 system admin 可用，沿用 `memoryContext` 的角色规则。
- 外部引擎先过滤只是性能优化；最终命中仍必须回 PG 再判一次可见性，防止权限变化尚未同步时泄漏。

### 4.5 外部文本与密钥处理

- embedding 使用 OpenAI 兼容 `POST /v1/embeddings`，配置只从环境变量读取；API key 不写库、不进日志、不进响应。
- ES/Milvus 凭据同样只走环境变量；诊断响应只回健康状态、索引名、模型名、维度和任务计数。
- 送往 ES、Milvus 和 embedding 的文本统一经过现有 `MaskPIIKeepUserMasked`；查询文本做同样处理，避免索引与查询规则不一致。
- 最终注入仍从 PG 取原文，并沿用现有 `toSchemaMessages` 的模型输入脱敏。
- embedding 向量也按敏感派生数据处理：同租户隔离、同项目删除、同套重建纪律，不因“只是向量”而例外。

## 5. 存储与外部索引契约

### 5.1 新增 PG 表 `dialogue_index_jobs`

一场对话块的新版本对应一条索引任务；任务内分别记录 ES 与 Milvus 是否完成，避免“ES 已成功、Milvus 失败”时重复写 ES。

| 字段 | 含义 |
|---|---|
| `id` | `dij_<ULID>`，任务主键 |
| `run_id` / `session_id` | 来源 run 与会话 |
| `tenant_id` / `user_id` / `workspace_id` | 索引时的真实归属，删除任务也保留，供补偿使用 |
| `kind` | `upsert` / `delete` |
| `source_hash` | 当前 PG 正文哈希；执行前若已过时则跳过旧任务 |
| `index_hash` | PII 处理后的正文、schema 版本与 embedding 模型共同哈希 |
| `embedding_model` | 本任务使用的模型；delete 任务为空 |
| `status` | `pending` / `running` / `done` / `failed` |
| `es_done_at` / `vector_done_at` | 两臂各自的完成证据；两者都有值且非 delete 才算完成 |
| `attempts` / `next_attempt_at` | 已尝试次数与下次可领取时间，退避 1/5/30 分钟，第三次后 failed |
| `claim_epoch` / `lease_until` | 多副本领取代次与租约；默认租约 2 分钟，执行中续约 |
| `last_error` | 最近一次机器可读错误，不含正文与密钥 |
| `trace_parent` | 从来源 run 到索引消费者的 trace 透传 |
| `created_at` / `updated_at` | 审计时间 |

约束与索引：

- `UNIQUE(run_id, kind, index_hash, embedding_model)`：同一版本重复登记只回读原任务。
- `INDEX(status, next_attempt_at)`：领取到期 pending 与租约过期 running。
- `INDEX(run_id)`：回查一个 run 的索引历史。
- 领取使用 `FOR UPDATE SKIP LOCKED` 与 `claim_epoch+1`；完成写回必须同时匹配任务 ID 与当前 `claim_epoch`。
- 每个 upsert 执行前回读当前 `dialogue_chunks`：`source_hash` 已变化则任务按 `stale` 收尾，不覆盖较新版本；查询侧仍会丢弃这份旧候选。
- `delete` 只需按 `run_id` 从两个外部索引删除；任务元数据在 PG 保留，直到两个删除都成功。
- 项目删除事务先登记 delete 任务，再删除 `dialogue_chunks`；任务表不随项目级联删除，避免丢失补偿依据。

### 5.2 ES 索引 `tako_dialogue_v1`

| 字段 | 类型与用途 |
|---|---|
| `run_id` | `_id`，唯一文档键 |
| `session_id` / `tenant_id` / `user_id` / `workspace_id` | `keyword`，可见性过滤 |
| `passage` | `text`，`smartcn` 分词；施工首拍用 `_analyze` 实测中文、英文、数字与生造词 |
| `source_hash` / `index_hash` | `keyword`，陈旧候选识别与任务幂等 |
| `embedding_model` | `keyword`，模型版本隔离 |
| `run_finished_at` / `indexed_at` | `date`，证据时间与诊断 |

- 使用 BM25 `match` + bool filter，候选上限 10。
- 初始不强制 IK 插件，避免额外部署依赖；`smartcn` 若达不到既定分词用例，方案实施中止并报告，不静默换成另一套语义。
- 返回命中只取 `run_id`、分数和两个哈希，正文回 PG 取。

### 5.3 Milvus collection `tako_dialogue_v1`

| 字段 | 类型与用途 |
|---|---|
| `run_id` | `VARCHAR(64)` 主键 |
| `session_id` / `tenant_id` / `user_id` / `workspace_id` | `VARCHAR`，标量过滤 |
| `source_hash` / `index_hash` / `embedding_model` | `VARCHAR`，版本与模型识别 |
| `embedding` | `FLOAT_VECTOR`，维度由真实 embedding 探针确定 |
| `run_finished_at` / `indexed_at` | `INT64` 秒级时间戳 |

- `metric_type=COSINE`，HNSW，初始 `M=16`、`efConstruction=200`、查询 `ef=64`，候选上限 10。
- collection 的维度与启动探针不一致时拒绝启动；模型或维度变化使用新 collection 并全量重建，禁止混写。
- 命中只取 `run_id`、距离分数和两个哈希，正文回 PG 取。

## 6. 运行中 API 与诊断契约

### 6.1 保持不变的接口

`GET /api/memory/recall` 仍返回：

```json
{"code":0,"message":"","data":{"block":"…","dialogueHits":2,"injectedRunes":123,"memoryHits":1}}
```

`memoryHits` 仍来自 active 记忆，不把对话命中混进去。无新增帧 kind、无 SSE 字节变化、无前端假数据改造。

### 6.2 新增 `POST /api/dev/dialogue-retrieval/query`

仅 `-dev` 且登录后可用，用来证明两臂确实被调用。请求：

```json
{"query":"周末什么时候上线","workspaceId":"w_…","limit":10}
```

`limit` 缺省 10、最大 20。响应形状示例（不是已验收字节）：

```json
{"code":0,"message":"","data":{"mode":"hybrid","lexical":[{"runId":"r_…","score":3.1}],"vector":[{"runId":"r_…","score":0.82}],"merged":[{"runId":"r_…","rrfScore":0.0325,"sources":["lexical","vector"]}]}}
```

### 6.3 新增 `GET /api/dev/dialogue-retrieval/status`

仅 `-dev` 且登录后可用，返回模式、索引健康、模型与任务计数：

```json
{"code":0,"message":"","data":{"mode":"hybrid","lexical":{"kind":"elasticsearch","index":"tako_dialogue_v1","healthy":true},"vector":{"kind":"milvus","collection":"tako_dialogue_v1","healthy":true,"embeddingModel":"…","dimensions":1024},"jobs":{"pending":0,"running":0,"failed":0}}}
```

新增业务码登记到 doc/40：

| code | HTTP | message | 用途 |
|---|---|---|---|
| `119001` | 503 | 历史对话词法索引不可用 | ES 调用或 mapping 校验失败 |
| `119002` | 503 | 历史对话向量索引不可用 | Milvus 调用或 collection 校验失败 |
| `119003` | 503 | 历史对话向量生成服务不可用 | embedding 请求失败或响应形状不符 |
| `119004` | 409 | 向量模型或维度已变化，请重建对话索引 | 启动或更新时模型指纹不兼容 |
| `119005` | 409 | 当前未启用历史对话混合检索 | 非 hybrid 模式调用 hybrid 诊断端点 |

错误仍按 `code → message → data`，失败时 `data:null`；内部堆栈、SQL、URL 凭据与 API key 不进 `message`。

## 7. 写入、删除与恢复

### 7.1 正常写入

`indexDialogueRun` 从“只 upsert chunk”改为“chunk 与索引任务同事务”。登记任务后才允许外部调用；外部调用不参与 PG 事务，避免把网络故障扩散到 run 主链。现有反查循环继续提供漏建补偿，不新增强制 broker。

### 7.2 项目删除

删除事务先枚举本项目 `run_id` 并登记 delete 任务，再按现有规则清理 `dialogue_chunks`。消费者按任务中的归属信息删除 ES/Milvus 文档。若删除时外部服务不可用，业务删除与任务持久化仍成立，后台按退避继续，最终不得残留可检索记录。

### 7.3 崩溃与多副本

- 消费者领取靠 PG 租约和 `claim_epoch`；旧副本恢复后不能用旧代次写回完成状态。
- “PG 提交后、外部写入前”崩溃：对账器重新领取任务。
- “ES 成功、Milvus 前”崩溃：重试只处理 `vector_done_at` 为空的半边，ES 不重复创建文档。
- “外部写入成功、done 写回前”崩溃：按同一 `run_id` 幂等 upsert，数量不翻倍。
- 两副本同时消费：同一任务只有一个有效 `claim_epoch`；文档主键固定，最终至多一条当前版本。

### 7.4 全量重建与模型变更

新增离线命令：

```bash
go run ./cmd/yktako -rebuild-dialogue-retrieval
```

- 必须在隔离环境或明确维护窗口执行，扫描全部 `dialogue_chunks`，逐行幂等登记/重做任务，并清理 PG 中已不存在的 `run_id` 对应外部记录。
- 重建期间允许“尚未索引”的暂时缺口，不允许把陈旧正文当当前正文；命中哈希复核是最后一道保护。
- 模型或维度变化时新建 collection，完成全量重建和计数校验后再切换配置；旧 collection 只在确认新路径可用后清理，清理动作不自动执行。

## 8. 观测与验收

新增/扩展 span：

- `dialogue.index.es`、`dialogue.index.embedding`、`dialogue.index.milvus`：任务 ID、run ID、模型、耗时、结果，不记正文与密钥。
- `dialogue.recall.es`、`dialogue.recall.embedding`、`dialogue.recall.milvus`、`dialogue.recall.rrf`：各臂候选数、融合候选数、最终注入数与降级原因。

至少覆盖以下真实场景：

1. **语义增益**：同一份历史对话，`pg_search` 对“周末/发布”类换说法查询取不到目标，hybrid 取向量候选并能返回原 run；诊断接口同时出现 ES 与 Milvus 调用证据。
2. **跨 session、限项目**：同用户同项目的另一 session 能查到；同用户另一项目查不到；另一租户查不到。
3. **改口与历史**：旧约定与新约定都能按时间找到，active 记忆仍只返回当前结论，证明两条线没有互相覆盖。
4. **更新与删除**：对话块更新只留新版本；项目删除后 ES 与 Milvus 都无记录。
5. **崩溃恢复**：PG 提交后、ES 成功后、Milvus 成功后三个窗口 `kill -9`，重启后最终一致且不重复。
6. **双副本**：两个消费者同时领取，任务与外部文档数量不翻倍，旧 `claim_epoch` 写回无效。
7. **全量重建**：隔离环境删除外部索引，离线重建后文档数与合格 PG 对话块数一致，查询恢复。
8. **负路径**：embedding 失败、ES 失败、Milvus 失败、维度不符、非法响应、无权限查询，均不静默降级或泄漏。
9. **既有回归**：`go test ./internal/runengine ./internal/observability`、`go vet`、前端 typecheck/build、现有契约与 spotcheck 全过；`memory_items` 与常驻记忆相关测试无行为变化。

完成验收必须留下真实请求/响应、ES/Milvus 文档计数、PG 任务状态、崩溃与双副本日志。缺少可用 embedding 服务时，可以完成单元与接口测试，但**不得宣布本方案完成**。

## 9. 施工顺序

1. 先用 curl 打通隔离 ES、Milvus 与 embedding：固定 mapping、collection、分词、向量维度与诊断端点真实字节。
2. 建 PG 任务表与事务登记，完成 upsert/delete 的幂等与租约测试。
3. 接 ES 写入与查询，再接 embedding/Milvus，最后接 RRF 与 PG 命中复核。
4. 接入 `Store.Recall` 的 hybrid 分支，保持 active 记忆与现有响应形状。
5. 补删除、对账、双副本、崩溃与全量重建。
6. 补诊断端点、观测、机器可重跑验收与文档；先 curl 实字节再写 contract test 与 `expected.json`。
