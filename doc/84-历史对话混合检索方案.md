## 0. 一句话与完成线

采用 **Transactional Outbox + Redpanda + 至少一次投递 + 幂等消费者 + 定期对账与全量重建**，给 `dialogue_chunks` 建立 ES 词法索引和 Milvus 向量索引。两路各取候选后按 RRF 合并，命中结果带来源会话、run、日期和原文片段；Milvus 零命中时，整个 `<dialogue-context>` 都不生成。

完成线不是“两个服务能连上”，而是下面这条链真实成立：

```text
会话 A 说「发布窗口改到周六凌晨」
  → PG 对话块与 outbox 事件同事务提交
  → Redpanda 按 run_id 分区投递
  → ES 与 Milvus 各自幂等完成索引
  → 会话 B 问「周末什么时候上线」
  → ES 与 Milvus 各取候选，RRF 合并
  → 带来源和原文片段注入，且只用于参考
  → 另一个项目、另一个租户取不到
  → 项目删除后外部记录最终消失
  → 消费者崩溃、消息重复或乱序后，最终仍收敛且不重复
```

缺真实 embedding、未做故障与双副本验收、没有原文引用或权限证据，都不能宣布完成。

## 1. 为什么这样设计

当前有三种不同的数据，不能混用读取方式：

| 数据 | 当前职责 | 本方案边界 |
|---|---|---|
| resident 硬性指令与用户偏好 | 每场全量进 system prompt | 不检索、不修改 |
| active 长期记忆 | 判重、改口、冲突与 supersede 历史链 | 代码逻辑不改 |
| `dialogue_chunks` 历史对话原文 | 查“当时具体怎么说的” | 本次唯一施工面 |

典型失败故事是：会话 A 说“发布窗口改到周六凌晨”，会话 B 问“周末什么时候上线”。BM25 可能因“周六/周末”“发布/上线”词面不同而漏掉，但用户需要的是那段原文，不是重新生成一条 active 记忆。

同时，PG、ES、Milvus 和外部 embedding 不在一个事务里。不能通过把网络调用塞进 PG 事务来假装原子提交：ES 已成功而 Milvus 失败时，PG 可以回滚，ES 却不会自动回滚。大型系统应接受最终一致，用持久事件、幂等、重试、对账和重建处理，而不是追求不现实的分布式事务。

## 2. 范围、初始化与非目标

### 2.1 本期做

- 延续 `runlog_entries → dialogue_chunks`，每个完成的 run 一个对话块，不重写 chunking。
- PG 对话块与 outbox 事件同事务写入；Redpanda 按 `run_id` 分区运输。
- ES 与 Milvus 使用独立消费者组，至少一次投递、幂等写入、失败重试、死信与对账。
- 两路各取至多 10 个候选，RRF 合并后最多注入 3 段，带来源和原文引用。
- 项目内跨 session 查询，租户、用户、项目过滤，项目删除和会话移动同步。
- 全量重建使用版本化 ES 索引和 Milvus collection，验证后切换活跃指针，保留旧版本用于回滚。
- 保留 `GET /api/memory/recall` 的响应形状，新增 dev `query/status` 诊断接口。

### 2.2 明确不做

- 不改 `memory_items`、resident 快照、`search_memory`、active 判重或 supersede 历史链的代码逻辑。
- 不把全部 runlog 交给模型，不为 active 记忆增加每回合固定 embedding 成本。
- `pg_search` 与 ES 是词法臂二选一；pgvector 与 Milvus 是向量臂二选一。正常查询不叠加、不互备。
- 不做跨 PG、ES、Milvus 的分布式事务，不承诺 exactly-once。
- 不做租户级 embedding 管理面、在线 reranker、知识图谱、知识库产品或 embedding 模型迁移。
- 不把“服务健康”当成“数据覆盖完整”，不把检索结果当成完整事实或不存在证明。

### 2.3 初始化：只清对话数据，保留账号与配置

本次不迁移旧对话。账号、租户、成员、项目与模型配置、`teamInstructions` 等硬指令配置保留；对话数据按同一批清理，包括：

- `sessions/runs/runlog/run_model_messages/run_journal`；
- `memory_items/memory_jobs`；
- `dialogue_chunks/dialogue_index_jobs` 与 outbox 事件；
- 相关 Task、通知、后台 job、Redis 临时运行态和会话运行文件；
- ES/Milvus 中对应的派生记录及 Markdown 模式的对话记忆文件。

清理时递增 `index_version`，消费者忽略旧版本消息，避免已投递但尚未消费的旧事件把对话重新建回来。active 记忆代码逻辑不变，从空表建立新链；硬指令继续从配置注入。

不得调用 `/api/dev/reset`，它会连账号和配置一起清掉。实际需要一个显式的“仅对话数据”清理步骤，不由 hybrid 功能自动执行。后文“全量重建”只针对这批新数据，不做旧对话 backfill。

## 3. 总体业务链

```text
【写入与投递】
run 完成
  → runlog_entries（永久正本）
  → dialogue_chunks（可重建对话块）
  → 同一 PG 事务写 outbox 两类任务：target=es / target=milvus
  → outbox relay 读已提交事件并投递 Redpanda
  → 按 run_id 分区
       ├─ ES 消费者组：取对话块 → upsert ES
       └─ Milvus 消费者组：取对话块 → embedding → upsert Milvus
  → 各目标任务写回 done；失败按任务状态退避、重试或进入死信

【查询与引用】
新用户消息
  → ES BM25 Top-10
  → query embedding → Milvus COSINE Top-10
  → RRF 合并
  → 按当前 tenant/user/workspace 过滤
  → Milvus 有命中才继续；零命中不生成任何检索块
  → 取前 3 段，带来源会话、run、日期和原文片段注入
```

outbox 消息只带事件与归属元数据，不带 passage 或密钥。两个消费者分别回 PG 读取本次要索引的对话块，避免在 MQ 中复制大段敏感文本；查询时则直接使用外部索引中保存的不可变历史副本，不逐条回 PG。

## 4. 数据与事件契约

### 4.1 对话块与 `index_version`

- `runlog_entries` 是永久正本；`dialogue_chunks` 是检索块，包含 `run_id/session_id/tenant_id/user_id/workspace_id/passage/indexed_at`。
- 完成后的 runlog 不做日常修改，compact 也不改 runlog，因此不做正文 SHA 或每次查询回表校验。
- `index_version` 由 passage 生成算法、PII 规则、embedding 模型和初始化代次组成。它用于幂等、版本切换和忽略旧消息，不用来证明权限。
- ES 与 Milvus 保存脱敏后的 passage、向量（仅 Milvus）及来源元数据。命中后直接引用该历史副本；PG 只负责正本、删除和重建。

### 4.2 Outbox 表 `dialogue_index_jobs`

一个业务事件对应两条目标任务：`target=es` 与 `target=milvus`，使两边能独立领取、重试和完成。

| 字段 | 含义 |
|---|---|
| `id` | `dij_<ULID>`，目标任务主键 |
| `event_id` | 同一业务事件的稳定 ID，两个目标共用；用于消息去重 |
| `run_id` / `session_id` | 来源 run 与会话，也是 Redpanda 分区键 |
| `tenant_id` / `user_id` / `workspace_id` | 真实归属，delete 任务同样保留 |
| `target` | `es` / `milvus` |
| `kind` | `upsert` / `delete` / `move`（仅改项目元数据） |
| `index_version` | 索引与初始化代次 |
| `embedding_model` | 本任务模型；delete 可为空 |
| `status` | `pending` / `running` / `done` / `failed` |
| `attempts` / `next_attempt_at` | 尝试次数和下次可执行时间，退避 1/5/30 分钟 |
| `claim_epoch` / `lease_until` | 该目标任务的执行代次和租约，默认 2 分钟并续约 |
| `published_at` / `done_at` | 投递与完成时间，分别用于 relay 对账和完成判定 |
| `last_error` | 最近一次机器可读错误，不含正文与密钥 |
| `trace_parent` | 来源 run 到消费者的 trace 透传 |
| `created_at` / `updated_at` | 审计时间 |

约束与不变量：

- `UNIQUE(event_id, target)`：同一事件的同一目标只登记一次。
- `UNIQUE(run_id, kind, index_version, target)`：同一版本、同一目标重复登记回读原任务。
- `INDEX(status, next_attempt_at)`：处理到期 pending 和租约过期 running。
- 同一事件只有在 ES 与 Milvus 两个目标任务都 done 后才算业务完成。
- 消费写回必须匹配 `id + claim_epoch`，旧代次不得覆盖新代次。
- 消息正文 `{eventId, runId, target, kind, indexVersion}`；消费者组只处理自己的 target，并据此回读任务和对话块。消息不包含正文、密钥或向量。

### 4.3 版本化活跃指针 `dialogue_retrieval_pointer`

单例行记录当前生效的 `index_version`、ES index/alias 和 Milvus collection。全量重建先创建新版本，验证后在一笔 PG 事务中切换指针；各副本都以该指针为读取目标。旧版本只在新版本验证通过后，按显式操作清理，不自动删除。

版本对象名 = 基名 + `_v<版本号>`（如 `tako_dialogue_v1_v2`）。后缀用下划线不用连字符：Milvus collection 名只允许字母/数字/下划线，连字符会被 `Invalid collection name` 拒收（rebuild 活体实测）；ES 下划线同样合法，两侧同一函数派生。

## 5. ES 与 Milvus 契约

### 5.1 ES：词法索引

索引 `tako_dialogue_v1`：

- `_id=run_id`；
- `session_id/tenant_id/user_id/workspace_id` 为 keyword；
- `passage` 为脱敏后的 text，索引分词 `ik_max_word`、查询分词 `ik_smart`（IK 社区惯例搭配）；
- `index_version/embedding_model` 为 keyword；
- `run_finished_at/indexed_at` 为 date。

ES 实例必须安装与 ES 版本一致的 infinilabs analysis-ik 插件（本实例实测 9.5.0，对应 `elasticsearch-analysis-ik-9.5.0.zip`）。使用 BM25 `match + bool filter`，最多 10 个候选。mapping 和 `_analyze` 必须先实测中文、英文、数字、生造词及中英混排；启动预检用 `_analyze` 验证 `ik_smart/ik_max_word` 真实可用，插件缺失或既定用例不通过则启动失败并报告，不静默换语义。

### 5.2 Milvus：向量索引

collection `tako_dialogue_v1`：

- `run_id` 主键；
- 归属字段与脱敏后的 `passage`；
- `index_version/embedding_model`；
- `embedding FLOAT_VECTOR`，维度由真实 embedding 探针确定；
- `run_finished_at/indexed_at INT64`。

使用 `COSINE + HNSW`，初始 `M=16`、`efConstruction=200`、查询 `ef=64`，最多 10 个候选。维度不符返回 `119004`。本期固定 embedding 模型，不做模型迁移，不混写不同模型或维度的向量。

Zilliz Cloud serverless 使用 `URI + token + TLS + DB`；token 只从环境读取，P0 核实官方 SDK 的 token 字段。验收 collection 由脚本生成 `tako_dialogue_eval_<timestamp>`，只清理脚本自己创建的 collection，不碰已有业务 collection。

## 6. Redpanda 与消费者可靠性

### 6.1 至少一次投递，不追求 exactly-once

- relay 读取已提交 outbox 事件并投递；`published_at` 未写成功时，对账会再次投递，允许重复消息。
- 两个独立消费者组：`tako-dialogue-es-v1`、`tako-dialogue-vector-v1`。
- 按 `run_id` 分区，保证同一文档 upsert/delete 顺序；不同 run 可并行。
- 消费者先持久化处理结果，再提交 offset；失败则按 PG 任务状态驱动重试，避免 MQ 与 DB 双头重试。

### 6.2 幂等与失败处理

- ES/Milvus 都按 `run_id` 幂等 upsert；`eventId + target` 用于识别重复消费。
- 临时错误、429、5xx：按 1/5/30 分钟退避，第三次后 failed。
- 永久错误、维度不符、非法响应：将目标任务置为 `failed` 作为持久死信并告警，保留事件与错误分类，不无限重试。
- 对账器处理到期 pending、租约过期 running 和 `published_at` 缺失的已提交事件。
- embedding 采用批量、限流和背压，防止全量重建时打爆供应商。

### 6.3 删除与会话移动

- 项目删除事务先枚举 run_id 并登记 delete 任务，再删除对话块；两个外部目标都确认不存在后，事件才完成。
- 会话移动项目时，同一事务更新对话块项目归属并登记 `kind=move` 事件，只更新 ES/Milvus 的 `workspace_id` 元数据，不重新 embedding。
- 初始化清空对话数据时递增 `index_version`，旧消息和旧任务不得覆盖新代次。

### 6.4 对账与全量重建

周期性比较 PG 中应存在的 run_id/index_version 与 ES/Milvus 实际记录，缺失则重新投递，多余则清理。

执行 `-rebuild-dialogue-retrieval` 时：

1. 创建新版本 ES 索引和 Milvus collection；
2. 扫描新数据的 `dialogue_chunks` 并幂等回放；
3. 校验文档数、失败数和抽样查询；
4. 一笔事务切换 `dialogue_retrieval_pointer`；
5. 旧版本保留用于回滚，清理只能显式执行。

重建期间可以有“尚未索引”的缺口，但 Milvus 零命中时不能向 LLM 注入任何文本，也不能用提示语或 PG 兜底凑内容。

## 7. 查询、权限与原文引用

### 7.1 RRF

两路 rank 均从 1 开始：

```text
RRF(run) = Σ 1 / (60 + rank)
```

同一 run 在两路出现时累加，按 RRF 降序、runID 升序打破平分。原始 BM25 与向量分数只用于各自排序，不跨引擎比较。

### 7.2 权限

- 普通用户：按当前 `tenant_id + workspace_id + user_id` 过滤。
- owner/admin 的 `scope=tenant` 预览：按 `tenant_id + workspace_id`，不按单个 user。
- dev 查询先校验 `VisibleWorkspace`；跨租户 `tenantId` 仅 system admin 可用，沿用 `memoryContext`。
- 外部过滤是必要条件和性能优化；会话移动与项目删除通过事件同步，不靠正文哈希证明权限。

### 7.3 零命中与原文引用

**Milvus 零命中时，即使 ES 有候选，也不生成 `<dialogue-context>`，连空壳和提示语都不给 LLM。** 异常与缺数只进日志和诊断接口。

有命中时，每条引用都包含 `session_id/run_id/run_finished_at` 和脱敏后的原文片段：

```text
<dialogue-context>
以下历史对话检索结果仅供参考，不代表完整历史，也不一定是当前事实。
- (2026-11-19, 会话 s_123, run r_01ABC) 用户：发布窗口改到周六凌晨
</dialogue-context>
```

`session_id + run_id` 是回查原 run 的稳定坐标。引用由程序按模板拼接，不由 LLM 生成；长 passage 只按长度截取，不总结、不改写。

## 8. 配置、API 与观测

### 8.1 配置

```text
TAKO_DIALOGUE_RETRIEVAL=pg_search | hybrid
TAKO_ES_URL=http://43.135.163.238:9200
TAKO_ES_INDEX=tako_dialogue_v1
TAKO_ES_USERNAME=elastic
TAKO_ES_PASSWORD=<从本机 .env 读取，不写入文档>
TAKO_MILVUS_URI / TAKO_MILVUS_TOKEN / TAKO_MILVUS_USE_TLS / TAKO_MILVUS_DB / TAKO_MILVUS_COLLECTION
TAKO_DIALOGUE_EMBEDDING_BASE_URL / API_KEY / MODEL / TIMEOUT / BATCH_SIZE / MAX_INPUT_TOKENS
TAKO_REDPANDA_BROKERS / USER / PASSWORD / MECH
```

- 缺省仍为 `pg_search`；`TAKO_RAG=off` 时不启动对话索引与召回。
- hybrid 启动必须真实检查 ES mapping/分词、Milvus collection/维度、最小 embedding 和 Redpanda topic；失败则启动失败，不静默降级。
- 运行中任一臂失败，本次召回不注入，worker 记日志并继续 run；不静默退回单臂或 `pg_search`。
- embedding 为实例级配置；密钥只从环境读取，不写库、日志或响应。

### 8.2 保持不变的接口

`GET /api/memory/recall` 仍返回 `{block,dialogueHits,injectedRunes,memoryHits}` 的信封数据。`memoryHits` 仍来自 active 记忆，不与对话命中混算。无新增帧 kind、无 SSE 字节变化、无前端假数据改造。

### 8.3 新增 dev 接口

`POST /api/dev/dialogue-retrieval/query`：输入 `{query,workspaceId,limit}`，limit 缺省 10、最大 20。成功 data 键序为 `mode → lexical → vector → merged`，分别返回词法候选、向量候选和 RRF 结果。

`GET /api/dev/dialogue-retrieval/status`：返回模式、活跃指针、索引健康、embedding 模型与维度，以及 `pending/running/retry/failed` 任务数、最老未完成任务时间、消费 lag 和覆盖水位。不得只显示服务健康而隐藏数据缺口。

错误码：

| code | HTTP | message | 用途 |
|---|---|---|---|
| `119001` | 503 | 历史对话词法索引不可用 | ES 或 mapping 失败 |
| `119002` | 503 | 历史对话向量索引不可用 | Milvus 或 collection 失败 |
| `119003` | 503 | 历史对话向量生成服务不可用 | embedding 失败或响应非法 |
| `119004` | 409 | 向量模型或维度已变化，请重建对话索引 | 维度或模型指纹不兼容 |
| `119005` | 409 | 当前未启用历史对话混合检索 | 非 hybrid 调用诊断接口 |

全部使用 `{code,message,data}`，失败 `data:null`，不返回堆栈、正文或凭据。

### 8.4 观测

新增 outbox relay、ES/Milvus 消费、embedding、RRF span；记录 run/event ID、模型、耗时、候选数、失败分类。持续记录：

- 各分区消费 lag 与最老未完成任务时间；
- pending/running/retry/failed 数量；
- PG 与外部文档数差异；
- 索引进度水位和当前活跃版本。

不记录正文、向量原文或密钥。导出失败只记日志，不影响业务 run。

## 9. 验收与完成线

至少完成以下真实场景：

1. **语义增益**：同一 query 在 `pg_search` 下取不到目标，hybrid 的 Milvus 能找到目标 run；dev 诊断同时出现 ES 与 Milvus 调用证据。
2. **跨 session、限项目**：同项目另一 session 可查，另一项目和另一租户不可查。
3. **active 与原文分离**：active 记忆按当前结论，历史对话按时间引用，二者不互相覆盖。
   > 2026-11-21 真 run 实测：**检索面通过**（改口前后两条原文都在且可召回）；**active 面暴露 doc/65 记忆线的缺陷**——较早 run 的 `postrun` 抽取晚到时，会把较晚 run 改口后的新结论 supersede 回旧结论（两次复现，时间戳+引擎日志为证）。缺陷归 **doc/65 线**，本方案不改；此项在记忆线修好前**不算通过**。
4. **零命中与缺数**：Milvus 无结果时即使 ES 有候选，也没有 `<dialogue-context>`；有结果才生成带原文引用的参考块。
5. **删除与移动**：项目删除后 ES/Milvus 目标记录为 0；会话移动后只更新 workspace 元数据。
6. **重复与乱序**：同一事件重复投递、不同版本乱序，最终只有当前版本一条有效记录。
7. **崩溃恢复**：PG 提交后、ES 成功后、Milvus 成功后、done 写回前分别 `kill -9`，重启后最终一致且不重复。
8. **双副本**：两个消费者同时工作，只有一个有效 `claim_epoch`，旧代次写回无效。
9. **失败与死信**：embedding 超时/400/500/坏 JSON/维度错、ES/Milvus 不可用，均有退避、死信和告警证据，不静默降级。
10. **全量重建**：新版本回放、数量与抽样校验、指针切换和旧版本回滚均成功。
11. **既有回归**：Go test/vet/build、前端 typecheck/build、现有契约与 spotcheck 全过；active 与 resident 行为不变。
12. **真实回合端到端**（2026-11-21 补，DEEPSEEK 恢复后）：`POST /api/runs` 打真模型的对话能完成 → 被索引（`dialogue_chunks` + ES）→ 被 hybrid 召回命中（用与原文词面不同的查询，向量臂真跑通）。脚本 `scripts/acceptance/dialogue_hybrid_realrun_live.sh`（绿 9／红 0）。

必须留下真实请求/响应、Redpanda lag、PG 任务状态、ES/Milvus 文档计数、崩溃与双副本日志。缺真实 embedding 或任一组未过，不得宣布完成。
