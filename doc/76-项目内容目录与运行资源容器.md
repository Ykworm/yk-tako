## 1. 目标：用户内容与执行资源不再混在一起

以用户项目 Tomcat 为例，目标逻辑布局是：

```text
Tomcat-project/                    # 项目资源容器：删除项目时整容器清理
├── Tomcat/                        # 项目内容根：用户真正需要看到的内容
└── runtime/                       # 执行资源：默认不出现在用户文件清单
    ├── orchestrations/<编排组ID>/  # 异步工作区、不可变结果、验证与发布记录
    ├── tmp/                       # 有明确清理规则的临时文件
    ├── media/                     # 上传媒体与内部读取副本
    └── memory/MEMORY.md           # Markdown 模式的项目记忆
```

真实磁盘仍可使用租户与工作区 ID 防重名，例如：

```text
<workspace>/tenants/<tenantId>/workspaces/<workspaceId>/
├── content/
└── runtime/
```

`workspaces/<workspaceId>` 从“模型直接读写的项目根”改成“项目资源容器”；`content/` 才是用户内容根。UI 中的项目名 Tomcat 与磁盘 ID 分离，不因项目改名移动目录。

这个方案解决的是：用户打开 Tomcat 时只看到自己想看的内容，而不是 `.tako`、`.media`、工作副本、验证记录或项目记忆。

## 2. 当前真实布局与差距

当前代码把以下内容混在项目根：

```text
workspaces/<workspaceId>/
├── .media/
├── .tako/bash/
├── .tako/fetch/
├── MEMORY.md
└── <用户文件>
```

同时，异步隔离组在租户级：

```text
tenants/<tenantId>/.tako/orchestrations/<orchestrationId>/workspace/
```

技能与工具则在：

```text
tenants/<tenantId>/skills/
tenants/<tenantId>/tools/
```

当前项目删除只删除项目根和关联会话目录；编排组目录仍等终态过窗后清理。技能、工具与用户 `USER.md` 不随项目删除。

所以目标与现状有三个根本差距：

1. 项目根既是用户内容，又承载运行资源；
2. 编排组归租户目录，不归项目资源容器；
3. 删除没有一个可以完整代表项目磁盘资源的容器边界。

## 3. 两个目录概念必须分开

| 概念 | 操作定义 | 谁使用 |
|---|---|---|
| 项目内容根 `content/` | 文件工具、普通聊天和用户文件列表所看到的项目根 | 用户与普通文件操作 |
| 项目资源容器 | 内容根与 runtime 的共同父目录；删除项目时的磁盘边界 | 引擎、迁移与删除 |
| 运行资源根 `runtime/` | 保存异步工作区、结果、临时文件、媒体与项目记忆 | Provider、Worker、清理器 |
| 会话目录 | 保存子代理 wire 等会话自有档案 | 现有会话生命周期 |
| 租户资源根 | 保存租户共享技能、工具与用户记忆 | 租户级能力，不归单个项目 |

代码不能继续让 `workspaceDir()` 同时回答“内容根”和“资源容器”。需要拆成：

```text
projectContainerDir(root, tenantId, workspaceId)
projectContentDir(root, tenantId, workspaceId)
projectRuntimeDir(root, tenantId, workspaceId)
```

`WorkspaceRef.Root` 表示当前执行者真正的工作根；另增通用 `RuntimeRoot` 承载 bash 输出、抓取全文等内部落盘。媒体与项目记忆通过各自路径函数定位，不再从 Root 猜资源位置。

## 4. shared 与 isolated 在容器里的准确含义

本方案讨论的是**异步 Task**。普通聊天仍可直接修改 `content/`，行为不变。

### 4.1 shared 异步工作区

`shared` 表示同一编排组里的 Task 共用一个工作现场，不是直接写用户内容根：

```text
runtime/orchestrations/<编排组ID>/workspace/work/shared/
```

- A/B 在同一个共享工作目录中工作；
- 文件工具的短写入保护仍生效，但 bash 任意写仍是非合作边界；
- 中间结果不直接进入 `content/`；
- 最终结果经过接受与发布后进入 `content/`。

### 4.2 isolated 异步工作区

`isolated` 表示每 Task 一个工作现场：

```text
runtime/orchestrations/<编排组ID>/workspace/work/<taskId>/
```

- Git 项目仍由 GitProvider 使用本组中间仓库与 linked worktree；
- 非 Git 项目仍由 DirectoryProvider 使用独立目录副本与变更清单；
- 不可变父结果通过现有结果引用交接；
- 最终发布仍走 doc/74 的验证、项目准入与恢复。

因此 shared／isolated 的区别是“**同组共享现场还是每 Task 独立现场**”，不是“一个写项目、另一个不写项目”。两种异步模式都不把中间产物直接暴露到用户内容根。

模式选择与默认值是否调整不在本篇范围；本篇只改变目录归属与发布边界。

## 5. 结果、产物与临时文件

### 5.1 不可变结果

每个 Task 的已接受结果保存在：

```text
runtime/orchestrations/<编排组ID>/workspace/results/<taskId>/<resultRevision>/
```

中间 Task 结果只供下游、审查与恢复使用，不复制进 `content/`。只有最终 Task 的结果经发布链进入用户内容根。

结果产物仍通过 doc/74 的 Task artifact 端点按版本读取；项目当前文件仍走现有 media／文件出口。两者不能因为路径相同就混用。

### 5.2 临时文件

统一逻辑落点为 `runtime/tmp/`，但不同用途仍分子目录与清理规则：

- Provider staging；
- 目录复制与迁移 staging；
- 内部 Git 临时输出；
- 其他有明确超时与清理者的临时内容。

不能把所有临时文件堆到一个无归属目录。每个条目必须带组／任务／操作归属，过期清扫只删满足既有时间与安全条件的条目；正在使用、身份不明或包含唯一未保存工作的目录保留。

bash 全文与 web_fetch 全文是有恢复价值的运行输出，不叫临时垃圾。它们分别进入当前工作现场对应的 `runtime/` 记录区，不进入 `content/.tako/`。

## 6. 技能、工具、plugin 与记忆的归属

### 6.1 本期不变的部分

```text
<workspace>/system-skills/                  # 系统技能
<tenant>/skills/                            # 租户技能
<tenant>/tools/                             # 租户上传工具
<tenant>/users/<userId>/USER.md             # 用户记忆
```

这些不是 Tomcat 项目独占资产，不移动到 Tomcat 的资源容器，也不随 Tomcat 删除。

当前没有用户级 skill／plugin；本期不增加。当前也没有项目级技能归属，不从现有租户技能推造一层。

### 6.2 项目记忆

Markdown 模式的项目 `MEMORY.md` 改到：

```text
runtime/memory/MEMORY.md
```

它仍按原 WorkspaceID 归属与加锁，仍随项目删除；只是不再出现在用户文件清单中。pipeline 模式的 PG 记忆与任务不受目录迁移影响，项目删除仍按 scope 清理。

## 7. 项目删除：整容器删除，但不误删租户资产

目标删除链：

```text
用户删除项目
→ 锁项目与发布准入
→ 拒绝默认项目、活 run、未收口组、publishing／blocked 发布
→ PG 事务软删会话、清项目记忆／记忆任务、删项目行
→ 提交后删除整个项目资源容器
→ 删除关联会话目录中的项目私有档案
→ 发既有 workspace_deleted 事件
```

整容器删除包括：

- `content/`；
- `runtime/`；
- 本项目的全部异步工作区、结果、验证与发布记录；
- 项目记忆文件与媒体；
- 本项目临时文件。

不删除：

- 租户技能与工具；
- 系统技能；
- 用户 `USER.md` 与用户级记忆；
- 按 doc/37 仍需保留的 PG run／runlog／用量档案。

目录删除失败只记日志并保留清理记录，API 不把“目录没删掉”伪装成磁盘已清理；现有业务响应与保留策略如需调整，在施工包中单独钉契约，不顺手改旧接口。

## 8. 存量项目迁移

不能因为目录改名就丢现有项目。每个存量项目独立迁移，迁移期间禁止该项目新 run 与发布：

```text
锁项目
→ 检查无活 run／未收口组／发布
→ 在同级创建唯一 staging 容器
→ 把现有用户文件复制到 staging/content/
→ 把 .media、.tako、MEMORY.md 复制到 staging/runtime/ 的对应位置
→ 把本项目已有编排组目录复制到 staging/runtime/orchestrations/
→ 校验迁移清单与文件哈希
→ 当前容器改名为 backup，staging 原子改名为正式容器
→ 成功后按保留策略清 backup
```

要求：

- 迁移清单记录源、目标、哈希与完成状态，崩溃后可对账；
- 不把未知目录或别人的容器删了；backup 清理只认本次迁移身份；
- 任何一个文件校验失败则该项目不切换，旧容器仍可用；
- 同一项目同时只有一个迁移者，其他项目可独立迁移；
- 迁移与启动装配解耦，不能让引擎启动时无界扫盘；由显式迁移命令或有限批量任务执行；
- 已有 PG 路径字段若只存逻辑项目 ID 则不变；若存有绝对路径，施工时先列清单并迁移，不留双写。

doc/74 当前工作区实现需要同步改路径来源；不得保留一个仍指向租户 `.tako/orchestrations/` 的旧写口。

## 9. 权限、安全与多副本

1. 文件列表、项目文件下载和普通文件工具只以 content 为根；runtime 不通过项目文件枚举暴露。
2. Task artifact 是唯一的不可变结果读口；权限仍走 Task 属主链。
3. 所有路径由租户、工作区、编排组和 Task ID 推导，模型不能指定容器路径。
4. 项目容器、会话目录与租户资源仍位于所有引擎副本共享的持久卷；本机另造目录不算恢复。
5. 内容迁移、工作区准备、发布和删除各有共享锁与恢复记录；不把文件操作塞进 PG 事务。
6. 存储配额继续按整租户目录计算；容器重归后不得重复计数或绕过配额。
7. 日志与 trace 不记录敏感文件正文；迁移报告使用相对路径与哈希。

## 10. 验收与完成线

### 10.1 目录与迁移

1. 新建项目得到 content/runtime 容器；普通聊天写文件只影响 content。
2. 媒体、bash 输出、抓取全文与项目 MEMORY.md 不出现在 content 或用户文件清单。
3. 存量项目迁移后用户文件逐字不变，运行资源进入 runtime；迁移中途 kill -9 可恢复，不双份混入正式目录。
4. 迁移过程中该项目不能开新 run 或发布；其他项目不受影响。
5. 租户技能、工具、系统技能与用户 USER.md 路径不变。

### 10.2 异步链

1. shared 同组 Task 共用工作目录，不直接写 content；最终发布后才看到结果。
2. isolated Git／Directory 各 Task 使用独立目录，不可变结果与父结果交接不受迁移影响。
3. 中间 Task 完成不污染 content；最终 Task 验证与发布失败时 content 不被冒充更新。
4. 结果产物仍可按版本读取；项目当前文件与结果版本不混淆。
5. doc/74 的 Git、Directory、双副本与崩溃场景在新路径下全绿。

### 10.3 删除

1. 活 run、未收口组与发布受阻仍阻止删除；默认项目仍不可删。
2. 删除成功后整个项目容器不存在，包括 content、工作区、结果、媒体、项目记忆与临时文件。
3. 关联会话私有档案按现有规则清理；租户技能／工具、系统技能、用户记忆与 PG 保留档案不受影响。
4. 目录删除失败有日志与清理记录，不能宣称物理清理成功。

### 10.4 标准门禁

除 Go／前端／契约测试外，还需真实跑：存量迁移、shared／isolated、Git／Directory、项目删除、kill -9、双副本、浏览器文件可见性与 doc/70／72／73／74 回归。

完成线是：**用户只看到项目内容；所有异步执行资源都归项目容器；中间结果不提前污染项目；最终发布与删除边界一致；存量项目不丢文件；租户共享资产不被误删。**

## 12. 所以这解决了什么

doc/76 把“项目目录”从一个混杂的大目录拆成用户内容根与项目资源容器：用户只看到 Tomcat，异步工作区、结果、媒体、项目记忆和临时文件都在容器内但不污染内容根。

它同时统一了 shared／isolated 的最终发布边界和项目删除边界，并明确租户共享技能、工具与用户记忆不属于某个项目。这样目录结构、可见性、隔离与生命周期才指向同一个项目模型。
