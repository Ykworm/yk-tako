0. 大白话版

今天缺什么。 tako 现在有两层半「记住」：笔记（notes）是用户明说「记下来」的 规矩，每场直接进系统提示；search_history 只在本会话里按词翻原文；跨会话仍然成立的 东西——「dev 库是 5433」「上次拍板用 Gin」——只活在那场 run 的轨迹里，新会话的模型 看不到也搜不到。

要加什么。 两条流水线，共用一份原料（runlog_entries，每次 run 已有的事件日志）：

  1. 线一 · 抽取（写完一场，后台做）：run 定稿后，同一个事务里登记一条「待抽取」任务； 常驻后台循环捡起任务，把这场 run 的轨迹拼成有界文本，交给抽取模型，输出「本场一句话 摘要 + 最多 5 条跨会话事实」，校验后写进 memory_items。
  2. 线二 · 索引（写完一场，后台做）：另一个常驻循环每 2 秒扫一次——哪些 run 已 complete 还没进索引，就拼出它的对话原文块（用户消息 + 助手终稿 + 子代理终稿），写进 PG 的新表 dialogue_chunks；这张表上建着 pg_search 的全文索引（自带中文分词 lindera 和 BM25 排名，都是扩展内部的事，我们不写一行分词/排名代码）。
  3. 召回（下一场开头，同步做）：新 run 组装好模型输入后，两线各查各的库：线一拿本轮 用户消息的词（我们的 bigram 切词）去 memory_items 查；线二把本轮用户原文直接交给 pg_search 查询（分词它自己做），按 BM25 分取前 3。命中结果拼成 <memory-context> 和 <dialogue-context> 两个姊妹块，追加在本轮用户消息末尾。系统提示和更早的历史 一个字节不动——前缀缓存不破。

三个名词准入：

  • pg_search：ParadeDB 出品的 PostgreSQL 扩展——把全文搜索引擎（Rust/Tantivy 内核） 装进 PG：建索引时声明分词器（我们选 chinese_lindera，词典中文分词），查询用 @@@ 操作符，相关分由扩展按 BM25（全文检索的行业标准排名公式：稀有词加分、词频饱和、 文档长度归一）算出。代价：它是 Rust 扩展，需要装进 PG 安装目录并要求 shared_preload_libraries 预加载（dev 实例要改一次配置并重启，源码硬门槛无豁免）。
  • chinese_lindera：pg_search 自带的词典中文分词器——把「数据库端口」切成 数据库/端口；数字与英文整词入索引（5433 不拆）、英文小写归一。WeKnora 生产同款。 查询端扩展自动用同一分词器，我们侧不需要切词。
  • 对话索引：dialogue_chunks 只是可重建的派生副本（doc/16 §4 护栏 1 的全文检索 版）——正本永远是 runlog_entries，索引清掉重建即可，不存任何正本没有的信息。

为什么是 pg_search 而不是「PG 内核 tsvector + Go 侧 BM25」（第三稿）。第四稿前的 实证（tmp/pgsearch-verify/）：中文分词 8 项断言全过（常规中文、中英混排 go1.27、数字 5433、生造词 flibbertigibbet、契约题「周末不命中周六」）、BM25 稀有词判官 PASS （5433 迁移 中 5433 文档 1.72 分压过「迁移×3」噪音文档 1.57 分）、查询延迟 0.3–5ms、 词典重载 issue（#4840）在我们的规模不复现。第三稿的自研方案（bigram 预处理 + 生成列 + GIN + Go 侧重排约 60 行）能省掉这全部——分词质量更好（词典切词 > bigram）、排名是厂商 实现、还顺手打开模糊匹配/短语/未来混合检索的门。换来的确定成本：dev 实例一次重启 + preload（见 §8），以及部署矩阵多一个扩展。

为什么这样切。 抽取要调模型、可能几秒，绝不能塞进用户等回复的主链路；索引写入是 本地毫秒级，但也保持后台循环、EndRun 零新增失败面。召回是当轮起手一次本地查询 （实测 0.3–5ms），必须在模型调用前完成。

为什么不全塞进笔记。 笔记每场都进系统提示，上限只有 2200+1375 字；自动抽出来的东西 没经用户点头，不能当「规矩」常驻；而且每场都变会破坏前缀缓存。检索出来的东西只进当轮 用户消息，错误的推断最多影响一轮，下一轮不再出现。

明确放弃什么（契约）。 词面检索的天花板是「字面重合」：问「周末」找不到原话里的 「周六」，这一类换说法问旧事不做——分词器再好也是词面检索（「周末」「周六」被切成 两个不同的词），这是 2026-10-18 的裁决（语义召回需要向量库 + embedding 服务商 + 外部调用面），不是技术漏项。验收 §11 把它固化成期望 0 命中。

所以这解决了什么。 新会话里，agent 自动知道上次说过的环境和拍过的板（线一），也能 按原话里的关键词找回三周前那场的现场（线二，词典分词 + BM25 排名）；用户不用重述，每条 都能顺着 source_run_id + source_seq（线一）或 run_id（线二）回到原话现场；错误的召回 最多影响一轮；三个开关一关，系统退回纯结构化存储。

1. 背景与病灶（故事先行）

1.1 三场会真实发生的戏

戏一：环境事实。 2026-10-18，用户在会话 A 里和 agent 排查构建失败，顺口说了一句：「这个 项目的 Go 不在 PATH，得用 PATH=$HOME/sdk/go1.27.0/bin:$PATH，shell 默认那个是 1.22。」 修好后会话结束。三周后，用户在会话 B 里说：「给新服务加个 HTTP handler，跑一下测试。」agent 直接 go test，用的是 1.22，报了一屏 package requires go >= 1.27。它不知道这句话；notes 里没有，因为用户当时没说「记下来」；search_history 只能搜会话 B 自己。于是 agent 花了 五轮重新排查——同一件事，用户第二次付了时间。

戏二：决策。 2026-10-09，用户在会话 A 里和 agent 比较了半小时 FastAPI 和 Gin，最后拍板 「Go + Gin，理由是单二进制部署」。两周后，会话 B 里用户说「给新服务写个接口」。agent 的 上下文里没有任何决策记录，于是又推荐了一次 FastAPI；用户不得不把结论重述一遍。这不是 笔记能救的：它是过程性决策，发生在对话里、没被显式记下。

戏三：跨会话找原话。 2026-10-18，用户在会话 A 里处理数据库迁移，和 agent 来回十几轮， 定下来：dev 库挪到 5433，「迁移窗口定在周六凌晨，5432 上那个旧实例只读到月底」。四周后 会话 B，用户问：「5433 那件事，旧实例读到几号？」

  • 词面检索（线二建成后）：「5433」被整词命中，原文现场召回，agent 答「只读到月底」。 「记得关键词、找原话现场」这类问题，线二解决。
  • 换说法检索（「之前排过周末要做的事吗」）：原话写「周六」、问的是「周末」，字面零重合。 这一类，本篇明确放弃（§0 契约，验收固化）。

前三场戏的共同点：原料其实都在——runlog_entries 完整记着；断的是「把上一场 run 的轨迹变成下一场可用的记忆 / 可搜的原文」这两段。

1.2 为什么现有几层接不住

层 现有机制 接不住的那一半
笔记 memory 工具 + notes 表 + 每场系统提示快照（doc/17 §7） 只收用户显式要求记住的短规矩；上限 2200+1375 字；不检索
会话检索 search_history 按词查本会话 runlog_entries（doc/21） 只搜本会话；命中数无排名；跨会话搜全量原文会又慢又噪

线一（本篇） — 补「可回忆」里的结论半边：跨会话事实的提炼与按需取用
线二（本篇） — 补「可回忆」里的现场半边：跨会话原文的按词面检索与排名

2. 边界：一份原料，两条加工线

两份语料都从 runlog_entries 加工，但形态、预算、召回路完全不同，混在一张表一个召回 函数里必互相拖累（WeKnora 也是这么分的：蒸馏记忆与聊天历史检索两套独立，见 §10）：

线一 · 蒸馏记忆 线二 · 对话原文
一行是什么 一条 ≤200 rune 的短句（fact/preference/decision/episode） 一场 run 的 Q/A 原文块（passage，≤4000 rune）
谁写 抽取模型归纳（调 LLM，慢） 机械拼接（不调 LLM，毫秒级）
什么时候写 run complete，outbox 登记 run complete，未索引反查（每 2s）
存哪 PG memory_items + memory_jobs PG dialogue_chunks（pg_search 索引）
召回路 ILIKE 词法（我们 bigram 切词 + 命中数） pg_search @@@（lindera 分词 + 扩展内 BM25）
回答什么问题 「上次拍过什么板、环境是什么」（结论） 「当时具体怎么说的」（现场）
预算 ≤5 条 × 600 rune 共上限 ≤3 条 × 300 rune，另设上限

四条不重叠的判据：

  1. 用户明说「记住」→ notes（人写的，可当规矩）。
  2. 模型处理中需要本会话原文 → search_history（精确原文）。
  3. 上一场 run 里发生过、跨会话仍成立的结论 → 线一（模型提炼的，只当参考数据）。
  4. 记得关键词、想找回原话现场 → 线二（原文块，BM25 排名）。

工具行（tool_call/tool_result）两条线都不进。 理由：工具输出大、噪、多是网页和文件 原文，不是「对话内容」；索引它们会把召回池灌满无关候选。需要精确找时本会话有 search_history。（WeKnora 的 IndexMessageToKB 也只索引 Q/A 对——这一 borrow 与存废 路线无关，保留。）

子代理终稿两条线都要进。 tako 的大活常整体委派给子代理（doc/23、25）：root 终稿可能 只有「researcher 已确认，改完了」一句，真正有价值的对话在子代理轨迹里。两线的输入文本 都收子代理终稿（线一截 1000 rune 进抽取输入；线二截 1000 rune 进 passage）。不收， 委派型 run 的记忆和索引都是空壳——而委派是 tako 最主要的用工形态。

3. 端到端链路

写链一 · 抽取（后台）：

用户发消息 → run 跑完，EndRun 同一事务：定稿 runlog + INSERT memory_jobs(pending)
  → 常驻抽取循环 claim 一条 job（PG SKIP LOCKED）
  → 读本 run 的 runlog_entries（seq 升序，拼有界文本：user 全留、root/子代理终稿全留、工具行截断）
  → 调抽取模型 → 输出 JSON（episode + ≤5 items）→ 校验 → 事务写 memory_items + job done
  → 失败：attempts+1 退避重试；三次后 failed（只留日志，run 早已 complete）

写链二 · 索引（后台）：

run complete → 常驻索引循环每 2s 扫一次：runs 表 status=complete 且 run_id 不在 dialogue_chunks
  → 读本 run 的 runlog_entries（seq 升序）：user 原文 + root 终稿 + 子代理终稿(≤1000 rune)
  → 拼 passage（总上限 4000 rune）
  → PG 单条 upsert：INSERT ... ON CONFLICT (run_id) DO UPDATE（§5.3；pg_search 索引随写维护）
  → 崩溃/重扫安全：重放同 run 只覆盖同一行，不翻倍

读链（当轮起手，同步，两线共用出口）：

下一场：POST /api/runs → prepareInput 组装历史（user 原文，不含任何记忆）
  → 切两半：mh 全序 → 「历史」+「本轮输入」（mh 严格是历史；只有 user input 没有 reply
    的那行不算历史，它是本轮输入——doc/30 §6 的 mh 定位：下一轮模型应该看到什么）
  → 线一召回：本轮 user 文本两段切词（§6.1）→ 查 memory_items（ILIKE OR + 命中数）
  → 线二召回：本轮 user 原文直接交 pg_search（@@@ 查询，lindera 分词 + BM25 在扩展内完成）
  → 各截上限 → 渲染 <memory-context> + <dialogue-context> → 追加到**本轮输入**末尾
  → 块写回 mh 的本轮 user 行（seq=1）——mh 里存的就是模型这一枪真看到的那份
  → 折叠（自测含块）→ 模型读到 → 回复
  → 下一 run 读 mh，历史里的 user 行自带上一轮的块（随历史累积，交给折叠链消化）

重建链（运维，随时）：

DELETE FROM dialogue_chunks 全清（或引擎旗标 `-rebuild-dialogue`，启动时清空）→ 扫描循环从 runlog_entries 全量重建
memory_items 不参与重建——它是 PG 正本的一部分（抽取产物），不是可弃副本

每条链的四问。 写链一做什么：把轨迹提炼成结论短句；不做：坏输出、模型挂，job 重试 兜底，run 本身早已 complete（输入 runlog，去向 memory_items）。写链二做什么：把原文变成 可全文检索的索引行；不做：run 定稿零新增失败面（输入 runs/runlog，去向 dialogue_chunks）。 读链做什么：当轮按需取回结论与现场；不做：历史与系统提示一个字节不变（输入本轮 user 文本，去向发送给模型的 state）。重建链做什么：副本整体重算；不做：正本 runlog_entries 一个字节不动。

两条写链的交点不存在——线一唯一的写方是抽取循环、唯一读方是记忆召回；线二唯一的 写方是索引循环、唯一读方是对话召回。两线只在读链的出口汇合（同一个注入点）。

4. 线一：抽取

4.1 触发点：run 终态 + outbox（为什么这条用 outbox，线二不用）

候选触发点 为什么不选
每轮对话后 一条用户消息往往只是「继续」；每轮抽一次 token 成本 × 轮数，同一事实反复写
会话结束 tako 没有「关会话」信号：session 可以长期存在，用户只是不再发消息
压缩前 runlog_entries 不可变、一行不丢；抽取不依赖压缩前的抢救
run 终态（本文） run 是唯一有明确边界的单位：一次用户请求 + 完整处理结果；原料恰好在这时全部定稿

为什么写 job 和 runlog 在同一个事务里（EndRun，store.go:230）。 如果 run 提交后、 登记任务前进程崩溃，这场 run 的记忆永远丢了，而且没有任何补偿线索。同事务意味着 run 定稿 ⇒ 待抽任务一定存在。这是 outbox 模式，不引入新基础设施。

为什么线一用 outbox、线二只用未索引反查：outbox 的价值在「调用慢且外部，必须 留补偿线索」——抽取要调 LLM，成立；线二的写入是本地毫秒级，反查 + 幂等重扫以更 少的件达到同等可靠性（§5.2）。为什么都不塞进 EndRun 同步做：EndRun 保持零新增失败 面与零新增延迟，主流程不欠记忆/索引任何东西。

只抽 complete。 error / stopped 的 run 没有可信的「结果」，且 EndRun 在这两种终态 本就零写入或只写配对工具行——没有完整轨迹可抽。

4.2 读什么：有界的 run 轨迹

按 run_id 读 runlog_entries（seq 升序），拼成文本：

role 进去的形态 边界
user 「用户：原文」 全留
assistant（root） 「助手：终稿」 全留
assistant（子代理） 「子代理(researcher)：终稿」 每条截 1000 rune
tool_call 「工具调用：name(args)」 args 截 200 rune
tool_result 「工具结果：输出」 每条截 500 rune

总上限 8000 rune。超上限时按优先级丢：先丢最旧的工具行（整行），仍超再截子代理终稿；user 与 root 终稿优先保——但单场本身超过 8000 rune 时仍从尾部截断（root 终稿可能被截），没有第三种 腾挪空间。没它会怎样：不加上限， 跑了 20 次搜索的 run 会把几十万字节灌进抽取调用，成本和延迟双失控。

为什么不带同一会话其他 run 的行。 抽取的单位是「一场 run」，跨 run 合并归召回（读时 组合）和二期 consolidate。一场一抽保证每批记忆都有明确的 source_run_id，能回现场。

4.3 提示词与输出契约

抽取输入 = 上面的轨迹 + 当前 notes 的 content 清单（上限内全带），让模型避开已经写在笔记里的规矩。

输出必须是纯 JSON（允许 ```json 围栏，解析前剥掉）：

{
  "episode": "本场一句话：谁要什么、做了什么、结果如何（≤200 字）",
  "items": [
    {"kind": "fact", "topic": "project.dev-pg-port", "content": "dev 库是 PostgreSQL 5433 端口；5432 是另一个实例的"}
  ]
}

kind 词表（四值，固定写死；不是配置）：

kind 含义 例子
fact 项目 / 环境事实 dev PG 端口 5433；构建要 Go 1.27
preference 用户工作偏好（从行为推断，不是显式规矩） 喜欢先给结论再展开；改文件前先读
decision 做过的选择与理由 选 Go + Gin，理由是单二进制部署
episode 每场 run 的一句话摘要（由 episode 字段生成为一条 item） 「用户要求把构建脚本修好，最终改了 Makefile 并跑通」

WeKnora 的 profile / interest / task 三个 kind 不采用：tako 是工作伙伴不是知识库/个人 助手；「用户是谁」归 fact，「任务进度」明确不抽（下次 run 会重算，写下来只会过期）。

提示词要点（逐条对应一个已知失败）：

  • 「只抽跨会话仍然成立的东西」——防把「已修复 X」写进记忆，下周变成过期事实。
  • 「不抽密钥、token、密码」——抽取模型看到的是工具输出原文，可能夹带 .env 内容。
  • 「下面给出已有笔记，不要重复」——防 notes 与 memory 两条同样的规矩同时出现。
  • 「topic 用小写 kebab-case，≤40 字符」——topic 是后续「同 topic 取最新」的键，自由文本 会让去重失效。
  • 「没有值得记的就输出空数组」——防模型为了交差硬编。

4.4 校验与写入（机械规则，不做智能判断）

逐条校验，坏条目丢弃并记数（不因一条坏而整坏 job 失败）：

  1. kind 必须在词表内。
  2. topic 匹配 ^[a-z0-9][a-z0-9._-]{0,39}$。
  3. content 非空、≤200 rune。
  4. content/topic 过 scanNoteInvisible（复用 notes.go 的 17 码点检查）。
  5. content 不含 <memory-context / </memory-context / <dialogue-context （两种块边界的伪造；§6.4 的 HTML 转义是第二道防线）。
  6. episode 超 200 rune 截断（摘要损失可接受，不因此重试）。

JSON 本身不可解析 → 整个 job 重试（这是模型/配置问题，单条校验兜不住）。

写入事务：

-- episode：每 run 一条，重放安全
INSERT INTO memory_items (...) VALUES (...) ON CONFLICT (source_run_id) WHERE kind = 'episode' DO NOTHING;

-- items：精确去重（同租户/工作区/kind/内容只留一行）
INSERT INTO memory_items (...) VALUES (...)
  ON CONFLICT (tenant_id, workspace, kind, content) WHERE kind <> 'episode' DO NOTHING;

UPDATE memory_jobs SET status = 'done' WHERE id = ?;

为什么 episode 不参与内容去重：两场摘要可能逐字相同，但它们是两个不同 run 的记录， 都该留、都能顺着各自的 source_run_id 回现场。内容去重只约束 fact / preference / decision。

重放闸（实测补记）：内容级去重只挡逐字相同的输出；生成模型即使 temperature=0 也会把 「dev 库是 PostgreSQL 5433 端口」改写成「端口 5433；5432 属于另一个实例」——重放同一 job 会多出一条同义 fact。因此在 processMemoryJob 起手加一道机械闸：本 run 的 memory_items 已有任何一行（items 与 job=done 同笔事务提交过）→ 直接翻 done、不再调模型，日志记 memory extract done <jobId>: replay skip。抽取调用本身固定 temperature=0（降低抖动， 不承诺确定性）；「重放假 job 不翻倍」由重放闸保证，不靠模型输出稳定。

一期不做 supersede / consolidate：写入层只增不改，同 topic 的矛盾由召回层兜底（同 topic 只取最新一条，§6.1）。

4.5 重试、幂等与观测

  • job 唯一键 = run_id（一个 run 一条任务，ON CONFLICT DO NOTHING）。
  • claim：UPDATE ... WHERE id = (SELECT ... WHERE 可捡 ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED) RETURNING ...。
  • 可捡 = status='pending' AND next_attempt_at <= now() 或 status='running' AND lease_until < now()（崩溃恢复）。
  • 失败：attempts+1，指数退避（1min / 5min / 30min），三次后 failed。
  • 幂等：episode 按 source_run_id 唯一、items 按内容唯一；外加 §4.4 的重放闸（本 run 已有记忆行 = 上次 attempt 已完整提交，重放直接翻 done 不调模型）——重放同一 job 不会翻倍。
  • 日志三行（验收观测面）： 
    memory extract claim <jobId> run=<runId> attempt=N
memory extract done <jobId>: episode=1 items=N dup=M tok_in=X tok_out=Y
memory extract fail <jobId> attempt=N: <err>

接线点：抽取循环是 cmd/yktako/main.go 里一条与 server 同生命周期的 goroutine （go extractor.Run(ctx)），每 2s 轮询一次；只依赖 *runengine.Store 和 TAKO_MEMORY_MODEL 解析出的 chat model，不碰 run 的执行路径。进程重启后 pending / lease 过期的 job 会被任何副本重新捡起。

为什么用 PG 表 + SKIP LOCKED 而不是 asynq：当前代码零 asynq（go.mod 无依赖）；任务必须与 runlog 同事务登记（outbox），PG 表是最直接的载体；多副本下 SKIP LOCKED 天然不重复。

5. 线二：对话原文索引

5.1 passage 的形状（一个 run 一块，不切块）

[会话 s_01J... · 场 r_01K...]
用户：<本轮 user 原文>
助手：<root 终稿>
子代理(researcher)：<终稿，截 1000 rune>   ← 有委派才有这行

总上限 4000 rune，超出从尾部截（用户问题在前优先保），截断行记 truncated=true。

为什么一个 run 一块（WeKnora 同款：knowledge_process.go:165-180）：passage 自带 「一问一答」边界，切块会把问答拆散，召回回来的可能只有问题没有结论；切块引入的 overlap、 跨块去重、半问答对齐，全是没有对应收益的历史包袱。

为什么上限 4000：一场普通 run 在一两千 rune；上限住「子代理连读十份网页」的极端 run， 防单块膨胀（索引噪声失控）。

5.2 触发：未索引反查（每 2s）

常驻 goroutine 每 2s 扫一次：runs 表 status='complete' 且 run_id 不在 dialogue_chunks 里的，就是待索引项。这是反查，不是 watermark 游标——反查能顺手自愈 「行被误删/上次写到一半崩了」；代价是每次扫全量 complete 行，历史涨到十万级再换成 「finished_at 游标 + 定期全量对账」，现在不做。每轮取一批（dialogueIndexBatch = 20）： 反查会把「功能上线前所有历史 run」一次全判为待索引，不设批量上限会在启动后第一分钟把 全库 runlog 读一遍；分批发酵只是慢几分钟，不丢项。不建 outbox、不建 jobs 表、不与 EndRun 同事务——理由 §4.1 已给：本地毫秒级写入不需要补偿线索，幂等重扫自愈。

5.3 幂等与重建

  • dialogue_chunks 以 run_id 为主键。写入姿势 = 单语句 upsert： 
    INSERT INTO dialogue_chunks (...) VALUES (...)
ON CONFLICT (run_id) DO UPDATE SET
  passage = EXCLUDED.passage, runes = EXCLUDED.runes,
  truncated = EXCLUDED.truncated, indexed_at = EXCLUDED.indexed_at;
    为什么不照抄 WeKnora 的「先删后插」：多副本下两个扫描者会同时扫到同一个未索引 run； A 的 DELETE 删不到 B 未提交的行，随后两条 INSERT 撞主键，B 报错（下一轮自愈，但留错误 日志、浪费一轮）。upsert 是单语句、无竞争、天然幂等。前提：pg_search 索引对 UPDATE 自动维护——B1 第三项探针验（实证只验过 INSERT）；若 UPDATE 不维护索引，退回 「pg_advisory_xact_lock(hashtext(run_id)) 串行化 + 先删后插」（与 notes 的 workspace 锁同款，闸在库里）。
  • 重建 = 清空 dialogue_chunks + 等下一轮反查（或引擎旗标 -rebuild-dialogue，启动时 清空、索引循环随即扫描）。输入只有 runlog_entries——doc/16 §4 护栏 1「副本可重建」的 全文检索版表述。TAKO_RAG=off 时旗标拒绝启动（索引循环没起，清空后没人重建）。

5.4 存储：pg_search 全文索引（ParadeDB 扩展）

形态：dialogue_chunks 是普通 PG 表（存原文与元数据），上面建一个 pg_search 索引：

CREATE INDEX dialogue_chunks_search_idx ON dialogue_chunks
USING paradedb (run_id, passage)
WITH (text_fields = '{"passage": {"tokenizer": {"type": "chinese_lindera"}}}');

（逐字照实证台账 tmp/pgsearch-verify/run-tests.sql 的语法：v0.26.2 的索引 AM 名是 paradedb 而非 bm25；key_field 已废弃，但键列仍必须写在索引列里、且在第一位 （实证是 (id, content)）；tokenizer 要写成对象 {"type": "chinese_lindera"}，不是裸字符串。 B1 已实证 TEXT 键列可用：run_id TEXT 直接作键列建索引、@@@ 与 score() 都工作， 不需要 BIGSERIAL 代理键。CREATE EXTENSION pg_search 必须带 CASCADE——它依赖 vector，裸建报 required extension "vector" is not installed，CASCADE 一并装上 pg_search 0.26.2 + vector 0.8.6。）

索引维护的实测范围（B1 三项探针已跑）：INSERT 后查询立即可见；UPDATE 后命中新文本、 不命中旧文本（§5.3 的 upsert 成立，不退回 advisory lock + 先删后插）；DELETE 后索引跟随 （B2 删行自愈、B4 清空重建都依赖它，实测清空 114 行后重建回 114 行）。

一个查询形态的实测坑：把 runs JOIN 进来取 finished_at 会让 pg_search 报 WARNING: JoinScan not used（查询仍能跑，但走了非预期计划）；B3 改成相关子查询取日期 （(SELECT r.finished_at FROM runs r WHERE r.id = c.run_id)）消除告警。

分词与排名全在扩展内：lindera 词典中文分词（建索引与查询自动用同一分词器，我们侧 零切词代码）；BM25 相关分由扩展计算（实测判官：稀有词 5433 文档 1.72 分 > 常见词×3 噪音文档 1.57 分）。实测延迟 0.3–5ms，GitHub issue #4840 的词典重载延迟在 本规模/版本不复现。

schema（PG 一张表 + 一个 pg_search 索引；索引用手写迁移）：

CREATE TABLE dialogue_chunks (

  session_id  TEXT NOT NULL,
  tenant_id   TEXT NOT NULL DEFAULT 'default',
  workspace   TEXT NOT NULL,
  passage     TEXT NOT NULL,
  runes       INTEGER NOT NULL,

  indexed_at  TIMESTAMPTZ NOT NULL

CREATE INDEX dialogue_chunks_scope ON dialogue_chunks (tenant_id, workspace);
-- + 上面的 pg_search 索引

  • 观测项（不挡施工，留意）：实测中两个不含查询词的文档拿到了 0.1 分上下的微小分值 （正常应为 0），top-3 判定不受影响；上线后若噪声文档挤进 top-3 再查。

6. 召回与注入（两线共用出口）

6.1 线一召回：词法

时机（2026-10-22 改）：prepareInput 之内——mh 全序切两半（历史 / 本轮输入）→ 召回 → 块拼进本轮输入 → 写回 mh 的 seq=1 → 折叠 → agent.Run。与预览端点同一个 Store.Recall（开关也同一份）。

块参与折叠计数（进 base → countInput 数得到它）、落 run_model_messages 的本轮 user 行（seq=1）——mh 的定位是「下一轮 run 的模型应该看到什么」（doc/30 §6）， 落进去之后下一轮读 mh 拿到的就是模型这一枪真看到的那份，折叠重建时文本也从 mh 取。

只注入新 run：doc/30 的续跑（resume）路径不召回——续跑不是「新一场开头」； 但续跑仍走同一条切分（本轮输入那行独立出来），装配形状两条路径一致。

词从哪来（这是词法召回最容易踩空的一步）：用户输入是自然中文，strings.Fields 只按 空格切——「dev 数据库端口是多少？」变成 dev + 整段中文两个词，那段中文几乎不可能与记忆 原文逐字相同，几乎必然 0 命中。所以召回自己做一个机械的两段切词（不引入分词库，线一 专用）：

  1. 英文 / 数字：连续的 [a-zA-Z0-9_.-]，长度 ≥2，转小写。
  2. 中文：连续汉字串切 2-gram（「数据库端口」→ 数据 / 据库 / 库端 / 端口）；单字串保留单字。
  3. 去重，最多取 12 个检索词（按在原文中出现的先后，截断丢掉末尾）。

查询（OR 宽召回 + 命中数排序）：

SELECT id, kind, topic, content, created_at,
       (CASE WHEN content ILIKE ? THEN 1 ELSE 0 END + ... ) AS hits
FROM memory_items
WHERE tenant_id = ? AND workspace = ?
  AND kind IN ('fact', 'preference', 'decision')
  AND (content ILIKE ? OR ...)
ORDER BY hits DESC,
         CASE kind WHEN 'preference' THEN 0 WHEN 'fact' THEN 1 ELSE 2 END,
         created_at DESC
LIMIT 20
  • 为什么 OR 不是 AND：记忆召回是宽召回，「dev 库是 5433」用「dev 数据库端口」问时 必须能命中——AND 会因「数据库」不在原文里而漏掉。
  • 为什么命中数排前：命中词多的更相关。
  • 为什么 kind 有优先级：preference 决定「怎么干活」，比孤立 fact 更该被看到。
  • ILIKE 要转义 % 与 _：词表允许 _（工具名如 read_media_file），不转义会变成通配符。
  • episode 不参与召回：它是叙事不是跨会话事实；召回它会每场带回历史任务细节，噪声大。 它的消费方是时间线/管理面（GET /api/memory/items?kind=episode）。
  • 规模：%term% 是全表扫。每场 run 最多写 5 条、只增不删，万级以内毫秒可回； 到十万级再给 content 加 pg_trgm/GIN——现在不加，是因为先要量、不是先要索引。

Go 侧后处理：20 条候选 → 同 topic 只留最新一条 → 取前 5 条 → 按 600 rune 上限截断 （整条放不下就停，不切半条）。

6.2 线二召回：pg_search @@@

  • 查询：本轮 user 原文交给 paradedb.match('passage', $1)——@@@ 的左边是索引键列 （run_id，不是 passage），右边是查询构造器；v0.26.2 实证的形态是 WHERE id @@@ paradedb.match('content', X) ORDER BY paradedb.score(id) DESC （见 run-tests.sql 的 Q1–Q8/T3）。所以这里写： 
    SELECT run_id, passage, paradedb.score(run_id) AS score
FROM dialogue_chunks
WHERE run_id @@@ paradedb.match('passage', $1)
  AND tenant_id = $2 AND workspace = $3
ORDER BY score DESC
LIMIT 3;
    不要写成 WHERE passage @@@ '<query>'——那不是 pg_search v0.26 的语法，B3 会直接报错。 查询端分词由扩展按索引声明的 tokenizer 自动完成，我们侧零切词。 用 paradedb.match 而不是 paradedb.parse：前者是词面匹配（安全、不做查询语法解析）， 用户输入里的引号 / : / * 不会被当成查询运算符；B3 仍要补一发特殊字符探针确认。
  • match 是「token 析取」（v0.26.2 实测）：查询切成 token 后，任一 token 在 passage 中出现即命中。后果两面：①注入路径用的是整句原文，虚词 token（「要」「干嘛」这类）会给 无关块带出弱命中，相关性由 BM25 排序 + LIMIT 3 上限压住；②「无命中」只在所有 token 都不在索引里时成立——验证「周末」找不到「周六」的探针必须只发「周末」这个词，写成 「周末要干嘛」会靠「要/干嘛」命中一堆块（实测 3 条），那是虚词噪声，不是语义召回， 不能拿它当反例。
  • 取数：按相关分排序 LIMIT 3 → Go 侧每条截 300 rune（整条放不下就停）。
  • 租户/工作区过滤：查询带 tenant_id/workspace 等值条件（一期值恒 default， doc/28 落地后换构造点，与 §7.1 同一本账）。

6.3 已接受的限制（契约）

换说法问题（「周末」找「周六」）在词面检索路上必然 0 命中——这是裁决（2026-10-18「太 麻烦」：语义召回需要向量库 + embedding 服务商 + 外部调用面）的固化，不是漏项；分词器 改变不了它（「周末」「周六」被切成不同词）。验收 §11 B 组第三问把它写成期望行为。

7. 数据模型与 API 契约

7.1 PG 表（AutoMigrate 由六张扩到九张；dialogue_chunks 的 pg_search 索引用手写迁移）

（六张现役 = session / runs / run_model_messages / runlog_entries / notes / run_journal—— 最后一张是 doc/30 崩溃续跑加入的，本文初稿写「五张」时还没有它。）

memoryScope{tenant, workspace} 是所有 PG 表读写共用的过滤键：tenant 一期恒 "default"， workspace 与 notes / 文件工具同一个根；构造点只此一处，doc/28 落地后在那里换值。

// MemoryItem = `memory_items`：一条跨会话记忆。只增不改（一期无 update/delete）。
type MemoryItem struct {
    ID              string    `gorm:"primaryKey"`                                   // mem_<ULID>
    TenantID        string    `gorm:"not null;uniqueIndex:memory_items_dedup,priority:1,where:kind <> 'episode';index:memory_items_recall,priority:1;index:memory_items_topic,priority:1"` // 一期恒 default（doc/28 落地后接 ctx）
    Workspace       string    `gorm:"not null;uniqueIndex:memory_items_dedup,priority:2;index:memory_items_recall,priority:2;index:memory_items_topic,priority:2"`
    Kind            string    `gorm:"not null;uniqueIndex:memory_items_dedup,priority:3;index:memory_items_recall,priority:3"` // fact | preference | decision | episode
    Content         string    `gorm:"not null;uniqueIndex:memory_items_dedup,priority:4"`
    Topic           string    `gorm:"not null;index:memory_items_topic,priority:3"`  // 小写 kebab-case；episode 用 run:<runId>
    SourceSessionID SessionID `gorm:"not null"`
    SourceRunID     RunID     `gorm:"not null;uniqueIndex:memory_items_episode_once,where:kind = 'episode'"`
    SourceSeq       int64     `gorm:"not null"`                                     // 回原话现场：runlog seq
    CreatedAt       time.Time `gorm:"not null"`
}

// MemoryJob = `memory_jobs`：run 终态登记的抽取任务（outbox，线一专用）。
type MemoryJob struct {
    ID            string     `gorm:"primaryKey"`                 // mj_<ULID>
    RunID         RunID      `gorm:"not null;uniqueIndex"`       // 一个 run 一条
    SessionID     SessionID  `gorm:"not null"`
    TenantID      string     `gorm:"not null"`                   // 一期恒 default
    Workspace     string     `gorm:"not null"`
    Status        string     `gorm:"not null;index:memory_jobs_claim,priority:1"` // pending | running | done | failed
    Attempts      int        `gorm:"not null"`
    LeaseUntil    *time.Time
    NextAttemptAt time.Time  `gorm:"not null;index:memory_jobs_claim,priority:2"`
    LastError     string
    CreatedAt     time.Time  `gorm:"not null"`
    UpdatedAt     time.Time  `gorm:"not null"`
}

// DialogueChunk = `dialogue_chunks`：一场 run 的原文块（线二，可重建副本）。
// passage 列上有 pg_search 索引（§5.4），GORM 不管理，迁移手写。
type DialogueChunk struct {
    RunID      RunID     `gorm:"primaryKey"`
    SessionID  SessionID `gorm:"not null;index"`
    TenantID   string    `gorm:"not null;index:dialogue_chunks_scope,priority:1"` // 一期恒 default
    Workspace  string    `gorm:"not null;index:dialogue_chunks_scope,priority:2"`
    Passage    string    `gorm:"not null"`
    Runes      int       `gorm:"not null"`
    Truncated  bool      `gorm:"not null"`
    IndexedAt  time.Time `gorm:"not null"`
}

为什么 source_session_id / source_run_id / source_seq 三列全存（线一）：记忆的 去向是模型上下文，来源必须可对质——用户问「你凭什么记得这个」，顺着 runlog 的 seq 能 打开原话现场，和 notes 的 source_run_id + source_seq 同一套追溯口径。

为什么仍不建 status / superseded_by 列：一期没有写方（不做 supersede），空列只 增加语义负担；二期 consolidate 再 ALTER TABLE。

9. 顺序：轨迹与记忆（回答「先轨迹、后记忆」）

先核一件事：轨迹要的原料已经在落库。 runlog_entries 从 A/D1 起就是不可变事件日志： session_id / seq / run_id / role / agent / model / message_id / text / payload / created_at （pgstore.go 的 RunlogEntry），GET /api/sessions/:id/log 已按 seq 升序输出。也就是说：

  • 如果「轨迹」= 时间线视图（把一次 run 的事件按时间排出来给人看），它不需要新建采集， 直接读现有的 runlog；两线吃的也是同一张表。两者不构成先后依赖。
  • 如果「轨迹」= 更丰富的事件模型（每步耗时、模型中间思考、调用成本、训练导出字段），那它 会改 runlog 的写入形状——真正的依赖是「两线的输入构造跟着字段变」，而不是「两线要等 整条轨迹做完」。

所以推荐：记忆与对话召回直接开工，直接吃现有 runlog。 开工前只留一个检查点：确认轨迹 方案不会在本期施工期间改 runlog_entries 的列或 role 枚举；若会，先把那个增量定下来， 两线的输入构造再过一遍——这是几小时的活，不是前置工程。

检查点现状（2026-10-18 核过）：doc/30 崩溃续跑已落地，但它没有改 runlog_entries 的列与 role 枚举——新增的是独立的 run_journal 表和 runs.lease_epoch；runlog 仍是 RunlogEntry 原样。检查点未触发，本期施工期间继续按此口径盯。

反向的供料关系：线一抽出的 episode（每 run 一句话摘要）正好是时间线要的人读摘要。 两线先做，轨迹的时间线可以直接 GET /api/memory/items?kind=episode 拿到每场的标题，不必 自己再设计一套摘要。
