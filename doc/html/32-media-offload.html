32 · media_offload（对话只存 path）

性质：已落地（2026-10-21 收口）。A1–A7 随 dcf3e6b 入库（2026-10-18）；A3-1 至 A3-5 与 A8-1/A8-2 随 6e4de68 入库（2026-10-20）。 本篇覆盖两个半边：半边一（存储纪律，入口图与工具回执只落占位）= A1–A2； 半边二（模型可见，本轮图在发送份里还原成真图 part）= A3-1 至 A3-5，2026-10-20 已落地。 施工台账：tmp/32-media-offload/（A1–A7 的 planning + todos + 验收实录）与 tmp/32-media-offload/a8-pdf/（A8）； A3 五拍当时没另起台账，施工与活体验收记录只在本篇 §4。 验收结论：A1–A7 与 A8 的逐拍实录见上述台账（2026-10-18 引擎 8947/8916、2026-10-20 引擎 8909/8910）。 2026-10-21 活体抽验（引擎 127.0.0.1:8942、独立库、Redis db 8，本篇 7 项断言全过）：带图投消息拿到 sessionId； user 行是占位（path=workspaces/<wid>/.media/…，锚在工作区目录）；runlog 零 base64； GET /api/media?path=… 取到字节且与上传同长；跨租户取同一张图回 404；删默认工作区回 409 114005（doc/35 A8a）。 这一批明确不做的：扫描件 OCR（2026-10-20 已拍）、音视频内容（2026-10-20 已拍）、 CJK 兼容字形归一化、复杂版式不承诺、「文本只进当枪发送副本」这一另拍的半边。 扫描件 OCR、音视频内容不在本篇范围内。 本篇是 doc/16 能力表 #4b「media_offload」在 v6 的方案真源。旧线实现（doc/18，internal/mediaoffload） 已随 2026-10-03 仓体翻篇删除，doc/18 降级为旧线实现存档，不作施工面；它踩过的坑在本篇第 6 节吸收。 关联：doc/35（附件锚点已迁到 workspaces/<wid>/.media/）、doc/19v6-08 第 3 节 （read_media_file 声明面、多模态消费）、doc/19-v6（存储真源划分）。

核心裁定（用户 2026-10-18 拍）：对话里面只保存 path。字节从进系统那一刻起就只落盘； 对话的三份落库面里，媒体永远只是一行占位文本，占位里带 path。

结论先给一句：把「不背字节」从旧线的发送侧技巧升级成 v6 的存储纪律——盘上是唯一字节真源， 对话里抄的只有路径；需要模型看图的当枪发送份临时还原成 image part，落库面始终只有占位。

1. 先演一场失败

v6 今天的对话是纯文本的：用户发不了图（postRunsRequest 只有 Text，server.go:117）。 但模型自己能把大字节拉进对话——唯一的一条路是 read_media_file。按今天的代码逐步演：

  1. 用户说「看一下 assets/shot.png 帮我改配色」。模型调 read_media_file{"path":"assets/shot.png"}。
  2. 工具读盘，返回一行 data:image/png;base64,iVBORw0…——2MB 的截图 base64 后约 2.7MB， 全在这一行文本里（filetools.go:591）。
  3. 这行文本作为工具结果进 TurnEntry.Text，EndRun 把它落进三处： runlog_entries 的 tool_result 行 text 列、同一行的 payload JSON（{name, output}）、 run_model_messages 的 text 列（store.go:235-247、store.go:403-409）。
  4. 下一枪 prepareInput 从 model_history 重建输入，这 2.7MB 原样重发给模型。 模型按提示「再仔细看看」又调一次，对话里再多一整行。
  5. 十几轮之后，窗口和账单里可能背着几十 MB 的 base64——而模型在当前文本管道下 根本看不见图（19v6-08 第 3 节挂账：data URI 暂被当文本）。这些字节纯粹在烧窗口、烧钱。

病根一句话：字节已经在盘上了（workspace 里的 shot.png），对话却把它再抄一份进自己怀里， 从此每轮都背着。media_offload 要改的就是「抄」这一步：对话不抄字节，只抄路径。

2. 一条纪律，两个半边

纪律（用户拍）：媒体字节永远不进对话的落库面。三份落库面——runlog_entries、 run_model_messages、帧（runlive）——里与媒体有关的内容只有一行占位文本。

字节只允许活在两个地方：盘上的文件、当枪发给模型的请求体。

这条纪律与旧线 doc/18 的设计是反的，翻案理由要讲清：旧线是「正本不动、只改发给模型的那一份」—— 因为旧线正本在进程内存里，字节留着无所谓。v6 的正本落 PG 且目标多副本：字节进了行就是 行体永久膨胀（备份、复制、读侧每轮都背着），「发送时再换掉」是在错误的层补救。 把纪律移到存储面之后，发送面反而获得自由：还原与否变成按需决定，不再是救火。

两个半边，各自独立成拍：

  • 半边一（存储纪律）：入口图落盘换占位、read_media_file 回执换占位。 不依赖多模态，今天就能做、今天就有收益（第 1 节的失败当场断根）。
  • 半边二（模型可见）：本轮的图在发送份里还原成真图 part；历史轮只留元数据。 2026-10-20 已由 A3-1 至 A3-4 落地：user 图与当前 run 的 read_media_file 回执在发送份还原， 同一 run 的 user 图只附在第一次成功回复之前的那一枪，落库面不动。目录没标 vision 的模型 和 TAKO_MEDIA_SEND=off 的部署都不还原。图片 token 按 DeepSeek v41 计入窗口压力（A3-5），只算这一枪实际会发送的图。

3. 占位行真身

所有占位（入口图、工具回执）用同一条格式：

[media seq=2 name="photo.png" path=workspaces/ws_01…/.media/ab12cd34….png mime=image/png size=182340B sha=ab12cd34ef56…；要看就调 read_media_file 读这个路径]

PDF 入口占位用同一套字段，句尾换成「要看就调 read_pdf_text 读这个路径（可分页）」。图片和音视频仍指向 read_media_file。

  • path 相对租户根——就是 read_media_file 现有入参的形状（filetools.go 的 resolveReadMediaPath），同一根、同一牢笼，模型拿占位就能直接调，不需要新的放行规则。
  • 2026-10-20 起按 doc/35 的附件锚点：字节落在 <tenantRoot>/workspaces/<wid>/.media/<sha 前 16 位>.<扩展名>，占位 path 是 workspaces/<wid>/.media/<sha16>.<ext>。GET /api/media 和 read_media_file 共用 VisibleWorkspace，再在租户根下的 workspaces/<wid>/ 读；sessions/<sid>/... 直接读不到。旧 sessions/<sid>/.media/ 由启动清理，不做两套路径并存 （细节与验收见 doc/35）。
  • mime/size/sha 三个字段让模型不读文件也能判断值不值得重看（一张 30KB 的示意图 和一张 4MB 的大图，重看的代价不同）。
  • sha 是内容寻址：同一张图在对话里出现多少次，盘上只有一份、占位里的 path 也相同。
  • 工具回执用同一套字段，不带 seq/name。句尾是「已按路径读取。媒体字节不会写入对话记录，请勿重复调用」。 这句话告诉模型：字节不在落库的对话里。它不表示这一枪的发送份里没有图。

通信字段（2026-10-18 用户增补拍：name 与 seq）：

  • seq= 全会话累计序号（按上传先后 1、2、3……），恒在；name= 用户上传时的 原始文件名，可省，值以引号包裹（文件名含空格不破坏按空格分字段的读法）。 两者合起来是模型跟用户对话的坐标：用户说「第二张」模型对 seq=2，说「photo.png 的新版本」对同 name 不同 seq 的两行。盘名不受影响——同名两版是两个内容、两个 sha 名，区分靠 name="photo.png" + seq 这对字段，不靠改盘名。
  • 名字的分工要分清：name/seq 帮模型说图（引用有坐标），不帮模型看图 （看得见仍靠第 4 节多模态拍把字节拼进请求）。
  • seq 的多副本来源：占位行只由 user 行携带；postRuns 准入时数本会话 runlog user 行 里既有的 [media 占位个数、+1 起编。同会话同时只有一个 run 在写（409 忙闸）， 计数无并发竞争；闸在 PG 不在进程，多副本下照成立。
  • name 的 sanitize：去控制字符与换行（占位行必须保持单行，换行会破坏前端逐行解析）、 去引号（name 值以引号包裹，内嵌引号会截断解析）、截 120 字符；清完为空 → 整个 name= 字段省略，不写字面空值。
  • 回执变体不带 name/seq：工具回执发生在读盘时，无从知道会话序号；模型对回执与 入口占位靠 path/sha 对上（同一文件的这两个字段两边一致）。

4. 分步

A1 入口拍（契约）

POST /api/runs 请求体加图：images 数组（每项 {mime, dataBase64, name?}）。 服务端在一笔写里完成：校验（mime 白名单、大小上限）→ 内容寻址写入 workspaces/<wid>/.media/（<sha 前 16 位>.<扩展名>）→ user 行 Text = 正文 + 每图一行占位。

  • 为什么内容寻址：用户把同一张图连发两次，盘上一份、占位一致，不需要去重逻辑。
  • 为什么落工作区不另设缓存目录：字节进 workspaces/<wid>/.media/ 后，read_media_file 的现有牢笼（VisibleWorkspace + resolveInWorkspace）天然覆盖读回路径；旧线要另建 .media-cache 是因为旧线字节来源是消息内联、无处安放——v6 入口字节从第一刻起就在 工作区里。锚点迁移细节见 doc/35。
  • 准入（2026-10-18 翻案）：图不折算进 413 准入线——初版把 base64 原文喂给 cl100k 折进 AdmitText 预算，两个后来的事实把它打翻：① tiktoken-go 对 MB 级 base64 是分钟级 （300KB 实测 39s，3MB 截图≈分钟，而用户随手截图就 3MB）；② deepseek-flash 实测按张 平价 ~384 token，cl100k 数字节差三个数量级——就算跑得动也是拒错人（文本管道下 3MB 图 实际只发一行占位进模型窗口）。图的门槛退回硬上限（≤5MB/张、≤4 张、白名单，字节比较瞬时， 在 ingestImages 里、token 准入之前）；AdmitText 签名去 blobs（「不折算」编译层钉死）。 图片进窗口的 token 按 DeepSeek v41 另计，只加实际会发送的图（A3-5 已落地）。AdmitText 仍只数正文。usage 仍是已经发出去的请求的锚点，估算只补锚点之后新增的图。不回这套字节折算。翻案活体：3MB 图 POST 43ms 落占位行（翻案前 300KB 就要 39s）。
  • 验收（curl 手打）：POST 带 1×1 PNG 的 base64 → 202 → GET /api/sessions/{id}/log 的 user 行 text 里出现占位行（含 path/mime/size/sha 四字段、无 base64）→ workspaces/<wid>/.media/ 下出现该 sha 文件 → 再发一次同图，盘上仍只有一份。

A2 工具回执拍

read_media_file 的返回从 data URI 单行改成占位行（第 3 节同格式）。

  • 现在就改、不等 translator 的理由：当前文本管道下模型本来就把 data URI 当无意义的 长文本看，换成占位是零损失；留着 data URI 则第 1 节的失败继续发生——模型每调一次， 对话里就永久多一行几 MB 的 base64。
  • 注意 v6 与旧线的分工差异：旧线的落盘动作发生在「消息内联字节 → 缓存」这一步； v6 里 read_media_file 读的文件本来就在工作区，这一拍没有落盘动作，只有回执换字。 落盘只发生在 A1（用户从浏览器带来的字节）。
  • A3-2 起回执句尾是「媒体字节不会写入对话记录，请勿重复调用」（mediaReceiptPlaceholder）。 这句是给模型的状态说明：字节不在对话里，但下一枪发送份会把图附在 tool 消息上； 落库的 tool_result 行、payload 与帧仍是这句占位。
  • 验收（curl）：让模型读一张 100KB 的图 → GET /log 的 tool_result 行 text 与 payload output 都是占位行，不含 base64 字样 → 同场对话下一枪的 usage 帧 promptTokens 不出现 MB 级跳变。

A3 多模态拍（2026-10-20 分五拍；A3-1 至 A3-5 已落地）

发送侧包壳在新文件 internal/runengine/media_send.go，挂在 overflow guard 里面 （模型调用点最内层）；它只改这一次模型调用的输入副本，存储面（runlog_entries、 run_model_messages、帧）零改动。guard 的折叠、计数与救援看到的仍是占位文本。

发送份形状（A3-1/A3-2）：

  • user/tool 消息变成 Content="" + UserInputMultiContent（text part + image part）。 text 里保留 seq/name/path/mime/size/sha，句尾是 attached marker； Content 必须清空，否则 openai 适配器因两字段同时非空报 ErrContentFieldsMisused。
  • attached marker 明写「像素已随本条消息（或本条工具结果）直接发送，不要调用 read_media_file 或 bash 读取该文件」。2026-10-20 活体证明：只说「已附上」时，模型仍会 照占位句去读文件，拿到「字节不在对话里」的回执后反而否认自己刚看到的像素。
  • 历史 user 占位（最后一条 user 之前）换成说明行：保留 seq/name/path/mime/size/sha。 图片和音视频写明本轮不再附像素，问当时的分析直接引用随后 assistant 的回复，明确要求重看时再调 read_media_file。 PDF 另写一句：该 PDF 只在当时那条消息里出现，需要重读时调 read_pdf_text，不要为核对重复抽取。历史 tool 回执不还原。
  • 可还原格式只 image/png、image/jpeg、image/gif、image/webp；入口白名单里的 BMP/SVG/PDF/音视频继续留占位。读盘复用 resolveReadMediaPath（与 read_media_file 同一把 VisibleWorkspace + 路径闸），再校验普通文件、≤5MB、size 与 sha 前缀一致； 任一失败保留原占位并记 media skip ... reason=...，不阻断 run。
  • 工具回执只在下一枪的发送份里还原；tool_result 的落库行、payload 与帧逐字是占位。 A8-1 起，这条 tool 消息还要过双闸：最后一条 user 之后的 assistant 消息先收成 ToolCallID 到工具名的映射，只有映射到 read_media_file、且该行是「已按路径读取」回执时才还原。映射缺失不还原，也不读盘。入口 user 占位不查这句回执。细节见 A8。 deepseek-flash 接受 tool 角色 content 数组里的 image_url，已在本机活体验证。
  • 工具图去重靠 foldBox 的 mediaSentTools（已确认发过）与 mediaPendingTools （本枪已附、待确认）：每次模型调用把可还原回执记 pending；root 成功回复后在 worker drain 分支 commitMediaSend()，失败/取消/零帧不 commit，下一枪重试同一 ToolCallID。 没有 foldBox 的旁路调用不去重。
  • user 图的第一枪闸用同一容器的 mediaSentUser / mediaPendingUser。restoreUserMedia 看到已经确认发过，就不再读盘，占位原样留在输入里。commitMediaSend() 把本枪附过的 user 图和工具图一起收成已发送；这一枪没有附上 user 图时，不把 user 标志置上，读盘失败 的下一枪还能再试。Stream 要等 worker 把流排干才知道成功，提交点只在 drain 分支； Generate 一次调用就拿到完整回复，成功返回后由 mediaSendModel 自己提交。 续跑或接管会新建 foldBox，标志回到 false，保守再还原一次。
  • 两把闸都开才还原（A3-4）。用户把 SVG，或一张图发给目录里没标 vision 的模型时， 包壳如果照旧读盘、把像素塞进请求，provider 会拒收这一枪，整场 run 变成 error。 TAKO_MEDIA_SEND 回答这次部署发不发图：未设置是开，字面 off 才关。关的时候 NewWorker 不把 mediaRestoreHandler 挂进 root 的模型链，模型看到的输入与占位逐字节相同， 日志里没有 media send。目录字段 vision 回答这个模型收不收图，缺省 false。 pack 按 model id 从厂商条目里取，目录没有这个 id 就是 false。assembleRun 把它写进 RunProfile.Vision。每次调用前包壳读 profileFrom(ctx).Vision；ctx 里没有 profile （启动自检、旁路）时用装配默认值 false，不读盘。false 且输入里真有占位时，打一行 media skip <session>/<run>: reason=model_no_vision，输入原样返回。纯文本不打这行。 多张占位也只打这一行，不按张计。
  • 官方 deepseek 条目的模型 id 从 deepseek-v4-flash 改成 deepseek-flash （2026-10-20 GET https://api.deepseek.com/models 只返回 deepseek-flash 和 deepseek-v4-pro）。只给 deepseek-flash 标 "vision": true。deepseek-v4-pro 没有收图实测，不标。别的厂商条目里的 deepseek-v4-flash 是那些厂商自己的模型 id，不动。
  • 还原白名单是 png、jpeg、gif、webp。bmp、svg、pdf、音频、视频走 media skip reason=mime_not_restorable，不读盘。缺文件、超过 5MB、sha 不符、 路径越出作业根、符号链接指向根外、不是普通文件，都保留原占位并各打一行 media skip， run 继续。media send 只在这枪输入里出现过占位时打。行尾 img=<n>tok 是这一枪实际还原成功的图，按 DeepSeek v41 加总。纯文本不打这行。800×800 是 422。 像素少于 544×544 时计算器先放大再投影，100×100 是 184。
  • 包壳只挂在 root worker 上。子代理自己的 handler 链不含它，子代理里的模型调用不还原。 子代理折叠如果和 root 共用同一套长度估算，也会给占位计价；那只是多出来的折叠压力， 像素仍然不进子代理的请求。

A8-1 补文本层这一环。模型按占位 path 调 read_pdf_text，工具按页抽出文字，作为普通工具结果写入 runlog 和 run_model_messages。扫描件返回正常说明，run 继续。音视频不处理，也不做 OCR。

链路：用户 POST 带 PDF → postRuns 落盘并写占位 → 模型看到句尾，调用 read_pdf_text → resolveReadMediaPath 把 path 收进工作区 → pdftext.go 逐页抽文本 → 工具结果落库 → 下一枪模型读到页文本并回答。图片回执链在旁边：只有模型自己调了 read_media_file，下一枪才把图附上。引擎不因为历史里还有一张图就重发。

工具契约。 read_pdf_text 声明 read，父池排在 read_media_file 后面。path 必填，与 read_media_file 共用 resolveReadMediaPath。解析成功后还要是普通文件、扩展名 .pdf、不超过 5MB，否则返回工具错误。page_from 可省，默认 1。page_to 可省，默认从起点起共 3 页，并夹到总页数。单次最多 10 页；请求超过 10 页而且这个窗口后面还有没读的页时，页眉写「单次最多 10 页，已夹取」。

成功时先给一行 [pdf path=… pages=N；第 a-b 页；文本层抽取]，再按页写 --- page N --- 和该页文本。空页写「本页无文本层」。单页解析失败写「本页无法抽取」，其他页继续。单次正文上限 16KB，超过时在 rune 边界截断，末尾写「（本页文本超过单次上限，已截断；请缩小页范围）」。page_from 超过总页数时返回 [pdf … pages=N；page_from 超出范围]，这是正常结果。请求范围内每一页都没有文字时返回 [pdf … pages=N；未检测到文本层（可能是扫描件），无法抽取文本；可让用户上传页面截图]，也是正常结果。加密、损坏、上下文已取消返回 Go error，wrapToolErrors 收成「错误：…」，run 继续。

抽字在 pdftext.go，库是 github.com/ledongthuc/pdf（pin v0.0.0-20260907135840-6c8c28e0e8a0，BSD-3，纯 Go）。字形按 Y 分行、按 X 从左到右排。相邻字形的空隙超过左侧字号的 0.2 倍，并且两侧都是 ASCII 字母或数字时，才补一个空格。中文两侧不补。不承诺版式还原，也不做 CJK 兼容字形归一，不另存派生文本。成功返回后引擎打一行 pdf read <sid>/<run>: pages=a-b chars=…，chars 是写进正文的页文本 rune 数。

7. 所以这解决了什么

第 1 节那场失败里，用户损失的是窗口和账单：模型每看一眼图，对话就永久多背 2.7MB， 十轮下来光图就占掉半个窗口，而模型全程没真正看见过图。本方案把它换成三件确定性的事： 字节只存一份（工作区、内容寻址）；对话只抄路径（三份落库面零字节， 历史和备份不再膨胀）；看图变成明确的当枪发送副本——A3-1/A3-2 已让当前 user 图与 read_media_file 回执在下一枪带上 image part，模型真的看得见，而落库面仍只有占位。 多副本目标栈下，这条纪律同时把「PG 行体膨胀」和「每轮重发大字节」两个账一起结了。 A3-3 把同一张 user 图收成「本 run 成功回复之后不再重复发送」；模型要重看，走工具回执那一条。 A3-5 把这一枪还会发出去的图片按 DeepSeek v41 加进窗口压力：800×800 是 422，像素不足 544×544 的 100×100 先放大再投影，是 184。 发送前准备看见超限就折叠。活体用 -compact-window 940（limit 752），加图那一枪估算 814，其中 422 来自这张图，剩下 392 低于触发线。 更早的 user 图和已经发出去的图不加。AdmitText 仍只数正文。厂商 usage 仍是已经完成的请求的锚点，估算只补锚点之后还没发出去的图。 A8-1 让 PDF 的文本层按页进入工具结果，user 行仍只有占位；图片要再次进入请求，仍得模型自己调 read_media_file。
