0. 定位与边界

tako 是什么：从 pi 式 agent 循环长出来的 AI 工作伙伴，单入口产品（cmd/yktako）。核心是"一个能自主干活、带任务看板、带工具安全、能长时间跑任务的 agent"。

tako 不是什么：不是知识库 / RAG 产品。RAG、记忆这些能力会被借鉴进来，但只作为支撑 agent 干活的横切能力，绝不反客为主把 tako 变成"以文档检索为中心"的系统。这条边界是本文所有取舍的总闸（见 §4 护栏）。

tako 也不是协同编辑产品（2026-10-22 形态收窄，doc/42）：一个员工 = 一个项目，项目里的文件由他的多场 session 共享；团队共享账号、额度与审计，不共享文件。 不做「共享文件的多人在线同时修改」——那是协同编辑（CRDT/OT、在线状态、冲突合并、版本历史），是另一个量级的产品，不在本项目范围。

技术栈：Go + Eino（CloudWeGo）。主线在 yk-tako-eino/。

0.1 现状快照（2026-11-16）

先看这一节再往下读：tako 今天是什么、不是什么、还欠什么。逐项状态与代码落点在 §2 表，专项设计在 §6 索引。

是什么：一个多租户的 agent 运行时（Go + Gin + Eino + PostgreSQL + Redis(asynq) + Redpanda（记忆 pipeline 模式的派送）+ Vue 前端）。用户发一句话，引擎起一个 run，模型可以在里面调 bash、读写文件、搜历史、搜网络、委派子代理；帧流式回给页面；崩了能续跑；隔天的对话能召回。

不是什么：不是知识库／RAG 产品（§4 护栏）。记忆和召回只作支撑 agent 干活的横切能力。

4. 借鉴 WeKnora 的护栏（对话 → RAG / 记忆）

用户明确：想把 WeKnora 偏"通用 agent"的能力借鉴过来（例如把对话内容存进 RAG 供后续召回），但不想让 tako 变成 WeKnora 那种以 RAG 为定位的项目。护栏如下：

  1. 正本永远是结构化存储（event_log / messages 表），向量库只是可重建的派生副本——用于语义模糊召回，不用于精确回放/审计/恢复。（依据：WeKnora 里 embedding 模型一旦索引不可换、需重建，删会话时两侧同步清理）
  2. 双写是手段不是目的：结构化表管"精确、按序、可恢复"，向量库管"语义召回"，两种查询模式互不替代，所以才双写（承 §Q：为什么双写）。tako 引入 RAG 时沿用这个分工，但只在"agent 需要回忆历史"这一场景服务 agent，不做面向用户的知识库检索产品。
  3. 召回结果进 agent 上下文，不进 UI 主流程：RAG 是 agent 的一个 tool / 中间件（"记忆召回"），产出喂给模型，而不是把 tako 的界面改成"搜索框 + 文档列表"。
  4. 可延后、可关：RAG / 记忆属于 #6、#10，排在子代理之后。没落地前 tako 已是完整可用的 agent；落地后也应能通过配置关闭，退回纯结构化存储。
