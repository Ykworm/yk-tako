0. 背景与动机

0.1 起因

2026-10-22 复核运行时机制时，把「共享项目」这件事从机制层一路追到了产品层，追出来的不是某个 bug，而是产品形态没定：

  • 代码里有一道「项目闸」：同一项目同时只允许一场 run 在跑（pgstore.go:512-515 的部分唯一索引 one_live_run_per_workspace），撞了就回 409「项目正在另一场会话里运行」（server.go:418）。
  • 当年定这道闸的理由写得很清楚（tmp/35-项目目录/planning.md 规则 8）：共享目录让两场 run 第一次写同一块可变状态，失败是无声的——A 的 agent 正在重写 output/report.json，B 的 agent 同时读它，读到写了一半的字节；更糟的是 bash：B 的 agent 起手 rm -rf output/，A 十分钟的产物消失，两道 run 都报「成功」，没有一方收到错误。
  • 同一份台账里也写了正解：「哪天真要同时改，正确解是乐观并发（write_file 写前校验读时版本、变了让模型重读重做），不是放宽闸——留为远期缝，v1 不做」。

也就是说：闸不是最终解，是在"改不动写协议"的前提下选的替代方案。 而「共享项目」这个产品能力本身，从来没有被当成一个产品决定拍过——它是一路从「多租户隔离」长出来的副产品。

0.2 为什么现在要收窄：三个理由，只有一条致命

理由 成立吗 说明
共享文件的多人在线同时修改 成立，且致命 这是另一个产品：协同编辑要 CRDT/OT、在线状态、冲突合并、版本历史、撤销重做。tako 现在的形态是「agent 写文件 + 帧流回页面」，没有这个地基。
权限是问题 可解，不致命 可见性模型已经在（workspaces.visibility 两值 + 三处判定），真要做不难。
共享目录的存储是问题 可解，不致命 配额与计量都已有（租户级整树统计），要做只是加粒度。

准确的表述（比"难做"硬得多，也好讲得多）：

「共享文件」真正要做的是协同编辑。tako 不做协同编辑 → 于是共享项目这条线整条不立。

这条护栏与 doc/16 §4「不做 RAG／知识库产品」同款：它是一条边界，不是一个待补的功能。

0.3 砍掉之后，tako 是什么

tako 是多租户的 AI 工作台：一个员工 = 一个项目，项目里有多场对话。 团队共享的是账号、额度、审计；不共享文件。不做协同编辑（共享文件的多人同时修改）。

不是什么（新增一条，与 §4 RAG 护栏并列）：

不做协同编辑 / 共享文件的多人同时修改。 项目是个人的：别人看不见你的项目、读不到你的文件、进不去你的 run。

2. 资源模型（本文的主轴）

2.1 三层三个单位

层 单位 文件归属 用量计量 生命周期 闸
租户 租户 全树 额度总上限 + 日 token 租户删除 租户并发闸（待修，见 §4.3）

2.2 产出落点要跟着改（这是本次改动里最实的一处）

现状（今天）：产出和会话档案混在同一个会话目录里——sessions/<sid>/ 下既有 .tako/、.media/，也有 agent 写的 report.md。挂了项目的会话，产出落项目目录；没挂的，落会话目录。

改后：拆成两层，各归各的。

tenants/<tid>/
├── workspaces/<wid>/          ← 项目：产出落这里（报告、代码、中间件）
│   └── .media/                ← 附件（内容寻址 sha16，并发写是 no-op）
└── sessions/<sid>/            ← 会话：只放会话自己的档案
    ├── .tako/subagents/*.jsonl  ← 子代理 wire
    └── .media/                 ← 旧媒体兜底

这么改顺带解掉一个真缺口：今天删会话只清 .tako 与 .media，产出文件原地留下（product_api.go:269-282 的注释写明「产出留在会话目录里」），于是软删会话的产出成了没人认领的孤儿，还继续吃租户配额（配额按 tenants/<tid> 整棵树算，worker.go:479）。产出挪到项目层之后，删会话不再产生孤儿——垃圾只有一种（会话档案），而垃圾的清理路径已经存在。

项目要成为默认落点（用户 2026-10-22 拍板：游离会话强制挂默认项目）：既然项目是资源管理单位，它就该是默认的作业根——每个成员有一个默认项目（今天叫「默认工作区」，workspaces.is_default），会话默认挂在它下面。不再保留"不挂项目"的游离会话（那类会话的产出落会话目录 → 删会话后成孤儿 → 与 §2.2 的解法直接冲突）。挂载点在建会话时定死，不再提供"游离"这个选项。

2.3 闸退役后，项目里两场会话同时跑会怎样

先说清楚退役后剩下什么：

原闸挡的场景 退役后
两个员工同时改同一目录（A 的产物被 B 的 rm -rf 删掉） 不存在了——项目是个人的，别人进不来
同一个人的两场会话同时写同一个文件 仍在。后果：自己覆盖自己，或一场会话的 rm -rf 删掉另一场的产物

所以闸退役不是白退，它把"防人"换成了"防 agent 互相踩"。这一档怎么处理，取决于两件事：

  1. 危险 bash 由 doc/41 的人审闸收掉（doc/41 §3.1：v1 bash 一律 ask，deny 表优先）——rm -rf output/ 这种要人点头。这是闸退役的前提条件，§6 的 Loop 顺序因此把 doc/41 排在前面。
  2. 同名文件覆盖：靠内容锚定（下节 Kimi 的做法）——冲突要显式失败让模型重读，不能静默覆盖。

2.4 同文件冲突：抄 Kimi 的做法（2026-10-22 核对 ref-agent/kimi-code）

Kimi 的三层（packages/agent-core-v2/）：

① 同文件写串行 src/agent/toolExecutor/toolScheduler.ts:17-70 + src/tool/toolContract.ts:184-206（ToolAccesses.conflict） 每个工具声明它对文件的访问集（读/写/搜 + 路径）；两个调用有一个是写且路径重叠 → 后来的排队等前面的跑完 文件（不是项目/工作区）

抄哪几层，抄不了哪一层（这是关键，不能照抄）：

Kimi 的层 tako 现状 结论
① 同文件写串行（进程内） Eino ToolsNode 默认并行；跨 run 更是跨进程/跨副本 抄，但换手段：进程内 mutex 只管一个进程 → 改用 flock（OS 级，同机跨进程跨副本都串），比 Kimi 强一档
② bash = 访问一切 → 独占 tako 无「访问集」概念 不抄——被下面的 ④ 覆盖；且 bash 超时 30 秒（bash.go:16），让它持全局锁会30 秒内阻塞整个项目的文件写（Kimi 是单进程桌面应用，才敢这么干）
③ Edit 内容锚定 tako 的 edit_file 已经是同款（filetools.go:255-270：OldText 精确匹配，不匹配就报错让模型重读） 已有 ✓
④ Write 禁增量覆盖 Kimi 那条其实是 prompt 级（writeTool.ts:88-92 的实现是 fs.writeText(path, content)——整份覆盖、零检查）；tako 的 write_file 同样无约束（filetools.go:120-140） 抄，但要做成程序级（tako 的 ③ 比 Kimi 的 ④ 还硬）
⑤ 真 CAS（版本号 + 原子递增） 无 抄，但版本号用文件系统指纹（(mtime, size, sha256)）：零状态、跨机天然成立、不碰 PG

⚠️ 本节 2026-10-22 16:53 修正两处（前一条消息里的分析有错，已按代码复核改正）：

  1. 「内容锚定不保证写回的整体是最新的」——错。 edit_file 的第一步是编辑时刻现读磁盘（filetools.go:257），写回时用的也是它 → 别的写者在你读之后落盘的改动，会被原样带过去。所以内容锚定 + 现读 = 只在"锚点那一段"被并发改动时才失败，别的段落不失败、也不会被抹掉。丢更新的真实窗口因此从「模型读→模型写」（几秒到几分钟）压到「程序读→程序写」（微秒到几十毫秒）。
  2. 「不需要任何跨 run 的锁」——要限定。 跨机没有共享锁可依（flock 只在同机有效），但可以做显式失败：写前比对指纹，变了就拒（跨机成立，因为判据是文件本身）。同机则用 flock 真串行。

落到 tako's 结论：

乐观并发 = 四件事（2026-10-22 已落地，见 tmp/文件写入并发/）： ① flock 写锁（粒度=文件；锁文件 tenants/<tid>/.tako/locks/<桶号>.lock（256 桶：锁键 = sha256(路径) 首字节 % 256 → 锁文件数恒 ≤ 256，锁目录永远不大）；接进 write_file/edit_file/move_file）——同机全串，跨机看共享盘是否支持 POSIX 锁（CephFS/NFSv4 ✓；NFS 崩溃后要等 lease ~30s）→ 部署前提要钉； ② Edit 内容锚定（tako 已有）：old_text 精确匹配，且编辑时刻现读 → 别的写者的改动被带过去； ③ write_file 写前比对指纹（新落地）：没读过 → 拒；读过但内容变了 → 拒（引导改用 edit_file）；读过但文件被删/移走 → 拒。判据 = 从磁盘现算的 sha256（内容级；>64MB 降级 mtime+size 且显式标注弱判据）； ④ run 级基准表（新落地，内存，键 = agent 名 + 绝对路径）：「我读到的是哪一版」。不落库、不跨 run 共享、零清理。

关键：比对必须在锁内做——锁让「检查—写」成为原子的一段（否则两者之间有缝）；快照让「拒」成为可能。只有锁 → 照样用旧版覆盖；只有快照 → 检查与写不原子。

诚实边界：跨机的极窄窗口（指纹比完到写之间）关不掉——共享文件 + 无协调的写者这个模型下没有免费的原子 CAS（rename 是 last-writer-wins；O_EXCL 只对新建有效），而 bash 绕过工具层会让任何外部协调状态与磁盘脱节。要 100% 就得禁止并发，那等于把闸请回来，与本文直接矛盾。 本篇的选择是：允许并发，冲突显式失败。

不做：Redis 锁 / PG advisory lock（flock 够；Redis 也是 advisory 的、对 bash 一点帮助没有，还要 TTL + 新依赖 + 破坏 doc/38 的「Redis 只留两键」收敛）；版本号表（版本信息只取自目标文件自身，避免「文件写了 version 没跟上」的裂缝）；rename 日志（「B 把文件移哪去了」查不到，机制补不了）。

当时的展开施工：tmp/文件写入并发/（planning.md + todos.md，七拍：W1 指纹+基准表 → W4a 锁封装 → W2 write 判据 → W4b edit/move 接入 → W3 edit 基准+单测 → W5 文案 → W6 收口；现已落地，临时目录不保留）。当时的拍序理由是：比对必须在锁内 → 先把锁封装好再写判据，否则返工。当前代码仍是 flock + SHA256 指纹（>64MB 降级为 mtime+size，且显式标注弱判据）；多副本 PG 锁与原子替换的后续方向见 doc/71（方案待点头），不把该方案写成本篇已经落地。

所以开放问题 1 落定：闸退役后，同文件冲突靠** flock + 内容锚定 + 写前指纹比对**处理；bash 的写由 doc/41 的人审兜底。乐观并发从"远期缝"提上来，与闸退役同批。

G1 的两拍顺序（为什么不能一把梭）：

唯一索引是数据库层面强制的——代码不做任何检查，INSERT 撞了照样报错。所以两件事的顺序会决定"中间那段时间用户看到什么"：

顺序 中间窗口里发生什么 后果
先删索引，再发新代码 索引没了 → 老代码的"冲突分支"永远不触发 → 老副本静默放行两场并发 闸的保护提前消失（窗口 = 从 DDL 到滚动完成）。不报错，但保护没了
先发新代码（且不留兜底），再删索引 索引还在 → 新代码的 INSERT 撞唯一约束 → 没人翻译这个错误 → 500 用户看到"服务暂时不可用"（随机：老副本 409、新副本 500）。报错，但是错的那种
先发新代码（保留 409 兜底），再删索引 ✅ 索引还在 → 新旧代码都把冲突翻译成 409 → 用户看到的与今天一模一样；索引删掉后两边都不再冲突 → 并发真的放开 没有坏行为的窗口

所以两拍是：R2a = 代码侧把"唯一约束冲突"统一成 409（不再有"项目忙"的专属语义），索引不动 → 行为零变化；R2b = 执行 DROP INDEX IF EXISTS one_live_run_per_workspace（纯 DDL）→ 并发真的放开。多副本下 DDL 在所有副本升级完之后执行；此时老副本的行为也已经是"新行为"（它不再期待冲突），所以没有不一致窗口。

4.3 顺带修的两处（本次形态收窄的副产品，量小）

先澄清「租户闸」是什么（容易误会）：它不是"租户之间"的闸。不同租户的数据互相隔离、互不可见，本来就没有共享资源要争。它是同一个租户内同时最多跑几场 run 的上限（max_concurrent_runs，默认 8），保护的是共享资源：模型供应商的 API 配额与成本、同一台机器的 CPU/内存。 所以它与本文退役的「项目闸」是两码事：项目闸管"一个项目内能跑几场"（管的是共享文件），租户闸管"一个租户总共能跑几场"（管的是算力与成本）。前者随本文退役，后者留下但要修。

  1. 租户并发闸改成 DB 约束 → 已落地（2026-10-23，doc/43）。原状：overQuota（product_api.go:26-57）用 CountLiveRuns 读-判-写 → 并发下可超发（两个请求都读到 7 < 8 就都放行，实际 9 场在跑；2026-10-23 活体实测：上限 2，并发四打进来 4 场）。落地形态：数活 run 与插 run 行收进同一笔 PG 事务，中间持一把所有副本共享的顾问锁（pg_advisory_xact_lock）→ 并发下不可能超发。无 DDL、无存量迁移、计数口径逐字不变（僵尸行不算活 → 不误拒）、契约字节不变（满租户仍回 429 113001）。槽位唯一索引那种「插入冲突=满」的形态没选（要 DDL + 存量回填 + 全租户僵尸清扫），取舍见 doc/43 §3。
  2. 并发额度分成员：现在并发额度是租户共享池（一个成员占满 8 场，其他人全被挡），且它与日 token 配额共用同一个业务码 codeQuota 与同一句文案（product_api.go:41-56）→ 用户分不清是 token 没了还是并发满了。形态定成"租户=员工的集合"后，并发额度该能分到成员。

这两条不在本文的必做范围（用户 2026-10-22 拍板：不同批做）。它们是"租户=员工集合"这句话的直接推论。 注意区分：额度分档（计费）已随「团队计费」整组移出路线图（2026-10-22 用户裁）；但并发闸是运行时闸、不是商业化项——它现在有竞态、且被单个成员占满就挡住全租户，这一条仍建议修（与本文的闸退役同属"闸要真"这一族）。

9. 所以这解决了什么

产品形态从"没定"变成"一句话"：tako 是多租户的 AI 工作台，一个员工一个项目，团队共享账号与额度、不共享文件。 这条形态一旦写死，三件一直悬着的事当场落地：① 跨成员共享项目退役（连同它的权限分支与存储分支）；② 项目闸退役——它当年挡的"两个员工互相删产物"场景，因为项目变个人的而不复存在；③ 产出与会话档案分层，删会话不再产生孤儿文件，项目的配额与清理归口明确。

同时把当年那条"乐观并发是远期缝"的搁置理由掀了：它当初被搁置是因为"闸先顶着"，而闸现在要退役——但落法变了：不是加版本号列，而是抄 Kimi 的内容锚定（§2.4）——edit_file 的 old_text 匹配 tako 已经有了，只差 write_file 写前比对内容。这是无状态、无迁移、跨副本天然成立的版本，比当年设想的版本号方案便宜一个量级。

代价也要说清楚：团队叙事从"共享一个项目"收窄为"各自的项目 + 共享额度与审计"，对外可讲的故事少了一条（doc/16 §2 的 #9b 团队协作前端仍在，但它讲的不再是"一起改同一个项目"）；跨成员共享文件这条需求从"待做"变成"明确不做"（doc/16 §5.1 第 3 项与 doc/28 §15 要同步改口）。这是定位收窄，不是工程量收窄——换来的是不用去做协同编辑这个级别的地基。
