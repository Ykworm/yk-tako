0. 术语（2026-10-08 用户裁；2026-10-10 补 3 条模型侧术语）

先看「观测 / 存储」侧三个词，三种形状 / 住处 / 消费者，勿混：

词 形状 住处 消费者 粒度
Model message OpenAI messages（role/content/tool_calls） 主线程 → run_model_messages 表；子代理 → 只在进程内（AgentTool runner state） worker 组装模型输入 消息
runlive 帧（kind + agent + model + 负载） Redis tk:runlive:{runId} LIST（TTL 300s） frames API（客户端轮询） 帧

再看「模型选型 / 客户端」侧三个词（§4 开始大量用，先钉死定义）：

词 形状（正向定义） 住处 消费者 例子
ref 字符串，格式 = 厂商ID / 模型ID。唯一身份：带厂商命名空间，避免同名模型撞车。 不单独存：从环境变量 TAKO_MODEL 读、或从子代理 md 的 model: 行读 ResolveModel 解析它、ModelRegistry 拿它当缓存 key、帧/行里的 model 字段存它 deepseek/deepseek-v4-flash、anthropic/claude-sonnet-4、ollama/qwen2.5-coder:14b

index 概念表对 runlive/runlog 的定义不变；本篇钉死的是「模型输入侧叫 Model message、观测侧叫帧/runlive」， 以及两者永不混写：子代理的 Model message 不进 mh、帧不进 mh。

2. 工具消息的两个投影

同一次工具调用，两个投影各自成形状（种类由 role 取值承载，2026-10-07 已裁）：

  • mh（Model message，模型输入）：OpenAI messages 形状。assistant 行 text = 纯正文不夹带； 新增 tool_calls / tool_call_id 两列（§6）；tool 行 text = 工具结果。 多轮时逐轮一行：工具轮的前导语在自己那行（与 tool_calls 同行），不并进终稿行——终稿行只放最后一轮正文。
  • runlog（展示与历史）：消息粒度活动行——assistant 正文行 + 扩展行 （role=tool_call / tool_result，payload 列存 name/args/output 等结构化负载）。 assistant 行 text = 全 run delta 累计（所见即所得，收口替换的锚）。
  • runlive（实时观测）：帧粒度——tool_call / tool_result 帧 + 流式 delta 帧。

3. 帧契约扩展（已落 19v6-01 §2，2026-10-08 七修）

  • 每帧带 model 字段（2026-10-10 纠偏）：生效 ref（厂商/模型）——契约已补 19v6-01 §2，随 T3-1b 落地； 行侧 model 列随 T3-2（§6 已登记，PG 落库）。

ModelRegistry.Get 到底在做什么？（最小伪代码，30 行以内讲明白）：

// ModelRegistry 就是进程内一张带懒加载的缓存表。
// 注意：这是解释性伪代码，不是产品代码。产品代码细节（double-check、锁粒度等）落地时再抠。
type ModelRegistry struct {
    mu    sync.RWMutex
    cache map[string]*ChatModel // key = ref，value = 已经建好的 HTTP 客户端
    env   Env                   // 进程启动时的环境变量快照（Key/BaseURL 都从这里读）
}

func (r *ModelRegistry) Get(ctx context.Context, ref string) (*ChatModel, error) {
    // 1. 先查缓存：之前有人用过这个 ref → 直接返回
    r.mu.RLock()
    if m, ok := r.cache[ref]; ok {
        r.mu.RUnlock()
        return m, nil
    }
    r.mu.RUnlock()

    // 2. 缓存空 = 第一次用到这个 ref。走与 TAKO_MODEL 完全相同的解析链：
    //    ResolveModelWithRef(r.env, ref) → 查出厂商、Key、baseURL、协议
    //    build(ctx, resolved)            → 按协议建对应的 HTTP 客户端（openai / claude）
    resolved, err := ResolveModelWithRef(r.env, ref)
    if err != nil {
        return nil, err // 没配这家的 Key / 厂商不在目录 / ref 格式错 → 上层拒载该规格
    }
    chatModel, err := build(ctx, resolved)
    if err != nil {
        return nil, err
    }

    // 3. 塞进缓存。下次同样的 ref 就不用再走解析 + 建客户端了。
    r.mu.Lock()
    defer r.mu.Unlock()
    if m, ok := r.cache[ref]; ok { // double-check：并发下可能别人刚好塞了
        return m, nil
    }
    r.cache[ref] = &ChatModel{Chat: chatModel, Protocol: resolved.Provider.Protocol, Ref: resolved.Ref}
    return r.cache[ref], nil
}

几个有意这样设计、不按直觉改的点（别看到进程内就想搬去共享存储）：

  • 「多实例」= 同一张缓存表里可以同时有 deepseek 客户端、claude 客户端、ollama 客户端——只要你在规格里写了不同 ref，第一次用到时就各建各的，互不干扰。

  • 「晚解析」= 进程启动时 ModelRegistry.cache 是空的。你写了 20 条子代理规格，但只有 3 个被真正装载用到 → 只建 3 个客户端。剩下 17 个永远不会浪费内存去建。

  • 解析链同源：写法三里那个「ResolveModel + build」和主 worker 启动时 config.Open() 调的是同两个函数（只是 ResolveModel 会抽一个通用版 ResolveModelWithRef，主 worker 的 TAKO_MODEL 也是拿这个通用版喂环境变量），保证 TAKO_MODEL=deepseek/x 和 md 里 model: deepseek/x 行为 100% 一致——不会出现「主 worker 能调通、子代理调不通」这种同一个 ref 两种行为的诡异 bug。

  • 为什么 ModelRegistry 放「进程内存」，不放 PG/Redis 共享存储？（一张表说清楚判断依据）

    判断原则来自仓库级硬规则 AGENTS.md：「凡是要长期存在的状态，先问『多副本下它在哪』」——但不是所有东西都叫「长期状态」。四种东西对比一下：

    东西 本质是什么 需要跨副本一致吗？ 放哪里（v6 现状） 为什么这么放
    会话「单 run 跑着」的闸 互斥锁：两副本同时抢同一会话会出两份 run、写乱帧序 ✅ 必须全集群唯一 PG runs 表部分唯一索引（插入失败本身就是 409） 共享可变状态 = 必须放共享存储。进程内 chan 或 mutex 一上多副本就废
    runlive 帧流 生成中帧的实时队列：客户端不管打哪个副本的 frames API 都得看到同一批帧、同一顺序 ✅ 必须全集群同序 Redis tk:runlive:{runId} LIST（TTL 300s） 时序队列 = 必须放共享。各副本各写各的，客户端轮询就丢帧乱序了
    runlog 历史行 会话的定稿历史：用户关了浏览器再开，历史必须还在 ✅ 必须持久、不丢 PG runlog_entries 表 持久化数据 = 必须放共享。进程内存里一重启就没了
    ChatModel 客户端实例 一个无状态的 HTTP 请求发件器：装着 URL + Key + 协议 + 模型 ID，不记任何对话，同样的 ref 建 100 个和建 1 个行为字节级一样 ❌ 不需要一致 进程内存（本进程的 ModelRegistry） 它是「连接句柄」，不是「数据」：
    1. 跨进程传不了 HTTP client（里面有连接池、goroutine 私域），物理上就没法塞 Redis
    2. 多副本各建一份成本可以忽略：扫几十条环境变量（μs 级）+ 分配几个 struct，真金白银的成本是后面几百 ms 的 LLM 请求本身
    3. 同 ref 解析结果必然一致：所有副本读的同一套环境变量 + 同一套厂商目录，不存在「A 副本解析成功、B 副本解析失败」的可能（除非滚动部署时半更新，那是部署纪律的锅）
    4. 缓存丢了也没关系：进程一重启、ModelRegistry 空了，下次 Get 再建就行，不丢任何业务数据——缓存只是「省一次解析」，不是真源

    总结成一句话：数据（要持久、要跨副本一致的）放共享存储；连接句柄（用了就扔、重建成本极低的）放进程内。 ChatModel 客户端是连接句柄，不是数据。

  • Model message = 进程内：AgentTool 每次调用起独立 runner（独立 compose state），跑完即弃， 只有最终文本作为 tool result 回主 run。崩溃即丢，符合「run 死、会话活」语义。

  • runlog 落消息粒度行：委派 tool_call / 子代理动作行 / 子代理终稿，agent 列非空、model 列 = 该 agent 生效 ref（PG 落库随 T3-2）； 历史组装按 root 过滤（event.AgentName == root——不过滤会把子代理内部 tool 消息混进主历史）。

  • runlive 帧流：子代理帧与主 agent 帧进同一归一层、同一 LIST，每帧带 agent 与 model（生效 ref）。

  • 粒度裁定（2026-10-08）：runlog 记消息粒度、不记帧——主 agent 的 delta 本就不落历史表， 子代理同构：delta 帧只进 runlive，不落 runlog。

  • 并行：同一 run 内多 goroutine 各跑独立 state，帧事件全经主 run 的单一 writer（归一层）落库， seq 串行分配——并行不改表，无共享可变状态。

  • 嵌套：默认禁止（子代理规格不挂委派工具，pi 同款）；开放时 max=1 且深度持久化防 resume 绕过 （dsh 默认）——随用例再立。

  • 规格的工具面字段（tools 2026-10-09 定为三态；2026-10-16 加 exclude_tools 成四态，doc/26）： 不写 → 继承父池（父池已摘掉委派工具 = 禁嵌套；pi/harness 同款）/ 白名单（按名从父池映射）/ [] 空集（「不写 vs 写空」用 nil / 空 slice 分开表达）/ exclude_tools: [名字…] → 继承父池减去列出的名字（新字段，与 tools: 互斥：同写整条拒载； 排除一个父池没有的名字也拒载；exclude_tools: [] 视同不写。结果序是池序、元素是父池同一批对象。 四态表与操作定义只在 doc/26 §3 一份，这里不复述）。 「+search」= 保留名 tool_search 显式进列表才挂（用户 2026-10-08 裁「子代理挂 search，当然要」； 2026-10-20 已拍：继承档——不写 / exclude_tools——不自动加，搜索面是能力面，不悄悄多一把工具）—— 搜索范围 = 自己的池（统一规则见 §5）。分级落地后子代理池同样分 direct/deferred，池内工具不再全声明。

  • 预算面（2026-10-09 三裁）——取消是控制面的事（abort 级联），不是时间面的事（用户裁，并指 Google ADK 同立场）：

5. 工具目录与 tool_search

  • 施工状态（2026-10-09 裁触发式；2026-10-20 开工并当日落地）：原裁「等 MCP 工具 loop 进来（工具多到 撑上下文）或子代理库长到几十条再动工」；MCP client（doc/33）已落地、工具规模信号成立，用户 2026-10-20 裁「一步到位把 T5 也做了」——T4（分级 + tool_search）与 T5（BM25 排序）同批施工， BM25 是首版排序器，不先做名称/描述直出再替换。分离原则不变： 「可执行集合 ⊇ 声明集合 ⊇ 可检索集合」；T3 期「一个源、一个装载点、一个声明状态（全声明）」到此让位给分级。 施工与验收结论见本节尾条。
  • 分级 = 启用工具全注册 + 声明过滤：装配时决定放不放进池——不放 = 禁用，不进 tools node， 既不可执行也不可检索；放进池的工具全部注册进 tools node。每轮模型调用前， BeforeModelRewriteState 用本 run 保存的完整目录重建 state.ToolInfos 决定模型看见什么—— direct = 常声明 / deferred = 目录层，整条 ToolInfo（名字、描述、参数 schema）都不进声明面， tool_search 激活后才声明。不能对当前 state.ToolInfos 做减法： 首轮过滤后 deferred 项已不在其中，减法的源会丢；完整目录必须另存（run-local）。 不设 hidden 档（2026-10-20 裁）：tako 的池每 run 重建，禁用就是装配时不 append，不存在 pi 「注册表撤不掉、只能重注册成 hidden」的问题。把 hidden 定义成「永不声明」也不成立——工具仍在 node 里，而 Eino tools node 按全量工具表按名分发（名字不在节点才报 tool X not found，v0.9.21 compose/tool_node.go 实读），执行面并没有关，模型猜中名字仍可能调起。今日没有「只给代码调、 不给模型调」的消费者（三条来源都在装配时不放；子代理池从入口快照按名收窄、只减不增，§4）， 所以不留这一档；将来真出现该需求，按新需求重新立档并同时设执行闸。
  • tool_search（T4/T5 合批，2026-10-20 用户裁）：模型检索目录、BM25 排序、命中即激活（同一 run 的 下一次模型调用即声明）。首版就是 pi 的 Go 移植——camelCase 分词 + 朴素词干 + 停用词；Okapi BM25 （k1=1.2、b=0.75）；文档 = 名字 + 下划线拆词 + 描述 + 参数 schema 的描述与属性名（MCP 工具再加 server 短名）；query 必填、limit 缺省 8、空 query / 非正整数 limit 当场报错；无命中回 No matching tools found.。直出版不落地。
  • mh 与激活集分家（2026-10-20 定）：mh 只记 tool_search 的 assistant 调用行与 tool 结果文本 （Loaded N tools...），不记工具 schema、不记「已激活」。激活集是 run 状态；每轮模型看见哪些工具 由 BeforeModelRewriteState 用完整目录按「direct + 激活集」重建 state.ToolInfos 决定， 同一 run 内由 run-local 状态延续。新 run 读回 的历史里只有那句结果文本，没有声明——「记录了」不等于「模型这一轮看得见」。
  • 激活集寿命（2026-10-20 已拍：只活一场 run）：新 run 从零激活（tool_search 本身是 direct，模型可重检）； 崩溃续跑同一场 run 时同样从零激活（doc/30 账本不存激活集），模型凭历史里上次的回执与调用参数重检。 回执固定写 Loaded N tools for this run...——不照抄 pi 的 available from your next call（跨 run 读回 历史时会变成半句假话）。若产品将来要「加载过就一直可用」，必须把激活集结构化持久化（多副本不能靠 进程内状态），从 mh 文本重放会被折叠折走、不可靠——那是另立方案。
  • 首版分级来源（2026-10-20 已拍：按来源的机械规则）：mcp__ 前缀 = deferred（工具规模增长源）； 一手工具 + 子代理 = direct。不新增配置面；单个 MCP 工具若将来要固定 direct，再加 server 级覆盖。
