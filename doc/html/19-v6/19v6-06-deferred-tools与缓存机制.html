19v6-06 · 工具分级与 deferred tools（机制篇）

本篇是 doc/19-v6 文档集的 deferred tools 机制篇：工具分级为什么存在、前缀缓存的失效力学、 client mode 与 hosted mode 的完整链路、各厂商支持矩阵（2026-10-08 实证）、provider 原生通道的接法。 分级的 v6 落点（启用工具全注册 + BeforeModelRewriteState 声明过滤、两档定义）见 19v6-05 §5——本篇不重复裁定， 只给机制背景与 provider 原生通道的对照。本篇不做契约承诺，所有 provider 原生内容均为「背景素材」。 2026-10-20 校正：§1 的 hidden 原文「代码内部/子代理用」先校正为 pi 的操作定义（注册但不可达）， 随后裁定 tako 不设 hidden 档——只留 direct / deferred，禁用工具 = 装配时不 append。见 19v6-90 十九修。 2026-10-21 裁定（终态）：用户裁 client mode 即终态底座，hosted mode（provider 原生 deferred）不接—— 理由三条见 §6。本篇降为纯背景篇：§4–5 的链路与矩阵保留作将来复用的参考，不作施工面、不进待办。

0. 一句话

工具分级解决「工具一多，声明成本（token / 注意力 / 缓存）爆炸」；deferred tools 是各厂商对同一问题的 协议级回答——目前无标准名、无标准协议，形态碎片化，这正是 v6 把客户端过滤定为默认底座的原因。

1. 为什么需要分级

  • 模型在协议上只能调用当前请求 tools 数组里声明了的工具；声明 = 占用前缀 token。
  • 上百个工具的全量 schema 既烧 token 又稀释注意力 → 只常声明一小撮（direct）， 其余进目录（deferred：模型经检索按需激活）；不想要就在装配时不放进池（tako 不设 hidden 档）。
  • pi 的 hidden（仅作对照，tako 不采纳）：原文是 registered but unreachable—— 工具仍在注册表里，但模型与 ctx.executeTool() 两条路都够不着，激活也不生效 （packages/coding-agent/docs/extensions.md「Tool exposure」）。pi 需要它是因为注册表没有 unregister，只能重注册成 hidden 来「撤回」；MCP 配置里它也是 server 级默认值与工具级覆盖的 一个取值（"delete_*": "hidden" 做黑名单，server 默认 hidden + 逐工具覆盖做白名单）。 但 tako 的池每 run 重建，禁用 = 装配时不 append，不需要这一档；只撤声明、不撤执行的 hidden 在 Eino 下也关不住执行面（tools node 按全量工具表按名分发，见 19v6-05 §5）。
  • v6 两档 = pi ToolExposure 五档（direct / model-only / codemode / deferred / hidden）中取 direct / deferred；model-only / codemode 不在 v6 范围，hidden 按上条不采纳。

2. 缓存力学（一切的根源）

  • 无状态协议：服务端不记会话，每轮客户端全量重发 history → provider 按「前缀哈希」做 prompt caching （Anthropic 实证：写缓存 = 断点处前缀的哈希；命中要求逐字节相同）。
  • 前缀层级固定：tools → system → messages。改 tools 段 = 三层缓存全灭 （Anthropic 失效表原话："Modifying tool definitions invalidates the entire cache"）。
  • KV 按位置缓存：前缀任何位置变更，其后所有位置的 K/V 作废；tools 排最前，所以一改全灭。
  • 追加不破坏缓存：tool result 作为新消息追加在尾部，是缓存友好动作——多轮对话本身就是 「恒定前缀 + 尾部追加」结构，agent loop 天然适配。破坏缓存的是「改写已存在的前缀内容」， 不是「出现 tool result」（ tool_use / tool result 块在 Anthropic 均可被缓存）。
  • 缓存价值：读 ≈ 0.1x 价、TTFT 大降；一 run 多轮的 tool loop 是最依赖缓存的负载——声明集稳不稳是真金白银。

3. client mode = v6 现在（手写声明过滤）

  • 全工具注册进 tools node（永远可执行，注册 ≠ 声明）；deferred 的整条 ToolInfo（名字、描述、 参数 schema）都不进声明面，模型不知道目录里有哪些非必要工具，只知道 tool_search 这个入口存在。 BeforeModelRewriteState 每轮用本 run 保存的完整目录重建 state.ToolInfos，决定本轮发给模型的 tools 数组（eino 钩子，provider 零感知）。不能对当前 state.ToolInfos 做减法：首轮过滤后 deferred 项已不在其中，目录必须另存。
  • tool_search 是普通工具：模型调用 → 客户端 BM25 检索 → 命中名单写进本 run 的激活集 （tool_search 的 handler 持有；不扫消息文本）→ 钩子每轮按「direct + 激活集」从完整目录重建 state.ToolInfos → 下一轮模型才「看见」。结果文本同时落消息历史，供模型读「加载了什么」——它只是回执，不是激活真源。
  • 代价：激活那轮 tools 数组在中段变更 → 前缀哈希作废 → 缓存失效（本 run 内单调收敛：搜出即常驻， 之后稳定，仅「发现期」几次 miss；跨 run 不保留——激活集只活一场 run，2026-10-20 已拍，见 19v6-05 §5）。
  • 优点：对 provider 零要求——任何模型、任何兼容端点都能跑。T4/T5（分级 + BM25 目录）复刻的就是检索层。

出处 叫法

4.2 完整链路（请求携带式 hosted，OpenAI 文档 + eino-ext 源码实证）

# 步骤 执行者 输入 输出 作用
0 目录组装 客户端（eino wrapper 每轮附加 WithDeferredTools） 应用的工具注册表 请求 tools 数组：全量 schema + defer_loading 标记 + {type:"tool_search"} provider 本轮知道库存
1 扣留暂存 provider 网关 tools 数组 暂存区（deferred schema 隔离，不进 KV key） 目录保管在上下文外
2 前缀预填充 provider 摘要层 + 常声明工具 + system + messages 前缀 KV；模型开局视野 建立恒定可缓存前缀
3 检索词生成 模型 任务上下文 + 摘要层 query / paths（hosted 下为内部信号） 模型唯一发言点：搜什么
4 索引检索 provider 检索索引 query + 暂存区 命中的工具 schema BM25/regex 机械匹配（无任何智能成分）
5 末尾注入 provider 基础设施 命中 schema 追加在上下文末尾（只增区） 模型看见 schema 且前缀不动
6 工具调用生成 模型 注入的 schema 普通 function_call / tool_use 与常声明工具同构
7 工具执行 客户端 function_call tool result（下轮 messages 追加） 客户端常规职责，零特殊逻辑
8 事件记录 provider → 客户端 步骤 3–5 过程 响应里的 tool_search_call / tool_search_output item 可观测；多轮回放保持状态

循环规则：同轮可 3→6 多遍（需要第二个工具就再搜）；跨轮重复 0–2 时前缀字节相同 → 缓存命中，注入区累积在尾部。

4.3 关键机制点

  • defer_loading 的实质：全量 schema 仍随每轮请求上行（占带宽、不占上下文），但被剥出模型工作 上下文、不进 KV key——「provider 本轮替你保管目录」。
  • 摘要/细节二分：模型开局只见摘要层（名+描述，常驻前缀、供生成检索词）；被扣的是参数 schema。 加载粒度 = 检索路径命中的子树（如搜 paths:["crm"] → 整个 namespace 进来），模型不能逐工具勾选， 不满意只能再搜。
  • 注入位置是护城河："All tools are loaded at the end of the model's context window"（OpenAI 原文）—— 变更永远落在只增不改的尾部，所以缓存保活。client mode 永远做不到这点（只能改 tools 段中段）。
  • tool_search 用 type 不用 name：tools 数组是联合类型（function / namespace / tool_search / web_search…），type 是判别字段；name 只属于模型按名调用的用户函数。
  • 变体：
    • client-executed（OpenAI）：模型发 tool_search_call（execution:"client"），客户端执行检索、 下轮把 tool_search_output 塞进 input——检索位置灵活，但加载仍走尾部注入（协议化的 client mode）。
    • MCP 自动发现（OpenAI Agents API）：provider 自己连远程 MCP server 做 tools/list，目录不进请求。
  • 铁律不变：工具定义的控制权在应用/MCP server 侧，模型不能给自己造工具（所有模式一致）。

4.4 缓存友好的三条路线（同一原则的实现谱系）

原则：变更只能落在「只增不改」的尾部，或干脆不落在模型上下文里。

路线 工具变更落在哪 前缀旧段 代表
前缀外通道 provider 暂存区（不进 KV key） 原样 defer_loading（Anthropic / OpenAI / DeepSeek）
尾部追加 messages 尾部 原样 Anthropic tool_addition（inline-tools beta）；OpenAI additional_tools；Kimi messages[].tools
认损 tools 段中段 被破坏（发现期） client 过滤 = v6 现在

5. 厂商支持矩阵（2026-10-08 实证）

厂商 支持 形态 eino-ext 组件

Gemini ❌ 仅标准 function calling（feature request 仍开） —
Qwen / 豆包 / GLM ❌ 未见 仅标准 function calling（托管 web_search 是厂商自带工具，与用户工具 deferred 无关） —

要点：

  • 「支持」本身也分裂：DeepSeek 认 Anthropic 式标记、Kimi 用自家消息通道、Anthropic 带服务端 BM25—— 没有两家同协议，升级路只能按家适配。
  • eino 核心只定义 option，翻译靠组件、可用性靠 provider 运行时校验（eino 不做任何能力探测； eino-ext openai 组件静默忽略 option 即是例证）。
  • 顺手的推论：deferred schema 不进 KV key → 原生模式下改目录本身可能缓存中性 （与 client mode 的中段变更形成对照），待接入时以厂商文档最终确认。

6. v6 的裁定与升级路

  • 默认底座 = client 过滤（19v6-05 §5）：碎片化格局下的最大公约数，不挑 provider。
  • 2026-10-21 用户裁定（终态）：client mode 即终态底座，hosted mode 不接。 理由三条：
    1. 覆盖面对不上——本仓 provider 目录 39 条里 36 条是 openai 协议、3 条 anthropic 协议； eino-ext 只有 claude 组件翻 defer_loading（openai 组件 v0.1.13 无翻译层）， 接了 hosted 只覆盖那 3 条，主力那 36 条吃不到。
    2. 代价与收益不对账——hosted 唯一的增量是「发现期不毁缓存」，而 client 模式的缓存损失有界： 激活集同 run 内常驻（搜出即常驻、之后单调收敛），只有最初「找工具」那几轮 miss；跨 run 不保留激活集， 本来就是每场重新发现。
    3. client 模式对 provider 零要求——任何模型、任何兼容端点都能跑，不挑厂商、不吃私有协议、 不等 eino-ext 上游。
  • §4–5 的链路与厂商矩阵保留作背景（将来若换厂商组合、或某家把 client-executed 变体做成标准， 可直接取用），但不作施工面、不进待办。§4.2 步骤 0–8 与 §5 矩阵在本仓均无对应代码。
  • T4/T5（分级 + BM25 目录）复刻的是检索层——client mode 即终态，这套客户端目录与匹配逻辑就是执行体。
  • 第一个真实负载已经到场（2026-10-18 补；2026-10-20 开工）：MCP client（doc/33）落地后，MCP 工具以 mcp__短名__工具名 直接进池；用户 2026-10-20 裁「一步到位把 T5 也做了」——T4/T5 合批开工， MCP 工具是 deferred 目录的第一批真实负载（19v6-05 §5，施工台账 tmp/19-v6/）。
