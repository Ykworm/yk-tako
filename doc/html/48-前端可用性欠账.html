对话页是唯一的高频页面，先修它。

A1 · Markdown 完全不渲染（P0 · 契约违背）

病灶。 doc/19-v6/19v6-03 第 118 行写着：「text 里的 \n 原样保留，客户端按 markdown 渲染，排版不受影响。」而 App.vue:932 是 <p v-if="b.text" class="bubble-text">{{ b.text }}</p>——纯文本插值，一个标签都不多。

实测（2026-10-23，模型被明确要求输出 markdown）：回复里的 ## hello.txt 说明、| 属性 | 值 | 表格、```text 代码块、1. 2. 3. 列表、**加粗**，全部以字面符号显示。用户看到的是一堆管道符和井号。

为什么这件事是 P0 而不是「美化」。 模型输出 markdown 是这个系统的常态，不是意外：doc/19-v6-07 里 compact 摘要本身就是用 ## 槽头组织的 markdown 骨架；用户给模型的指令（"整理成待办清单"、"写份说明"）几乎必然引出 markdown。现在每一轮对话都在把模型的结构化输出退化成符号噪音，用户要自己把 | 和 --- 翻译回表格。而且这不是"少实现一个功能"，是v6 文档写明的渲染责任从来没被实现——按 AGENTS.md「与代码冲突时先判断哪一边过期」，这里过期的是代码。

做什么。

  1. 新增 web/src/markdown.ts，导出三个函数：

    导出 做什么 碰 DOM 吗
    renderMarkdown(text): string marked.parse(text) → HTML 字符串 否（纯函数）
    sanitizeHtml(html): string DOMPurify.sanitize(html) 是
    renderSafe(text): string 前两者串起来 是（浏览器里跑）

  2. 依赖装两个：marked@18.1.1 + dompurify@3.4.17（选型出处见下）。

  3. App.vue 的气泡正文从 {{ b.text }} 改成 v-html="renderSafe(b.text)"。

  4. 样式：给 .bubble-text 补 markdown 元素的排版规则（标题字号、表格边框、代码块底色、列表缩进、行内代码底色）。

为什么是 marked + dompurify（选型出处，不是拍脑袋）。 参照仓库里三家同类产品的现成选型：

参考实现 markdown 库 消毒
pi（ref-agent/pi，TS agent，doc/16 §2b 的主要参考） marked@18.0.11（TUI + coding-agent） —
opencode（ref-agent/opencode） marked@18.0.11 dompurify@3.4.14
WeKnora（ref-agent/WeKnora，Vue 聊天） marked@^17.0.5 dompurify@^3.4.11

三家全部是 marked，没有一家用 markdown-it。 而且 marked 的 sanitize 选项早已废弃（官方指引：改用 DOMPurify），所以「marked + DOMPurify」是这对库的现代标准写法——三家做法一致不是巧合，是这条路已经被走通了。

doc/16 §1 的借鉴纪律说「抄『问题本质』不抄『历史包袱』」。这里的「问题本质」是**「用成熟解析器 + 成熟消毒器」，不是「用哪个包」——所以照抄这个组合**是对的，不是抄历史包袱。

版本取当前最新（2026-10-23 查 npm registry）：marked 18.1.1（三家参考实现都钉在 18.0.x，同一大版本）、dompurify 3.4.17。

代价与好处。 代价：多一个依赖（DOMPurify 约 20KB min+gzip），且它是 DOM-only 的（Node 里跑要 jsdom）。好处：与三家参考实现一致（出问题时有人可对照）、marked 的 GFM 表格/任务列表/代码块开箱即用、生态成熟。

这个代价怎么绕开。 上表里 renderMarkdown 不碰 DOM → node --test 直接测它，不需要为测试额外引 jsdom；而「<script> 会不会被执行」这条 XSS 断言放到 playwright 浏览器里测（浏览器才是 DOMPurify 的真实运行环境）。

每一步的输入输出。 输入 = 气泡里的 b.text 原始字符串（runlog 里的原话，服务端一个字都不改）；输出 = 一段 HTML 字符串，交给 v-html。

没它会怎样。 已在 §0.3 讲透：模型所有结构化输出退化成符号噪音。

一个必须一起处理的坑。 b.text 里还可能夹着 media 占位行（[media seq=… path=… mime=… size=…B sha=…；…]）。现在这些行是被 parseMedia 剥掉的（api.ts 的 parseMedia 过滤掉占位行、留下正文），所以渲染的输入已经是剥干净的正文，不含占位行。改造时不要把整条 runlog 原文直接喂给渲染器——那会把占位行当普通文本渲染出来。

验收。 机器断言用 Node 内置 test runner（零新依赖，Node 22 自带 --experimental-strip-types + node:test）钉住渲染输出：

cd yk-tako-eino/web && node --experimental-strip-types --test src/markdown.test.ts

期望字节（node --test 钉住 renderMarkdown 的输出）：

输入 期望输出包含
## 标题 <h2>标题</h2>
- a\n- b <ul> 且含 <li>a</li>
| a | b |\n| --- | --- |\n| 1 | 2 | <table> 且含 <th>a</th> <td>1</td>
```text\nx\n``` <pre><code class="language-text">

XSS 那条要单独说清楚：marked 本身不转义原始 HTML（它会原样输出 <script>）——这正是必须配 DOMPurify 的原因。所以 <script>alert(1)</script> 这一条不能在 node 里断言（node 里没有 DOMPurify），要放到 playwright：发一条含 <script> 的消息 → 断言页面把它当文字显示、window.alert 未被调用。

这个分工是刻意的：结构在 node 里测（快、零依赖），执行在浏览器里测（真实环境）。

A2 · 对话页没有会话历史入口（P0）

先说清楚不动的部分（用户 2026-10-23 表态：「很多 agent 都是项目下面挂着对话」）。 「会话挂在项目下」这个数据结构保留不动——sessions.workspace_id 这一列不动、项目页的树形结构不动、GET /api/sessions?workspaceId= 不动。本条要补的只是一个直接回到旧对话的入口：结构照旧挂在项目下，但用户不必先想到「是哪个项目」才能回去。

病灶。 侧边栏只有「对话 / 项目 / 助手 / 团队」四个按钮，没有任何会话列表。想回到上一场对话，路径是：点「项目」→ 找到那个项目 → 点「查看对话」展开 → 在两场会话里靠标题认 → 点「打开」。而标题是模型用首句生成的，不是用户起的名。实测那个项目里两场会话叫「说一句 ho」「说一句 hi」——用户拿这两行字认不出哪场是昨天那场。

A3 · 运行中没有「停止」按钮（P1）

病灶。 引擎有 POST /api/runs/:runId/stop（server.go:75，doc/17 §4 手动停止，带条件 UPDATE 竞态裁决 + 跨副本 cancel）。前端一次都没调过。用户让模型干一件耗时的活，做到一半发现方向错了，唯一的办法是刷新页面——那场 run 还在服务端跑着，token 还在烧。

做什么。

  1. api.ts 加 stopRun(runId: string): Promise<{ status: string }>（走现成的 request()，信封统一）。
  2. chat.ts 加 stopCurrent()：拿当前 busy 那条气泡的 runId 调 stopRun；成功后把该气泡 state 置 'stopped'（chat.ts 的 closeOut 已有 stopped 分支，App.vue:947 已有「已停止，没有写进历史」的文案，不用新写文案）。
  3. App.vue 的 composer 栏：busy 为真时，把状态提示「正在回复」换成「正在回复 · 停止」按钮；点了就调 stopCurrent()，按钮进入 disabled + 「正在停止…」。
  4. 排队中（pending.length）不显示停止——那不是 run，是本地队列（chat.ts 的 pump）。

每一步的输入输出。 输入 = 气泡上的 b.runId；输出 = 服务端把 run 标成 stopped → 前端把那条气泡渲染成「已停止，没有写进历史」。

没它会怎样。 方向错了只能刷新；正在跑的那场 run 继续烧 token，用户还以为它停了。

验收。 浏览器活体：

窗口 A（浏览器）：发一条要跑很久的请求 → 状态栏出现「停止」按钮 → 点它
窗口 B（终端）：curl -s -X POST -H "Authorization: Bearer $TOK" "$BASE/api/runs/$RID/stop" | jq -c .

期望：窗口 A 的气泡变成「已停止，没有写进历史」；窗口 B 在 A 点之前调会回 {"code":0,…,"data":{"status":"stopped"}}（幂等：A 已经停过再调一次仍回 stopped，不报错）。

补记（2026-11-03，生产验收后修的一轮）。 上线后用户报「当前会话找不到停止按钮」。排查下来不是样式问题，是三处真实缺口：

  1. 按钮只认本实例的忙态。 busy 由本页的投递（deliver）和轮询（pollFrames）置位。同一场 run 若是另一个标签页 / 另一台设备发起的，本页没有轮询者，busy 一直是 false，按钮根本不渲染——可这场 run 确实在烧 token。用户看到的正是这一条。
  2. busy 是布尔开关，多个写者互相覆盖。 投递与每个轮询者各自在 finally 里把它置 false，先结束的一轮会把仍在跑的那轮按钮一起关掉。同一场 run 还会被 reconcile 与投递各起一个轮询者：画两个 streaming 气泡，问答面板随之出现「2 / 2」。
  3. stopError 只写不读。 点停止失败时页面毫无变化，看起来跟「没有停止能力」一模一样。

修法（chat.ts + App.vue）：chat.ts 增加会话级 liveRunId——值来自 getSession(sid).liveRunId，在 gateIdle、投递成功、轮询、reconcile 处记录；页面可见且空闲时每 5 秒跑一次 probeLive 兜底，发现本实例不认识的活 run 就接管帧面（从 offset 0 起拉，与 reconcile 同一套），并给出停止入口。busy 改成持有者计数（holdBusy/releaseBusy），pollingRuns 保证同一 run 只有一个轮询者，delivering 让 reconcile 认出「这一轮是我自己的」不再重放。App.vue 的 canStop = 有 liveRunId，或任一 streaming/offline 气泡带 runId；stopCurrent 依次按 target.runId → 气泡 runId → liveRunId 取目标；runId 还没回来（投递在飞）时按钮显示「正在启动…」并禁用；stopError 在输入栏与提问面板都渲染出来。

验收（2026-11-03，PRD）。 四场活体全过：当前会话自己发起的 run（按钮出现、点击后气泡变「已停止，没有写进历史」）、另一台设备打开同一会话（3 秒内出现可点的「停止」，点了之后发起端同步变 stopped）、刷新时 run 仍活着（刷新后按钮仍在并可停）、ask_user 等待面板（面板里的停止按钮可点，点了面板消失、气泡变 stopped）。

流式反馈一轮（2026-11-04，390×844 实测）。 用户报「回复不是一个字一个字出的，会停一段时间突然出一段，停的时候也不知道它在干嘛」。量下来是两件事叠在一起：

  1. 源头不是问题。 引擎把厂商 chunk 逐条压成 delta 帧（一帧 1–3 字，中位间隔 0ms、均值 7ms，一轮 782 字共 522 帧）；SSE 通道同样以 ~150ms、每批 25–66 字送达。停顿发生在两个地方：模型首字之前（TTFT 2.2–3.8s），以及工具执行期间（bash sleep 6 实测算工具卡 1.4s 出现、之后 5.8s 页面没有任何变化）。
  2. 前端 400ms 一拉、一拉一刷。 POLL_MS = 400 把 ~90 字攒成一次 DOM 更新，所以看到的是「停一下、出一段」；空等时页面上只有三个点，没有任何阶段或时长信息。

修法两拍（纯前端，不动帧与端点）：

  • 状态行（A1）。 Bubble / ToolCard 各记一个 startedAt（进入 streaming、调用帧到达时打点）；正文空且没有在跑的工具时显示「● ● ● 正在思考 · Ns」，工具在跑时秒数挂到卡片 chip（「执行中 · Ns」），工具都回执了还没出字显示「正在继续 · Ns」；正文一出，点和状态行同时消失，只留光标。计秒用 1s 时钟，只在存在 streaming/offline 气泡时跑，收口即停。
  • 自适应轮询（A2）。 上一拉有帧 → 150ms 后再拉；空拍 → 400ms。冗余 status 核对从「每 5 拍」改成「每 ≥2s」（按拍数算会在有帧时变成 0.75s 一次）。

实测（同一模型同一提示）：正文刷新间隔中位 162ms、每次 25 字（改前 ~400ms / ~90 字）；bash sleep 6 一轮里空拍 407–423ms、有帧拍 156–164ms，session 核对间隔 2.1s / 2.1s / 1.8s。npm run typecheck 通过。

3. Loop B · 产出可达

B1 · agent 产出的文件，用户拿不走（P0）

病灶。 用户让模型「把结果写成 report.md」，模型说写好了。然后没有然后：

  • 项目页只列项目与项目下的会话，不列项目目录里的文件；
  • 聊天里那行 report.md 是个 .bubble-file 文字片（App.vue:925），不可点击；
  • GET /api/media 挂着 authn 中间件要 Bearer 头，用户右键另存、贴进新标签页都会 401。

agent 干完活，成果锁在服务端目录里，用户唯一能带走的是模型复述的那段话。

关键事实（决定了这条要多少工作量）。 getMedia（server.go:1278）的 path 形如 workspaces/<wid>/<相对路径>：它先 parseSessionMediaPath 拆出 wid，再 VisibleWorkspace 校验项目可见性，然后把 root 设成项目目录、rel 设成 wid 之后的相对路径，最后过 resolveInWorkspace 那把围栏。也就是说 GET /api/media?path=workspaces/<wid>/report.md 今天就能读到 agent 写出的文件。

所以 B1 缺的只有两样：① 一个「列目录」端点；② 前端的一个入口。 字节取用复用现成的 GET /api/media，不新开下载端点。

做什么。

① 后端新增一个端点（本篇唯一的全新端点）：

GET /api/workspaces/:id/files?path=<相对路径，默认 ".">
  • 成功体：{"code":0,"message":"","data":{"path":".","entries":[{"name":"report.md","kind":"file","size":1234,"modifiedAt":"2026-10-23T…"},{"name":"sub","kind":"dir"}]}}
  • 围栏：复用 resolveInWorkspace(root, path)（filetools.go:33）——越出项目目录与绝对路径一律 400 111002「路径不对」（与 agent 侧工具同一把锁，还带符号链接逃逸检查，不新开一条能绕过的路）。错误码按现状取 111002，不是 111001：同一个 resolveInWorkspace 失败在 product_api.go 的 dev 文件端点上已经用 111002（codeBadInput「路径不对」），沿用同一个码，前端能复用同一套处理分支。
  • 可见性：先 VisibleWorkspace(ctx, wid, tenantID, userID)，看不见回 404 114001。
  • 内部目录不列：.media/（入口媒体，doc/32）与 .tako/（搜索截断落盘，doc/21 H3：<项目>/.tako/search/*.md）不进 entries。用户不需要看这两样，看了反而困惑。（更正：子代理 wire 不在项目目录——它在会话目录 .tako/subagents/，doc/39；这个端点碰不到它。）但 .media/ 里的图片仍然要能显示——见下条。
  • 符号链接不列：symlink 条目直接跳过。它可能指向项目外，列出来等于泄露「那边有什么」，而点进去 resolveInWorkspace 也会挡住——列了是坏体验，不列是安全。
  • 排序：目录在前，同类按名字升序（与 list_directory 工具口径一致）。
  • 大小与时间：size 是字节数，modifiedAt 是 mtime（ISO8601）。

② 前端（2026-10-23 已落地，web/src/ProjectsView.vue）：

  • 项目页每个项目卡片加一个「文件」区（默认收起，与「查看对话」并列的两个可展开区之一）。
  • 展开时 GET /api/workspaces/:id/files?path=.，列出条目；点目录 → 往下钻（面包屑：项目根 / sub）；面包屑可点回任意一层。
  • 取字节走 GET /api/media?path=workspaces/<wid>/<相对路径>（前端要带 Bearer，用现成的 authFetch）。因为要带 Authorization 头，不能直接把 href 指过去（浏览器直接导航不带 → 401），所以一律先 fetch 成 blob：图片出缩略图、文本出内容、其他给「下载」。
  • 「预览」按钮按扩展名白名单给（图片 png/jpg/jpeg/gif/webp/bmp/svg/ico；文本 txt/md/markdown/csv/json/log/yml/yaml/toml/html/css/js/ts/go/py/sh/xml/ini/conf）。为什么不看 Content-Type：/api/media 的 mime 表（mediaMimeByExt）只覆盖图片/pdf/音视频，.md/.csv/.txt 落到 application/octet-stream，blob.type 判断不出文本。服务端条目里也没带 mime 字段（那是字节出口的事），所以前端按扩展名近似——判错的后果只是「少一个预览按钮」，不会出错内容。
  • 文本预览最多显示 2000 字，超出部分提示「用下载拿全文」。

③ .media/ 的可达性（2026-10-23 已查清，开放项关闭）。 「内部目录不列」会让 .media/ 里的入口图片从文件浏览器里消失。查了落盘口径（media.go:69）：.media/ 里只有用户上传的入口图，文件名是内容寻址的 sha256[:16] + 扩展名（没有原名）；模型产出的图不走这里（模型自己 write_file 写进项目目录）。而入口图在聊天气泡里全部能看（App.vue 的 <img class="bubble-media">）。→ 不列 .media/ 不会让用户失去任何入口，这一条不用再改。

每一步的输入输出。

  • 输入：项目 id + 相对路径；输出：该项目目录下的直接子项清单。
  • 输入：workspaces/<wid>/<相对路径>；输出：文件字节（Content-Type 按扩展名，表外为 application/octet-stream，见 mediaMimeByExt）。
  • 前端把两者接起来：点文件名 → 取字节 → 图片内联 / 其他下载。

没它会怎样。 agent 的产出不可达。这个产品的价值主张是「agent 帮你把活干完」，干完的东西拿不走，价值就断在最后一步。

4. Loop C · 破坏性操作与文案

C1 · 默认项目跟普通项目长得一样（P1）

病灶。 系统「默认」项目在项目页里跟用户自己建的项目完全一样：有「删除」按钮、有改名按钮。点删除，弹窗先许愿：

「"默认"会被删除。项目里的 2 场对话会一起删除（保留窗口内仍可恢复）。项目目录里的文件会清掉。」

用户读完这段会以为文件要没了、点了「删除」，等来一句错误——服务端 auth.go:169 的 codeWorkspaceDefault = 114005 必然拒绝（我核对过服务端实现）。

为什么前端不知道哪个是默认项目。 api.ts 的 Workspace 类型注释写得很直白：「默认项目不单独标 isDefault，删除时靠 409 message。」于是前端只能等点了才知道删不掉。

做什么。

  1. 后端：GET /api/workspaces 的每个 workspace 对象加一个字段 "isDefault": bool（默认项目为 true）。加字段不改既有字段，是增量，不是契约翻转——但仍是字节变更，所以要进 expected.json + 19v6-04 同批改。
  2. 前端：
    • api.ts 的 Workspace 类型加 isDefault?: boolean。
    • 项目页：默认项目不渲染「删除」按钮（改成一句静态说明「默认项目不能删除」），「重命名」也去掉（改名默认项目没有意义，且会让用户失去「这是默认项目」的视觉标识）。
    • 项目名后面加一个「默认」徽标（跟「新对话落点」徽标同款样式）。
    • 「新对话落点」那一行的文案：「默认项目」改成「默认」，跟列表里的项目名对上（见 C4）。
  3. 保留后端 409 作为兜底（前端隐藏按钮不等于后端放松；老前端、直接 curl 仍要撞 409）。

没它会怎样。 每个新用户第一次进项目页，都会看到「删除」按钮加一段会清空文件的许诺，然后失败一次。

验收。 字节：GET /api/workspaces 的 workspaces[] 里默认项目那一项含 "isDefault":true，其余含 "isDefault":false；浏览器：默认项目卡片上没有「删除」按钮，有「默认」徽标。

C2 · 密钥 •••• 是真实值，改一下就写成垃圾（P1）

病灶。 Configure.vue:255 把密钥值设成字面量 '••••' 存进 row.value，同时 row.masked = true。用户在那个输入框里改字时，@input 只做 row.masked = false（Configure.vue:493），不会清掉已有的 '••••' 占位符。用户手一抖就是在 •••• 后面续写，保存进去的密钥变成 ••••sk-xxxx——带占位符前缀的垃圾值，这把密钥就此失效。

还有两条并行的删除路径：文案只说了「把格子清空再保存，会删掉它」，但界面上还有一个「移除」按钮（Configure.vue:494）直接 splice 掉那一行、没有任何确认。用户以为「移除」只是把它从列表里拿走，保存后它真的被删了。

做什么。

  1. 密钥值不再是输入框里的真实值。 改成 type="password" 的输入框 + 一个独立的「显示/隐藏」按钮（像登录页的密码框那样，App.vue:842 已有这个模式，直接抄）。
    • 服务端返回 •••• 时：输入框留空，placeholder 写「已保存（留空则不改动）」。
    • 用户输入了内容 → masked = false，保存时用用户输入的值。
    • 用户没输入 → 保存时传 ••••（服务端认这个占位符、保留原值）。
    • 这样「输入框里有什么」与「保存什么」永远是同一件事，占位符永远进不了真实值。
  2. 「移除」改名为「删除这把密钥」，并加二次确认（复用现成的 ConfirmDialog.vue）：「删掉 DEEPSEEK_API_KEY？保存后这把密钥不再可用，模型调用会失败。」
  3. 「清空格子删除」这条路径取消（已拍，2026-10-23）。因为 1 改完后，「清空」和「输入新值」不再能靠「格子是不是空的」区分了。所以：
    • 输入框留空 = 不改动（不是删除）；
    • 点「删除这把密钥」= 删除。
    • 一个输入框的「空」只该有一种含义。文案改成：「留空表示不改动；要删除请点删除按钮。」
  4. originalSecrets 那段「删除的行在保存时写 ''」的逻辑（Configure.vue:283）同步改成「只有显式点删除的行才写 ''」。

每一步的输入输出。 输入 = 用户在输入框里敲的字符（空 / 非空）；输出 = 保存请求里 secrets[name] 的值（非空=用户值；••••=不改；''=删除）。

没它会怎样。 用户改一把密钥，改完就再也调不动模型了，而且看不出是哪一步坏的（前端显示保存成功）。

验收。 浏览器活体 + 字节交叉核对：

窗口 A（浏览器）：团队 → 设置 → 密钥 → 在 DEEPSEEK_API_KEY 的值框里输入 sk-test123 → 保存
窗口 B（终端）：curl -s -H "Authorization: Bearer $TOK" "$BASE/api/tenants/$TID/runtime-config" | jq -c '.data.config.secrets'

期望：窗口 B 里 DEEPSEEK_API_KEY 的值不含 •••• 前缀（今天会返回 ••••sk-test123，这是 bug 的证据）。

C3 · 一个表单，一个保存按钮，藏在最后一个卡片里（P1）

病灶。 模型、密钥、MCP 三块共用一个 <form>（Configure.vue:481），「保存」按钮只出现在「自定义 MCP」卡片底部（Configure.vue:517）。用户改了个默认模型，要滚到页面最下面才找得到保存。而且「测试连接」按钮紧挨着表单内容，用户理所当然认为它测的是正在编辑的内容——而它测的是服务端已存的配置（testMcp 打 GET /api/mcp-status，读的是库里的配置）。

做什么。

  1. 每个卡片自带自己的「保存」。拆成三个独立的 <form>（模型 / 密钥 / MCP），各自一个保存按钮，卡片底部。
    • 「密钥」和「模型」的保存只提交自己那部分字段。
    • 「自定义 MCP」的保存只提交 mcpServers +（可选）测试。
    • 服务端 PUT /api/tenants/:id/runtime-config 是整体 PUT（Configure.vue:301），所以拆 form 后，前端在提交某一块时要带上其它块的当前值（不然整份配置被覆盖成空）。实现上：保留一份 cfg 状态，各卡片保存时组装完整请求体再 PUT。
  2. 「测试连接」挪到 MCP 卡片的顶部，并改名为「测试已保存的配置」。或者：改成测当前编辑内容——这需要后端给「未保存的 MCP 配置」开一个试连入口（后端加端点，超出本篇范围，不做）。所以本篇采用改名 + 挪位。
  3. 保存后不再自动 testMcp()（Configure.vue:313）——保存完自动测一次连接，会让保存这个动作变慢且可能拉起 MCP 子进程。改成保存成功后提示「已保存」。

没它会怎样。 用户改了模型但没找到保存 → 以为改了其实没改；或者点了「测试连接」看到「连接失败」，实际失败的是旧配置。

验收。 浏览器活体：改「默认模型」→ 不滚动就能看到「模型」卡片里的保存按钮 → 点它 → 刷新页面，模型仍是新值；改 MCP 但不保存 → 点「测试已保存的配置」→ 报的是旧配置的连接状态（且按钮文案明确写着「已保存的」）。

C4 · 「个人工作区没有成员」在 owner 视角下自相矛盾（P1）

病灶。 实测：当前租户 a7-envelope-test，kind=personal，而当前用户角色是 owner（侧边栏底部就写着「所有者」）。点「团队 → 成员」，整页只有一句：

「你就是所有者，怎么可能没有成员」——这句话是写给「个人租户不搞成员制」这个实现事实的，不是写给用户的。用户会当成 bug。

做什么。

  4. 项目页顶部那行「新对话落点」改名为「新对话默认进入」——「落点」是内部词。

没它会怎样。 新用户第一次点「团队」，看到一句自相矛盾的话；项目页上「默认项目」和「默认」两个词让人怀疑自己看错了。

验收。 浏览器活体：个人租户 → 团队 → 成员 → 看到「这是你一个人的工作区」；项目页 → 「新对话默认进入：默认」。

8.1 「清空密钥格子 = 删除」是什么意思

现在的界面长这样（团队 → 设置 → 密钥）：

密钥
格子里仍是 •••• 时，保存不会改这把密钥。把格子清空再保存，会删掉它。

DEEPSEEK_API_KEY  │  ••••  │ [移除]

三个事实：

  1. 格子里的 •••• 不是密钥本身，是服务端给的占位符，意思是「这把密钥已经存在，但我不给你看真值」。
  2. 今天的 •••• 是真的躺在那个输入框的 value 里。用户以为那 4 个点是遮罩、点进去会看到真密钥——其实点进去看到的就是 4 个点。
  3. 于是有两条删除路径，界面只用一句话带过：
    • 路径甲：把格子里的 •••• 删干净（留空）→ 保存 → 这把密钥被删除。
    • 路径乙：点「移除」按钮 → 那一行从界面上消失 → 保存 → 这把密钥也被删除（而且「移除」这个词听起来只是「从列表里拿掉」，没有任何确认）。

更要命的是第三条路径——用户想改一把密钥，不是删：

  • 他点进值格子，全选 ••••，敲下新密钥 sk-abc123 → 没问题，格子变成 sk-abc123，保存正确。
  • 但他没全选，只是在末尾接着敲、或者只删掉一个点 → 格子变成 •••sk-abc123 → 保存进去的就是这个带占位符前缀的垃圾串 → 这把密钥当场失效，而界面照样弹「已保存」。

所以这条要拍的是：输入框的「空」到底该表示什么。

  • 现状：空 = 删除（甲），外加一个「移除」按钮也 = 删除（乙），外加「空 = 不改动」这条只在一个字都没动的时候才成立——同一个状态三种含义。
  • 建议：输入框的「空」只表示「不改动」（这是绝大多数人改设置时的期望）；删除走单独的按钮 + 二次确认。这样「输入框里有什么」与「保存什么」永远是同一件事，占位符永远进不了真实值。

另外一条要你确认的（不算拍板，是澄清）：A2 我按「项目下挂对话的结构保留，只在对话页加一个『最近 10 场』的快捷入口」写。如果你要的是完整的项目-会话树也搬到对话页，那是另一套（侧边栏要变三栏），施工量翻倍，请明确说一声。

10.1 病灶：同一份 markdown，聊天里排好版，项目文件里是符号

用户在对话页让 agent 写一份说明文档。agent 写完，在回复里说：「文档写好了，见 docs/设计说明.md。」

用户点开那份文档。右侧工作区弹出文件标签，正文是这样的：

# 设计说明

## 背景

本系统需要解决三个问题：

| 环节 | 现状 | 目标 |
| --- | --- | --- |
| 拉取 | 轮询 | 增量 |

表格边框没了，标题跟正文一样大，# 和 | 直接摆在眼前。

用户想看的是排好版的文档，看到的是一堆符号。于是他不用文档了——他让 agent「把要点直接写在回复里」，或者下载到本地用编辑器看。文档写下来，没人看。

这不是「少了个功能」，是同一套能力已经存在、只是没接上：

  • web/src/markdown.ts 里早就有 renderSafe()（marked 解析 + DOMPurify 消毒），聊天气泡与任务交接正文都在用；
  • 而项目里的两个文件视图，一个把 .md 归进 TEXT_EXT 后用 <pre> 吐原文，另一个同样。

同一份 markdown，聊天里是排好版的，项目文件里是符号。

入口 代码位置 改前的样子 谁在用

10.3 做了什么（每一步：做什么／为什么／输入从哪来／输出到哪去）

第 1 步 · 判定：哪些文件按 markdown 渲染。 按扩展名，只有 md 与 markdown 两个。

  • 为什么按扩展名而不看 Content-Type：/api/media 的 mime 表只覆盖图片/pdf/音视频，.md 落到 application/octet-stream，blob.type 判断不出文本。
  • 为什么只这两个：json/yaml/csv 这些也在 TEXT_EXT 里，但把它们当 markdown 渲染是倒退——散文排版套在数据文件上，读不懂。
  • 输入 = 文件路径（两个入口各自已有）；输出 = 一个布尔「这是不是 markdown」。

第 2 步 · 渲染：复用 renderSafe()，不新写解析器。

  • 为什么不新写：① 安全口径已经过验收（DOMPurify 那一步本就是为「模型写进来的原始 HTML 不能被执行」加的，md 文件同样是外部内容：agent 写的、用户上传的，一样可能有 <script>、onerror）；② 不引新依赖（marked + dompurify 已在 package.json 里）；③ 裸链接的中文标点处理白捡（markdown.ts 那条 CJK_STOP 规则是为中文句子里的裸链接写的，项目里的 md 多半是中文）。
  • 换行规则分家：聊天气泡用 breaks: true（模型输出常把一句拆成多行，不折行会挤成一坨）；md 文件用 breaks: false（文件里的换行是作者排版的结果，标准 markdown 语义下单个换行不等于换行，GitHub 的 README 就是这样渲染的）。
  • 实现上不能改全局 setOptions（改了会把气泡的换行规则一起带跑），而是给渲染函数加一个可选参数：renderMarkdown(text, opts?) / renderSafe(text, opts?)。marked 的 parse(src, opts) 是「全局默认值 + 本次 opts」合并（{...this.defaults, ...opts}），per-call 覆盖不回写全局——所以传过 { breaks: false } 之后，默认渲染仍是 breaks: true。
  • 输入 = 文件字节（取字节的路径一个字没变：仍是 GET /api/media，带 Bearer 头）；输出 = 一段已消毒的 HTML 字符串。

第 3 步 · 样式：抽成全局一份，三处共用。 新建 web/src/markdown.css，类名 .md-body。

  • 这一步最容易做错：Vue 的 scoped 样式只作用于本组件的元素。气泡那套排版原先写在 App.vue 里、选择器是 .bubble-text :deep(h1)——直接复制到 WorkspaceFileView.vue / ProjectsView.vue 里，一条都不会生效（scoped 的 data-v 属性不在别人组件的元素上）。所以排版必须抽到全局样式表，用一个中性类名承载，三个入口挂同一个类。
  • 气泡专属的不搬：用户气泡是深色底，那套「浅底深字」的反色覆盖（.bubble.user .bubble-text :deep(code) 等）留在 App.vue 不动——搬过来会让用户气泡的代码块变浅色，那是视觉回归。
  • 为什么不用 .bubble-text 当类名：气泡样式带着用户气泡的深底覆盖，与文件视图的浅底排版不是一回事，混在一起会互相污染。
  • 没它会怎样：三个入口各写一份 :deep() 段，前两份根本不生效（用户看到的还是没排版的符号），第三份生效——同一个产品里两种排版。

第 4 步 · 截断先于渲染。 顺序是「取字节 → 截断 → 渲染」，不是「渲染 → 截 HTML」。

  • 为什么：markdown 渲染后再截，会拦腰砍断表格与代码块——半张表比显示原文更糟。截断拿到的是纯文本，渲染的是截断后的结果。
  • 上限沿用现状，不新造：项目页 2000 字（超出照旧显示「…（还有 N 个字，用「下载」拿全文）」）；对话页右侧 256KB（超限仍走「不能内嵌预览」那一档）。

第 5 步 · 安全：不多开一个口子。

  • md 内容走 DOMPurify.sanitize（与聊天气泡同一条管线 = 同一份保证），<script>、onerror、javascript: URL 一律剥掉。
  • 相对图片保持原样：md 里写 ![](logo.png) 时 marked 出的 <img src="logo.png"> 是相对路径，找不到就是坏图。本次不做路径改写（属独立一拍），但不许把 src 改成一个会 401 的 /api/media URL——那会制造一堆坏图请求；坏图显示浏览器的默认占位。
  • 不把 token 拼进 URL（包括给图片造 /api/media?access_token=）：字节出口挂在 authn 上，前端不新增任何绕过鉴权的取字节方式。
