77 · 对话页右侧任务面板

性质：方案（已落地）。把当前项目的 Task 从「必须切到任务页才能看」变成对话页右侧常驻面板。 状态：✅ 2026-11-13 落地（未 commit，等验收）。npm run typecheck / npm run build 通过；headless 走查覆盖展开／收起＋刷新保持、详情抽屉、任务页互不弹重复抽屉、项目跟随（30 条任务的项目）、聚焦重拉、800px 隐藏无横向溢出、任务页回归；go test ./internal/runengine 通过。处理条用一个 route 替身注入 plan_review（指向真实编排组）验证了「点击在页内开详情」，没有用真实待办验（dev 库四个项目的 task-attention 当前都是 0）。走查还发现并修掉一个布局错误：面板最初直接挂在纵向 flex 的 .stage 下，掉到输入框下方、收起按钮被 composer 挡住，补 .chat-wrap 横向外壳后归位。 代码落点：web/src/App.vue（.chat-wrap 布局与面板壳）、web/src/TasksView.vue（嵌入模式）。无后端改动。 前置真源：doc/70（持久 Task 与 DAG）、doc/72（有界修订、Task HITL、左侧处理项）、doc/73（交付失败恢复）、doc/74（发布受阻）、doc/75（计划待决策）、doc/60（多会话实例）、doc/51（视觉基线）。 边界：只加一个读取／操作入口，不改 Task 的存储、状态机、调度与任何 API 字节。 2026-11-13 部分被 doc/78 取代：§3 第 4 条「不把 Todo 合并进面板」作废（Todo 进右侧工作区标签，桌面端输入框上方不再保留）；其余条款（面板跟当前项目、详情抽屉复用、定位 nonce 互斥、≤860px 不渲染）仍现行，并在 doc/78 中按多标签工作区形态继续有效。

1. 病灶：任务在后台跑，人却得离开对话去看

一场真实的使用：

用户在对话里让助手派发三件 Task（A 调研、B 调研、C 汇总）
→ 助手回一句「已派发」，继续聊别的事
→ 用户想知道 C 什么时候开始、A 有没有卡住
→ 必须点左侧「任务」→ 选项目 → 找到那一行 → 看完
→ 想接着聊，再点回对话，会话上下文和输入草稿的位置都要重新找

更糟的是需要人处理的时候。doc/72 已经把这些时刻聚合到左侧「任务」入口：计划停在检查点等你决策、Task 在提问、执行中断、交付失败、发布受阻。但左侧只给一行标题和一串计数：

  • 计划待决策只显示组 id 与计数，看不出停在哪一步、哪件 Task 已完成；
  • 待回答只显示「待回答（2）」，看不到问题本身；
  • 用户往往要在「对话」和「任务」两个页面之间来回跳几次，才能把一件事看完、答完、继续聊。

Task 是异步的：派发在对话里，执行在后台，结果回到对话。可观察面却只在另一页，链路在「看」这一环断了。

2. 完成线

  1. 对话页右侧出现一个当前项目的 Task 面板，桌面端默认展开，可收起；收起后留一个带处理项计数的窄条入口。
  2. 面板列出该项目全部 Task（与任务页同一份数据、同一个排序）：key、状态、执行者、内容摘要、更新时间；有「需要我处理」时先显示处理条。
  3. 点一条 Task 在当前页打开与任务页相同的详情抽屉：任务详情、编排组视图、计划修订、Task 问题、停止／恢复、发布面板、交接文件——不复制第二套实现。
  4. 点处理条（待回答／计划待决策／已中断／交付失败／发布受阻）在对话页内直接打开对应详情；「协调 run 中断」仍按 doc/73 进来源会话。
  5. 新 Task、状态推进、新提问、计划暂停都由既有事件驱动自动出现，不需要手动刷新；重连事件流或窗口重新聚焦后从服务端重建。
  6. 切换会话／项目时面板跟着当前对话的项目走；切换对话实例不残留上一场的列表。
  7. 宽度 ≤860px（与现有移动断点一致）时不出现面板，对话布局与今天一致。

3. 非目标

  • 不做按会话过滤：面板跟当前项目，不跟某一场对话。理由：编排与 Task 本来就是项目级对象，一个项目下的多场对话可以共同推进同一组任务；只看本场发起的任务，会在切换会话时凭空「丢」任务。 2026-11-14 更新：本条已被 doc/80 取代——面板/任务页默认看「本会话」，可一键切「本项目全部」；GET /api/workspaces/:id/tasks 新增可选参数 sessionId（不传=全部、非空=按来源会话过滤、未知会话=200 空列表），处理条仍项目级聚合。
  • 不做 Task 创建／编辑表单：创建仍只由对话里的助手用 delegate_task／create_orchestration 发起（doc/70 §11 的边界不变）。
  • 不做面板拖拽调宽、不做第二个通知中心、不做未读表。
  • 不把「Todo」（run_tasks，doc/41：一场 run 内的待办）合并进面板。两者仍分开：Todo 在输入框上方，任务是右侧项目面板。 2026-11-13 更新：本条已被 doc/78 §4.5 取代——桌面端 Todo 进右侧工作区的「Todo」标签（读 GET /api/runs/:id/tasks，刷新后仍在），输入框上方的 Todo 条只在 ≤860px（工作区不渲染时）保留。

4. 已拍定的设计选择

4.1 嵌入现有任务页，而不是新写一套列表与详情

任务页的详情抽屉承载了六七块互相咬合的逻辑：编排组视图、计划修订时间线、Task 问题作答、停止确认、恢复、发布重试、继任组交接。任何一块在右侧面板里重写一遍，都会在下一轮改协议时变成两份要同步的代码。

因此面板不是新组件，而是给 TasksView.vue 加一个 embedded 模式：隐藏页头（标题、说明、项目选择器），保留列表、筛选、详情抽屉与全部操作；抽屉本身是 Teleport to body 的全屏浮层，放在对话页里打开时覆盖整页，不受面板 22rem 宽度限制。

没这么做会怎样：要么面板只能「看」不能「处理」，用户还是得跳页；要么两套详情各自实现，第一次协议变更就漂移。

4.2 面板跟当前对话的项目

2026-11-14 更新：本节被 doc/80 §4.3 取代——面板仍以「当前项目」为容器（workspace 不变），但列表默认显示本会话派发的任务，可一键切「本项目全部」；换会话时嵌入的任务页按 workspaceId:sessionId 重挂载。下面这段「按项目 id 设 key、换项目即重挂载」仍成立，只是 key 里多了会话 id。

App.vue 的当前项目来自活动对话实例（doc/60 的单主视图 + 后台实例）。面板复用左侧处理项已有的项目解析（活动项目不在清单里时回退默认项目），并给嵌入的任务页按项目 id 设 key——换项目即重挂载，列表、搜索、已打开的抽屉一起重来，不留下上一项目的行。

4.3 刷新靠既有事件，不新增轮询

嵌入的任务页已有 agent_tasks_changed／agent_orchestrations_changed 订阅（收到即重拉）；对话页本身在同样的事件上重拉处理条。补两条现有页面没覆盖的时机：事件流重连、窗口重新聚焦时也重拉一次——否则断线期间发生的推进要等到下一条事件才可见。

4.4 处理条复用左侧同一份聚合读面

面板顶部直接渲染 GET /api/workspaces/:id/task-attention 的结果（App 已为左侧入口拉取），点击走与左侧相同的处理语义；区别只是「打开」发生在对话页内：写面板自己的一份定位参数，由嵌入的任务页消费并打开抽屉，而不是 goPage('tasks')。

面板与任务页各用一份定位参数（nonce）互不消费：对话页是 v-show 常驻，若共用一份，左栏点击处理项跳任务页时，对话页里隐藏的面板也会弹出一张重复抽屉；反过来，回到对话页时也不该重弹任务页刚用过的定位。

4.5 收起态与持久化

  • 展开时宽 clamp(18rem, 24vw, 22rem)，左边框分隔；对话区继续用现有铺满布局。
  • 头部有「收起」；收起后右侧留一条 2rem 窄条，竖排「任务」+ 处理项数字，点开恢复。
  • 状态存 localStorage（tako.chatTaskDock），默认展开。项目切换不重置该偏好。
  • 面板内列表独立滚动（与对话列表各自滚动）：两栏高度都钉在视口上，任务多时不挤占对话。这是列表自然增长时的取舍，不用分页。

4.6 移动端不出现

≤860px 时对话页保持单列，右侧面板整体不渲染（CSS 隐藏 + 收起态窄条也不显示）。移动端仍走左侧抽屉里的「任务」入口，与今天一致。

5. 复用的既有契约（不改字节）

用途 现状
项目 Task 列表 GET /api/workspaces/:id/tasks，created_at/id 倒序，全量
处理项聚合 GET /api/workspaces/:id/task-attention（五种 kind，doc/72 §4.6、doc/74 §4.6）
任务详情／编排组／修订／问题／停止／恢复／发布重试／交接 任务页当前使用的端点，一个不增
变更通知 账号级 SSE：agent_tasks_changed、agent_orchestrations_changed（doc/46 §7.7）

结论：这是纯前端施工，不改任何请求／响应／帧字节，不需要重跑契约验收。

6. 验收

前端构建与活体走查（详见施工包）：

  1. npm run typecheck、npm run build 绿。
  2. 对话页右侧默认出现面板，列出当前项目任务；收起／展开在刷新后保持。
  3. 在对话里派发一件 Task，面板在事件到达后自动出现该行，不手动刷新。
  4. 点行打开详情抽屉（任务详情与编排组视图都可进出），Esc 关闭。
  5. 造出「计划待决策」或「待回答」处理项，面板顶部显示；点击在对话页内打开对应详情。
  6. 在对话页点左侧「任务」里的同一处理项 → 仍按原行为跳任务页，不出现第二张抽屉；从任务页回到对话页时也不自动重弹。
  7. 切到另一项目的会话，面板只列该项目任务；切回恢复。
  8. ≤860px 视口无面板、无横向溢出；任务页本身行为不变（选择器、左侧定位、详情）。

7. 边界与风险

  • 面板与任务页同时挂载时会各自订阅事件、各自拉一次列表；事件已有 120ms 去抖，量级可接受。只有对话页打开且面板展开时才多一份开销。
  • 详情抽屉从面板打开时覆盖整页，这是有意的：处理 Task 时对话退到背景，关闭后回到原位置，不丢草稿（草稿在对话实例里，不受面板影响）。
  • 若未来给任务列表加分页或按会话过滤，应改在服务端契约里做，不在面板里做第二套。

8. 所以这解决了什么

用户在对话里派发任务，执行发生在后台；现在看状态、答问题、做计划决策、恢复中断都能在同一页完成，不需要在两个页面之间搬运上下文。任务页仍然保留，承担项目切换、筛选与更完整的说明，但不再是「看一眼」的唯一入口。
