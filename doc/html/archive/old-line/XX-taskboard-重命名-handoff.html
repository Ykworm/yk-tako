Handoff · 包重命名：taskboard → tasktracker

性质：纯 handoff 文档。不改动任何代码；记录本次命名对话的决策背景、 被否决的候选、影响面清单、以及逐文件的操作步骤，留给后续执行重命名时对照。

触发对话（2026-09-30）：用户先问 taskboard.go:L1 有什么用 → 引申到「包名不合理」 → 排查与 eino plantask/Claude Tasks 的概念冲突 → 否决 tasks（概念歧义）、 planning（反三层分离、且与已删除旧包同名）、ledger（联想财务）、 board（联想前端 dashboard）→ 终定 tasktracker。

1. 决策：为什么是 tasktracker

1.1 三层分离约束（硬边界）

三层分离写死在 internal/taskboard/taskboard.go#L5-L6 及 doc/07 §4.1：

层 含义 命名禁区
Plan 给人审的方案（动手前拆步骤） ❌ 不能沾 plan/planning
Tasks 施工期勾选看板（开干后跟踪状态） ✅ 包名必须落在这一层
Actions bash/文件读写等干活工具 ❌ 不能沾 action/exec

1.2 被否决的候选（每次否决都是心智雷区）

候选 否决原因 谁的直觉
taskboard board 会联想到「前端 dashboard / UI 面板」，掩盖「跟踪施工状态」的核心职责 用户（核心否决）
planning 指 Plan 层，直接违背三层分离；且与 2026-09-26 删除的旧 internal/planning 同名，历史混淆 用户+文档
tasks 与 eino plantask、Claude Tasks 概念撞脸，每次读代码要做「哦是第三种 task」的消歧 用户+我们在 §2 一起确认
ledger / account 强联想「财务、钱」，虽然工程界有「事件流水账=ledger」的泛义，但压不过用户的先验语义 用户（核心否决）
dashboard / panel 纯 UI 概念，比 board 更坏 直接排除
kanban 比 board 好（是方法学不是 UI），但中文心智里仍是「看板=墙上那块板」，且用户没提这个词 保留但不推荐
worktrack 弱化了 task 前缀，但对外工具名是 TaskCreate/TaskUpdate（给模型看的），包名 vs 工具前缀拧巴 保留但不推荐

1.3 tasktracker 终定理由

  • 无语义冲突：软件工程界 bugtracker / issuetracker / tasktracker 用法现成， 没有人会把 tracker 联想到前端 UI 或财务账。
  • 过程语义精准：track 直接对应 pending → in_progress → completed 的状态跟踪动作； 既不是「规划前」（planning）、也不是「展示」（board）、更不是「账」（ledger）。
  • 与工具名自洽：对外工具名 TaskCreate/TaskUpdate/... 前缀是 Task，包名 tasktracker 前缀一致， Go 代码里看到 tasktracker.NewStore() 和模型看到 TaskCreate 不会产生两套心智。
  • 不撞历史：仓库里从未出现过 tasktracker，git 考古不串台。

4. 风险点清单

风险 概率 应对

5. 本次对话的决策摘要（防止将来又绕一圈）

核心分歧：board → 你联想「前端 dashboard」；ledger → 你联想「财务账」； planning → 违背三层分离且踩历史包名；tasks → 与 eino/Claude Task 概念消歧成本高。

收敛标准：命名必须是「软件工程有现成先例」「不占用你的已有语义雷区」「落在 Tasks 层（施工跟踪）」。 满足全部三条的只有 tasktracker（参考 bugtracker/issuetracker 用法）。

对外协议不动：TaskCreate/TaskUpdate/TaskList/TaskGet 四个工具名（给模型的）、 pending/in_progress/completed/deleted 状态值、EventBoard 呈现类别标签—— 这些都不是 Go 包名层面的事，本次不碰。
