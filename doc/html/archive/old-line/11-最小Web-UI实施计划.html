3. T1 事件 sink 重构 ✅（2026-09-26 完成）

目标（《10》§4.1）：adkrun 只产生结构化事件，呈现归 sink；判定标准—— 重构后 adkrun 不再自己决定输出到哪，REPL 退化成第一个 sink。

3.1 侦察结论（已核实的事实，实现时直接用，不必重查）

  1. adkrun.Run 调用方只有 2 处：cmd/yktako/main.go:106、internal/adkrun/turn_test.go:61。 taskboard 集成测试直接用 runner.Run（integration_test.go:178/215/244），不受签名影响。 → 加 sink 参数只改这 2 处。
  2. REPL sink 不能进 internal/repl：该包头注释承诺「与 Eino 无关」（repl.go:1）， 而 sink 实现要 import adkrun（进而拉入 Eino），会破坏承诺。→ 落点候选： cmd/yktako（消费方，最贴合「呈现归消费方」）——已定：cmd/yktako（P2 关闭， 理由记在 sink.go 注释）。
  3. Sink 用函数类型：包内已有先例 type Ask func(info guard.ApprovalInfo) (string, error) （turn.go:66），单方法无状态，函数类型足够，不必定义 interface（也就不需要编译期断言）。
  4. eino 类型事实（go doc 核实，v0.9.21）：
    • adk.MessageVariant = TypedMessageVariant[*schema.Message]，关键字段 Role / ToolName （Role==schema.Tool 且 ToolName 非空 = 工具回执）；
    • schema.ToolCall.Function 是 FunctionCall{Name, Arguments}；
    • schema.Message 自带 ToolName 字段，构工具消息用 schema.ToolMessage(content, id, schema.WithToolName(name))。
  5. 重构前分类逻辑的位置（拆分依据）：printMessage（turn.go:157-193）实际 3 个分支—— ① ToolCalls → 调用；② Role==Tool → 回执（IsBoardTool 再分看板）；③ Content → 正文。 「子代理前缀」（agentName != root）只是修饰，不是独立分支。3 支映射《10》§4.2 的 message / tool_call / tool_result / board 四类（看板是回执的子类）。 §4.2 另外两类不在 printMessage：approval 来自 interrupt（turn.go:142-151）、 error 来自 event.Err（turn.go:129-131）——产出点归属见 T1.1 的口径。
  6. 测试素材可复用：taskboard/integration_test.go 的 scriptModel + toolCallMsg 模式 能构造「调工具 → 回执 → 收尾」的真实事件序列；turn_test.go 的 fakeAgent 走的是 Run 入口，直接可用。
