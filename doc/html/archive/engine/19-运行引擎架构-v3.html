19 · 运行引擎架构 v3（设计草稿）

v3 是文档版本，不是软件版本。它描述的是一个完整的设计方案。§9 的「阶段」是方案内的实施顺序（先做什么、后做什么），不是软件发布阶段或开发阶段。

v3 的变化：v2 把「一次执行」拆成了四个职责单一的组件，但入口仍然是 POST /api/chat → SSE 流，也就是**「输入」与「执行」是同一个动作**。 v3 把这两者解耦：POST 只负责投递，执行由调度器决定何时发生。

这不是推翻 v2。 v2 的 Event、Subscription、RunLog（run 级）、 Archive、Approval、Checkpoint 全部原样继承，已并入本文 §4.1–4.4、§4.10–4.11。 v3 只重写三处：Engine 的生命周期入口（§4.8）、Transport 的路由与响应形态（§4.12）、 以及新增两个组件（Inbox §4.6、SessionLog §4.7）。执行链路（drive 的 stream 循环、 A/B 两路、compact 补偿事务）不动，见 §5.3–5.6。

v3 内部分两个阶段（§9）：阶段一（第 1–13 步）只改入口与调度，数据面沿用 v2 的 Event 帧（Partial/sealed）；阶段二（第 14–18 步）按 §11 的增量协议重写数据面 ——帧的含义从「发生了一件事」变成「某实体的某字段变成了这个值」，正文 op:"append" 只推增量（O(n²) 重发 → O(n)），Partial/sealed 整套机制退役，崩溃窗口（§10 问题 7） 结构性消失。分阶段不改变「数据面重写量级独立」的判断（§11.5），改变的只是路线图位置： 它是 v3 的第二阶段，不是另一个版本。

性质：设计草稿，未实施。重写，不是重构。 术语：message 指用户投递的一条输入；run 指一次执行；一场 run 可能消费多条 message。 诊断依据：见《会话级并发：从 409 到收件箱》访谈稿（含 Kimi 实测与代码位置对照表）。

1. 三真源（v2 是双真源）

v2 有两条真源。v3 在会话粒度上再加一条，另有一个暂存区：

run_log run_archive session_log inbox
粒度 run run 会话 会话
回答的问题 这场 run 发生过什么 下一轮该给模型看什么 这个会话发生过什么 还有哪些话没被回答
写规则 只追加，永不改 可改写（compact 破坏性覆盖） 只追加，永不改 可变：行会被消费或删除
读者 人 / UI / 回放 / 对账 LLM UI / 多客户端同步 调度器
seq 命名空间 per-run — per-session per-session（仅排序用）
生命 永久 永久 永久 短暂：消费即删

为什么 inbox 与 session_log 是两张表而不是一张？

因为它们的写规则相反。session_log 是事实（只追加，回答「发生过什么」）， inbox 是状态（可变，回答「现在还有什么没做」）。硬合成一张就得在事实表上 做 UPDATE（标记 consumed），破坏追加式纯净性；或者用「追加一条 consumed 事件、 读时做差集」，把简单查询变成折叠计算。分成两张，各自的语义都干净—— 这与 v2 §2 把 run_log 和 run_archive 分开的理由是同一个。

inbox 被消费后，「m1 曾排队过」这个事实不会丢：它在 session_log 里有 message_queued 帧，在 run_started 帧的 messageIds 里也有一份。 所以断线重连的客户端能完整重建时间线。

推论（继承 v2 并扩展）：不能从 run_log 重建模型上下文（压缩是有意的信息销毁）； 也不能从 session_log 重建 run 内容（它只记「发生了什么」，不记「产出了什么」）。 四份存储不是冗余，是四种不同的东西：run 级事实 / 当前模型视图 / 会话级事实 / 待办队列。

2. 不变量

v2 六条。v3 删 1 条、扩 2 条、增 3 条。

# 不变量 v3 状态
1 run 的命不属于任何连接。runCtx 是进程 ctx 的子 ctx；浏览器关掉、刷新、断网，run 照跑、帧照落库。只有 Stop 能取消它。 不变
2 库操作一律用进程 ctx，绝不用请求 ctx。 不变
3 先落库，再推浏览器。 扩展：也包括「先落库，再回 2xx」。用户打的字比输出帧更贵重——丢一帧输出可以从库补，丢一条用户输入无从恢复。
4 seq 是唯一的续传坐标。 扩展：现在有两个独立的 seq 命名空间（run 级、会话级），各自续传，互不换算。
5 终局唯一。Finish 在一个事务里写终局帧 + 改 status，之后 Append 直接拒绝。 不变
6 响应三态不得跨越：未提交 / 已提交 / 已结束 删除。投递永不冲突（不变量 7），没有需要在写 header 前判完的状态；POST /api/message 也就用不着返回流了。注意因果方向：不是「因为不返回流所以不用判」，而是「因为没有冲突可判所以不必返回流」。返回流本身无罪（§11.4：外部产品的数据面就是流式 POST）。
7 投递永不因状态冲突失败。Enqueue 只可能因存储故障失败（500），绝不会因为「会话正忙」被拒。忙是调度器的内部事实，不是 API 层错误。 新增
8 放闸与调度必须原子。drive 收尾时，「置 live = nil」与「检查 inbox 是否非空」必须在同一个临界区里完成。 新增
9 runID 只在事务提交后才对外可见。发布 runID 的那一帧（run_started）与 run 的档案行、start 帧在同一个事务里写入。 新增

不变量 8 为什么是硬要求：如果放闸和查收件箱之间有窗口，那么正好落在窗口里到达的 消息会永久搁浅——它入队时看到闸是 occupied（所以没触发调度），而收尾时查收件箱 又发生在它入队之前。除非下一条消息到来，它永远不会被执行。这是经典的 「signal lost between unlock and wait」竞态，只能靠原子性解决。伪代码见 §4.8。

不变量 9 消灭了 v2 遗留的一个窄竞态：v2 里 LiveRunID() 在占闸那刻就有值， 而档案行要等 BeginRun 才写；这个窗口内客户端拿到 runID 去订阅会吃 404 （诊断见《会话级并发》§2.1）。v3 里客户端只可能从 run_started 帧得知 runID， 而那一帧与档案行同事务提交，窗口不存在。

4. 组件详细设计

4.0 三级订阅：先说使用场景，再说结构

先说一个容易踩的语义陷阱。如果把投递接口（POST /api/message）的含义定义成「开一场 run」， 那么会话正忙时这个含义无法兑现，只能用状态码拒绝（409）；而 POST 又要返回流、状态码只能提交一次， 于是 409 必须赶在写 header 之前判完——输入与执行就此绑死，「你输入的时机不对」被迫表达成一个 HTTP 错误：

POST 的含义是「开一场 run」
  → 会话正忙时这个含义无法兑现
    → 只能用状态码拒绝（409）
      → 而 POST 又返回流，状态码只能提交一次
        → 409 必须赶在写 header 前
          → 投递入口必须同步完成占闸 + 开跑
            → 输入与执行绑死

根因不在实现，在语义。 把 POST 的含义从「开 run」改成「投递」，整条约束链自然消失： 投递永不失败，没有冲突需要表达，409 这个概念不存在（不变量 7）。

罪不在「返回流」本身——外部产品的数据面恰恰就是流式 POST（§11.4）。有罪的是 流的寿命被绑死在一个 runID 上，以及 POST 的含义是「开 run」而非「投递」。 把这两点改掉，返回不返回流是自由选项。

由此得到一条贯穿本节的判断：

当有了一条常开的控制面通道，单次请求就不再需要承载状态语义。 「正忙」「已排队」「已开始」从「HTTP 状态码」降级成「流内状态」——客户端本来就在监听。

那么这条常开的控制面该推什么、推给谁？「为什么不止一条流」这个问题，答案不在架构里， 在谁需要知道什么里。先把场景摊开：

# 场景 谁需要知道 需要知道什么 这信息属于哪场 run
1 A 在页面里发了一句，等模型逐字回答 A 这一场的正文、工具调用、看板 r_17
2 A 刷新了页面，run 还在跑 A 从上次断点续上 r_17 r_17
3 B 打开着同一个会话，A 发了一句 B 「有人投递了 m_1」「r_17 开始了」 不属于任何 B 已知的 run
4 r_17 跑完了，调度器合并 m_2+m_3 开了 r_18 A 和 B 「r_17 落幕了」「r_18 开始了，runID 是这个」 r_18 此刻还不存在于任何客户端
5 B 在会话列表里删掉了这个会话 A 「这个会话没了，你正在看的 run 被停了」 属于账号，不属于会话
6 A 在 APP 上发了消息，网页端会话列表要冒出新条目 网页 「多了一个会话」 属于账号

第 3、4 行是决定性的。 这两条信息不属于任何客户端已经知道的 run， 所以它们在 run 级流里没有位置可放——run 级流的地址空间是 (runID, seq)， 而「r_18 存在了」这句话本身是客户端获得 r_18 这个 ID 的前提。 用一个尚不存在的 runID 去订阅它自己的诞生通知，是循环依赖。

第 5、6 行再往上推一层：会话的增删本身也不是会话级事件，是账号级事件。

于是粒度天然是三级：

级别 订阅键 生命周期 推什么 tako v3 Kimi
账号级 userID 与登录态同寿 会话列表增删改、跨会话通知 不做（单用户，会话列表在 localStorage） WS topic
会话级 sessionID 常驻，页面开着就在 投递、排队、撤回、run 开始/落幕 GET /api/session/stream WS topic
run 级 runID 一场 run 的寿命 正文、工具调用、看板、审批 GET /api/chat/stream 流式 POST 的响应体

注意 Kimi 把账号级和会话级复用在同一条 WS 上（多路复用），tako v3 只做到会话级。 这不是偷懒：v3 的会话列表在前端 localStorage 里，没有服务端实体， 所以账号级订阅无源可订。要做它得先把会话提升成服务端资源（见 §10 问题 9）。

由此得出的两条物理连接（v3 的选择，代价见 §7.1）：

① POST /api/message          ───▶ 投递，短请求，JSON 应答，永不因状态冲突失败
② GET  /api/session/stream   ───▶ 会话级订阅，常驻，只收「发生了什么」的通知
③ GET  /api/chat/stream      ───▶ run 级订阅，收到 run_started 才挂，收内容

②③ 是两个逻辑通道。它们是否必须是两条物理连接，是另一个问题—— 浏览器对同一 host 的 HTTP/1.1 并发上限是 6，SSE 会长期占坑 （2 个标签页 × 2 条 SSE = 4 个坑），这个缺陷只在多标签页下暴露， 而多标签页正是本次要修的场景。§11 记录 Kimi 的替代拓扑。

三个通道的技术差异，是拆分的后果，不是拆分的原因：

会话级 run 级
Partial 帧 无（通知是一次性的，不存在「半个通知」） 有，且需要预留号 + sealed 机制
游标 per-session seq per-run seq
寿命 不自然结束，页面关才断 终局帧后自然结束
重连代价 补几帧通知，很轻 可能要重放整场 run

打个比方：会话级通道是门磁推送（「有人进屋了」），run 级通道是摄像头画面（点开才看）。 你不会为了知道「有人进屋」而 24 小时开着摄像头，也不会指望门磁告诉你屋里人在干什么。

4.1 Event（run 级领域帧）

文件：internal/run/event.go

描述「发生过什么」的一条记录。不带 seq（落库时由 RunLog 分配）、不带 JSON tag（序列化是 transport 的事）。

type EventKind string

    EventMessage    EventKind = "message"

    EventToolResult EventKind = "tool_result"

type ToolCall struct {
    Name string // 工具名

    Kind      EventKind

    ToolName  string          // 工具名（tool_result / board 用）

4.2 Subscription（run 级阻塞式订阅）

文件：internal/run/event.go（与 Event 同文件）

type Subscription interface {
    // Next 阻塞到下一帧可用。
    // 冷启动时先把库里 seq > from 的帧按批吐完，再切到实时。
    // run 不存在 / ctx 取消 / 流已关 → 返回 false。
    // 「run 是否已结束」在 Subscribe 里一次判掉，不留给调用方轮询。
    Next(ctx context.Context) (StoredEvent, bool)

    // Close 释放订阅资源。幂等。
    Close()
}

Partial 帧照常从 Next 推出：带着内存预留的 seq 反复推同一号，只更新文本，读者游标不前移； sealed 那条沿用同一预留号落库后推出，游标才走到这个号。不变量 4 不受影响—— 重连的读者（from ≥ 预留号）只会收到 sealed 的那一条，不丢不重。

sealed（定稿）：流式正文逐字产出期间只有 Partial 帧（不落库）；流结束那一刻， 把最终全文作为一帧经 AppendSealed 按预留号落库、原位替换内存里的 Partial 帧—— 这个动作叫 sealed。「sealed 那条」指定稿后的那帧全文。

冷启动按批吐完的例子：run r_17 库里已有 seq 1..80，仍在跑。

读者 A：Subscribe("r_17", 50)   ← 断线重连
   ├─ 追赶阶段：Next 不阻塞，把库里 51..80 按 seq 升序逐条立即返回
   └─ 实时阶段：追平后 Next 开始阻塞，run 产出 81、82… 时才返回

读者 B：Subscribe("r_17", 0)    ← 第一次打开页面
   └─ 1..80 全部吐完，再切实时

读者 C：Subscribe("r_17", 80)   ← 一直在看，没断过
   └─ 无可追赶，直接阻塞等 81

三个读者调的是同一个 Next，签名不变；「按批」只是说追赶阶段不阻塞、连续返回， 不是返回一个切片。run 已结束时，追赶阶段吐完最后一帧后 Next 返回 false（流完即止）。

「同一预留号反复推」的例子：模型流式输出「早安」，库里已有 seq 1..4，缓冲预留号 = 5。

内存缓冲（库不动）：[1..4 sealed] [5: Partial "早"]
读者收到：{seq:5, text:"早",  partial:true}     ← 读者游标停在 4，不前移
文本更新，原位改：  [5: Partial "早安"]  (bump)
读者收到：{seq:5, text:"早安", partial:true}     ← 同一 seq 再推一次，前端原位替换半截气泡
流结束 AppendSealed：[5: sealed "早安，今天…"]   ← 这时才 INSERT 进库
读者收到：{seq:5, text:"早安，今天…", partial:false} ← 游标这才走到 5

前端凭 partial:true + 相同 seq 判断「替换而非追加」；读者游标不前移意味着 断线重连（from=5）不会收到任何 Partial，只会收到 sealed 那条——不变量 4 的另一面。

Next 伪代码（难写点：一个方法里混着冷启动追赶、实时阻塞、Partial 同号替换三种状态， 还要不空转、不丢帧、run 结束即退出）：

func (s *subscription) Next(ctx) (StoredEvent, bool) {
    for {
        s.log.mu.Lock()
        buf := s.log.runs[s.runID]        // Subscribe 时已保证存在且装满（内存没有则 readAll）

        if ev, ok := buf.at(s.next); ok { // 缓冲里正好有 seq == s.next 的帧
            if ev.Partial {
                if buf.gen == s.seenGen { goto wait } // 文本没变过，不重推，防忙等
                s.seenGen = buf.gen
                s.log.mu.Unlock()
                return ev, true           // 游标不动：sealed 原位替换后 s.next 仍指这个号
            }
            s.next = ev.Seq + 1           // sealed / 持久帧：游标前移
            s.seenGen = buf.gen
            s.log.mu.Unlock()
            return ev, true
        }

        // 走到这说明内存已追平（s.next 超过缓冲最大 seq）
        if s.log.runFinished(s.runID) {   // status 已不是 running
            s.log.mu.Unlock()
            return StoredEvent{}, false   // 流完即止
        }
    wait:
        ch := buf.notify                  // 持锁时拿下这一代通知通道
        s.log.mu.Unlock()
        select {
        case <-ch:                        // 有 bump（新帧/文本更新），回顶部重扫
        case <-ctx.Done():
            return StoredEvent{}, false
        }
    }
}

type RunLog interface {
    // ── 写（一律用进程 ctx）──

    // Reconcile 把上次进程没写上终局的 run 标成 failed。启动时调一次。
    Reconcile(ctx context.Context) error

    // BeginRun 开一轮 run：插入 run_archive 行 + 写 seq=1 的 start 帧，同一事务。
    BeginRun(ctx context.Context, runID, sessionID, userMessage, agentName string) (StoredEvent, error)

    // Append 给仍在 running 的 run 追加一帧。seq 由库分配。
    // ev.Partial 的帧例外：不写库，只在内存缓冲里预留下一个 seq 并返回
    // （StoredEvent.Seq 即预留号）；同一条流出正文反复调用沿用同一预留号，只更新文本。
    // run 已经不是 running → 返回错误。
    Append(ctx context.Context, runID string, ev Event) (StoredEvent, error)

    // AppendSealed 把流式正文的最终全文按预留号落库。
    // seq 必须正好是库内 max+1，否则返回错误——预留号只存在于内存，
    // 若 seal 前被别的持久帧占了号（理论上只有并发写库能造成），
    // 这里报错，由 drive 按 persistErr 走 error 终局。
    AppendSealed(ctx context.Context, runID string, seq int64, ev Event) (StoredEvent, error)

    // Finish 写终局帧 + 改 run_archive 状态，同一事务。
    // kind 只接受 "complete" / "error" / "stop"。
    // 只有 complete 写入 producedJSON；失败和停止不把产出放进模型历史。
    // patch 非 nil 时在同一事务里改 user_message 和清空被换掉的行。
    Finish(ctx context.Context, runID, kind, text string, producedJSON []byte, patch *ArchivePatch) (StoredEvent, error)

    // RestoreMessage 把浏览器补发的一条正文写入库。保留（§10 问题 7 已决）。
    // 兜的崩溃窗口：进程死在流结束与 AppendSealed 之间——Partial 不落库，
    // 浏览器手里的全文是唯一副本。补发按原序号写回事件表并修复 produced_json，
    // 下一轮模型档案才不缺这条正文。幂等：该序号已存在则 stored=false。
    RestoreMessage(ctx context.Context, sessionID string, seq int64, ev Event) (bool, error)

    // ── 读 ──

    // Subscribe 返回阻塞式订阅。from=0 从头。
    // run 不存在 → ErrRunNotFound。
    // 内部判断 run 是否已结束：已结束则冷启动装库后流完即止。
    Subscribe(runID string, from int64) (Subscription, error)

    // HistoryPage 返回会话里已结束的 run（档案 + 事件），按 created_at 降序分页。
    // cursor 格式 "<created_at>|<run_id>"，空表示第一页。
    // 不含 status='running' 的行——正在跑的 run 由 LiveRunID 报告。
    // 归 RunLog 而非 Archive：响应里带事件帧，且 run_archive 的
    // status/produced_json 本来就由 BeginRun/Finish 的事务写，是同一块地盘。
    HistoryPage(ctx context.Context, sessionID, cursor string, limit int) (HistoryPage, error)

    // HasEvent 报告事件表里是否已有这个序号。给 RestoreMessage 用。
    HasEvent(ctx context.Context, runID string, seq int64) (bool, error)

    // Close 关闭底层连接。
    Close() error
}

Append / AppendSealed 伪代码（难写点：Partial 预留号是纯内存协议， Drop/Discard 要作废预留号不留空洞，seal 要防「号被占」，且一律先写库再 bump——不变量 3）：

func (l *runLog) Append(ctx, runID, ev) (StoredEvent, error) {
    l.mu.Lock(); defer l.mu.Unlock()
    buf := l.runs[runID]
    if buf == nil || buf.status != running { return ErrRunFinished } // 不变量 5：终局后拒绝追加

    if ev.Drop || ev.Discard {
        buf.dropPartialTail()   // 作废预留号：把内存尾部的 Partial 帧直接摘掉。
        buf.bump()              // 库内 max 从没动过，下一条持久帧自然接上，不留空洞
        return StoredEvent{}, nil
    }

    if ev.Partial {
        if last := buf.tail(); last != nil && last.Partial {
            last.Text, last.Ts = ev.Text, nowMillis() // 同一条流出正文：原位更新，沿用同一预留号
            buf.bump()
            return *last, nil
        }
        se := StoredEvent{Run: runID, Seq: buf.maxSeq() + 1, // 预留号 = 此刻若落库将得的号
                          Ts: nowMillis(), Event: ev}
        buf.append(se)          // 只进内存，不写库
        buf.bump()
        return se, nil
    }

    seq, err := l.insertEvent(ctx, runID, ev)  // 写库：INSERT，seq 由库内 max+1 分配
    if err != nil { return StoredEvent{}, err } // 写失败不进缓冲——读者永远看不到库里没有的帧
    se := StoredEvent{Run: runID, Seq: seq, Ts: nowMillis(), Event: ev}
    buf.append(se); buf.bump()
    return se, nil
}

func (l *runLog) AppendSealed(ctx, runID, seq, ev) (StoredEvent, error) {
    l.mu.Lock(); defer l.mu.Unlock()
    buf := l.runs[runID]
    tail := buf.tail()
    if tail == nil || !tail.Partial || tail.Seq != seq || buf.maxSeq() != seq {
        return ErrSealConflict  // 预留号被别的持久帧占了 → drive 按 persistErr 走 error 终局
    }
    if err := l.insertEventAt(ctx, runID, seq, ev); err != nil { // INSERT 指定 seq
        return err
    }
    buf.sealTail(ev)            // 原位替换：Partial=false，Text=最终全文
    buf.bump()
    return *buf.tail(), nil
}

Stage / CommitPatch / RevertStage 伪代码（难写点：这是一套「补偿式事务」—— 内存先改、库要等到收尾的 Finish 事务才写；中间任何一步失败都必须能干净退回， 否则模型视图和 run_archive 永久分叉，见 §5.6 补偿路径）：

func (a *archive) Stage(c compact.Commit) error {
    a.mu.Lock(); defer a.mu.Unlock()
    if !a.staged {                      // 本轮第一次压缩：留快照，作为回退基准。
        a.snapMsgs = copy(a.modelMsgs)  // 同一轮再压，仍相对这份原始快照取舍
        a.snapRuns = copy(a.runs)
        a.staged = true
    }
    a.runs = filter(a.runs, r => c.KeptRunIDs.contains(r.RunID)) // 丢掉被换掉的轮
    a.modelMsgs = rebuild(a.runs)                                // 按保留集重装消息列表
    a.pendingDrop = append(a.pendingDrop, c.DroppedRunIDs...)
    a.liveModelText = c.CombinedUser    // 摘要接在本轮用户原话前的整句
    return nil                          // 全程不碰库；被丢原文的去处是 Handler 调 WriteRAG 写 compact_rag
}

func (a *archive) CommitPatch() (ArchivePatch, bool) {
    a.mu.Lock(); defer a.mu.Unlock()
    if !a.staged { return ArchivePatch{}, false }
    return ArchivePatch{UserMessage: a.liveModelText, DropRunIDs: a.pendingDrop}, true
    // 调用方（drive）把它交给 Finish，与终局帧同一事务写 run_archive
}

func (a *archive) RevertStage() {
    a.mu.Lock(); defer a.mu.Unlock()
    if !a.staged { return }             // 没 Stage 过，无事发生（幂等）
    a.modelMsgs, a.runs = a.snapMsgs, a.snapRuns
    a.staged = false
    a.pendingDrop = nil
    a.liveModelText = ""
}

type SessionLog interface {

    Close() error
}

存储与传输分离（重要）：上面的 Subscribe 返回的是一个阻塞式迭代器， 它把「会话级事件增量怎么拿到」和「用哪种连接推给客户端」绑在了一起—— 一旦绑死，换成轮询或 WS 多路复用就得改接口。拆成两层：

// SessionFeed 是「拿到增量」的能力，与传输无关。SessionLog 实现它。
type SessionFeed interface {
    // Since 非阻塞拉取 (from, from+limit] 的帧。轮询模式直接用这个。
    Since(ctx context.Context, sessionID string, from int64, limit int) ([]StoredSessionEvent, error)

    // Subscribe 阻塞式推送。SSE / WS 用这个。语义同前。
    Subscribe(sessionID string, from int64) SessionSubscription

    // Notify 注册一个「这个会话有新帧」的信号，不带内容。
    // WS 多路复用用这个：一条连接上挂着 N 个会话，只需要知道谁变了，
    // 再按需 Since 取内容——避免为每个会话各建一个 Subscription。
    Notify(sessionID string) <-chan struct{}
}

三种传输都建在同一份 session_log 上，可互换：

传输 用法 何时选它
SSE Subscribe + 逐帧写 v3 的默认。最简单，自动重连
轮询 JSON Since(?since=) 降级路径；或客户端不便持有长连接时
WS 多路复用 Notify + Since 多会话/多标签页，受浏览器 6 连接上限约束时（§4.0）

v3 先只做 SSE，但接口按可互换来设计——因为 §11 那条拓扑（一条 WS 承载所有会话） 是明确的演进方向，不该等到要做时才发现接口绑死了。

trySchedule —— v3 的核心，也是唯一的难写点：

// trySchedule 尝试开一场 run。可以从任意 goroutine 调，幂等。
//
// 难写点：三件事必须原子——「判断闸空」「取空收件箱」「开 run 并占闸」。
// 少任何一步的原子性都会漏消息或开两场 run（不变量 8）。
//
// 调用点有两个，缺一不可：
//   - Enqueue 之后（消息到了，看看能不能立刻跑）
//   - drive 收尾放闸之后（闸空了，看看有没有排队的）
func (e *Engine) trySchedule(ctx context.Context) {
    e.mu.Lock()
    if e.live != nil {          // 闸忙：什么都不做。消息已在收件箱，收尾时会再来一次
        e.mu.Unlock()
        return
    }
    // 关键：**占闸与取空收件箱之间不留窗口**。
    // 先乐观占一个哨兵，防止并发的另一个 trySchedule 也进来。
    e.live = &liveRun{}         // 哨兵：id 为空，表示「正在开跑」
    e.mu.Unlock()

    // 以下在一个 DB 事务里完成（不变量 9：runID 只在提交后可见）
    runID, msgs, stored, err := e.beginRunAtomic(ctx)
    //   beginRunAtomic 内部：
    //     tx:
    //       msgs, ok := inbox.Drain(tx, sessionID)        // 取空收件箱
    //       if !ok → 回滚，返回 ErrInboxEmpty
    //       merged := join(msgs, "\n\n")
    //       runLog.BeginRunInTx(tx, runID, sessionID, merged, agentName)
    //                                                  // run_archive 行 + seq=1 start 帧
    //                                                  // + message_ids 列（§4.9）
    //       sessionLog.AppendInTx(tx, sessionID, SessionEvent{
    //           Kind: SessRunStarted, RunID: runID,
    //           MessageIDs: ids(msgs), MergedText: merged,
    //       })                                          // 同一事务，runID 此刻才对外可见
    //     commit
    //     → bump sessionBuffer（推给会话级订阅者）
    //     → bump runBuffer（推给 run 级订阅者）

    if errors.Is(err, ErrInboxEmpty) {
        e.mu.Lock(); e.live = nil; e.mu.Unlock()   // 收件箱空，放掉哨兵
        return
    }
    if err != nil {
        e.releaseSentinelAndReport(ctx, err)
        // 开跑失败不是 HTTP 错误（没有 HTTP 请求在等）——
        // 写一帧 message_queued 之外的会话级错误帧，或退回收件箱由下次重试。
        // 决策见 §10 待定问题 2。
        return
    }

    e.mu.Lock()
    e.live = &liveRun{
        id: runID, cancel: cancel, userText: merged, messageIDs: ids(msgs),
    }
    e.mu.Unlock()

    messages, err := e.archive.ModelMessages(ctx, e.sessionID)  // §4.4，冷热缓存
    if err != nil { /* 走 error 终局，见下 */ }
    messages = append(messages, schema.UserMessage(merged))

    go e.drive(runCtx, runID, messages)   // ← §5.3–5.6 的 drive，一字不改
}

Enqueue 伪代码：

func (e *Engine) Enqueue(ctx context.Context, messageID, clientID, expectedRunID, text string) error {
    if n, _ := e.inbox.PendingCount(e.ctx, e.sessionID); n >= maxQueueDepth {
        return ErrQueueFull                    // → transport 回 422 + 当前条数（§10 问题 4）
    }

    e.mu.Lock()
    live := ""
    if e.live != nil { live = e.live.id }
    e.mu.Unlock()
    if expectedRunID != "" && expectedRunID != live {
        return &StaleViewError{LiveRunID: live} // → 409 + 当前 liveRunID（fencing，§10 问题 12）
    }

    err := e.inbox.Put(e.ctx, e.sessionID, messageID, text)  // ① 落库（进程 ctx，不变量 2）
    if errors.Is(err, ErrMessageIDTaken) { return err }      // → 409，正当的重复投递
    if err != nil { return err }                             // → 500。唯一的意外失败路径

    _, err = e.sessionLog.Append(e.ctx, e.sessionID, SessionEvent{   // ② 落库 + 广播
        Kind: SessMessageQueued, MessageID: messageID, ClientID: clientID, Text: text,
    })
    if err != nil {
        // 消息已入收件箱但没广播出去。不回滚 inbox——
        // 用户的字比一帧通知重要（不变量 3 的优先级排序）。
        // 客户端下次 Snapshot / 重连时会从 Pending() 看到它。
        log.Printf("会话级帧落库失败: %v", err)
    }

    e.trySchedule(e.ctx)                      // ③ 闸空就立刻开跑
    return nil
}

注意 messageID 现在由客户端给，Put 不再返回它——这是相对本文早期草稿的变化， 理由见 §10 问题 12。它带来一个好处：message_queued 帧的 ID 与前端 pending 气泡的 ID 天然是同一个，对齐不需要映射表。

  │                            把 messageIds 对应的气泡标记为「已被回答」
  │     on run_terminal     → run 级流自己会结束；这里只更新状态文案
  │
  └─ ③ run 级流（可能同时有多条？不——闸保证每会话最多一场 run）

关键性质：

  • 发送按钮永远可用。state.busy 这个概念删掉。用户随时能投递，投递永远成功。 这解决了当前实现里「run 期间发送键被停止键替换、连排队的入口都没有」的问题 （index.html:967-971）。
  • 多标签页 / 多设备自动同步。每个客户端都开着会话级流，任何一端投递， 所有端立刻收到 message_queued。《会话级并发》§2.1 的 t3–t5「A 看不到 B」整行消失。
  • 409 处理逻辑删除。不存在这个状态码了，attachLive() 那套「只在加载时调一次」的 补丁也不需要了——会话级流就是活的 attachLive。

撤回的语义边界要在 UI 上表达清楚：只有 message_queued 且尚未出现在任何 run_started.messageIds 里的气泡能撤回。一旦被消费，撤回按钮消失 （服务端 Cancel 会返回 404，但前端不该让用户点到）。

停止后的排队提示：Stop 不清收件箱（§4.8），所以按下停止后如果还有排队消息， 它们会立刻开跑。前端必须在停止按钮旁边明示「还有 N 条排队，会继续」并提供一键清空， 否则用户会觉得「我明明停了它怎么又跑了」。

删掉 state.localEcho：当前实现在 send() 里先 appendUser(text) 画一个本地气泡， 再等服务端确认。v3 下这会变成画面分裂的来源——A 本地画的气泡，B 要等会话级流推来才画， 两端时序不同，撤回时更容易对不上。改成服务端回显：send() 只 POST， 气泡由 message_queued 帧画出（帧里带 text 全文，正是为此）。 POST 失败就把输入框内容还回去。代价是本地回显的那点即时感没了（多一个 RTT）， 换来的是所有客户端画的用户消息来自同一个 seq 序列——同步是免费的。

一条消息气泡的状态机（前端只需实现这一个，所有转移都由流帧驱动）：

                    POST /api/message
                          │
       ┌──────────────────┴───────────────────┐
       │ 失败                                  │ 成功
       ▼                                      ▼
   [输入框内容还回]                    ┌───────────────┐
                                      │  queued        │ ← message_queued 帧画出
                                      │  （可撤回）     │
                                      └───┬───────┬───┘
                       DELETE /api/message│       │ run_started.messageIds 含它
                                          ▼       ▼
                                  [气泡消失]   ┌───────────────┐
                                              │  consumed      │ ← 撤回按钮消失
                                              │  （正在被回答） │
                                              └───────┬───────┘
                                                      │ run_terminal
                                                      ▼
                                              ┌───────────────┐
                                              │  answered      │ ← 与助手回复配成一对
                                              └───────────────┘

四个状态对应服务端的三处存储：queued = inbox 里有行；consumed = inbox 行已删、 run_started.messageIds 含它、run 仍 running；answered = run_terminal 已到。 前端不保存任何服务端不知道的状态——刷新后靠 Snapshot + 会话级流冷启动重建， 不需要 localStorage 兜底。

5. 完整链路：八幕

v2 是五幕，主角是 drive。v3 是八幕，主角前移——第一幕的主角是投递请求， 第二幕是调度器，drive 从第三幕才出生。

示例数据（贯穿六幕，每幕末尾只列增量）：

  • 会话 s_1 已有两个完成的 run：r_15、r_16；
  • 用户发「读一下 doc/19」→ m_1 → 立刻开跑 r_17；
  • r_17 跑工具期间（耗时长），用户又发「顺便看看 v1」→ m_2，再发「对比一下差异」→ m_3，两条都排队；
  • r_17 落幕，调度器合并 m_2 + m_3 开出 r_18；
  • r_18 期间上下文超阈值，压缩换掉 r_15。

5.3 第三幕：模型开口，一句话变成两件事

drive 把第一幕取好的 messages 交给 eino Runner，模型开始吐字。 吐出的每条 *schema.Message 在 drive 的 stream 循环里一变二：

  • A 路（给模型的）：只有 root agent 的消息被攒进一个 list，一轮结束时整体序列化成 produced_json——下一轮 Archive 的原料（第六幕用）。子代理的消息不进档案。
  • B 路（给人的）：Classify 把它翻译成领域 Event（§4.1），经 emit 写进 RunLog。 这是外界观察这轮 run 的唯一出口。

进图前先认识两个词：

  • emit：drive 里「写一帧进库」的闭包。写失败会记下 persistErr 并取消整轮 run—— 帧写不进库就不许推给读者（不变量 3：先落库，再推浏览器）；
  • sealed（定稿）：流式正文先以 Partial 帧在内存里反复更新（不碰库）， 流结束时才把最终全文一次落库（定义和逐帧例子见 §4.2，伪代码见 §4.3）。 这是阶段一机制；阶段二的增量协议下「哪一帧才算数」这个问题不成立， sealed 连同整套 Partial 机制一起消失（§11.3）。
模型吐 *schema.Message（eino 包成 AgentEvent，流进 drive 的循环）
  │
  ├─ Classify(agent, mv, msg) → (Event, ok)   纯函数；ok=false → 这条没有可呈现内容，跳过
  │
  ├─ A 路：agentName == root → msgs = append(msgs, msg)   子代理不进档案
  │
  └─ B 路：emit(ev) → runLog.Append
        ├─ Partial → 只进内存，预留下一 seq，库不动
        ├─ 定稿   → AppendSealed 按预留号落库（sealed），订阅者可见
        ├─ Drop    → 模型流出失败，预留号作废，不落库
        └─ Discard → 半截被最终结果取代（例如变成了工具调用），静默丢掉
        作废不留空洞：库内 max 从没动过，下一条持久帧自然接上

读者从哪来？第一幕的 handler 是第一个，但 run 不要求有读者：刷新页面走 GET /api/chat/stream?from=N 续传、第二个标签页、将来的 IM/cron（#8b）和 MQ（#8c） 都只是又一个 Subscribe。一个读者都没有时，run 照跑、帧照落库（不变量 1：run 的命 不属于任何连接）。所以 B 路的终点是 RunLog 而不是 SSE——执行与观察彻底解耦， 新读者类型接入时一行引擎代码都不用改。

5.4 第四幕：中途停顿，等人拍板

模型要调一个需要审批的工具，eino 把 run 中断。drive 里构造的 ask 闭包接住中断，做五件事：

  1. 生成审批 id；
  2. emit 一帧 approval——读者立刻看到审批卡片（走的就是第三幕的 B 路）；
  3. 挂起：阻塞在一个 channel 上，什么都不干；
  4. 决策从 POST /api/approval 进来，Engine.Approve 把它塞进 channel （与 Stop/断连的竞态处理和伪代码见 §4.8）；
  5. emit 一帧 approval_result，把 decision 交还 runner，run 从原地继续（回到第三幕）。

要点：挂起的只是 drive 这个 goroutine——闸没放（本会话开不了第二轮）、 SSE 没断（读者先看到卡片、再看到后续）。若用户等不及按了 Stop，runCtx 取消， ask 从 Done 分支醒来、清掉挂起表，run 直接进入第六幕的「停止」结局。

v3 的交互改善：审批挂起期间闸不放，所以此时投递的消息一律排队。 这在 v2 里是「用户困惑为什么打不了字」，在 v3 里变成「用户看到排队气泡， 知道系统在等自己拍板，顺便把下一句先说了」。同一个机制，体验完全不同。

              ＋ r_17 seq=7 {kind:"tool_call", tool_calls:[{name:"bash", args:"…"}]}   ← runner 恢复，回到第三幕

Archive 内存   不变

compact 不是独立的一幕，它藏在第一、三幕的 middleware 链里：每次要调模型前， 如果上下文超了阈值，它就地改写发给模型的消息，并调 archive.Stage() 把 「丢了哪些轮、摘要是什么」记进内存（§4.4 有伪代码）。

5.6 第六幕：落幕与再调度

r_17 的 stream 循环结束。drive 自包含地收尾，依次回答三个问题：

问题一：这轮算什么结局？ terminalOf 按四个输入定终局，判断顺序就是优先级：

判断（按序） 终局 为什么
persistErr != nil error 第三幕写库失败引发的 cancel，让流循环只看得到假象 context.Canceled；真因在 persistErr，必须优先
err == nil complete 正常跑完，A 路攒的 list 成为 produced_json
stopped == true stop 用户按了 Stop
其他 error 模型 / API 报错

问题二：第五幕 Stage 的压缩改动怎么办？ 只有 complete 才配提交—— CommitPatch() 取出补丁，交给 Finish 与终局帧同一事务写库； 其余一切情况先 RevertStage() 退回内存。还有一个容易漏的补偿： complete 但 Finish 本身写库失败时，同样必须 RevertStage—— 库没提交，内存就不能留着压缩结果，否则放闸后下一轮 ModelMessages 会读到 数据库里从未发生的压缩，模型视图和 run_archive 永久分叉。

问题三：这一轮的产出怎么接进下一轮？ complete 且落库成功后 archive.AddRun(produced, userText, runID)——第三幕 A 路攒的 list 进缓存， 成为下一轮第一幕的档案原料。最后放闸：e.live = nil，会话可以接下一条消息了。

v3 的增量：放闸后多做两步——广播落幕 + 再调度。

drive 收尾
  │
  ├─ kind := terminalOf(persistErr, err, produced, stopped)      // 判断顺序见上表
  ├─ Finish(+ CommitPatch)  同一事务                              // §4.3 不变
  ├─ 成功且 complete → archive.AddRun(produced, userText, r_17)   // §4.4 不变
  │

  │
  ├─ ★ sessionLog.Append(run_terminal{r_17, "complete"})

inbox（待办队列） 空 Put / Drain / Cancel
compact_rag r_15 被换掉的原文（第六幕压缩发生后） WriteRAG

session_log 是这个会话的完整编年史，六帧讲清了「谁在什么时候说了什么、 系统什么时候开始回答、哪些话被合并回答了」。这份时间线在 v2 里根本不存在—— v2 只能从 run_log 里各个 run 的 start 帧反推，而排队消息因为从未成为 run， 在 v2 的存储里没有任何痕迹。

5.8 进程重启

Reconcile 在 v2 只做一件事（把遗留 running 标 failed）。v3 多做一件：

启动
  ├─ sessionLog.Reconcile(ctx)
  │     ├─ 遗留 running 的 run → 标 failed（同 v2）
  │     └─ ★ 返回所有 inbox 非空的 sessionID
  │
  └─ 对每个 pendingSession：engine.trySchedule(ctx)
        → 重启前排队的消息**继续被回答**，不静默丢弃
        → run_started 帧带 Resumed:true，UI 明示「这条是重启前排队的」

为什么自动继续而不是等用户确认：不变量 3 说用户的字比输出帧贵重。 既然它已经落库了，进程重启就不是丢弃它的理由——这与不变量 1 「run 的命不属于任何连接」是同一个精神：执行的生命周期独立于任何偶然事件。

样例约定（下面所有 JSON 都按这个写，字段来源可查）：

  • 两条流都是 data: <JSON>\n\n，不带 event 名（sse.go:74）。 下文说「会话级 SSE 推」= GET /api/session/stream?id=&from=（handleSessionStream， 背后 sessionLog.Subscribe()，§4.7）——页面加载时挂一次、常驻不断开， 一个会话一条；说「run 级 SSE 推」= GET /api/chat/stream?run=&from=（handleStream， 背后 runLog.Subscribe()）——收到 run_started 才新挂，一个 run 一条、见终局帧即关。 两者的生命周期不同，这是 §4.0 三级订阅的核心。

一处 v3 尚未覆盖的空档：Reconcile 只改 run_archive.status， 不给 r_17 补写终局帧——run_log 里没有 kind:"error"，session_log 里也没有 run_terminal(r_17)。于是：

修法有两条，都不贵：Reconcile 时给这些 run 补写一帧 kind:"error" （文本「进程重启，本轮中断」）；或者让 run 级流在档案 status 非 running 且无更多帧时 主动收尾。已挂进 §10 问题 14，倾向补帧，随实施第 6 步（Inbox + SessionLog 落地）一并定。

以下 7–14 是打断路径与边界。前六个用例都是「一件事按顺序发生」， 这八个里有一半是两件事同时发生——真正的复杂度在这里。

用例 7：审批挂起期间排队

场景：r_17 要调 write_file，卡在审批上等人拍板（§5.4）。用户等不及，又发一句。 这是 v3 相对 v2 最直观的体验差：v2 里发送键被停止键替换，连排队的入口都没有； v3 里投递照常成功，只是不会有新 run 开出来。

run 级流（r_17 已挂着）
  data: {"run":"r_17","seq":5,"ts":"T5","kind":"approval",
         "approval":{"id":"s_1-a1","tool":"write_file","args":"{\"path\":\"doc/20.md\"}","message":"要写这个文件"}}
        ↑ ask 闭包产出（session.go:319）。此刻：drive goroutine 阻塞、闸没放、SSE 没断

→ POST /api/message {"sessionId":"s_1","messageId":"m_2","clientId":"A-desktop","text":"顺便把 v1 也看看"}
← 202
会话级流
  data: {"seq":4,"ts":"T6","kind":"message_queued","messageId":"m_2",…,"text":"顺便把 v1 也看看"}
        ↑ 后面不会跟 run_started——闸被挂起的 r_17 占着。UI 该显示的是
          「排队中，等 r_17 结束」，不是「马上开始」

→ POST /api/approval {"sessionId":"s_1","requestId":"s_1-a1","decision":"approve"}
← 200
run 级流（同一条 r_17 流，接着往下推）
  data: {"run":"r_17","seq":6,"ts":"T7","kind":"approval_result","approval":{"id":"s_1-a1","decision":"approve"}}
  data: {"run":"r_17","seq":7,"ts":"T8","kind":"tool_result","toolName":"write_file","text":"已写入 doc/20.md"}

  data: {"run":"r_17","seq":9,"ts":"T9","kind":"complete"}

decision 只接受 approve / reject（server.go:511）；reject 时 run 不结束， 模型收到拒绝后自己决定怎么办（继续别的、或收尾），所以后面仍可能是 complete。

关键点：审批挂起占的是闸，不是收件箱。二者分离正是 v3 的结构， 这个用例是它唯一能被用户直接感知的地方。

用例 8：停止

场景：r_17 在跑，m_2、m_3 在排队。用户按停止。

→ POST /api/stop {"sessionId":"s_1","run":"r_17"}
← 200（run 对不上则 404，server.go:310）

run 级流
  data: {"run":"r_17","seq":6,"ts":"T5","kind":"stop"}          ← 终局帧，流关闭
会话级流
  data: {"seq":4,"ts":"T5","kind":"run_terminal","runId":"r_17","terminalKind":"stop"}
  data: {"seq":5,"ts":"T5","kind":"run_started","runId":"r_18","messageIds":["m_2","m_3"],
         "mergedText":"顺便看看 v1\n\n对比一下差异"}
        ↑ ★ 立刻又开跑了。因为 Stop 不清收件箱（§10 问题 3 已决）

这是全套用例里最反直觉的一帧：用户按下「停止」，系统却开始了新一轮。 §4.13 因此要求停止按钮旁边明示「还有 2 条排队，会继续」并给一键清空 （DELETE /api/message/:id 逐条，或 §4.8 的 Delete 之外的批量清空——见 §10 问题 15）。 不做这个提示，用户会觉得「我明明停了它怎么又跑了」，而这恰恰是产品决定（§10 问题 3）： 停止的语义是「这一轮不对」，不是「我说的话不算」。

用例 9：新会话（删会话）

场景：r_17 在跑，首帧还没到（模型还在思考）。用户点「新会话」。 这正是 §6 第四行那个 bug 的现场：v2 的 startNewSession() 依赖 state.runID， 而它只在收到第一帧 SSE 时才被赋值（index.html:1215），所以 if (run) 为假、 stop 根本没发，旧 run 继续写进一个用户以为已不存在的会话。

v2（错）：
→ POST /api/stop {"sessionId":"s_1","run":""}     ← state.runID 还是空，前端压根没发这个请求
   旧 run 无人知晓地续跑，帧写进 s_1

v3：
→ DELETE /api/session/s_1
← 204
   服务端按 §4.8 的 Delete 五步走：取消 live runCtx（不依赖客户端知道 runID）
   → 清 inbox → 一个事务删 run_log / run_archive / session_log / inbox 的会话行
   → SessionLog.CloseSession 断开该会话所有订阅 → 从 map 摘掉 Engine

所有客户端的会话级流：连接被服务端关闭（不是收到一帧，是流断了）
所有客户端的 run 级流（r_17）：同样被关闭

被取消的 r_17 若已在写帧：emit 撞到已删除的行 → 写失败 → drive 记下 persistErr 退出。
**它写不进任何东西，因为没有行可写**——这是「删表」比「发 stop」强的地方。

验收方式：点「新会话」后立刻用 sqlite3 查四张表，session_id='s_1' 的行数必须是 0； 再等 10 秒查一次，仍必须是 0（证明旧 run 没有复活写入）。

用例 10：队列上限（422）

场景：r_17 跑得很久，用户已经排了 10 条。第 11 条投递。

→ POST /api/message {"sessionId":"s_1","messageId":"m_11","clientId":"A-desktop","text":"…"}
← 422 {"error":"队列已满","queued":10,"limit":10}
   前端提示：「已经排了 10 条，先停一下当前任务？」

§10 问题 4 已决：排到 10 条说明这场 run 已经久到用户在对着它自言自语， 静默排队是不诚实的。这与不变量 7 不冲突——不变量 7 说的是「不因状态冲突失败」， 队列过深是用户的输入本身需要被重新考虑，是 4xx 的正当用途。 注意它不写 inbox、不推帧：422 是唯一一个「投递没发生」的出口，前端不该画任何气泡。

用例 11：滚到顶翻历史

场景：会话里有 40 个已结束的 run，页面首屏只画最近的。用户滚到顶。

→ GET /api/session/history?session=s_1&limit=20
← 200 {"runs":[{"runId":"r_16","createdAt":"…","status":"complete","events":[{…},{…}]},
                {"runId":"r_15",…}, …],
       "nextCursor":"2026-09-30T08:11:02Z|r_-3"}

→ GET /api/session/history?session=s_1&limit=20&before=2026-09-30T08:11:02Z|r_-3
← 200 更早的一页

接缝在哪里：HistoryPage 不返回 status='running' 的行（logdb.go:474）—— 正在跑的 run 由 Snapshot.liveRunId 报告、由 run 级流呈现。所以「历史」与「实时」 天然不重叠：一个是已结束的 run 数组，一个是活的帧流。

但 v3 引入了一处新的接缝：排队中的消息既不在 history 里，也不在任何 run 的帧里 （它只在 inbox 和 session_log 的 message_queued 帧里）。刷新页面时它靠 Snapshot.queued 恢复（用例 3），而翻历史翻不到它——正确，因为它还没成为历史。 UI 要把排队气泡画在输入框上方那一区，不要混进历史流，否则翻页时会被重复插入。

用例 12：SSE 单独断线重连（≠ 用例 3 的整页刷新）

场景：网络抖了一下，会话级流断了 3 秒。这期间另一端投递了 m_2，r_17 也落幕了。 页面没刷新，JS 状态还在，state.sessionSeq 停在 3。

断开前最后收到：data: {"seq":3,"kind":"run_started","runId":"r_17",…}
—— 连接断开 3 秒 ——
重连：GET /api/session/stream?id=s_1&from=3
  data: {"seq":4,"ts":"T5","kind":"message_queued","messageId":"m_2",…,"text":"顺便看看 v1"}
  data: {"seq":5,"ts":"T6","kind":"run_terminal","runId":"r_17","terminalKind":"complete"}
  data: {"seq":6,"ts":"T6","kind":"run_started","runId":"r_18","messageIds":["m_2"],…}
        ↑ 补齐了漏掉的三帧，然后切实时

同时 run 级流 r_17 也断了：GET /api/chat/stream?run=r_17&from=7
  data: {"run":"r_17","seq":8,…}  data: {"run":"r_17","seq":9,"kind":"complete"}
        ↑ 它自己会收尾关闭

为什么这条用例必须存在：§7.2 失败模式 1 说会话级流的 from=seq 续传 「不是可选优化」，session_log 持久化就是为它存在的。用例 3 走的是整页刷新 （JS 状态归零，靠 Snapshot 重建），没有验证「JS 状态还在、只补漏帧」这条路—— 而它才是日常最常见的那种断线。

前端实现上的关键：sessionSeq 必须每收一帧就更新，不能等批处理完； 否则重连时 from 报小了会重放（气泡重复），报大了会丢帧（气泡永久缺失）。 重放可以靠 messageId 幂等兜住，丢帧兜不住。

用例 13：run 中途压缩

场景：r_18 跑到一半上下文超阈值，压缩换掉了 r_15（§5.5）。

run 级流（r_18）
  data: {"run":"r_18","seq":4,"ts":"T4","kind":"compact","text":"上下文较长，正在压缩早期对话"}
        ↑ compact 只表示「正在压缩」，text 是短句，不是摘要正文（sse.go:32）
  …后续帧照常

用户看到什么：一句轻提示，不是新气泡、不是新 run。压缩是暗处的事（§5.5）， 它不改 runID、不结束 run、不产生会话级帧——所以会话级流对压缩完全无感。 这是刻意的：压缩属于「模型视图真源」（Archive）的内部事务，不是会话级事实。

压缩之后翻历史会读到什么（接用例 11）：r_15 的 produced_json 被清空、 原文挪进 compact_rag（§4.4）。GET /api/session/history 读的是 run_log 的帧， 不是 produced_json，所以 r_15 的对话在历史里照样能翻到、字还在。 被压掉的只是「下一轮模型看到什么」，不是「用户看到什么」。 这个区分是 §1 三真源的直接后果，也是最容易被实现搞反的地方。

用例 14：inject 插话（后置能力，实施第 12 步）

场景：r_17 正在读错的文件，用户想立刻纠正，不等它跑完。

→ POST /api/message {"sessionId":"s_1","messageId":"m_2","clientId":"A-desktop",
                     "delivery":"inject","text":"不对，看 doc/16"}
← 202
会话级流
  data: {"seq":4,"ts":"T3","kind":"message_queued","messageId":"m_2",…,"text":"不对，看 doc/16"}
        ↑ 注意：**没有 run_started**，但 m_2 也不会等到 r_17 结束

run 级流（r_17 继续，下一个 round boundary 处模型就吃到了这句）
  data: {"run":"r_17","seq":6,"ts":"T4","kind":"message","role":"assistant","text":"好，我看 doc/16"}

与 after 模式的区别就在这一点：after 的 message_queued 后面必然跟着 （当前 run 落幕后的）run_started；inject 的后面什么都没有， 那句话直接进了正在跑的这一轮。前端因此不能用「有没有 run_started」判断消息是否被消费—— inject 消息的消费信号是它出现在 r_17 后续帧的语义里，没有专门的帧。

这是本用例集里唯一一个「帧协议不足以表达状态」的地方，所以 §10 问题 11 把它列为 可选阶段：要么加一种 message_injected 会话级帧（干净，但多一种帧）， 要么让 UI 对 inject 消息只显示「已插话」不再跟踪状态（够用，但状态机有例外）。 倾向前者，随实施第 12 步一并定。

启动条件：after 模式稳定，且你真的开始嫌「等它跑完」太久。没有它 v3 仍然完整。

v3 不是为这四个问题设计的，但它们都随解耦一起消失了。这本身是「根因正确」的证据。

问题（会话级并发访谈稿） v2 的表现 v3 为什么消失
B 吃 409 后变瞎子 前端只 appendError 就 return，不自愈 409 不存在。投递永远成功，B 的气泡立刻出现在所有端

7. 取舍与代价

诚实列出。这些是 v3 真实变复杂的地方，不是可以忽略的脚注。

7.1 复杂度上升

项 v2 v3
表 3（run_log / run_archive / compact_rag） 5（+ session_log / inbox）
流 1 种（run 级） 2 种（run 级 + 会话级）
客户端游标 1 个（runSeq） 1 + N（sessionSeq + 每 run 一个）
Engine 导出方法 Start / Stop / Approve / LiveRunID Enqueue / Cancel / Stop / Approve / Snapshot / Delete
并发临界区 占闸（一处） 占闸 + 取空收件箱 + 发布 runID（必须同事务）
浏览器连接占用 1 条 SSE 2 条 SSE（见下）

连接占用是唯一一个「只在多标签页暴露」的代价，而多标签页正是 v3 要修的场景， 所以它不能当脚注：浏览器对同一 host 的 HTTP/1.1 并发上限是 6，SSE 长期占坑， 2 个标签页 × 2 条 = 4 个坑，只剩 2 个给普通请求。 缓解手段是 §4.7 的 SessionFeed 分层（换 WS 多路复用不动存储）与 §10 问题 10。

7.2 新的失败模式

  1. 会话级长连接断开期间的事件会丢——所以会话级流必须支持 from=seq 续传， 这不是可选优化。session_log 持久化就是为它存在的。
  2. beginRunAtomic 事务失败时，消息何去何从？ 它已从 inbox 被 Drain（事务回滚则恢复）。回滚是安全的，但需要一个重试策略， 否则消息会躺在收件箱里直到下一次 Enqueue 才被捞起。见 §10 待定问题 2。
  3. 合并窗口让「我发的那句」与「回答」不再一对一。UI 必须能表达归组关系， 否则用户会困惑「我只问了一句，为什么回答里在讲两件事」。message_ids 就是为此存在的。
  4. 服务端回显引入一个 RTT 的延迟感（§4.13）。用户按下回车到气泡出现， 从「立刻」变成「一个来回」。这是拿即时感换多端一致性，是取舍不是纯收益。 已有解法（§10 问题 12）：messageID 改客户端生成，前端用自己的 ID 立刻画 pending 气泡， message_queued 帧到达时按同一 ID 对齐——即时感回来，且不需要 localEcho 那种猜。 采纳后本条可以删除。

7.3 什么没变（这是阶段一的主要优点）

以下「不变」指阶段一。阶段二会动数据面（B 路的 emit、RunLog 写方法、Subscription、 前端渲染），改动范围见 §9 第 14–18 步与 §11.5；Archive 与 A 路两个阶段都不动。

  • Archive 一行不改。合并发生在 Inbox 与 Engine 之间，Archive 看到的永远是一句 user 输入。
  • drive 的 stream 循环、A/B 两路、审批挂起、compact 补偿事务全部不改。
  • RunLog 的 run 级部分不改，只增加一个 BeginRunInTx 变体供事务内调用。
  • run 级 Subscription 不改，Partial 预留号、sealed、续传语义全部保留 （阶段一内；阶段二把这套机制整体退役，换成实体 + 字段补丁，见 §9 第 14–18 步）。
  • server_test.go 那 1200 行里，测 run 内部行为的部分全部保留， 只有测「同会话第二次 POST 得 409」的用例需要改写成「第二次 POST 得 200 + 排队」。

9. 实施顺序

v3 分两个阶段：阶段一只动入口与调度，数据面沿用 v2；阶段二按 §11 的增量协议重写数据面。 分阶段的理由在 §11.5——数据面重写量级不小于阶段一本身，捆成一步会丢掉阶段一最好的性质 （「执行与档案两个最难的部分完全复用 v2 的设计和测试」）。但分阶段 ≠ 分版本： 阶段二是 v3 的一部分，启动条件是阶段一的语义（投递永不因冲突失败）在 DB 上站稳。

本节是按「依赖」排的（先铺基础设施，再往上接）。实际执行按 doc/20 的用例 loop 排 （先让最痛的 409 消失，再为下一个用例引入下一个组件）。两套顺序不冲突，映射关系：

阶段二：数据面增量协议（第 14–18 步）

设计依据是 §11（Kimi 抓包对照）：帧从「发生了一件事」改成「某实体的某字段变成了这个值」， 流式正文 op:"append" 只推增量，O(n²) 重发变 O(n)，「流式中→定稿」退化为一次普通字段变更。 §11 给出的是形状与判断，不是可实施的规格——所以第 14 步是先把规格写死。

  1. 协议规格：实体树（message → block）、op:set/append + mask 字段路径、 跨实体全局单调 offset、带 offset 的 heartbeat、显式 done 终止符。 落成文档：存储 schema、帧形状、续传语义（重连 from=offset 时增量帧如何补齐—— 实体在库里，追赶者读实体当前态即可，这是增量协议续传比 Partial 简单的地方）
  2. 存储层：message 实体在 status:GENERATING 时创建即落库，正文 append 累积进库。 崩溃窗口（§10 问题 7）从这一刻起结构性消失；删 RestoreMessage 与 handleRestore 悬空路由——doc/15:252 的「等 MQ」注记就此撤销， MQ 不再承担这个兜底职责（多副本投递价值不受影响，doc/16 #8c 相应收敛）
  3. 订阅层：删 Subscription 的 Partial 分支——预留号、AppendSealed、 ErrSealConflict、dropPartialTail、游标不前移、buf.gen 防忙等全部退役； run 级续传统一为「按 offset 追赶 + 读实体当前态」； 「流式中→定稿」变成一次 op:"set" mask:"message.status"
  4. 前端：从「按 Kind 分派渲染」改成「维护实体树、按 mask 打补丁」； done 终止符替换 isTerminal 判定（连带消掉 liveID-有值-档案-未写的 404 窄竞态）； heartbeat 带 offset 让客户端能区分「服务端卡住」与「在等 LLM」
  5. 测试与文档：server_test.go 里测事件形状的大部分改写； doc/10、11、15、16 同步，本文 §10 决议销账

阶段三：连接拓扑演进（未来）

阶段二完成后，如果多标签页场景下浏览器连接上限成为瓶颈（§10 问题 10：HTTP/1.1 并发上限 6， 2 个标签页 × 2 条 SSE = 4 个坑），可以把两条 SSE（会话级 + run 级）换成一条 WS 多路复用 （per 账号，承载所有会话）。§4.7 的 SessionFeed 已做存储与传输分层，换 WS 不需要动存储层， 只需要写 SessionFeed 的 WS 实现。

不在本顺序里的：账号级订阅（需先有 session 表，见 §10 问题 9）、adk.TurnLoop 换底座（阶段二之后再评估，见 §10 问题 11）。两者都不要提前塞进 v3—— 账号级订阅有硬前置；TurnLoop 尤其诱人（它原生就有收件箱、合并窗口、抢占和 checkpoint-resume），但换底座等于同时改语义层和执行层， 而 v3 的全部风险预算应该花在语义层（阶段一）与数据面（阶段二）上。

每一步 -race 全绿再走下一步（v2 的门槛保留，两个阶段同样适用）。 第 7 步尤其要压测不变量 8： 写一个测试，让 Enqueue 与 drive 收尾在纳秒级并发，断言消息不会搁浅。 阶段二的对应门槛：第 16 步删 Partial 分支前，先用测试钉住 「重连读者在流式中途加入，能看到实体当前态且不重不漏」。

10. 待定问题

  1. 会话级 seq 与 run 级 seq 的关系：已决——独立命名空间，但 inbox.seq 与 session_log.seq 同源。理由：两者都是会话粒度，共用一个计数器能让「消息入队」 在两张表里用同一坐标，客户端对齐时间线无需换算。run 级 seq 保持 per-run， 因为它的续传语义（Partial 预留号）依赖「本 run 内 max+1」，跨 run 共用会破坏不变量 4。

  2. beginRunAtomic 事务失败后消息怎么办：未决。三个选项：

    • (a) 事务回滚，消息留在 inbox，等下一次 Enqueue 或 trySchedule 捞起 —— 简单，但可能长时间搁浅（如果用户不再发消息）
    • (b) 回滚后立刻重试 N 次，仍失败则写一帧会话级 error 通知客户端 —— 用户可见，但要新增一种 SessionEventKind
    • (c) 起一个后台定时器周期性 trySchedule 所有非空 inbox —— 兜底最稳，代价是多一个常驻 goroutine

    倾向 (a) + (c)：正常路径靠 (a)，(c) 作为低频兜底（比如 30 秒一次）。 (b) 的可见性收益不大，因为 (c) 会让它最终一定被执行。

  3. Stop 要不要清空收件箱：已决——不清（§4.8）。理由：停止的语义是 「这一轮不对」，不是「我说的话不算」。但前端必须明示剩余排队条数并提供一键清空， 否则用户会觉得「我明明停了它怎么又跑了」。这是产品决定，不是技术决定。

  4. 合并窗口要不要设上限：已决——设上限 10，超出拒绝。 参考实现（WeKnora internal/handler/session/steer.go:52-57）取 maxSteerQueueDepth = 10， 注释给的理由比「太长会混乱」更硬：

    past that the run is clearly ignoring its user and the honest answer is to refuse instead of queueing silently

    即：排到 10 条说明这场 run 已经跑得太久、久到用户在对着它自言自语， 此时静默排队是不诚实的——应该拒绝，让用户意识到「得先停下来」。 本文早期草稿倾向「软上限 5，超出的留给下一场 run」，那个方案是错的： 它把「拒绝」变成「悄悄延后」，用户看不到任何反馈。

    拒绝要怎么表达？投递永不失败（不变量 7）与「超出上限要拒绝」看起来冲突，其实不冲突： 不变量 7 说的是不因状态冲突失败（会话忙不是错误）， 而队列过深是用户的输入本身需要被重新考虑，这是 4xx 的正当用途。 POST /api/message 返回 422 + 当前排队条数，前端提示「已经排了 10 条，先停一下当前任务？」。

  5. session_log 要不要修剪：未决。它是永久追加的，长会话会无限增长。 run_log 有同样的问题（v2 未处理）。倾向两者一起解决，不在 v3 范围内。

  6. Queued 响应字段的意义：已决——整个响应体删掉。 本文早期草稿留了一个 messageResponse{MessageID, Queued}，Queued 恒为 true， 理由是「将来可区分已开跑与在排队」。但那要求 Enqueue 同步知道 trySchedule 的结果， 把异步调度变成同步等待，与解耦的初衷相悖。 §10 问题 12 决定 messageID 由客户端生成之后，响应体里再没有服务端才知道的信息—— 所以 POST /api/message 直接回 202 无体，实际状态由会话级流的 message_queued 帧报告。

    结论摘要：

    • 会被打断的三处全是从 v2 继承的进程内机制：闸（s.mu + s.live）、 审批（pending map[string]chan string，Go channel 不跨进程， 副本 A 阻塞等待、POST 落到副本 B → 404 → 审批永久卡死）、事件缓冲（eventMem）。

    • 两处需要新设计：审批跨副本投递（倾向复用 §4.7 SessionFeed.Notify 的模式）、 Subscription 的第二套实现（接口已分层，换实现不动调用方）。

11.3 最重的一条：Partial/sealed 是建模产物

v2 为了「流式正文」发明了一整套特殊机制（预留号、seal、冲突检测、尾部作废、游标不前移）。 根源在于把「正在输出」建成了一帧帧事件，于是必须回答「哪一帧才算数」—— 答案是「都不算，直到 sealed 那一帧」，机制由此展开。

增量协议把「正在输出」建成一个持久实体的一个状态字段（status: GENERATING）。 实体从一开始就存在、就在库里，内容通过 append 持续累积。 「哪一帧才算数」这个问题不成立，于是整套机制没有存在的必要。

连带消失的还有 RestoreMessage——它整个方法的存在理由就是 Partial 不落库造成的窗口 （v2 §9 决议 2）。而这个兜底现在只有一半，且是刻意如此的：服务端的路由、handler、DB 方法、测试都在， 浏览器那一半曾经有过、被主动移除；doc/15:252 明写「暂时保留，等 MQ 落地后再删」（核实过程见 §10 问题 7）。 所以增量协议不是「省掉一个已经工作的兜底」，是省掉一个已知悬空、正等着被 MQ 取代的兜底 ——这让 §11.5 的判断更强：两条路（增量协议 / MQ）都能关掉这个窗口，而增量协议还顺带省掉整套 Partial 机制。

11.4 连接拓扑：v3 的方案不是唯一解

11.5 判断：分两阶段——阶段一不动数据面，阶段二按本节重写

采纳增量协议要重写的东西：Event/StoredEvent/Classify、RunLog 的全部写方法、 Subscription 的 Partial 分支、RestoreMessage、前端整套渲染、以及 server_test.go 里 1200 行中测事件形状的大部分。这是一次独立的重写，量级不小于 v3 阶段一本身。

而阶段一要解决的问题（409、排队、多客户端同步）一个都不依赖它—— 它们全在入口与调度层。把两件事捆在一起做，会丢掉阶段一最好的性质： 「执行与档案两个最难的部分完全复用 v2 的设计和测试」（§4.1–4.4）。

所以结论不是「不做」，而是分阶段：阶段一落地入口与调度（数据面沿用 v2）， 阶段二按本节重写数据面（§9 第 14–18 步）。阶段二不是另一个版本，是 v3 的后半场； 它的启动条件是阶段一的语义（投递永不因冲突失败）在 DB 上站稳。 唯一现在就值得做的是 §4.7 的 SessionFeed 分层——它让将来换传输（SSE→WS 多路复用） 不需要动存储层，成本几乎为零，收益是保住演进路径。

12.2 但 WeKnora 自己已经走出去了：steer

routes_chat.go:72-79 有四个路由，注释写着「Mid-run message injection」：

路由注释里有一句是决定性的：

Accepts even when no run is live (the client then falls back to a normal send)

即投递永不因状态冲突失败——这就是 v3 的不变量 7。而这四个端点与 v3 §4.12 的 POST /api/message / GET /api/session（Snapshot 的 queued）/ DELETE /api/message/:id 一一对应，WeKnora 还多一个 v3 没设计的「提升」。

steerDataConsumed … lives on the event itself (not in process memory) so every replica agrees on what is still pending

12.2c 修正后的结论：窗口是「未上线」，不是「单进程」

12.5 多副本目标下，v3 哪些成立、哪些必须改

doc/03:42 的目标栈（PostgreSQL + Redis + asynq）意味着多副本。 这一节把 v3 的设计逐项过一遍，判定它在多副本下是否成立。

会被打断的三处（全是进程内机制，且都是从 v2 继承的）

机制 当前代码 多副本下的后果
闸 s.mu.Lock(); if s.live != nil { return false }（session.go:93-96） 每个副本各有一把 mutex，互不知情 → 同一会话在两个副本上各开一场 run，两边都写 run_archive、都改模型上下文，互相覆盖
审批 s.pending[id] = make(chan string, 1)（session.go:241-247） 最严重：副本 A 的 ask 阻塞在 Go channel 上；用户的 POST /api/approval 被负载均衡送到副本 B；B 的 pending 里没有这个 id → 返回 404，审批永久卡死，A 那边的 run 一直挂着直到 ctx 取消。Go channel 不跨进程
事件缓冲 eventMem（进程内存，eventmem.go:75-153） 订阅只在拥有该 run 的副本上能拿到实时帧；其他副本只能读库追赶，Partial 帧永远看不到（它本来就不落库）。阶段二（§9 第 15 步）后正文随 append 进库，这行的「永远看不到」前提消失，剩下的只是实时帧跨副本投递问题（归 MQ/传输层）

WeKnora 正是为此才有 internal/stream/ 的 memory_manager 与 redis_manager 两套实现 （doc/10:100 已经注意到了这一点，但只当作「sink 抽象」的印证，没意识到它意味着 tako 迟早也要写第二套）。

恰好成立的部分（v3 的两个新组件）

inbox 与 session_log 都是 DB 表，不是进程内存——这正是 WeKnora steerDataConsumed「lives on the event itself, not in process memory, so every replica agrees」 那条教训的同一个答案。v3 独立走到了同一处。

更关键的是 beginRunAtomic：inbox.Drain + BeginRunInTx + run_started 在同一个事务里。 这是数据库级原子性，跨副本天然成立——不需要分布式锁，不需要 Redis。

一处必须改：把闸从 mutex 变成 DB 约束

v3 的不变量 8（放闸与调度必须原子）目前靠「持 e.mu 时判断 live == nil」实现， 多副本下失效。改法是把「每会话最多一场 live run」表达成数据库保证：

-- Postgres 部分唯一索引：同一会话最多一行 status='running'
CREATE UNIQUE INDEX one_live_run_per_session
    ON run_archive(session_id) WHERE status = 'running';

于是 trySchedule 的语义变成：

两个副本同时 trySchedule
  → 都在同一事务里做 inbox.Drain + INSERT run_archive(status='running')
  → 先提交的成功；后提交的撞唯一索引 → 事务回滚 → Drain 的消息自动回到 inbox
  → **插入失败本身就是闸**

不需要 Redis，不需要分布式锁，不变量 8 在多副本下照样成立—— 因为闸和事实在同一个事务域里。

对比 WeKnora：它用 Redis SetLiveRun + ErrLiveRunExists（redis_manager.go:15-17,383） 做这件事，因为它的事件缓冲已经在 Redis 里了，顺手。tako 用 Postgres 部分唯一索引更省一次网络往返， 而且闸的判定与 run 的创建不可能不一致（同一个事务）—— Redis 方案里 SetLiveRun 与后续写入是两个操作，中间有窗口。

⚠️ SQLite 也支持部分索引（CREATE UNIQUE INDEX ... WHERE）， 所以这一条在当前的测试环境下就能验证，不必等 Postgres。

两处需要新增设计（v3 尚未覆盖）

  1. 审批必须跨副本。pending map[string]chan string 换成 「决策写进 DB/Redis + 持有 run 的副本订阅它」。最小改动是把审批决策也做成一行记录， ask 从「阻塞在 channel 上」改成「阻塞在一个以 approvalID 为键的通知上」—— 与 §4.7 SessionFeed.Notify 是同一个模式，可以复用。 或者用 sticky session（按 sessionID 一致性哈希路由）， 代价是副本挂了那个会话的审批就丢了。倾向前者。
  2. Subscription 需要第二套实现。eventMem → 共享缓冲（Redis Stream 或 Postgres LISTEN/NOTIFY）。 接口已经是 RunLog / SessionFeed，换实现不动调用方—— 这正是 §4.7 把存储与传输分层的收益兑现之处。

结论

多副本目标不推翻 v3，反而是 v3 的一个论据： 它新增的两个组件本来就是 DB 表，事务原子性本来就是数据库级的。 需要改的三处全部是从 v2 继承来的进程内机制，与 v3 的新增部分无关。

换句话说：v3 相对 v2 的改动，恰好是多副本方向上的改动。 这不是设计时预料到的——v3 的全部动机是 409 与多标签页——但结果是对的。
