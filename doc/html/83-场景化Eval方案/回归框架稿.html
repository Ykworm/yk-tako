0. 为什么现在做这一层

0.1 背景与动机

tako 今天有两层机器能自动判红的东西，都是"接口有没有按约定回"，没有一层能判"这件事有没有做成"：

层 在哪 断什么 要模型吗
快闸 internal/runengine/contract_test.go（go test） 端点/帧的字节形状（信封字段序、帧 kind 词表、业务码值） 不要
契约 scripts/acceptance/expected.json + assert_contract.py 端点返回什么（HTTP 码 / 业务码 / 弹窗文案 / data 字段序） 分 tier：core 不要、model 要

这两层断的是"形状对不对"。它们看不见下面这些事：PII 脱敏挂在了错误的挂载点上、看板的正本又回到了进程内存、失败那一轮不落库、围栏被绕过、子代理不建板了。

0.2 病灶：两个具体的失败故事

故事一（这一周真的发生过，只靠现有两层查不出来）：2026-10-23 落地 PII 脱敏时，挂载点选错了——按原计划挂在 prepareInput（模型输入装配的首轮出口）。那个位置只管首轮；而折叠的原料是 mh 原文（user 行按设计存原文给页面显示）→ 对话一折叠，PII 就复活。

现有两层会怎么反应？

  • 快闸：全绿。信封字节、帧 kind 词表、业务码，一个都没变。
  • 契约：expected.json 里的用例全是"端点返回什么"，PII 挂错挂载点不影响任何一条 → 全绿。

也就是说：一个正在漏客户身份证号的缺陷，两层机器验证全部通过。 它之所以被查出来，是因为写代码的人恰好在同一天想到了折叠这条路径。下一条缺陷没这么走运，就是上线三个月后被客户报证件号泄漏。

故事二：2026-10-23 落地任务看板时，靠两样东西验收：存储层单测（换进程读回同一批行）+ 活体脚本（kill -9 → 重启 → resume）。但**"模型会不会真的去建板"这件事没有任何东西在管**——如果某天换了模型、或改了系统提示里的看板约定，模型不再调 TaskCreate，看板上就是空的，没有任何东西会红。它只会在某天有人打开页面说"看板怎么是空的"时才被发现。

所以缺的那一层是：给一个真实任务，看 agent 跑完之后事情有没有做成，并且能机器重跑。

0.3 这一层长什么样（先把名词钉死）

  • 场景（case）：一个可重跑的任务包。四件东西凑齐：
    1. 准备（prepare）：跑之前要有的东西——账号/租户/模型密钥、预置文件、工作区初始状态、特殊租户（见 §2a）。
    2. 动作（act）：让 agent 干什么（一句话，或一串工具调用）。
    3. 判定（assert）：什么算"做成了"。可以有多条。
    4. 证据（evidence）：红了要能复现——runId、帧 dump、runlog 行、文件内容。
  • 判定分四组：按「判定锁在谁身上」分，不按「模型会不会抖」分（这一层的关键设计）：
    • 理由：M=M 的门禁只有在被测对象确定时才成立。模型是随机的——若判定的是「模型有没有做 X」，M 次里过 2 次不是 bug 而是常态；把它判红，红灯就失去信号（flaky 红灯比没红灯更坏：训练人忽略它，久了就不信它）。
    • 组 判定锁在 形状 / 档 跑 M 次的稳定性 红了说明
      K · 系统行为 引擎的字节与裁决 probe / 快档 确定（M=M 必过） 引擎回归了，要修引擎
      S · 系统行为但要真 run 引擎的裁决（崩、留痕、装配） run / 慢档 确定 引擎在最坏情况下站不住了
      B · 模型行为 模型的行为涌现 run / 慢档 随机（M/M 不常有） 模型行为变了：看基线才知道是不是回归
      C · 只登记 — — — 不判红绿，只登记
    • 「硬断言」与「语义判定」不再是分档，而是判定方法：硬断言（run 终态、帧 kind、行数、文件内容、库里无明文）属 K/S 两组；语义判定（"回答切不切题"）要另一个模型当裁判，落 B 组。
  • 判定 / 归因 / 门禁：三层分开（一条案例红绿之后，还得说得清「红的到底是什么」）：
    • 层 问什么 取值
      判定 这个案例这次算不算过 passed == M → 过；否则不过。只有这一条是硬规则
      归因 红的成因 engine_regression（K/S 组红）· model_below_baseline（B 组红且低于基线）· model_baseline（B 组红但等于基线——已知的模型水平）· unasserted（C 组）· incomplete（有 run 没跑成 / 没触发）
      门禁 这次 eval 要不要非零退出 只有 engine_regression 与 model_below_baseline 让退出码非零；model_baseline / unasserted / incomplete 报告里单列
    • 基线（baseline）：B 组案例首次实测抄真值写进 yaml（同 doc/58 drop_ratio 的校准纪律）。基线只用于归因，不改变判定——判定永远是 M=M。模型水平低本身不算回归：B 组红且低于基线 = model_below_baseline（要查）；B 组红但等于基线 = model_baseline（已知的模型水平，不拦门禁）。
  • outcome 枚举：机器没跑成 ≠ 模型没做对（每次 run 的结果三态）：
    • scored：跑了，判了，过或不过都算数。
    • skipped：前提没满足（例：折叠景这次没折够、围栏景模型压根没去越界）→ 这一场不作数，不是失败。
    • errored：机器坏了（引擎 500、超时、DB 不可达）→ 这一场不作数，不是失败。
    • M 次里只要出现 skipped / errored → 该案例判 incomplete（待重跑），不是红。incomplete 默认放行 + 报告单列（不算红、不拦门禁，但报告里必须有一节写清「这次没覆盖到哪条、为什么」）；allow_incomplete: true 是声明不是开关——标出「这条设计上就可能不触发」（模型触发类负向场景）。
  • 语义判定怎么抗抖：抖动吸收在裁判层——一次 run 内让裁判采样 judge.samples 次取多数；案例层仍是 M=M（跑 M 次，每次的裁判结论取多数）。两层不混：裁判层吸收「同一次判定里的抖动」，案例层管「跨 M 次的稳定性」。
  • C 组·只登记不断言：模型行为本身不稳的用例，登记原因、不假装覆盖——与 expected.json 的 declared_not_asserted 同一处置。
  • 快档 / 慢档：
    • 快档（fast）：不需要模型（能靠探针/存储层直接判的），秒级，设计上每次提交都能跑（v1 手动——仓库的 pre-push 钩子只比远端 SHA，不跑测试）。
    • 慢档（slow）：要真模型跑一轮（几十秒到几分钟），发布前或每天跑。
  • 隔离实例：场景跑在一个独立的引擎上——独立 PG 库 + 独立 Redis db + 独立工作区目录。不能拿开发库当靶子（同 scripts/acceptance/README.md 的纪律：脚本会注册账号、建项目、留会话）。
  • 折叠的两件事必须先钉死（它是故事一守卫人的命门，缺一件整条场景就是假的）：
    • 怎么逼出来：折叠线由引擎的 -compact-window 启动参数决定（默认 256000，触发线 239616——两轮对话差三个数量级，永远折不了）。eval 引擎以小窗口起（v1 = 16384，触发线 = 16384 − 16384/5 = 13108 token）；折叠场景在 prepare 里往工作区写一个 ~80KB 的 decoy 文件、第二轮让模型读它——tool_result 一膨胀，下一次模型调用前必折。内容大小由 prepare 控制，不靠模型心情。副作用：其它慢场景也会偶发折叠（token 计费多几笔摘要调用、上下文变短），E2 全量跑时盯着，假红再把窗口调大。
    • 怎么知道折了：扫 run 的全部 usage 帧（kind=usage 带 promptTokens，跟 nextOffset 拉全），出现一轮环比骤降（v1 口径：掉 ≥50%，阈值 E2-1 用实跑校准抄真值）即判"折过"。不用 compacted 列——那是 run 末会话压缩给历史行翻的标志（store.go EndRun 语义，正常跑完也触发），会把"没折"误判成"折了"。
  • 断言配对原则：负向断言（"库里不含明文"、"越界调用被拒"）必须配一个正向锚点（"掩码串确实出现"、"工具确实被调过"）。只断负向的场景会被"这件事根本没发生"骗绿。

2. 形状：场景文件长什么样

一个目录 scripts/eval/cases/*.yaml，一个场景一个文件，人可读、可手改（不是 JSON——JSON 写不出注释，而"防的是哪次事故"必须写在文件里）。

id: b-pii-fold                 # 唯一 id（报告与台账都用它指认）
tier: slow                     # fast | slow
desc: 折叠一次之后，模型输入侧不许再出现明文证件号
guards: 2026-10-23 挂载点选错（只挂首轮装配）→ 折叠后 PII 复活

baseline: 5                    # B 组首次实测抄真值；只用于归因，不改变判定
prepare:
  tenant: seeded               # 注册账号 + 配租户模型（harness 已有 signup）
  workspace_files:
    decoy.txt: "……（约 80KB 的填充文本，专门把输入撑过窗口线 13108）"
act:
  rounds:                      # 单轮场景可只写一个 text 字段

  - type: usage_token_drop      # 前置：折叠确实发生（usage 帧 promptTokens 环比掉 ≥50%）

    table: run_model_messages
    column: text

2.0 两种场景形状（yaml 里用哪个由「有没有 act.rounds」决定）

形状 什么时候用 runner 做什么 跑法
probe 判定只需要一次 HTTP 响应的字节（K 组七条） 不发 run，只打 /api/dev/*（server.go:204-210，只在 -dev 模式注册） 秒级，不打模型，不花钱
run 判定要读帧 / 读库 / 读工作区文件（S 4 条 + B 4 条） 起 run、等 terminal 帧、再判帧与库 慢档，要真模型

probe 为什么存在：引擎已经有一批 -dev 才注册的诊断口（/api/dev/workspace/read、/api/dev/workspace/bash、/api/dev/pii-check、/api/dev/file-lock-check、/api/dev/file-fingerprint、/api/dev/workspace/file），它们让工具层的字节可 curl。没有它们，K 组就只能「起 run + 盼模型照着调」——而模型不听就是假红（这条道理是引擎自己在 product_api.go:904-908 写的）。

2a. 两类场景的准备硬约束（不写进 prepare 就进不了 cases/）

  • mcp-fence 类：进围栏的只有租户自己配的 MCP（mcp.go 对租户 server 套 seatbelt 围栏；引擎自己的 mcp.json 是系统 MCP，按设计不包——拿它造这条场景必假绿）。prepare 必须：
    1. 往该租户存储根放一个最小 MCP stdio server 脚本（python3，initialize / tools/list / tools/call 三招就够；探针工具去读 /etc/hosts 这种围栏外路径）；
    2. PUT /api/tenants/{id}/runtime-config（admin）注册进 mcpServers——command 必须是租户存储根内的绝对路径，外部命令（如 npx）启动即拒（mcp.go 的 commandInsideRoot 硬约束）；
    3. act 里模型确实调用该工具（配 tool_called 正向锚点），"被拒"这件事才有主体。
  • failtrace 类：确定性失败注入 = 注册一个配了无效模型密钥的独立租户（格式合法、模型调用必 401）→ run 必进 error 终态。若实跑发现无效 key 在起 run 前就被装配层拒掉（202 都拿不到），备选注入 = kill -9 仿 board-survives-crash 的路子，E2-3 实跑时钉死并回填这里。

判定类型（v1 清单，够用就好）：分两组，按场景形状对号入座。

probe 组（作用在一次 HTTP 调用的响应上——K 组七条全靠这六个）：

type 断什么 怎么读
http_status HTTP 状态码（202 / 400 / 409 …） 响应行
http_envelope 信封的 code / message / data 字段序与值（产品 API 的字段序是契约） 响应体
json_field data 里某字段 = / ≠ / ≥ / ≤ 某个值（waitedMs ≥ 1500、sha256 变没变、weak=false） 响应体
output_contains data.output 含某串（围栏说明、页脚、「Operation not permitted」） 响应体
output_not_contains data.output 不含某串（第 2 页不含第 1 行） 响应体
file_content 工作区某文件含 / 不含某串（notes.txt 含掩码串、不含明文） 工作区目录

run 组（作用在一场 run 上——S 组四条 + B 组四条全靠这七个）：

type 断什么 怎么读
run_status run 的终态（complete / error / stopped） GET /api/runs/{id}
frame_kind 帧里出现过某个 kind（task / tool_call / tool_result） GET /api/runs/{id}/frames（跟 nextOffset 走，单批上限 200 帧）
tool_called 某工具被调过（TaskCreate / bash …） 帧 + runlog 两处都查
db_rows 某表（可带 where:）某条件的行数（run_tasks 有 N 行） psql
db_no_plaintext 指定行不含明文（PII 类的核心判定；必须带 where: 排除按设计存原文的 user 行） psql
db_value_contains 正向锚点：某表（可带 where:）某列含某串（掩码串出现、摘要行存在） psql
usage_token_drop 折叠发生：usage 帧 promptTokens 环比骤降 ≥ 比例（前置断言，防"没折也绿"） frames 全量拉取

另外两个机制（不是判定类型）：

机制 是什么
llm_judge 语义判定（B 组用）：裁判模型判"回答是否切题"，输出 {"pass":bool,"reason":str}；配 judge.samples（默认 3）取多数——抖动吸收在裁判层
declare_only C 组：只登记原因，不断言

  • 两个目录不合并：acceptance/ 断接口，eval/ 断任务。它们用同一套底座（scripts/acceptance/harness.py 的 HTTP 调用、.env 取密钥、psql 补丁、红绿计数）——同一机制只留一份真源，不另起一套 Python HTTP 底座。
  • 报告形状（跟 acceptance 一致，红了退出码非零）：每条场景一行 ✅/❌/⏭️，失败行附复现材料（runId + 帧 dump 前 N 帧 + 相关 DB 行）。报告能整体贴进 commit message。
  • 报告要能回答「红的到底是什么」（§0.3 的三层）：每条案例一行带归因 reason（engine_regression / model_below_baseline / model_baseline / unasserted / incomplete）+ 基线 baseline + runs[] 逐次明细（每次 run 的 outcome / 过没过 / asserts[].detail / 时长 / runId）。退出码只由 engine_regression 与 model_below_baseline 触发，其余单列不拦。incomplete 另有一节写清「这次没覆盖到哪条、为什么」。
  • 落盘的报告（tmp/eval-report-<ts>.json，不入库）就是上面这套结构——将来接 CI 直接消费它。
  • v1 不落 CI（仓库现在没有 .github/workflows）：本地跑，报告由人决定贴不贴。接 CI 是后面的事（scripts/ 里那个 pre-push 钩子只比远端 SHA，不跑测试）。

5. v1 明确不做

  • 不做 UI 场景（Playwright 活体另立 loop——doc/44 那一档已经证明 UI 活体是独立的一摊）
  • 不做「从生产日志自动挖场景」（要先有日志挖掘，v1 语料手工固化就够）
  • 不做 CI（仓库没有 CI 基建；v1 是本地跑）
  • 不做性能压测 / 公平性压测（多租户公平性是 doc/28 那一档的活）
  • 不做「每次提交都跑慢档」（慢档要真模型、要钱、要时间）
  • 不改 internal/runengine/ 的生产代码：Eval 是站在引擎外面看它的；发现缺陷 → 另开一拍修引擎，而不是在 Eval 里加后门

6. 收尾：所以这一层解决了什么

一句话：tako 今天能自动判红的是"接口有没有按约定回"，判不了"活到底干完了没有"——而后者才是客户买的东西。

这一层把「任务 → 跑 → 判定 → 出证据」变成一条可重跑的流水线，于是：

  • 挂载点选错、围栏被绕、看板没人建、失败轮不落库——这些缺陷从"靠人想到"变成"机器会红"；
  • 那一周手工验过的活体场景，从"只有那天的会话记得"变成"任何人任何时候都能一键重跑"；
  • 判定分四组，该稳的稳（K/S：判定锁在引擎字节上，M=M 必过）、会抖的明说会抖（B：看基线，不把"模型今天心情好"当成通过）、不稳的登记不假装（C）；
  • 判定 / 归因 / 门禁三层分开：红了能立刻分清是引擎回归、还是模型就这水平——而不是只给一个红叉。
