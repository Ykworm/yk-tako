83 配套 · Tako Agent 全课程学习知识点表（含 EvalOps）

性质：学习辅助清单，不是施工契约；配套阅读为 企业级 Agent 课程对 Tako 的借鉴分析。已按完整十篇课程扩充，不再只覆盖 Eval 五章。 日期：2026-11-16。 评分口径：对 Tako 的有用程度按当前 Agent Runtime 与场景 Eval 的需要评 1～5 分，5 分最值得优先掌握；分数不表示该项是否缺失。 功能口径：✅＝已有对应能力；🔶＝只有部分、相关机制或只在公开基准中实现；⬜＝尚未具备；—＝模型原理、学习方法或非功能项。已有 Runtime 功能不等于已有自动 Eval。 User 一栏留空，可自行填「不知道／听说过／能解释／能实操」。

Token／Tokenizer／Prompt／Reasoning 理解模型输入输出如何计量、文本如何切分、指令如何进入，以及推理输出为什么不能等同于确定性执行。 4 / 5 — 属于模型基础，不是单独产品功能
PreTrain／SFT／RLHF 理解预训练、指令与工具训练、人类偏好对齐分别塑造什么能力和行为代价。 3 / 5 — 属于模型训练原理，Tako 不负责训练
Prefill／Decode／KV Cache 分清输入处理与逐 token 生成阶段，理解上下文长度、缓存和输出量对时延与成本的影响。 4 / 5 🔶 有 token 与 TTFT／TPOT 观测，推理内核由模型服务承担
Temperature／Top-p／Top-k／Logprobs 理解采样如何改变输出分布与稳定性；评测要记录可得参数，不能假设不同 Provider 都支持相同控制。 4 / 5 🔶 由模型客户端与厂商能力决定，未形成统一评测控制面

模型与确定性系统的职责边界 模型负责理解、规划和生成；权限、状态、预算、幂等、验证与恢复由可检查机制承担。 5 / 5 ✅ 是 Tako 现有架构的核心分工
Autonomous 与 Workflow 选型 开放探索用自主循环，固定步骤用工作流，复杂任务再组合；不是所有任务都套用同一图。 5 / 5 ✅ 已有模型工具循环、持久 DAG 与混合编排
ReAct 与 Plan-and-Execute ReAct 在决策—行动—观察中局部推进；Plan-and-Execute 先规划再执行，两者可在计划审批与重规划中组合。 5 / 5 ✅ 已有工具循环、计划审批与有界重规划
Workflow 常见模式 Prompt Chaining、Routing、Parallelization、Orchestrator-Workers、Evaluator-Optimizer 分别解决固定分解、选择、并行、协作和迭代优化。 4 / 5 🔶 已有并行、编排与验证，不需要为覆盖名词另建固定链
Agent 工程能力分级 从功能开发、业务链交付到系统设计和平台演进；可用能否解释、验证、归因和负责发布进行自评。 3 / 5 — 属于学习与职业能力模型
AI Native 资产与责任 人和 Agent 协作后仍需明确目标、审查、接管与责任；个人／团队规则、SPEC、Skill 和验证资产要分清归属。 3 / 5 🔶 有租户、Agent、Skill 与验证资产，组织方法不属于引擎功能
PE／CE／HE／LE／GE 五层视角 课程用 Prompt、Context、Harness、Loop、Graph 区分调优层次；实践顺序是先简单表达和信息，再改执行壳、循环和图。 4 / 5 🔶 五层都有相关机制；这些缩写是课程框架，不是统一行业标准
AI Coding 的责任与风险适配 从追求全自动改为按风险分配自动化；评价总交付成本，不只看生成速度和 token。 4 / 5 — 属于工程原则，由现有验证与审批机制支撑
SPEC／SDD 把模糊需求变成可执行规格，明确输入、输出、约束和验收，避免 Agent 自行猜完成标准。 5 / 5 ✅ 仓库已有方案真源、施工包与验收契约工作方式
Contract-First 与不变量驱动 先写接口和任何路径都不能破坏的条件，再实现；例如旧执行者不能写、审批前不能修改。 5 / 5 ✅ 契约验收和多种 Runtime 不变量已落地
Test／Eval-Driven Development 先用失败任务定义结果与评分，再实现功能；测试确定性机制，Eval 处理模型参与的开放任务。 5 / 5 🔶 测试和公开基准已有，场景 Eval 驱动流程待建
Loop Engineering 给模型工具循环加入停止、验证、预算、恢复和证据，而不是让 while 循环无限试错。 5 / 5 🔶 已有循环、停止、恢复与验证，完整原生自主预算未齐
Independent Verification 由未参与生成的检查或审查者验证产物，避免模型自己声明完成；它与外部 Eval Grader 可共享规则。 5 / 5 🔶 有结果验证与发布准入，未形成统一独立验证接口
Progressive Delivery 从代码完成到受控上线，经过离线评测、少量用户试用、监控和异常恢复。 3 / 5 ⬜ 尚无完整渐进发布系统
Agent-Friendly Repository 让代码、规则、真源、测试和文档有稳定落点，Agent 不需要猜项目约定或读取过期说明。 5 / 5 ✅ 已有 AGENTS、doc 真源、验收脚本与模块地图
Context Manifest 记录一次任务实际使用的规则、文档、工具、技能和版本，使上下文来源可复查、可复现。 5 / 5 🔶 有部分 Trace 与配置摘要，尚无完整 Manifest
AI Coding Harness 把 Context、工具、沙箱、编排、验证、恢复和观测组合成可治理执行壳，不等于单次 Agent Loop。 5 / 5 ✅ Tako 本身已有这类 Harness 的主要组成
模块化单体起步 先保持单入口与清楚模块边界，只有长任务和扩展需求出现才拆分布式组件，避免过早微服务化。 4 / 5 ✅ 当前采用唯一入口，并按需接 PG、Redis、Redpanda 等
Decision Matrix 与 ADR 对候选方案列约束、证据与取舍，记录决策和后续翻案，避免只留最后结论。 4 / 5 ✅ 有 doc/problems/ 决策档案与公开基准证据
M0 质量基线 在优化前记录首批任务的结果、证据、成本、时延、安全和失败类型，后续提升才有比较对象。 5 / 5 🔶 有 GAIA 基线，尚无完整产品场景 M0 基线
Provider Adapter 与统一模型调用 上层通过统一模型接口使用不同厂商，同时保留 Streaming、Tool Calling、Reasoning 等能力差异。 4 / 5 ✅ 有 OpenAI／Anthropic 适配、模型解析与 Translator
Model Registry 按模型引用建立并复用客户端；缓存连接不等于能力注册、自动路由或模型治理平台。 4 / 5 ✅ 有按 ref 与租户配置缓存的 ModelRegistry
Capability／Task Profile 路由 按任务需要的视觉、工具、推理、成本和稳定性选择模型；必须用配对 Eval 验证策略。 3 / 5 ⬜ 可手工指定 modelRef，不能按任务能力自动路由
Reliable Executor／Fallback 对模型失败按类型决定重试、超时、降级或停止；Fallback 不能无条件切换模型放大成本或改变行为。 4 / 5 🔶 有部分错误与超时处理，无统一自动降级链
Logical Call 与模型 Attempt 一次业务模型调用可能有多次网络尝试；它不同于 run、Task attempt 和恢复 epoch，不能混为同一计数。 4 / 5 🔶 有 run／epoch／Task attempt，未统一模型 Logical Call 模型
Structured Output 与 Output Contract 用 Schema 和校验阻止无效模型输出进入下游，失败时明确是重试、修复还是拒绝。 5 / 5 🔶 工具与部分结构化工具有校验，尚无统一模型输出契约层
Streaming 与最终提交 流式片段用于展示，最终业务状态只在完整校验和定稿后提交，避免半截输出变成事实。 5 / 5 ✅ 有帧流、runlog 与最终定稿分离
模型版本与治理 每次调用记录模型、租户、用量、Trace 和策略版本；模型升级要回归，不只看接口成功。 4 / 5 🔶 有 Trace、用量和模型 ref，完整路由策略版本治理未建
Analysis State 保存开放分析中的目标、假设、证据、未决事项和结论，不只依赖聊天历史恢复。 4 / 5 🔶 有 run 状态、runlog、journal 与 Task 记录，无统一 Analysis State 对象
Scheduler／Queue／Worker／Lease 调度器分配持久任务，Worker 持租约执行；心跳和代次用于接管与阻止旧执行者写入。 5 / 5 ✅ 已有持久调度、租约／epoch、双副本与崩溃接管
故障注入与 Runtime Invariant 主动 kill -9、断工具或制造并发，证明恢复后仍满足不重复、不越权、不写旧状态等条件。 5 / 5 ✅ 已有多类 kill -9 和故障活体，统一分类可继续完善
Decision Context Contract 为规划、工具调用、报告等不同决策规定必须、可以和禁止看到的信息；关键输入缺失时拒绝猜。 5 / 5 🔶 有统一装配与权限规则，未形成按决策的通用契约层
Context Schema／Provider 每条上下文携带来源、版本、权限、可信度和生命周期，由不同 Provider 提供身份、任务、状态与知识。 5 / 5 🔶 有多种装配来源，未统一成完整 Schema／Provider 模型
Metric Registry 与数据血缘 固定指标定义、别名、粒度、时区、来源和计算规则，防止模型从字段名猜业务含义。 1 / 5 ⬜ 属于 DataAgent 业务语义层，非 Tako 当前目标
动态 Context Assembler 按当前 Step 过滤、排序和分配 token，优先保留目标与必要状态，而不是一次性拼接所有历史。 5 / 5 🔶 有装配、折叠、溢出与预算，尚无统一按 Step Profile
硬过滤与软排序 权限、租户和有效期先作硬过滤，相关性只在合格候选中排序，防止高相关性越过权限。 5 / 5 ✅ 记忆与工具有权限／范围过滤，具体决策证据仍可增强
Artifact Store 与引用 大结果、日志、图表和文件落持久存储，Context 只带路径或引用，避免每轮重复传输。 5 / 5 ✅ 有项目 runtime、media、bash 输出、fetch 与不可变结果
Agentic Evidence／Claim-Evidence 围绕信息缺口持续查询，区分假设、证据与结论，让每条关键结论能回到具体来源。 5 / 5 🔶 有 researcher、搜索抓取和文件证据，未形成统一 Claim-Evidence 模型
上下文生命周期与摘要分工 分清 History、State、Checkpoint、Summary；步骤、阶段、交接和用户摘要不能混用或跨生命周期误带。 5 / 5 🔶 已有多种记录与折叠，统一生命周期契约仍可补强
Parent-Child Handoff 与 Context Drift 子任务只接必要目标、权限和证据；长任务监测目标偏移、事实失真、重复工作和来源丢失。 5 / 5 🔶 有子代理边界与继任 handoff，缺系统 Context Drift 评分
Context Security 与信任边界 系统规则、用户输入、企业知识和外部内容分级；网页和工具结果中的文本不能自动升级成指令。 5 / 5 🔶 有权限、PII 与部分不可信内容处理，完整信任分级评测可补
Context Decision Trace 记录候选信息、过滤原因、排序、预算、压缩和最终装配，区分没召回、被过滤、被挤掉与模型推理错误。 5 / 5 🔶 有最终输入与步骤 Trace，完整候选／过滤决策证据未齐
Context Eval 指标 评估关键上下文召回率、噪声率、新鲜度、引用正确性和 token 效率，而非只看最终答案。 5 / 5 ⬜ 尚无统一 Context 指标集
Capability Architecture 根据边界选择 API、Tool、Skill、Workflow、SubAgent 或 MCP；内部函数不必为了形式强行协议化。 5 / 5 ✅ 已有这些主要能力形态与明确分工
三层 Tool Contract 分别定义模型如何理解参数、Runtime 如何执行、企业如何治理权限和审计，避免所有职责塞进描述字符串。 5 / 5 🔶 有 schema、执行和权限机制，未统一称三层契约
动态最小 Tool Set 按租户、角色和任务阶段只给必要工具，降低误选、越权和上下文成本；同时测该出现与不该出现。 5 / 5 ✅ 有工具白名单、分级、tool_search、技能／子代理作用域
Action Runtime 将外部高风险行动拆成提议、校验、授权、审批、执行、验真与补偿，避免参数生成后直接写业务系统。 3 / 5 🔶 有局部审批与结果发布，无通用外部业务 Action Runtime
风险分级、短期凭据与幂等 查询、创建、付款等按风险分权；Agent 不长期持生产密钥；重复请求和部分成功必须有处理规则。 4 / 5 🔶 有沙箱、租户密钥隔离与部分幂等，无通用 Credential Broker
Skill Engineering／Validator Skill 不只装步骤，还应明确使命、边界、完成标准和验证；用固定任务评版本效果、兼容性和干扰。 5 / 5 🔶 技能安装、加载、作用域与任务记录已有，通用 Skill Validator 未建
MCP 与 CapabilityOps MCP 只解决协议接入，不自动提供认证、租户隔离、限流、审计、能力所有者和生产版本治理。 4 / 5 🔶 有 stdio MCP、围栏与 Trace，无完整远程能力运营平台
Memory 与权威数据边界 记忆不能替代当前数据库／文件，不继承历史权限，不覆盖当前任务；当前事实应重新读取权威来源。 5 / 5 🔶 有记忆与 State 分工，需用反例持续验证权限和当前事实优先级
记忆排序与使用追踪 召回同时考虑范围、可信度、新鲜度和来源，记录候选、过滤原因与最终注入，而非只看相似度。 5 / 5 🔶 有 BM25、scope 与证据时间，完整使用决策追踪未齐
召回与行动权限分离 历史记忆可以支撑表达和参考，但不能自动授予 SQL、预算调整或文件写入等当前权限。 5 / 5 🔶 有运行时权限与沙箱，需补“旧记忆不得授权行动”的 Eval
Memory Off／无治理／受治理对照 用同题配对比较无记忆、无治理召回和受治理记忆，证明记忆带来净收益且风险可接受。 5 / 5 ⬜ 尚无定型 Memory 对照实验；现有 A/B 协议可复用
正常／故障／演进三链验收 交付不只演正常 Demo，还展示故障恢复和版本对照，使可靠性、演进效果与证据同时可见。 5 / 5 🔶 有正常、故障和公开基准材料，未组织成统一三链报告
人与 AI 的责任关系 AI 承担更多执行后，人仍需保留目标、标准、验证、接管与最终责任，避免结果在推进而判断者缺席。 3 / 5 — 属于使用与协作原则，不是单独引擎功能
DSH／Claude Code／DataAgent 对照 比较通用 Harness、编码产品与企业业务 Runtime 的目标和取舍；结论需回到源码与实跑证据。 4 / 5 ✅ 本地有 deepseek-harness 参考与 dsh 公开基准臂

B. 场景 Eval、Runtime 与 Memory 核心知识点

知识点名字 知识点描述 对Tako的有用程度（5分满分） Tako是否已经具备对应功能 User是否知道这个概念
Agent Eval 给 Agent 一个任务，运行后根据结果、轨迹和系统代价评分；不是只比较一段最终文本。 5 / 5 🔶 有契约验收与公开基准，场景 Eval 未施工
Task Contract 在执行前写清任务目标、完成条件、允许动作、禁止动作和停止条件，避免“做完”全凭自述。 5 / 5 🔶 有 Task、计划与目标机制，未形成统一契约模板
Eval Contract（质量契约） 把任务成功转成机器可检查的条目：最终结果、必要轨迹、成本、证据与硬性风险。 5 / 5 ⬜ 目前只有方案，未形成统一 Case 契约
Outcome 评测 任务结束后读取文件、数据库、代码和 Task 状态，判断世界是否真的变成目标状态。 5 / 5 🔶 契约验收和公开基准有结果断言，未形成统一场景评分
Trajectory 评测 检查模型、工具、人和恢复机制实际发生的事件；只约束必要条件，不强制唯一工具顺序。 5 / 5 🔶 有 frames、runlog、Trace，尚无系统轨迹评分层
System 评测 统计 token、耗时、模型与工具调用、重试、后台等待和人工交互，揭示结果背后的代价。 5 / 5 🔶 已有用量与 Trace 数据，缺统一场景 Scorecard
关键行为与安全不变量 无论任务结果如何都必须成立的条件，例如不跨租户、不泄漏、审批前不写、交付不重复。 5 / 5 🔶 已有沙箱、权限、PII 等机制，缺统一 Eval 安全集
软评分与硬性否决 报告质量等可给部分分；安全违规直接判失败，不能被其他高分抵消。 5 / 5 🔶 有部分硬性运行时校验，Eval 计分规则未落地
Task Taxonomy 按编码、研究、记忆、长任务、编排、权限等任务类型组织语料，避免题目很多却只测一种能力。 5 / 5 ⬜ 尚无统一 Eval 任务分类
Eval Case 一个可重跑任务包：准备环境、执行动作、检查断言、保存证据，并可包含故障或人工操作。 5 / 5 🔶 有大量活体脚本，尚无统一场景 Case 格式
参考解法（Reference Solution） 用一个已知正确结果证明任务可完成、评分器会接受正确答案，防止把错题误判成能力不足。 5 / 5 ⬜ 场景 Eval 尚未建立逐 Case 参考解法

建议的填写方式

User 一栏不只是标记“见过名词”，最好按能否实际操作填写：

  • 不知道：第一次看到；
  • 听说过：知道大概用途，但不能定义输入和输出；
  • 能解释：能举出 Tako 的一个真实例子，并说明没有它会出什么问题；
  • 能实操：能写出一个 Case／Grader／对照实验，或指出现有实现与验收证据。
