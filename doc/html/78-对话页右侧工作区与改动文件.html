78 · 对话页右侧工作区：项目目录、任务与 Todo，以及改动文件回执

1. 病灶：文件写完了，人却在别的页面找它

一场日常的编码对话：

用户：把报价小工具补上折扣，顺便修一下那个红着的测试
→ 助手 write_file quote.py、edit_file test_quote.py，跑 bash 得到 unittest 输出
→ 回复写「已修好，test_discount 通过」
→ 用户想看看改成了什么样
→ 对话里只有一句「已修好」：工具卡里能翻到调用参数，但没有可点的文件
→ 离开对话 → 左侧「项目」→ 选项目 → 在项目页的文件列表里找 quote.py → 预览
→ 想接着聊，再点回对话，草稿和阅读位置重新找

第二次更糟：同一轮改了三个文件，用户只记得其中一个名字；或者过了两天刷新页面回来，回复还在，却没有任何线索指向「这一轮动过哪些文件」。

另一半问题在右侧面板本身。doc/77 之后，右侧只有一个任务列表：

  • 项目里有什么文件、目录长什么样，对话页里看不到——那是「项目」页才有的东西；
  • 看板 Todo 挂在输入框上方，任务列表挂在右侧，两者都在讲「要做什么」，却分在两个位置；
  • 面板展开时只有一条内容通道，想看文件就得把任务列表换掉，反之亦然。

完整业务链路（今天断在哪）：

用户发消息 → agent 调 write_file/edit_file/bash 写盘 → 调用记录落 runlog（role=tool_call，payload 带 name/args/toolCallId）
→ run 终态 → assistant 回复进 runlog → 对话页渲染回复
     ↑ 链到这里断：回复只说「做完了」，程序手里有调用记录，但没有任何读口把「这轮改过哪些路径」交给页面
→ 用户想核对 → 只能离开对话，从项目页重新找入口

面板的目标链路：

同一份 runlog 调用记录 → GET /api/runs/:id/changed-files（新增，程序派生）
→ 回复结尾「改动的文件」→ 点击 → 右侧工作区开一个文件标签
项目 content/ 目录 → GET /api/workspaces/:id/files（既有）→ 右侧「项目」标签的目录树 → 点击文件 → 同一套文件标签
run_tasks → GET /api/runs/:id/tasks（新增）→ 右侧「Todo」标签（刷新后仍在）

2. 完成线

  1. 对话页右侧是一个可收起的工作区，标签固定三枚——项目 / 任务 / Todo——外加打开文件时追加的文件标签（可关闭）。收起后留一条窄轨，三个入口都在，任务标签带处理项计数；点任一入口展开并切到对应标签。
  2. 「项目」标签显示当前项目 content/ 的目录树：目录可展开/收起（按需拉取子目录），点文件在右侧开文件标签；有刷新；旧布局项目显示可读的迁移提示。
  3. 「任务」标签就是 doc/77 的任务面板：处理条 + 嵌入的任务页，行为逐条不变（含 dockFocus 定位互斥、事件/重连/聚焦重拉）。
  4. 「Todo」标签显示当前会话最近一场 run 的看板（编号、主题、状态、完成数/总数），刷新页面后仍在；桌面端输入框上方的 Todo 条移除，≤860px 仍留在输入框上方（此时右侧工作区整体不显示）。
  5. 每一轮写过或改过文件的助手回复，结尾多一行「改动的文件」：逐个文件一个可点条目，带「写入 / 编辑」标记；点击展开工作区（若已收起）并打开该文件标签。没有改动时不出现这一行。
  6. 文件标签能看内容：.md / .markdown 按 markdown 渲染显示（默认预览态，可切「原文」看原始字节，排版走全局 .md-body；doc/48 §10），其它文本按原样显示（超上限给截断说明与下载），图片直接预览，其它类型给下载；文件读失败有明确文案，不留白屏。
  7. 窄屏（≤860px）与今天一致：右侧工作区不显示、无横向溢出，Todo 回到输入框上方。
  8. 页面上不出现第二套任务详情实现、第二套文件列表协议或「假数据」占位。

3. 非目标

  • 不在右侧编辑文件。这一轮只做「看见 + 打开」，写入仍由 agent 的工具完成。编辑器、保存、冲突提示都不做。
  • 不做目录树上的新建/重命名/删除/上传；这些走项目页（doc/44、doc/48）。
  • 不做 diff 视图与版本对比：「改动文件」只回答改了哪些路径，不回答逐行改了什么。
  • 不做面板拖拽调宽（沿用 doc/77 的取舍），宽度是断点驱动的固定区间。
  • 不做按会话过滤任务：任务标签仍跟当前项目（doc/77 §3 第 1 条不翻案）。 2026-11-14 更新：本条已被 doc/80 取代——任务标签的列表默认显示本会话派发的任务，可一键切「本项目全部」（项目仍是容器，处理条仍是项目级聚合）。
  • 不让模型「自己汇报文件列表」：清单由程序从调用记录派生，模型的回复文字不参与判定（模型漏写路径不影响清单，模型编造路径也进不了清单）。
  • 不做文件标签的持久化：刷新后回到固定标签，已打开的文件标签不恢复（它们是临时查看态，不是用户数据）。

4. 已拍定的设计选择

4.1 右侧从「任务面板」变成「工作区」，标签是唯一的内容通道

doc/77 的面板只有一个内容面。再加文件树就必须有第二面，否则「看文件」和「看任务」互斥，用户又要在两个状态之间来回切。标签页是这一层最省的做法：固定标签回答「这里有哪些种类的信息」，文件标签回答「我正在看哪一个文件」。

  • 固定标签不可关、顺序恒定；文件标签按打开顺序追加，宽度均分、整行换行（不出现横向滚动条——标签本身就是导航，不能有藏起来的项）。
  • 同一路径重复打开只切到已存在的标签，不新建。
  • 收起是整块工作区的收起，不是「项目标签单独收起」；窄轨上三个入口与任务计数保留，保证收起后仍能一键回到任意标签。

没这么做会怎样：要么文件树只能以弹窗出现（离开对话的阅读位置，正是要修的病灶），要么把任务和文件塞进同一个纵向滚动区（两件事互相挤占，任务多了文件永远在屏幕外）。

4.2 目录树与文件字节全部复用既有端点

  • 列目录：GET /api/workspaces/:id/files?path=（doc/48 B1）；它已经只列 content/、目录在前、过滤内部目录与软链、旧布局回 409 117116。
  • 取字节：GET /api/media?path=workspaces/<wid>/<相对路径>（doc/32/76）；非 .media/ 路径按 content/ 读。前端用 authFetch 取 blob（该端点要 Bearer 头，不能直接塞 <a href>）。

没这么做会怎样：新写一套列目录/取字节，就要重新实现一遍「可见性判定 + 路径越界检查 + 旧布局拒绝 + 内部目录过滤」，漏一条就是一个越权或一个打不开的文件。

4.3 「改动的文件」由服务端从 runlog 派生，而不是从回复文字里抓

引擎在折叠上下文时已经有一份文件操作提取器（fileops.go：firstPartyFileEffects 声明表 + classifyToolCall + pathsFromArgs，含 bash 命令的写意图扫描）。它今天只服务「压缩后提醒模型自己做过什么」。这一轮把同一套判定放到 HTTP 读口上，按 run 读 runlog_entries 的 role=tool_call 行。

为什么不让模型在回复末尾自己写文件清单：模型会漏、会改写成口语、会在没写盘时说写了。清单要能回答「程序知道这一轮动了哪些路径」，只能以调用记录为真源；模型的文字是叙述，不是证据。

派生规则（与折叠的 file-ops 完全同源）：

输入 处理
工具名在 firstPartyFileEffects write_file/create_directory/bash… → 写入；edit_file/move_file → 编辑；read_* → 读取，不进清单；memory 等显式 none → 不计
工具名不在声明表 沿用前缀表（write/edit/create/save/append/touch → 写入，read/cat/ls/... → 读取）；有路径但判不出意图 → 记为写入（歧义按强信号记，与折叠一致）
路径来源 参数里的 path 字段 + bash 的 command 写意图扫描（重定向、cp/mv、tee/touch/mkdir/install、sed/perl -i、dd of=）
只保留可打开的 必须能解析到当前项目 content/ 下、stat 到普通文件；绝对路径、含 .. 段、.tako/、.media/、目录、当前已不存在的路径一律剔除
去重与顺序 按首次出现顺序；同一路径再次出现不换位置，op 取最后一次

已知边界（写进契约，不假装覆盖）：

  • move_file 只记录源路径（pathsFromArgs 只读 path 字段），目标路径不进清单；
  • heredoc 与解释器内部写盘对模式规则不可见（与折叠同一份有界性边界）；
  • Task 的隔离 run 写的是 runtime/ 里的工作现场，未发布前 stat 不到，因此不出现在清单里——这是对的：用户在 content/ 里确实还看不到它。

4.4 回复结尾的位置与触发条件

只挂在助手气泡上，且该气泡满足：有 runId、是这场 run 的最后一段（没有 segmentCallId）、状态已是终态（done / error / stopped / interrupted）。位置在用量/复制那一行之下，即「回复的结尾」。

  • 运行中不显示：文件清单随 run 结束才定稿，边跑边列会闪。
  • 停止与失败也显示：已经写下的文件是真实存在的，用户同样需要能找到它们。
  • 一场 run 只拉一次（按 runId 缓存在模块级 Map）；续跑会把状态从终态拉回运行，此时清掉该 run 的缓存，收口后再拉一次。

没这么做会怎样：每渲染一次气泡就打一次接口；或者把清单挂到每个工具卡里——用户还是得自己把多次调用拼成「这轮改了哪些文件」。

4.5 Todo 从输入框上方搬进工作区（桌面端）

同一份看板今天有两个位置会重复。桌面端右侧工作区常驻，Todo 进「Todo」标签；≤860px 工作区不渲染，Todo 仍留在输入框上方。数据源换成新端点（见 §5.2），因此刷新页面后 Todo 不再消失——这是从 doc/41 前端以来一直存在的缺口。

与 doc/77 的边界变更：doc/77 §3 第 4 条「不把 Todo 合并进面板」作废，由本节取代；其余条款（面板跟当前项目、详情抽屉复用、定位 nonce 互斥）全部继续有效（其中「不按会话过滤」一项已由 doc/80 取代）。

4.6 当前 run 的取法

Todo 标签跟「本场对话最近一场 run」：取当前会话气泡里最后一条带 runId 的助手消息。理由：用户看到的是这场对话，Todo 属于这一轮；刷新后历史气泡仍带 runId（rowBubbles 逐行赋值），所以同一规则在刷新前后一致。会话还没有 run 时显示空态，不请求接口。

5. 契约：两个只读端点

两个端点都挂在 authn 上，鉴权与 GET /api/runs/:runId/skills（doc/52 B4）同一套：按 run 所属会话的可见性判，看不见与不存在同字节。信封三字段 code → message → data。

5.1 GET /api/runs/{runId}/changed-files

200 {"code":0,"message":"","data":{
  "runId":"r_01J…",
  "files":[{"path":"quote.py","op":"write"},{"path":"test_quote.py","op":"edit"}]
}}
  • files 恒为数组，无改动返回 []（不是 null）。
  • op 词表只有两个值：write（新建/覆盖/命令写入）与 edit（原地修改）。前端据此显示「写入 / 编辑」。
  • path 是相对项目 content/ 的路径，分隔符 /，不带前导 ./。

错误：

401 {"code":111102,"message":"请先登录","data":null}
404 {"code":112002,"message":"找不到这次运行","data":null}
409 {"code":117116,"message":"这个项目还需要迁移目录后才能使用","data":null}
500 {"code":111901,"message":"服务暂时不可用，请再试一次","data":null}

409 与文件清单端点（doc/76）同一判据：旧布局项目的 content/ 还不能当读根。会话没有项目（历史数据）时返回 files: []。

5.2 GET /api/runs/{runId}/tasks

200 {"code":0,"message":"","data":{
  "runId":"r_01J…",
  "rows":[
    {"no":1,"subject":"读现有脚本","status":"completed","description":"","result":"读到 3 个函数","skillName":"","updatedAt":"2026-11-13T10:02:11Z"},
    {"no":2,"subject":"补折扣函数","status":"in_progress","description":"","result":"","skillName":"","updatedAt":"2026-11-13T10:03:40Z"}
  ],
  "total":2,
  "done":1
}}
  • rows 按 no 升序；deleted 行不列（ListTasks 既有口径）。
  • total = len(rows)；done = status == "completed" 的行数（详情、完成比在前端算，服务端只给这两个数）。
  • status 词表沿用看板：pending / in_progress / completed。
  • 错误字节与 §5.1 相同（除 409：看板不读盘，旧布局也照常返回）。

这是 run_tasks 的第一个 HTTP 读口；工具层的 TaskList 与 kind=task 帧不改字节。

5.3 不改的东西

  • 帧格式、task 帧文本、run_tasks 表结构、TaskCreate/TaskUpdate 回执、GET /api/workspaces/:id/files、/api/media：全部不动。
  • 新端点不写任何表、不发事件、不做缓存表。

8. 风险与边界

  • 清单可能多于用户直觉：bash 的写意图扫描是按模式规则抓的，cp、tee、重定向都会进清单；误抓的路径若不存在会被 stat 剔除，存在的就是真实被写过的文件。宁可多一行、不静默漏一个。
  • 清单可能少于用户直觉：move_file 目标、heredoc、解释器内写入不可见（§4.3）；这是既有提取器的有界性，不在本篇扩容——扩它要同步改折叠行为，另立方案。
  • 目录树逐层请求：目录很宽时要多次请求；目前按需展开、结果缓存在组件内，不做预取。项目文件量以个人工作台为口径，不按大规模仓库设计。
  • 旧布局项目：文件树与改动文件都回 409 提示先迁移；任务与 Todo 不受影响。

9. 所以这解决了什么

agent 写完文件，用户不必离开对话去项目页找：回复结尾直接列出这一轮动过的文件，点开就在右侧看；右侧本身也从「只能看任务」变成「项目目录、任务、Todo、文件」四类信息的一个工作区，收起只留一条窄轨。看、点、继续聊都在同一页完成。

本页由 scripts/build-doc-html.py 从 doc/78-对话页右侧工作区与改动文件.md 自动生成。内容以仓库里的 md 为准——要改，改 md 再重跑脚本。
