只回答「kimi 与 tako 在这两处差在哪」。kimi 指参照实现 kimi-code（本机 clone 在 ref-agent/kimi-code/），tako 指本仓。两边现状都以代码为准，指针见 §3；本篇不作施工真源。

1. 子代理设计

一句话：kimi 的子代理类型可以内置、也可以丢 Markdown 扩展，父代理拿回的是一张固定格式的回执 （编号、类型、成没成、怎么续）； tako 的规格是一个目录里的 Markdown（租户可导入、改、删），回传是子代理最后那段话加一个实例 id—— 交接内容全靠规格约束模型自己写全，程序不做抽取。

方面 kimi tako
规格 例子：
内置 coder 在代码里注册，三样东西：
· description: "General software engineering agent — the only subagent type with file-editing tools…"
· tools: CODER_TOOLS
· 角色前缀：最后一条消息就是全部交接——改了什么、为什么、碰过的每个文件路径、怎么验证

**描述：**内置类型（agent/coder/explore/plan）加多目录自定义 Markdown；frontmatter 还能写 whenToUse、disallowedTools、subagents，正文是带占位的系统提示模板。		 例子：
agents/coder.md 的 frontmatter，字段就这几行：
· description: 把一段要在 workspace 里改文件…的活整包交给它。…最后带回一份自足的交接：改了什么、动过哪些文件、怎么验证的、还剩什么
· tools: [write_file, read_text_file, edit_file, list_directory, search_files, memory, bash]
· 正文：批量活先写成脚本；终稿要自己说全四件事

**描述：**规格是 Markdown 立文件：出厂就是 agents/ 下这几份，租户可以导入、改、删；frontmatter 字段只有 name、description、tools 或 exclude_tools、model，正文不套模板。
回传 例子：
coder 改了 80 个文件，最后一条消息按角色要求写全：
· 改了什么、为什么
· 碰过的每个文件路径
· 怎么验证的

父代理收到带字段的交接：
· agent_id、actual_subagent_type: coder
· status: completed、stop_reason: completed
· [summary] ← 上面那段正文
· resume_hint ← 怎么续跑

**描述：**正文不截断；成没成、是什么类型、怎么续跑都是字段，父代理不用猜。		 例子：
同一个任务，coder 的最后一条消息就是交接，规格要求它自己写全：
· 改了什么、为什么这么改
· 动过的每个文件路径
· 怎么验证的（哪条命令、结果是什么）
· 还剩什么没做、什么值得跟进

父代理收到的：这段话原样，末尾加一行 （本次委派实例：sa_…）

**描述：**没有回执、没有状态字段、没有程序生成的清单文件；四件套是 coder 规格的要求，不是程序的保证（模型没写全，父代理就收不全）。50 KB 上限只是极端情况的一道保险。
续跑 拿编号调 Agent(resume=…)，它从自己的日志里把同一个实例重建出来，没跑完的也能接着干。 只认完整档案；正在跑或半截的拒绝；续跑产出新实例，metadata 写 resumed_from，续不续由模型自己决定。
工具权限 自身 profile 的 tools 与全局、工作区、会话三层策略求交，不是父池子集。 严格父池子集；委派、resume、技能工具在结构上就拿不到。
嵌套 默认禁，写 subagents: 白名单可放开；另有 AgentSwarm 批量派发。 永远不能，子代理拿不到委派工具。
模型 父调用时可以从池里选一个。 规格文件里写 model ref，不写就继承主模型。
运行形态 可后台跑，配 TaskList、TaskOutput、TaskWait、TaskStop；默认 2 小时超时；重启后未完成标 lost 并提醒。 纯前台阻塞，有池级并发闸，没有后台任务和超时管理。

2. 折叠回查

一句话：折叠之后想找回原文，kimi 的入口是程序机械贴在摘要末尾的路径与行号窗口，tako 的入口是 每轮随请求声明的 search_history 工具；两家都不保证一定查得到，差别在入口由谁塞给模型。

kimi tako
有没有专门的查询工具 没有 有，search_history（每轮随请求声明，不用挂）
原文在哪 磁盘 agents/main/wire.jsonl，一行一条 JSON，只追加；每个子代理有自己的文件 数据库 runlog_entries（本会话已提交的行）
模型怎么查 模型要自己想到一个原样出现在日志里的字面串。摘要末尾由程序机械贴了行号窗口，模型可以直接跳到那个区间读某一行（Read 带 line_offset、n_lines=1，长行按 column_offset 续读）；也可以先 grep 在区间里缩小范围；bash 可用时还能用它配合 jq 直接抽某个字段的正文 模型要自己猜出一个确信在原文里原样出现过的词，写进 query 参数；程序不做抽取，只按空格切词，再用 ILIKE %词% 要求所有词同时命中，按时间倒序取；它不对词做语义兜底，猜成同义词就返回零条
举个例子 **前提：**摘要末尾那段 Context Recovery 由程序机械贴上，告诉它原始日志在磁盘上、怎么读，于是它知道自己有得查。

**输入：**用户问“刚才那个 111408 是什么意思，是 key 配错了吗？”，模型从这句话里挑出 111408 这个字面串。

**处理：**在 bash 里跑 grep -n "111408" agents/main/wire.jsonl 拿到行号，再精确读第 2841 行（长 JSON 要按 column_offset 续读）。

**输出：**第 2841 行那条记录的完整内容，原始工具返回的字段和正文都在。		 **前提：**它每轮都能读到 search_history 的工具说明，上面写着“用户在问本会话更早一轮的错误码、原句或工具返回中的一截时使用”，于是它知道自己有得查。

**输入：**用户问“刚才那个 111408 是什么意思，是 key 配错了吗？”，模型从这句话里挑出两个词，填 query = "111408 key"。

**处理：**按空格切成两个词，拼成 text ILIKE '%111408%' AND text ILIKE '%key%'，在已提交的行里按时间倒序取。

**输出：**只返回两个词都出现的行，每行给一段以 111408 为中心、前后各 200 字的上下文；一行都不满足就是“命中 0 条”。
谁保证它能用 程序把路径、格式、行号窗口机械贴在摘要末尾——这部分是硬的；但“去不去查、怎么查”靠模型读那段说明加沙箱权限，是软的 工具 schema 每轮随请求声明，和系统提示同属提示词，能调就保证返回结果，不依赖 bash；但“想起来调、词猜得对”靠模型，是软的
