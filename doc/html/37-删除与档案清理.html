0. 本篇做什么

三件事，一条「保留窗口」主线贯穿：

  1. 项目连带删（D1/D2）：DELETE /api/workspaces/:id 从「有会话就 409」改成连带软删挂载会话 + 清目录。
  2. 单场删除（D3）：新增 DELETE /api/sessions/:id，仅会话属主本人可删；文件按所有权分层清理（系统档案清、产出留）。
  3. 子代理逐字档案的保留窗口（D4）：被 compact 压掉的逐字原文行（run_model_messages.compacted=true，含子代理消息）今天只进不出、永久留库；本篇给它们一个保留窗口，到期由持 PG 租约的清扫器物理删除。窗口同时是删除会话后的档案宽限期——同一个数（D-k）。

1. 背景与动机：两个失败故事

故事一（删除）： 用户「Q4 调研」项目下挂 12 场会话（自己 8 场、成员 4 场），按 doc/35 A6 想删项目得先逐场解绑——12 次操作劝退，项目越积越多，删除形同虚设。连带的问题是单场会话也删不掉：DELETE /api/sessions/:id 在 doc/28 权限表里只有一行设计，从没排期，代码里不存在（server.go 全部路由核实过）。

故事二（只进不出的档案）： 子代理每次委派跑完，逐字消息留在 run_model_messages——被 compact 压掉的原文行打 compacted=true 标记后永不删除（pgstore.go:85 注释明写「保留作审计，不进模型输入」）。会话长跑几轮，这张表只涨不清；runlog_entries 同样永久增长（server.go:1018 注释明说无上限）。借鉴 Kimi / dsh / opencode 梳理后的结论：tako 缺的是「会话生命周期 + 保留窗口 + 可租约的清扫任务」，三件不补，档案只进不出。

本篇把故事一的生命周期（删项目 / 删会话）和故事二的保留窗口合成一套：删除动作软删留档（可恢复、审计不断），清扫器按窗口做物理清除（空间回收）——两个阶段、同一个窗口数。

2. 名词

  • 软删：给 sessions 加一列 deleted_at（timestamptz，可空）。删会话 = 写上删除时刻；本篇之前这列不存在（pgstore.go:28-37 的 Session 结构体只有 8 列），会话从没有「被删除」状态。
  • 活 run：runs 表里 status='running' AND lease_until > now() 的行。lease 未过期 = 真有进程在跑；lease 已死的 running 行是待清扫僵尸，不算活。
  • 逐字档案：run_model_messages 里 compacted=true 的行——被 compact 压掉的原文（含子代理的完整消息序列）。模型输入不读它，页面不读它，纯留档。
  • 摘要行：run_model_messages 里 seq=0 的行（pgstore.go:80），compact 压出来的摘要，「发生过什么」的载体——永不删。
  • 保留窗口：档案从「不再被使用」到「允许物理清除」的时长（D-h，推荐 7 天，启动参数 -archive-ttl 可配）。借鉴口径：保留窗口 = 恢复承诺，两者必须同一个数——所以它也是软删会话的可恢复期。
  • 清扫器：按窗口物理删逐字档案的后台任务。多副本下用 PG 租约表互斥、删除幂等、进度用水印推进（D-j）。
  • 属主：sessions.user_id 指向的用户。删单场会话的唯一门槛（§5.4）。
  • 系统档案 / 产出：会话目录里系统生成的字节（.tako/ 搜索落盘、.media/）/ agent 写的用户资产文件。删会话时前者清、后者留（D-g）。

3. 现状（代码事实）

DELETE /api/workspaces/:id 今天的完整路径：

  1. handler deleteWorkspace（product_api.go:200-233）调 store，成功后事务提交之后 os.RemoveAll 项目目录（删目录在事务外，避免库回滚了目录已经没了）。
  2. store DeleteWorkspace（pgstore.go:292-320）单事务三步：lockOwnedWorkspace 锁项目行（FOR UPDATE）→ 查 is_default（默认工作区回 ErrWorkspaceDefault → 409 114005）→ SELECT COUNT(*) FROM sessions WHERE workspace_id = ?（只有这一个条件）→ 大于 0 回 ErrWorkspaceNotEmpty（409 114002），等于 0 才 DELETE FROM workspaces。

互斥现状有两层是现成的：删除事务锁 workspaces 行 ↔︎「新会话挂这个项目」的 AcquireRun（lockVisibleWorkspace）锁同一行；one_live_run_per_workspace 部分唯一索引（pgstore.go:428-432）保证同一项目同时最多一场活 run。没有的一层：删除与「已有挂载会话继续发消息」之间——那条路径锁 sessions 行（AcquireRun 的 SELECT ... FOR UPDATE WHERE id = ?），本篇软删会话的 UPDATE sessions WHERE workspace_id = ? 恰好也锁这些行，互斥顺带成立（§5.3）。

档案侧的现状：compact 只打 compacted=true 标记，没有任何代码路径删这些行；全库无外键无级联；runs.finished_at 记 run 终态时刻——这就是 D4 清扫条件的全部输入，不需要新档案表（D-i）。

4. 待拍决策与推荐

# 决策点 推荐 理由
D-a 会话删除语义：软删还是硬删 软删（新增 deleted_at 列） 硬删要顺手清 5 张 session_id 关联表（全库无外键无级联），动作大且掐断审计线；软删 + D4 清扫器分两阶段，兼得可恢复与空间回收
D-b 连带删的范围 见下表 原则是：表行软删保审计、磁盘字节删掉、计费数据不动；记忆按 scope 处理，D-l 在 2026-11-09 定为项目 workspace 行随删、个人 user 行保留
D-c 删除时遇到活 run 拒绝，项目 409 114006、会话 409 114007 删除不可逆，活 run 说明正在用；等跑完再删比自动 stop 安全（不误杀、不收尸）
D-d 成员挂在项目下的会话（A7b） 无差别连带软删 项目 owner 对项目内容有处置权（A7c）；软删不是抹除，runlog 仍在库里
D-e 114002 的去向 退役（本篇起 DELETE 项目不再返回它） 新语义下「有会话」不是拒绝理由；想留会话先解绑再删（A5）
D-f 单场删除的门槛（10-21 拍） 仅会话属主本人；tenant owner/admin 不豁免 doc/28 表格「owner/admin」口径作废。会话正文是私人对话；与 A5 同门槛同双轨错误
D-g 删会话时产出怎么办（10-21 拍） 产出保留，只清系统档案 所有权口径：系统档案（.tako/、.media/）随删清；agent 写的产出是用户资产，删对话记录不没收。删项目（D-b）是容器销毁，产出随之清——「只能由用户删或删项目」
D-h 保留窗口多长（10-21 拍） 7 天，启动参数 -archive-ttl（默认 168h） 借鉴口径「保留窗口 = 恢复承诺」：窗口内误删可恢复（行还在），窗口外物理清除。子代理暂不能「接着做」，审计主要靠 runlog 展示帧，窗口偏短；做成参数是上线后不改代码可调
D-i 要不要新增 subagent_runs 档案表（10-21 拍） 不新增 逐字档案已在 run_model_messages（compacted 行），归属由 run_id → runs.finished_at 推导；委派无实例 id（delegationTool 一次性调起）。「新增表按父 run + 子代理 id 存」是 Kimi 独立 wire 文件的解法，tako 没有独立 wire，新表只是同一份数据的第二个真源
D-j 清扫器形态（10-21 拍） 进程内 goroutine + ticker，互斥靠 PG 租约表 + 删除幂等 + 水印推进 借鉴材料明说不能用进程内定时器当互斥；多副本各跑各的 ticker，抢到租约才扫，DELETE 幂等，双跑只重复劳动不出错。闸在库（AGENTS.md 多副本纪律）
D-k 软删会话的档案何时物理清（10-21 拍） 与全局同一个窗口：sessions.deleted_at + 窗口 < now() 才清 「保留窗口 = 恢复承诺，同一个数」的推论：软删不是抹除，宽限期内行还在（未来恢复入口的余地），窗口外连同模型消息行一起清
D-l 记忆线跟不跟着项目一起删（11-07 拍；11-09 按 scope 修订） 项目记忆跟着删，个人记忆保留：pipeline 清 scope='workspace' 的 memory_items 与该项目 memory_jobs；markdown 清项目 MEMORY.md；两种模式都清 dialogue_chunks，都不动用户 USER.md / scope='user' 行 项目是容器，但个人偏好跟人走，不能因来源项目删除而误删；项目常驻规矩与召回事实也不分层残留。租户归档不动记忆行：归档不是销毁

5. 新 DELETE 语义

5.1 项目删除的请求响应

路由、鉴权、成功响应全不变：DELETE /api/workspaces/:id，仅创建者，成功仍是 200 {"code":0,"message":"","data":{"status":"deleted"}}。失败分支变化：

场景 旧语义 新语义
项目下有会话 409 114002 200 deleted，会话连带软删
项目下有活 run （撞项目闸 409 114004，仅新建 run） 409 114006「项目里有正在运行的会话，等它跑完再删」
默认工作区 409 114005 不变
别人的/不存在的项目 404 114001 不变
未登录 401 111102 不变

5.2 项目删除的事务时序（store 层新方法 DeleteWorkspaceCascade）

BEGIN
  1. lockOwnedWorkspace(id, tenantID, userID)     -- FOR UPDATE 锁项目行；没有 → 114001
  2. is_default? → ErrWorkspaceDefault            -- 114005（不变）
  3. SELECT COUNT(*) FROM runs
     WHERE workspace_id = :id AND status='running' AND lease_until > now()
     → > 0 回 ErrWorkspaceBusy（新错误 → 114006）
  4. SELECT id FROM sessions WHERE workspace_id = :id
     → 记下 id 列表（删目录用）
  5. UPDATE sessions SET deleted_at = now()
     WHERE workspace_id = :id                      -- 软删全部挂载会话
  6. pipeline：取得与 writeMemory 相同的 workspace advisory lock
     → 等已在写库的记忆任务收口，删除后旧 job 不得再写
  7. DELETE FROM memory_items
     WHERE workspace = :id AND scope = 'workspace'  -- 两层都删；user 行保留
  8. DELETE FROM dialogue_chunks WHERE workspace = :id
  9. DELETE FROM memory_jobs WHERE workspace = :id  -- markdown 没有此表写入
  10. DELETE FROM workspaces WHERE id = :id
COMMIT

handler：拿到 store 返回的会话 id 列表后（沿用「事务外删目录」的现状结构）：先 RemoveAll 项目目录（现状；markdown 的项目 MEMORY.md 随之删除），再对列表逐个 RemoveAll 会话目录。目录删除失败照旧只记日志、不改响应。逐字档案表（runs / run_model_messages / runlog_entries）不动，物理清除由 §5.5 清扫器按窗口做；项目记忆线（步骤 6–9）在这笔事务里就删掉了，个人 user 记忆明确保留，不进清扫器的窗口流程——项目容器销毁与个人偏好跟人走是同一条 scope 规则的两边。

5.3 时序竞争为什么安全

所有并发路径都在抢同两把锁中的一把，且活 run 检查在锁保护之内：

  • 新会话挂这个项目（AcquireRun 的 lockVisibleWorkspace）锁项目行：删除事务持锁期间它等着；删除提交后行没了，预检回 114001，不建行。反之它先提交，删除的计数能看到新会话（步骤 4/5 照常软删它）。
  • 已有挂载会话发消息（AcquireRun 锁 sessions 行）不锁项目行：步骤 5 的 UPDATE sessions WHERE workspace_id = ? 锁全部挂载会话行，两边互等。发消息方先提交 → 步骤 3 的活 run 检查看到 running 行 → 整笔回滚 114006；删除先提交 → 对方 SELECT ... FOR UPDATE 带软删过滤查无此行 → 旧体 404，不建行。

不会出现「会话已删、run 还在跑」或「run 在跑、项目没了」的孤儿态。

5.4 单场删除：DELETE /api/sessions/:id（D3）

端点至今不存在（§1），本篇新增。软删基础设施由 D1 铺好，本端点增量 = 路由 + handler + store 一个方法。

  • 路由：DELETE /api/sessions/:id，挂 RequireAuth。仓库里 sessions 相关路由只有 GET/PATCH（server.go:78-84），新增不冲突。
  • 门槛：sessions.user_id = 当前用户，tenant owner/admin 不豁免（D-f）。错误双轨对齐 A5：看不见 → 404 {"code":112001,"message":"找不到这场会话","data":null}（不泄露存在性；2026-10-22 换信封，见 doc/40）；同租户 visibility=tenant 看得见但非本人 → 403 {"code":111204,"message":"只有本人能修改","data":null}。
  • 活 run：拒绝，409 114007「这场会话正在运行，等它跑完再删」。
  • 事务（store 新方法 DeleteSession）：SELECT ... FROM sessions WHERE id = ? FOR UPDATE（D1 的软删过滤生效：查无 → 404 112001）→ 属主校验（403）→ 活 run 检查 → UPDATE sessions SET deleted_at = now()。
  • 文件清理（D-g，事务提交后，失败仅记日志）：RemoveAll(<会话目录>/.tako/)（搜索截断落盘）+ RemoveAll(<会话目录>/.media/)（旧媒体兜底），不存在算成功；产出保留，项目目录不动。
  • 成功：200 {"code":0,"message":"","data":{"status":"deleted"}}；幂等：再删一次 → 404 112001。
  • 并发：与 §5.3 同款——锁 sessions 行 ↔︎ AcquireRun 锁同一行互等；活 run 检查挡先发消息方，删除先提交则对方 404。

5.5 保留窗口与清扫器（D4）

清理对象（两类，都落在 run_model_messages）：

  1. 过窗 run 的逐字档案：compacted=true 的行，条件是所属 run 已终态且过窗： DELETE FROM run_model_messages WHERE compacted=true AND run_id IN (SELECT id FROM runs WHERE finished_at IS NOT NULL AND finished_at < now() - ttl)。seq=0 摘要行与 compacted=false 的行（模型输入）不在这类里——前者是「发生过什么」永不删，后者还在被使用。
  2. 过窗软删会话的全部模型消息：软删会话没有了「继续跑」的可能，它的 compacted=false 行也失去用途（D-k）： DELETE FROM run_model_messages WHERE session_id IN (SELECT id FROM sessions WHERE deleted_at IS NOT NULL AND deleted_at < now() - ttl)。

不清理：runlog_entries（页面展示线，本篇永不清）、runs、usage、摘要行。记忆线也不在清扫器的清理范围里——项目删除时只清 scope='workspace' 的记忆与该项目任务，scope='user' 行继续跟人走（D-l，§5.2 步骤 6–9），不进「宽限期 + 窗口」这套流程；清掉的是逐字档案，不是记忆。

单场会话删除（D3）不动记忆：项目记忆跨会话、用户记忆跨项目，删一场会话不等于记忆作废。pipeline 的 memory_items / memory_jobs 与 markdown 文件都不因单场删除而清；只有项目删除才按 D-l 的 scope 规则处理。

2026-10-27 补记（后加的两张会话级表）：run_tasks（doc/41）与 run_questions（doc/47）都带 session_id，语义上属于上面第 2 类，但今天不在任何 DELETE 里——run 结束、会话软删、过窗清扫都不动它们（全仓 DELETE FROM 实读，没有一条指向这两张表）。补法是同一拍各加一条按 session_id IN (SELECT id FROM sessions WHERE deleted_at IS NOT NULL AND deleted_at < now() - ttl) 的删除 + 单测；未排期，不在别的方案里顺手改。

清扫器结构：

  • 启动参数 -archive-ttl（默认 168h = 7 天，D-h）。
  • 新表 cleaner_state(key text PK, owner text, expires_at timestamptz, watermark timestamptz)，两行：key='lease'（抢租用）与 key='archive'（存本轮扫到的最大 finished_at/deleted_at，作下一轮的起点游标，避免每轮全表扫）。
  • worker 进程内 goroutine + ticker（每分钟）；每轮：抢租约（UPDATE cleaner_state SET owner=?, expires_at=now()+interval '5 min' WHERE key='lease' AND expires_at < now()，影响 0 行 = 别人持有，本轮跳过）→ 按游标删一批（每批 LIMIT，删完推进 watermark）→ 释放租约（expires_at = now()）。
  • 幂等与多副本：DELETE 本身幂等；两个副本同时持有过期租约的边缘情形只是重复删同一批，结果一致。闸在库，不是进程内互斥（D-j）。
  • dev 探针：POST /api/dev/clean-sweep（dev-only）手动触发一轮完整清扫，走同一租约与游标——验收靠它，生产靠 ticker。探针登记转正点：上线前 dev-only 门（-dev）挡住，未来如需手动触发再转正为 admin 端点。

与删除的联动：软删会话/删项目当时不动表（软删语义）；会话的模型消息（含子代理逐字）由清扫器在 deleted_at + ttl 后物理清（D-k）。想更快释放空间，调小 -archive-ttl。

10. 闭环

所以这解决了什么。 删除从「形同虚设」变成三个阶段各就各位：删除动作软删留档（可恢复、审计不断，D1/D3），文件按所有权分层（系统档案随删清、产出只随删项目清，D-g），档案按保留窗口物理回收（D4：过窗 run 的逐字行 + 过窗软删会话的模型消息，持 PG 租约的清扫器，多副本幂等）。子代理的逐字档案不再只进不出——压缩掉的原文行在窗口到期后真删，摘要行和 runlog 永留，「发生过什么」与「逐字过程」按价值分层保存。同一套软删语义和窗口数（D-k）把删除和清理焊成一个机制，而不是两个独立的垃圾来源。项目记忆跟着容器走，个人记忆跟着人走（D-l，2026-11-10 落地）：项目删除时，两层 scope='workspace' 行一起清，scope='user' 行仍能在其他项目出现；Markdown 的项目文件随目录清、用户文件不动。

仍不解决的： 恢复入口、runlog 物理清除、半截文件的自动处理、原子写/写清单/scratch——都在 §9 明说。
