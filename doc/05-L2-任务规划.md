# 05 · L2 任务规划

> L1 回答了"agent 有了手怎么防闯祸"，L2 回答一个效率问题：**面对多步任务，agent 怎么先列计划再执行，并且让用户看得见进度？**
> 复刻对象：deepagents 的 TodoListMiddleware（langchain 1.x 已收进官方中间件库）。

> 实现注记（2026-09-24）：本层最初用 TypeScript（LangGraph.js）实现，TS 版已随路线定案删除，
> 唯一实现现为 `yk-tako-eino/`（Go）。机制分析照旧成立；Go 侧有一处实现差异值得记住：
> ChatModelAgent 没有自定义 state 频道，清单放在进程内；模型节点之后只看最后一条消息有没有 tool call，
> 所以"半途而废提醒"不是追加 HumanMessage + `jumpTo`，而是补一次对模型隐藏的 `planning_nudge` 工具调用，
> 让图走进工具节点再回到模型（详见 `yk-tako-eino/README.md`）。
> 至于"write_todos 要不要和干活工具同轮互斥"这个本层遗留问题，Eino 官方的答案不在 middleware 层——见《06-Eino规划机制调研与路线定案》。

## 本层目标

给 agent 加一份"任务清单"能力：复杂任务先拆成步骤写进清单，执行中实时更新各项状态，用户随时能看到"做到哪了"。

```
用户输入 ──→ 模型 ←── [系统提示词：什么时候该列计划]
              │
              ├─→ write_todos（全量替换清单）──→ todos 频道（图状态）
              │
              └─→ 其它工具照常走 L1 的守卫链
```

关键认知：**清单是状态，不是消息**。它存在图状态的 `todos` 频道里（checkpoint 会记住它），而不是埋在对话历史里——所以 REPL 的 `/todos` 命令可以绕过对话直接 `getState` 读它。

## 从 harness / deepagents 读到了什么

### harness 自己没有 todo 中间件

带着"L2 参考 harness 哪个文件"的问题去翻 `harness_agent/middleware/`，24 个中间件里没有 todo——harness 直接用 deepagents 的。目录里的 `tool_order.py` 名字像规划，实际是另一件事：把 `task` 工具排到工具列表末尾，让父子 agent 的公共工具前缀对齐，**给 prompt cache 复用服务**的。这是一个提醒：按名字猜职责会踩空，得看实现。

### 官方 todoListMiddleware 的四个零件

官方实现是 Python 的 `TodoListMiddleware`（`langchain.agents.middleware`，deepagents 直接引用）。本仓库精读的是 langchain JS 移植（`agents/middleware/todoListMiddleware.js`，文件头写明 ported from Python，约 100 行有效代码），四个零件与 Python 版一致：

| 零件 | 机制 | 作用 |
| --- | --- | --- |
| 状态频道 | `stateSchema: z.object({ todos: ...default([]) })` | 给 agent 状态图加 `todos` 频道 |
| `write_todos` 工具 | 返回 `Command({ update: { todos, messages } })` | 全量替换清单 + 回执 ToolMessage |
| 提示词注入 | `wrapModelCall` 里拼 `systemMessage` | 教模型什么时候该用、什么时候别用 |
| 并行防守 | `afterModel` 检查一轮内 `write_todos` 调用数 | >1 次就全部换成错误 ToolMessage |

两个设计点值得停下来想：

1. **为什么是全量替换而不是增量操作**（没有 add_todo / complete_todo）：增量 API 需要 id 管理和冲突处理，而全量替换把"当前计划长什么样"的权威来源始终放在模型手里——模型每轮都能看到完整清单（在上次的 ToolMessage 回执里），改起来一步到位。代价是并行调用会产生歧义，所以要有零件 4 的防守。
2. **提示词是最大的代码量**。官方版有效代码约 100 行，提示词约 200 行（`WRITE_TODOS_DESCRIPTION` 带 8 组正反示例）。什么时候列清单、什么时候别列，全靠提示词约束——这不是工程问题，是 prompt engineering。

| | 官方版 | yk-tako 手写版 | 策略 |
| --- | --- | --- | --- |

| 回执 ToolMessage | `Updated todo list to {JSON 原文}` | 紧凑摘要（`2/3 已完成` + 状态图标列表） | **偏离**：模型只需要确认+概览，不需要 JSON 原文，省 token |

| 半途而废提醒 | 无 | afterModel + `jumpTo: "model"` | **外扩**：见下节 |

## 外扩：半途而废提醒

官方版有一个能力空档：模型列了计划，但执行到一半就输出最终回答收工了（清单里还有 `in_progress` 项），没有任何机制纠正它。我们补了一格：

```
afterModel 钩子：
  模型想收工（最后一条消息是无 tool_calls 的 AIMessage）
  + 清单里有 in_progress 项
  + 本轮用户发言之后有过成功的 write_todos
  + 本轮还没提醒过
  → 注入一条带 name 的 HumanMessage 提醒 + jumpTo: "model" 跳回模型节点继续
```

四条约束：

1. **只催 in_progress，不催纯 pending**。pending 旧账可能是上一轮放弃的计划，新话题下催它纯属打扰。
2. **只催本轮刚写过的清单**。判定是「最近一条真实用户消息之后存在成功的 write_todos ToolMessage」。上一轮留下的 in_progress 不催——否则下一句「现在几点」也会被拽回去继续旧计划。检查时发现并补上的。
3. **每轮最多催一次**。提醒消息带 `name: "planning_nudge"`（正文前缀是兜底，防止内容被折成 block 数组后前缀判定失效）。从后往前扫，撞到它就停。无状态、保证终止。
4. **jumpTo 只在「无待执行 tool_calls」时用**。这是读 `ReactAgent.js` 路由源码读出来的约束，见下节。

## 路由机制调研：afterModel 之后图往哪走

手写之前先搞清了一个前提问题：afterModel 钩子改了消息之后，图怎么路由？读 `ReactAgent.js` 的 `#createAfterModelRouter`（约 410-465 行）：

- 最后一条消息是**无 tool_calls 的 AIMessage** → 直接出图（exitNode）。这意味着"只追加一条 HumanMessage"不会让模型再走一轮——路由根本不看它。
- 想让模型继续，必须显式 `jumpTo: "model"`：钩子要声明 `canJumpTo: ["model"]`（`modelCallLimit` / `hitl` 等官方中间件同款写法），返回 `{ messages, jumpTo }`；路由消费后会自动清位（`jumpTo: void 0`），不会死循环。
- **为什么并行防守不能学这一招**：如果 AI 消息里除了并行的 `write_todos` 还有别的工具调用，jumpTo "model" 会跳过那些待执行的工具，留下"有 tool_calls 但没有对应 ToolMessage"的烂摊子，下一轮直接被 API 400 拒（L1 踩坑记录第 1 条同款）。所以并行防守保持官方语义：只换错误 ToolMessage，让正常路由去处理剩余的待执行调用。

顺带一个观察：官方并行防守在"所有 tool_calls 都是 write_todos"时，错误 ToolMessage 补上后路由会判定无待执行调用 → 直接出图，模型本轮看不到错误。不算 bug（下轮用户输入时错误在历史里），但提醒效果隔了一层。我们保持了一致行为，没在这里外扩——jumpTo 的风险收益比不划算。

## 实测记录

| 输入 | 手写版（01） | 官方版（02） |
| --- | --- | --- |
| `帮我规划一下：先查现在时间，再算 1234*5678，最后写个总结` | 先列 3 项清单（首项 in_progress）→ 并行执行时间+计算 → 更新 2/3 → 更新 3/3 → 总结 | 行为一致；回执是 JSON 原文 |
| `现在几点` | 直接回答，不列清单 ✅ | （提示词同样约束简单任务不用） |

紧凑中文提示词（15 行）在 deepseek-flash 上和官方 200 行版行为无差别——至少在这个量级上，"什么时候列清单"不需要 8 组示例。提示词长度与效果的拐点在哪，留给后面层级继续观察。

第三版硬编排（`l2planexec`，doc/06 §4 建议的落地）的实测记录单独记在 doc/06 §6：时序确实硬了，但 Replanner 会把末步并进 respond、Planner 看不见工具清单导致简单问题被过度规划——后者当天用入口闸门（Gate）治掉，见 doc/06 §7。

半途而废提醒在实跑中没有自然触发（模型太守规矩）。钩子级冒烟覆盖：并行防守、本轮写过清单才催、同轮不重复、上轮遗留的 in_progress 不劫持新话题、全完成不催、纯 pending 不催、有 tool_calls 不催、内容折成 block 数组时仍能认出提醒、摘要格式。另有一条脚本模型走真实图：催一次后停住，不会打到递归上限。

## 与官方版的差距（有意留下的）

- 提示词没有正反示例库，遇到更弱的模型可能约束力不够——到时候再抄官方的示例结构。
- 没有 `systemPrompt` / `toolDescription` 之外的定制面（官方版也就这两个）。
- 提醒文案是固定模板，官方风格的做法是做成可注入。
