# 异步委派、子代理与 DAG 讨论笔记

> 性质：**讨论记录**，不是方案，不作施工真源。
> 日期：2026-11-14。
> 状态：概念澄清；没有形成改造拍板，没有修改代码、提示词或工具描述。
> 取信口径：tako 结论以当日代码为准；Claude 结论以当日官方文档为准；DeepSeek Super-agent 与 Kimi 结论来自此前对本地源码的核对。

## 0. 一句话结论

**DAG 不是「让 Todo 异步并行」的开关，而是「多个独立执行单元及其依赖关系」；异步委派也不由 Bash、写文件、description、goroutine 或超时中的任何一项单独决定。** Claude 有依赖图式的 Agent teams 和代码式 Workflow，但本轮核到的官方资料没有显示它有 tako 这种默认统一的「持久 DAG 对象 + 独立 Task run + 依赖调度 + 结果通知」产品形态。

## 1. 讨论从哪里开始

最初想要一个看得懂的自然语言测试：用户只布置环境并说出目标，agent 自己建计划、执行，发现环境变化后重规划。用户台词不能点工具名，也不能提示「先核对」「失败就换方案」「分派给执行者」等行为。

早期演示脚本改为直接调 API、手写 `tasks` 和 `links` 来创建两节点 DAG。它只能证明「计划已经存在以后，系统能否复核」，不能证明「模型自己决定拆计划」，因此被判定为作弊，不再作为自主重规划的成功证据。

讨论随后从演示回到两个原始动机：

1. 长工作可以异步执行，不占住来源会话；
2. 用户知道目标很繁琐时，可以进入一种持续探索、动态规划、追踪目标的模式。

用户进一步结合自己的实际开发习惯修正了第二个动机：平时并不使用 goal 模式，而是让模型写带验收的文档，自己也不常看验收文档。因此本轮先把问题收窄为：**DAG、Todo、异步委派和普通子代理究竟分别是什么，Claude 又如何划分这些概念。**

## 2. tako 当前的四种对象

| 对象 | 谁在执行 | 调用方是否等最终结果 | 生命周期与用途 |
|---|---|---|---|
| `run_tasks` 任务看板 | 当前 run 的同一个执行者 | 不涉及委派 | 一场 run 一块看板；记录「我自己接下来分几步做」 |
| 普通子代理 | 一次委派的独立子代理实例 | **等** | 独立上下文与档案不等于异步；父调用拿到最终字符串后才继续 |
| `delegate_task` 创建的持久 Task | 独立执行者、独立 execution session/run | **不等** | 立即返回任务号；结果以持久通知回来源会话，并有调度与恢复链 |
| `create_orchestration` 创建的 DAG | 多个独立执行者 | **不等整组现场完成** | 一次原子提交节点和依赖；无依赖节点可并行，上游成功后下游才开放 |

代码证据：

- 看板与持久 Task 的边界写在 `internal/runengine/agent_task_tools.go:122`：前者记本 run 的待办步骤，后者创建独立执行的持久 Task，且执行者看不到来源会话。
- `delegate_task` 的描述在 `internal/runengine/agent_task_tools.go:141`：立即返回任务号、不等结果，完成或失败以持久通知回来。
- `create_orchestration` 的描述在 `internal/runengine/agent_task_tools.go:215`：一次提交整张任务依赖图，各节点按依赖自动推进。
- 普通子代理的调用在 `internal/runengine/agents.go:355`：`subagentShell.InvokableRun` 返回内层 `InvokableRun` 的最终字符串，调用语义仍是同步。
- 持久 Task 最终由 `internal/runengine/agent_task_runner.go:329` 的 `go ts.worker.Run(...)` 启动；在此前后还有 Task 领取、独立 session/run、工作现场、失败收尾、通知与恢复，不能只看见 `go` 这一行。

所以「复杂任务拆成 Task，每个 Task 内部再有自己的 Todo」在产品概念上可以成立，但这是两个层次：**外层是独立工作及其依赖，内层是某个执行者自己的步骤清单。** 外层 DAG 不来自内层 Todo 自动升级。

## 3. 本轮澄清的四个问题

### 3.1 DAG 是不是让 Todo 可以异步并行

不是。Todo 并行只描述「几件事同时做」，DAG 还描述「谁必须等谁」。

例如：

1. A 调研 API，B 调研 UI，两件工作互不等结果，可以并行；
2. C 写综合报告，必须同时拿到 A 和 B 的结果；
3. 程序只在 A、B 都成功后开放 C。

这里真正需要 DAG 的是第 3 条。如果只有一件长工作，`delegate_task` 就够了，不必制造一张单节点以外的图；如果三步都由同一个执行者顺序完成，任务看板就够了。

**没有依赖声明会怎样：** C 可能在 A、B 尚未完成时开始，执行者只能猜上游结果，或者重复做一遍。**没有异步会怎样：** 来源会话必须等整组结束才继续，但依赖关系本身仍然成立。异步与依赖是两个不同的轴。

### 3.2 异步是不是 Bash、写文件或 goroutine 决定的

不是。**同步／异步说的是调用方是否等待结果；goroutine 是 Go 用来并发执行代码的手段。**

- tako 的 Bash 在 `internal/runengine/bash.go:82` 使用 `cmd.Run()` 等待命令结束；超时分支在 `bash.go:86`，返回「bash 超时，死前输出」。它不会把命令自动转成后台任务。
- `write_file` 从 `internal/runengine/filetools.go:115` 开始，是同步整文件覆盖写，没有后台语义。
- 普通子代理即使底层存在并发执行，父调用仍等最终字符串，所以语义仍同步。
- 持久 Task 使用 goroutine 启动，但其产品语义来自独立持久生命周期：来源会话可以先做别的，Task 之后由调度、通知和恢复链接管。

因此，「一个异步子代理内部有 Bash、读文件、写文件等多种操作」完全正常。异步边界包住的是**整件工作**，工作内部仍然一步一步同步执行。

### 3.3 启动前怎么知道该不该异步

不需要先预测它会调用多少工具，也不需要准确预测耗时。判断顺序是：

1. **下一步是否马上需要这个结果。** 马上要，就倾向同步；不马上要，才考虑异步。
2. **这件工作能否自包含独立执行。** 执行者看不到来源会话，目标、路径、验收标准必须写全；做不到就先补齐输入，而不是直接派发。
3. **是否较长，且用户希望当前会话继续响应。** 两者同时成立时，异步才有明显收益。

`description` 不负责回答这套问题。它主要回答「这件工作是否适合委派，以及委派给哪种专家」；前后台边界是另一个维度。让 description 同时承担耗时预测和异步开关，会把两个判断揉在一起。

### 3.4 是否统一靠超时把长操作转异步

不是通用原则。超时转后台是特定工具的补救机制，不是任务规划方法。

Claude 的 Bash 支持显式 `run_in_background`，前台命令超过两分钟也会自动转后台；但这不是 Write 等所有工具的统一行为。tako 当前 Bash 的 30 秒超时则是终止并交回死前输出，不转后台。

**如果把超时当成统一异步入口会怎样：** 调用方一开始仍按同步语义组织后续步骤，只有超时后才突然发现结果尚未产生；任务边界、输入自包含和结果通知都没有提前建立。是否异步应在委派整件工作时决定，而不是等某个内部工具超时后补救。

## 4. `delegate_task` 目前确实只是可选能力

这是本轮确认的机制缺口，不是模型一定「不会拆任务」的证据。

当前工具描述说明了它能做什么：异步、立即返回、持久通知、输入自包含；但没有告诉模型**什么时候该用、什么时候不该用**。系统提示也没有补这层策略。因此，用户只说一个目标时，模型可以合理地选择自己直接做完；「工具可用」不等于「模型有理由使用」。

后续是否给 `delegate_task` 增加「何时用／何时不用」的策略，是候选改造方向，**本轮未拍板，也未修改工具描述。**

## 5. Claude 的准确对照

### 5.1 任务清单与后台任务是两件事

Claude 的 `TaskCreate / TaskGet / TaskUpdate / TaskList` 是单个 agent 的多步工作清单；`/tasks` 查看的是后台 shell 和子代理，不是同一份 Todo 的另一种展示。

较新模型默认不提供这些任务工具。官方理由是：这些模型不依赖书面清单也能跟踪多步工作，而工具定义和提醒会占用上下文；多步骤或用户明确要求时仍可启用。

这与 tako 当前「任务看板默认可用」的选择不同，是产品策略差异，不是哪一方缺少任务概念。

### 5.2 子代理的 description 管委派，不单独管异步

Claude 官方把 description 定义为自动委派的主要依据：主 agent 读取请求和各子代理描述，选择匹配者；用户也可以显式点名。

交互式主会话中的子代理默认后台启动，结果以后以通知送达；SDK／程序化调用则可用 `await` 等待，也可用 `Promise.all` 并发等待多个子代理。这里的 `await Promise.all(...)` 表示内部并发、外部仍等这一组结果，不能把它理解成「所有子代理永远同步」或「永远异步」。

### 5.3 Claude 不是没有 DAG 式能力

Claude 有两种不同形态：

- **Agent teams**：实验性、默认关闭。共享任务列表支持依赖，上游完成后自动解除下游阻塞，队友认领未阻塞任务。这是依赖图式协调。
- **Dynamic workflows**：Claude 编写 JavaScript，用 `await`、`parallel()`、`pipeline()` 表达依赖和并发，中间结果保存在脚本变量中。Workflow 会保存结果并支持恢复，但退出 Claude Code 后不会自行继续；恢复时需要回原会话并重启 Workflow。

因此准确结论是：**Claude 有 DAG 式协调能力，但不是 tako 当前这种默认统一的持久 DAG 编排组。** 不能把 Agent teams、Workflow、普通后台子代理和任务清单合并成同一种「任务」。

## 6. DeepSeek Super-agent 与 Kimi 带来的校准

此前对本地源码的核对给本轮讨论提供了两条边界：

- DeepSeek Super-agent 的 Router 不写实施计划；短请求不得改写成 work plan。worker 内部才使用 `todo_write`、`subagent` 等工具。出处：`ref-agent/dsh-superagent-prototype/prompts/orchestrator.md:4`、`prompts/dispatch.md:38`、`src/app/sessions.ts:61`。
- Kimi 的委派原则是琐碎工作不委派，只有收益抵偿上下文交接成本时才委派；Tower／Goal 属于显式开启的形态，不是模型从任意自然语言请求自行进入的重型模式。出处：`ref-agent/kimi-code/packages/agent-core-v2/src/agent/tools/agent/agent.md:13`。

**本轮由此形成的讨论判断：** 不能拿「成熟产品都会从一句自然语言自动建多 agent DAG」当前提。轻量委派和单 agent 清单可以由模型自决，重型编排是否默认自动进入，需要单独拍板；目前没有这个拍板。

## 7. 已确认与未拍板

### 已确认的事实

1. Todo、普通子代理、持久 Task、DAG 是四种不同对象。
2. 单个异步 Task 不需要 DAG；DAG 的独有价值是多个独立执行单元及其依赖。
3. 普通子代理的独立上下文不等于异步；tako 当前普通委派是同步调用语义。
4. 异步与工具类型无关；异步执行者内部可以有任意多种同步工具操作。
5. goroutine 是启动手段，不是持久 Task 的全部语义。
6. description 主要管委派选择，不是可靠的耗时预测器或异步开关。
7. Claude 的 Bash 超时转后台不能推广成所有工具的通用规则；tako 当前 Bash 超时也不转后台。
8. `delegate_task` 当前缺少「何时使用」的策略，确实只是模型可选用的能力。

### 尚未拍板的问题

1. 是否以及如何给 `delegate_task` 补「何时用／何时不用」的策略。
2. DAG 是保持显式重型编排，还是允许模型在默认对话中自行创建；触发边界是什么。
3. 普通子代理是否需要像 Claude 一样区分交互式前后台与程序化等待；本轮没有改造决定。
4. 是否存在需要「超时转后台」的具体工具场景；不能从一个 Bash 例子推广成统一机制。
5. 原动态重规划演示停在 `planHold`、复核 run 没有调用决策工具的问题仍未定位；`tmp/replan-demo/case.sh` 仍不能作为模型自主建计划的证据。
