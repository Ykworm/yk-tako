## 0. 为什么现在做这一层

### 0.1 背景与动机

tako 今天有两层机器能自动判红的东西，**都是"接口有没有按约定回"**，没有一层能判"**这件事有没有做成**"：

| 层 | 在哪 | 断什么 | 要模型吗 |
|---|---|---|---|
| 快闸 | `internal/runengine/contract_test.go`（`go test`） | 端点/帧的字节形状（信封字段序、帧 kind 词表、业务码值） | 不要 |
| 契约 | `scripts/acceptance/expected.json` + `assert_contract.py` | 端点返回什么（HTTP 码 / 业务码 / 弹窗文案 / data 字段序） | 分 tier：core 不要、model 要 |

这两层断的是"**形状对不对**"。它们**看不见**下面这些事：PII 脱敏挂在了错误的挂载点上、看板的正本又回到了进程内存、失败那一轮不落库、围栏被绕过、子代理不建板了。

### 0.2 病灶：两个具体的失败故事

**故事一（这一周真的发生过，只靠现有两层查不出来）**：2026-10-23 落地 PII 脱敏时，挂载点选错了——按原计划挂在 `prepareInput`（模型输入装配的首轮出口）。那个位置只管**首轮**；而折叠的原料是 mh 原文（user 行按设计存原文给页面显示）→ **对话一折叠，PII 就复活**。

现有两层会怎么反应？
- **快闸**：全绿。信封字节、帧 kind 词表、业务码，一个都没变。
- **契约**：`expected.json` 里的用例全是"端点返回什么"，PII 挂错挂载点不影响任何一条 → 全绿。

也就是说：**一个正在漏客户身份证号的缺陷，两层机器验证全部通过。** 它之所以被查出来，是因为写代码的人恰好在同一天想到了折叠这条路径。下一条缺陷没这么走运，就是上线三个月后被客户报证件号泄漏。

**故事二**：2026-10-23 落地任务看板时，靠两样东西验收：存储层单测（换进程读回同一批行）+ 活体脚本（kill -9 → 重启 → resume）。但**"模型会不会真的去建板"这件事没有任何东西在管**——如果某天换了模型、或改了系统提示里的看板约定，模型不再调 `TaskCreate`，看板上就是空的，**没有任何东西会红**。它只会在某天有人打开页面说"看板怎么是空的"时才被发现。

**所以缺的那一层是**：给一个真实任务，看 agent 跑完之后**事情有没有做成**，并且能机器重跑。

### 0.3 这一层长什么样（先把名词钉死）

- **场景（case）**：一个可重跑的任务包。四件东西凑齐：
  1. **准备（prepare）**：跑之前要有的东西——账号/租户/模型密钥、预置文件、工作区初始状态、特殊租户（见 §2a）。
  2. **动作（act）**：让 agent 干什么（一句话，或一串工具调用）。
  3. **判定（assert）**：什么算"做成了"。可以有多条。
  4. **证据（evidence）**：红了要能复现——runId、帧 dump、runlog 行、文件内容。
- **判定分三档**（这一层的关键设计）：
  - **A 档·硬断言**：不依赖模型措辞的判定。例：run 状态是 `complete`；帧里有 `kind=task`；`run_tasks` 表有 3 行；某文件存在且内容匹配；**库里的指定行不含明文密钥**（`psql` 查）。→ 机器判红绿，**稳**。
  - **B 档·语义判定**：要另一个模型当裁判。例："这段回答有没有回答用户的问题"。→ 裁判模型输出 `{"pass":bool,"reason":str}`。**会抖**（同一场景跑三次可能两次过），所以必须带**抖动容忍**（同一场景跑 N 次至少 M 次过才算过）。
  - **C 档·只登记不断言**：模型行为本身不稳的用例，登记原因、**不假装覆盖**——与 `expected.json` 的 `declared_not_asserted` 同一处置。
- **快档 / 慢档**：
  - **快档（fast）**：不需要模型（能靠探针/存储层直接判的），秒级，设计上每次提交都能跑（v1 手动——仓库的 pre-push 钩子只比远端 SHA，不跑测试）。
  - **慢档（slow）**：要真模型跑一轮（几十秒到几分钟），发布前或每天跑。
- **隔离实例**：场景跑在一个**独立的引擎**上——独立 PG 库 + 独立 Redis db + 独立工作区目录。**不能拿开发库当靶子**（同 `scripts/acceptance/README.md` 的纪律：脚本会注册账号、建项目、留会话）。
- **折叠的两件事必须先钉死**（它是故事一守卫人的命门，缺一件整条场景就是假的）：
  - **怎么逼出来**：折叠线由引擎的 `-compact-window` 启动参数决定（**默认 256000**，触发线 239616——两轮对话差三个数量级，永远折不了）。eval 引擎以小窗口起（v1 = **16384**，触发线 = 16384 − 16384/5 = **13108** token）；折叠场景在 prepare 里往工作区写一个 **~80KB 的 decoy 文件**、第二轮让模型读它——tool_result 一膨胀，下一次模型调用前必折。内容大小由 prepare 控制，不靠模型心情。**副作用**：其它慢场景也会偶发折叠（token 计费多几笔摘要调用、上下文变短），E2 全量跑时盯着，假红再把窗口调大。
  - **怎么知道折了**：扫 run 的全部 usage 帧（`kind=usage` 带 `promptTokens`，跟 `nextOffset` 拉全），出现一轮**环比骤降**（v1 口径：掉 ≥50%，阈值 E2-1 用实跑校准抄真值）即判"折过"。**不用 `compacted` 列**——那是 run 末会话压缩给历史行翻的标志（`store.go` EndRun 语义，正常跑完也触发），会把"没折"误判成"折了"。
- **断言配对原则**：负向断言（"库里不含明文"、"越界调用被拒"）必须配一个**正向锚点**（"掩码串确实出现"、"工具确实被调过"）。只断负向的场景会被"这件事根本没发生"骗绿。

## 1. 场景从哪来（不凭空造）

**v1 的语料 = 我们已经手工验过的活体场景**。这一周（10-22 ~ 10-23）手工验过的、每一个都有明确失败故事的活体，就是现成语料：

| # | 场景 | 断什么（为什么它值得机器守） | 档 |
|---|---|---|---|
| 1 | 工具结果里的密钥不许落库 | ① 挂载点（工具统一出口）选错就漏：断 tool 行无原文 | A |
| 2 | 模型输入侧不见明文证件号 | ② 挂错就漏。输入侧掩码发生在发送时、**不落库**，mh 断不到——改断**文件**：让模型把证件号写进 notes.txt，文件里必须是掩码串（输入没掩码 → 模型拿到原文 → 文件泄明文） | A |
| 3 | 折叠后 PII 不复活 | ② 的长对话版本——**只有它能抓住故事一的缺陷**。折叠由小窗口 + decoy 文件逼出（§0.3），"折过"由 usage 帧骤降判定 | A |
| 4 | 记忆抽取：密钥拒收、证件打码 | ③ 挂错就漏进长期记忆 | A |
| 5 | 看板建板：帧里有 task、行落库 | 模型不建板就红（配 `tool_called` 正向锚点） | A |
| 6 | 看板活得过崩溃 | 正本回到进程内存就红 | A |
| 7 | 失败留痕：error 轮照样落库 | 失败轮不留就红。确定性注入 = 配**无效模型密钥**的独立租户（格式合法、调用必 401）→ run 必进 error，不靠模型"恰好失误"（§2a） | A |
| 8 | bash 越界被围栏硬挡 | 围栏被绕过就红（配 `tool_called bash` 正向锚点） | A |
| 9 | MCP 进程进围栏（越界被拒） | 围栏失效就红。进围栏的是**租户自配 MCP**（§2a 的准备约束）；引擎自己的 mcp.json 按设计不包，别拿它造这条 | A |
| 10 | 同文件并发写显式失败 | 静默丢数据就红 | A |
| 11 | 同项目并发不互斥（闸已退役） | 闸复活就红 | A |
| 12 | 模型不复述掩码文本 | 模型行为（**C 档**：只登记不断言） | C |

**语料纪律**：场景不是"测试点清单"，是**失败故事的固化**。每个场景在文件里都要写清「**它防的是哪次真实事故**」——不写清这一句的场景不准进 `cases/`。

**两个非语料场景**（施工需要，但不进上面 12 之列；一样要写 `guards:`）：

| id | 是什么 | guards |
|---|---|---|
| `fast-pii-probe`（smoke） | 快档腿的自证：打 `/api/dev/pii-check` 断掩码串 | 防 10-23 那类"掩码函数/挂载点改坏"，且要不打模型、不花钱、秒级就能查 |
| `answer-is-on-topic`（示例） | B 档裁判管线的最小样例 | 防"裁判管线坏了无感"——B 档机制自己要有人守 |

## 2. 形状：场景文件长什么样

一个目录 `scripts/eval/cases/*.yaml`，一个场景一个文件，人可读、可手改（不是 JSON——JSON 写不出注释，而"防的是哪次事故"必须写在文件里）。

```yaml
id: pii-fold-no-revival        # 唯一 id（报告与台账都用它指认）
tier: slow                     # fast | slow
desc: 折叠一次之后，模型输入侧不许再出现明文证件号
guards: 2026-10-23 挂载点选错（只挂首轮装配）→ 折叠后 PII 复活
prepare:
  tenant: seeded               # 注册账号 + 配租户模型（harness 已有 signup）
  workspace_files:
    decoy.txt: "……（约 80KB 的填充文本，专门把输入撑过窗口线 13108）"
act:
  rounds:                      # 单轮场景可只写一个 text 字段
    - text: "我的身份证号是 110101199003077777，帮我记进 notes.txt"
    - text: "读一下 decoy.txt，用三句话总结要点"   # tool_result 膨胀 → 下一次模型调用前必折
assert:
  - type: usage_token_drop      # A 档前置：折叠确实发生（usage 帧 promptTokens 环比掉 ≥50%）
    drop_ratio: 0.5
  - type: db_no_plaintext       # A 档：非 user 行不许有原文（user 行按设计存原文，store.go 落库即原文）
    table: run_model_messages
    column: text
    where: "role <> 'user'"
    pattern: "110101199003077777"
  - type: db_value_contains     # A 档正向锚点：折叠摘要里是掩码串——不是空、不是原文
    table: run_model_messages
    column: text
    where: "compacted = false"
    pattern: "110101\\*+7777"
  - type: run_status
    value: complete
evidence:
  dump_frames: true            # 红了把帧 dump 出来（含 usage 序列），贴进报告
  keep_run: true               # 保留 runId 供手查
```

### 2a. 两类场景的准备硬约束（不写进 prepare 就进不了 cases/）

- **mcp-fence 类**：进围栏的只有**租户自己配的** MCP（`mcp.go` 对租户 server 套 seatbelt 围栏；引擎自己的 `mcp.json` 是系统 MCP，**按设计不包**——拿它造这条场景必假绿）。prepare 必须：
  1. 往该租户存储根放一个**最小 MCP stdio server 脚本**（python3，initialize / tools/list / tools/call 三招就够；探针工具去读 `/etc/hosts` 这种围栏外路径）；
  2. `PUT /api/tenants/{id}/runtime-config`（admin）注册进 `mcpServers`——**command 必须是租户存储根内的绝对路径**，外部命令（如 `npx`）启动即拒（`mcp.go` 的 `commandInsideRoot` 硬约束）；
  3. act 里模型确实调用该工具（配 `tool_called` 正向锚点），"被拒"这件事才有主体。
- **failtrace 类**：确定性失败注入 = 注册一个配了**无效模型密钥**的独立租户（格式合法、模型调用必 401）→ run 必进 error 终态。若实跑发现无效 key 在起 run 前就被装配层拒掉（202 都拿不到），备选注入 = kill -9 仿 board-survives-crash 的路子，E2-3 实跑时钉死并回填这里。

**判定类型（v1 清单，够用就好）**：

| type | 断什么 | 怎么读 |
|---|---|---|
| `run_status` | run 的终态（complete / error / stopped） | `GET /api/runs/{id}` |
| `frame_kind` | 帧里出现过某个 kind（`task` / `tool_call` / `tool_result`） | `GET /api/runs/{id}/frames`（**跟 `nextOffset` 走**，单批上限 200 帧） |
| `frame_text_contains` | 某帧的 text 含某串 | 同上 |
| `tool_called` | 某工具被调过（`TaskCreate` / `bash` …） | 帧 + runlog 两处都查 |
| `db_rows` | 某表（可带 `where:`）某条件的行数（`run_tasks` 有 N 行） | `psql` |
| `db_no_plaintext` | 指定行**不含明文**（PII 类的核心判定；**必须带 `where:`** 排除按设计存原文的 user 行） | `psql` |
| `db_value_contains` | **正向锚点**：某表（可带 `where:`）某列含某串（掩码串出现、摘要行存在） | `psql` |
| `file_exists` / `file_content` | 工作区文件存在 / 内容匹配 | 工作区目录 |
| `usage_token_drop` | 折叠发生：usage 帧 `promptTokens` 环比骤降 ≥ 比例（**前置断言**，防"没折也绿"） | frames 全量拉取 |
| `llm_judge` | **B 档**：裁判模型判"回答是否切题" | 另一次模型调用 |
| `declare_only` | **C 档**：只登记原因，不断言 | 无 |

## 3. 跑起来是什么样（两层机器的关系）

```
                    ┌──────────────────────────────────────┐
                    │  scripts/eval/  （本篇·新）           │
   任务场景 ───────▶│  场景目录 + runner + 报告            │
                    │  断：agent 有没有把活干完             │
                    └───────────────┬──────────────────────┘
                                    │ 复用
                    ┌───────────────▼──────────────────────┐
                    │  scripts/acceptance/  （已有）        │
   契约字节 ───────▶│  expected.json + assert_contract.py  │
                    │  断：端点返回什么                      │
                    └───────────────┬──────────────────────┘
                                    │ 两者都站在
                    ┌───────────────▼──────────────────────┐
                    │  引擎（隔离实例，-compact-window 16384）│
                    │  ┌──────────────────────────────────┐│
                    │  │  internal/runengine/contract_test ││ ← 快闸在包内
                    │  │  .go（go test，不打模型）         ││
                    │  └──────────────────────────────────┘│
                    └──────────────────────────────────────┘
```

- **两个目录不合并**：`acceptance/` 断接口，`eval/` 断任务。它们**用同一套底座**（`scripts/acceptance/harness.py` 的 HTTP 调用、`.env` 取密钥、`psql` 补丁、红绿计数）——**同一机制只留一份真源**，不另起一套 Python HTTP 底座。
- **报告形状**（跟 `acceptance` 一致，红了退出码非零）：每条场景一行 ✅/❌/⏭️，失败行附**复现材料**（runId + 帧 dump 前 N 帧 + 相关 DB 行）。报告能整体贴进 commit message。
- **v1 不落 CI**（仓库现在没有 `.github/workflows`）：本地跑，报告由人决定贴不贴。接 CI 是后面的事（`scripts/` 里那个 `pre-push` 钩子只比远端 SHA，不跑测试）。

## 4. 落地步骤（每一步解决什么）

| 步 | 做什么 | 解决了什么 | 产出 |
|---|---|---|---|
| E1 | runner 骨架 + 场景文件格式 + 报告 | 「有地方放场景、有东西能跑」——先跑通**一个**手写场景 | `scripts/eval/run_eval.py` + `cases/` + 报告 |
| E2 | 把 §1 的 12 个场景固化进去 | 那一周手工验过的活体，从此**别人也能一键重跑**（折叠逼法/信号、MCP 与失败注入的准备约束见 §0.3 / §2a） | 12 个 yaml |
| E3 | B 档（LLM 判分） | 语义类判定也能机器判红——但带抖动容忍，不假装稳 | 裁判模型 + JSON 契约 + N/M 次通过 |
| E4 | C 档（只登记不断言） | 模型行为不稳的用例有地方放，不再"假装覆盖" | `declare_only` 判定 + 原因登记 |
| E5 | 跑法收口（`--case` / `--tier` / `--all`，报告落盘） | 日常能当命令用 | CLI + JSON 报告 |
| E6 | 文档收口 | 状态与真源一致 | doc/45 头注、doc/16 §2b 第 6 行、doc/README |

**顺序理由**：E1 必须先有"能跑的东西"（硬闸门要求第一个 action 是可打可验的端点/命令）；E2 依赖 E1 的格式；E3/E4 是可选档，不做也不影响 A 档的机器判红；E5/E6 收口。

## 5. v1 明确不做

- **不做 UI 场景**（Playwright 活体另立 loop——doc/44 那一档已经证明 UI 活体是独立的一摊）
- **不做「从生产日志自动挖场景」**（要先有日志挖掘，v1 语料手工固化就够）
- **不做 CI**（仓库没有 CI 基建；v1 是本地跑）
- **不做性能压测 / 公平性压测**（多租户公平性是 doc/28 那一档的活）
- **不做「每次提交都跑慢档」**（慢档要真模型、要钱、要时间）
- **不改 `internal/runengine/` 的生产代码**：Eval 是站在引擎外面看它的；发现缺陷 → 另开一拍修引擎，而不是在 Eval 里加后门

---

## 6. 收尾：所以这一层解决了什么

**一句话**：tako 今天能自动判红的是"接口有没有按约定回"，判不了"**活到底干完了没有**"——而后者才是客户买的东西。

这一层把「任务 → 跑 → 判定 → 出证据」变成一条可重跑的流水线，于是：
- 挂载点选错、围栏被绕、看板没人建、失败轮不落库——**这些缺陷从"靠人想到"变成"机器会红"**；
- 那一周手工验过的活体场景，从"只有那天的会话记得"变成"**任何人任何时候都能一键重跑**"；
- 判据分三档，**该稳的稳（A 档）、会抖的明说会抖（B 档带容忍）、不稳的登记不假装（C 档）**——不把"模型今天心情好"当成测试通过。
