## 0. 一句话结论

同一个引擎里现在并存两套响应格式：新的产品接口回 `{code,message,data}`，旧的业务接口回裸 JSON 加 `{"error":"..."}`。这一笔把旧的五组接口（runs / sessions / mcp / media / memory）**整包**换成 `{code,message,data}`，**不动数据库、不动帧格式、不动 HTTP 状态码**，只改响应体的外壳，并把旧 `error` 字符串里混着的多种语义拆成互不重叠的数字业务码。

## 1. 背景与动机：这套格式是怎么长成两套的

2026-10-18 之前，引擎只有一套接口，它的响应体长这样：

```json
202 {"sessionId":"s_01","runId":"r_01","messageId":"m_1"}
404 {"error":"session_not_found"}
409 {"error":"session_busy"}
500 {"error":"internal"}
```

成功的时候，**业务字段直接摊在顶层**；失败的时候，只有**一个 `error` 字段**，里面放一个机器能认的短字符串。

2026-10-18 做了多租户（doc/28）。新加的接口（登录、租户、成员、邀请、项目、助手）从一开始就统一成：

```json
{"code":0,"message":"","data":{"accessToken":"…","tokenType":"Bearer","expiresIn":900}}
{"code":111101,"message":"邮箱或密码不正确","data":null}
```

这就是**信封**：成功时业务体塞进 `data`，失败时 `code` 给页面分支用、`message` 直接当弹窗文案、`data` 放「没有额外细节就 null、键仍然在」。

**病灶——一个具体会发生的失败故事：**

前端同学要写「发消息失败」的提示。他打开 `web/src/api.ts`，看到两种失败体同时存在：

```ts
export type ApiErrorBody = { error: string }     // 旧的
```

他写了个判断：`if (body.error === 'session_busy')`。跑起来发现，**登录过期**返回的是 `{"code":111102,"message":"请先登录"}`——没有 `error` 字段，他这个判断永远不成立，于是登录过期的用户看到的是一句空白的「操作失败」。反过来，会话 404 返回的是 `{"error":"session_not_found"}`——没有 `code`，他想按 `code` 统一弹窗的拦截器也接不住。

**同一个页面，同一个失败，两套拆包。**这不是审美问题，是「前端每个接口各写一个拆包」的必然结果：AGENTS.md 里那句「没这条规则时，登录弹一句、会话 404 再弹另一套，前端每个接口各写一个拆包」，说的就是现在这个局面。

**动机的落点**：`message` 已经是现成的弹窗文案，`code` 已经是现成的分支依据。前端只需要写**一次**拦截器——看 `code` 决定要不要跳登录页，把 `message` 弹出来。这个收益要等到旧接口全部换完才兑现，所以这是一笔**整体替换**，不能一半一半地留着。

## 3. 换完是什么样

同一组接口，换完之后：

```
POST /api/runs 成功   202 {"code":0,"message":"","data":{"sessionId":"s_01","runId":"r_01","messageId":"m_1"}}
POST /api/runs 失败   404 {"code":112001,"message":"找不到这场会话","data":null}
POST /api/runs 超长   413 {"code":113003,"message":"这条消息太长，裁剪后再发","data":{"limit":940,"tokens":1200}}
```

规则四条：

1. **HTTP 状态码一个字不改**。还是 400/401/403/404/409/413/429/500。状态给网关分类，业务码给页面区分同一种状态里的不同原因。
2. **`data` 里就是原来那个业务体，字段名一个都不改**。`{"liveRunId":"r_1","runlogOffset":1}` → `data` 里还是 `{"liveRunId":"r_1","runlogOffset":1}`。这次只换外壳，不顺手改字段名。
3. **失败时 `data` 是 `null`，但键必须在**。有额外诊断信息（图片为什么不合法、消息超了多少）就放 `data` 里，`message` 只放人话。
4. **204 没有 body**，SSE 帧面和二进制成功体不进信封（见 §6）。

### 4.2 本轮新增的码

| 旧 `error` | 新 code | HTTP | message | 为什么需要新的 |
|---|---|---|---|---|
| `bad_media`（图片 mime 不合法／base64 解不开／超 5MB／超 4 张） | `111004` | 400 | 图片不符合要求 | 旧的 `bad_media` 是「入口媒体」专有的，旧码表里没有对应项 |

| `session_busy`（这场会话已有活 run） | `112101` | 409 | 这场会话正在跑，等它跑完再发 | **注意与 `114007` 区分**：`114007` 是「删除会话时这场会话有活 run」（doc/37 D3），语义不同，码不能撞 |
| `not_resumable` | `112102` | 409 | 这场 run 已经定稿，没有可续的 | 前端要靠它决定「不显示续跑按钮」 |
| `run_alive` | `112103` | 409 | 这场 run 还活着，别抢 | 前端要靠它决定「不是失败，转去重建帧面」 |
| `resume_exhausted` | `112104` | 409 | 续跑次数用完了，重新发一轮 | 前端要靠它决定「提示重发」 |
| `message_too_large` | `113003` | 413 | 这条消息太长，裁剪后再发 | 旧的 413 带 `limit`+`tokens` 两个诊断字段，换信封后放 `data` |

### 4.3 media 那个 `not_found` 拆成三种语义

旧的 media 404 有四个出口都写同一个 `{"error":"not_found"}`，前端分不出「你根本没权限看这个项目」和「这个文件真的没有」：

| 旧出口 | 新 code | message |
|---|---|---|
| 路径不是 `workspaces/<wid>/…` 格式 | `114102` | 媒体路径不对 |
| `VisibleWorkspace` 失败（工作区看不见） | `114001`（已有 `codeWorkspaceMissing`） | 找不到这个项目 |
| `workspaceDir` 解析失败 | `114101` | 找不到这个文件 |
| `os.Stat` 失败或目标是目录 | `114101` | 找不到这个文件 |
| 缺 `path` 参数 | `111001` | 请求格式不对（`data.reason` = 「缺 path」） |
| 路径越出 workspace 且**无登录身份**（单测探针） | `111001` | 请求格式不对（`data.reason` = 「路径越出 workspace」） |

## 6. 三样明确不动的

1. **`GET /api/media` 的成功体**。它回的是图片字节（`http.ServeContent`），不是 JSON。套信封会把图片变成 base64 的 JSON——那是把 doc/32「对话里只存 path、显示时才换回字节」的设计推翻。**只换它的错误分支**。
2. **SSE 帧面**。`GET /api/runs/:id/stream` 回的是 `text/event-stream`，每一帧是 `data: {帧JSON}`。帧是长连接里的事件，不是某个 HTTP 响应的 body——信封在这里没有位置。流前面的 401 已经是信封（`viewRun` 里写的），流的 `event: gone` 保持原样。
3. **HTTP 状态码与 204**。204 没有 body，这条是 AGENTS.md 原话。

## 9. 收口

换完之后，前端只有**一个**拆包入口（`api.ts` 的 `request`）：看 `code` 决定跳不跳登录页，把 `message` 弹出来，`data` 是业务体。后端每个失败出口都带着一个互不重叠的数字码，页面不再靠拆 `message` 的句子来分支——这就是这一笔解决的东西。
