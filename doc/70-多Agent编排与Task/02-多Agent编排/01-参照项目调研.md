## 1. 先演一场戏：什么叫“编排”没有成立

用户说：“分别调研 A、B 两个市场，等两份证据都齐了，再写一份综合报告。”

如果系统只有一个主 Agent 依次调用 researcher，它可以完成工作，但这仍是主子代理调用。真正的多 Agent 编排需要系统明确知道：

```text
任务 A：调研 A 市场 → researcher
任务 B：调研 B 市场 → researcher
任务 C：综合 A＋B → writer；只有 A、B 都成功才可开始
```

并且当 B 崩溃时，系统不能假装 B 已成功、不能让 C 先跑、不能因为 A 已成功就把 A 无意义地重复执行。最后还要让 C 读到 A、B 的结构化结果，而不是让三个 Agent 无限共享全部聊天记录。

因此“多 Agent 编排”的操作定义是：**多个有独立上下文与权限的 Agent，围绕持久工作项进行分配、交接、依赖推进和结果汇合；系统能够解释每一步谁在执行、为何可以执行、失败后怎样继续。** 并行只是其中一种情况，不是唯一判据。

## 2. 三个参照不是同一种东西

| 参照 | 核心形态 | 已回答的问题 | 没回答的问题 |
|---|---|---|---|
| **tako 当前** | 主 Agent 通过工具委派 coder／researcher；子代理有独立上下文、权限和 wire 档案 | 主子代理隔离、执行、回传、完整档案 resume | 独立任务调度、依赖、跨代理汇合 |
| **Octop／harness-agent TeamManager** | 用户拥有多个具名 Agent；`agent_list` 发现同伴，`ask_agent` 同步或后台调用；后台结果经 inbox 回来 | Agent 发现、点对点调用、异步交接 | 任务依赖图、统一调度器、完整结果仲裁 |
| **Comma 当前** | Router 创建持久 Task；每 Task 一个 Worker；结果消息唤醒 Router | 持久委派、幂等创建、独立 Session、沉默监控、状态分权 | 当前 Task Graph 已退役；没有 Hermes 式依赖推进 |
| **Hermes Kanban** | 具名 Agent 围绕持久看板工作；任务有受让人、依赖、状态和运行记录；调度器启动与回收 worker | 任务分配、依赖、并行、审查、故障回收、审计 | 不是多副本 PG 架构；不证明模型判断或任务语义正确 |

所以“参考哪一个”不能只有一个答案：**做可靠 Task 看 Comma，做同伴互调看 Octop，做依赖与调度看 Hermes。**

## 3. Octop：同伴调用比主子委派多了一层什么

`TeamManager` 维护 Agent registry，并提供同步／异步协作与 inbox：`/Users/yuweikang/dev/ykcode/harness-pkg/harness-agent/harness_agent/teams/team_manager.py:55`。

模型侧有两把工具：

- `agent_list`：列出当前用户可见的 Agent 及能力说明；
- `ask_agent`：选择一个同伴，同步等回答，或以 background 方式交出长工作，完成后再次唤醒调用方。

真实工具定义见 `/Users/yuweikang/dev/ykcode/harness-pkg/harness-agent/harness_agent/teams/tools.py:140`。

它比普通子代理多出来的是“具名同伴＋后台交接”，但调用仍是 Agent 到 Agent 的点对点关系。没有任务依赖与结果仲裁时，不能因为出现 `ask_agent` 就宣称完整编排已完成。

对 tako 的启示：将来若需要专家目录，可复用现有 Agent 规格与权限清单，不必让模型任意创建高权限 Agent。本期方案不先做这个入口。

## 4. Comma：持久 Task 是地基，但当前不是完整任务图

Comma 的完整链路、代码证据和失败故事已写在 [Task 线的 Comma 调研](../01-Task/01-Comma持久Task调研.md)，本篇不复制条款。

对多 Agent 方向最重要的三项事实是：

1. 当前每个 Task 只有一个负责 Worker；
2. 当前创建入口明确拒绝旧 `workflow`，Task Graph 已退役；
3. Router 负责接收结果与推进状态，没有 Hermes 那种依赖满足后自动 claim／spawn 的现行调度链。

因此 Comma 的“Swarm Intelligence”产品表述不能代替代码核验。它仍非常适合回答“异步委派怎样可靠”，但不适合单独回答“任务依赖怎样由系统推进”。

## 5. Hermes Kanban：为什么它是完整编排参照

### 5.1 工作是持久记录，不是一次调用

每个 Task 是看板数据库中的一行，包含目标、受让人、状态和幂等身份；每次交接是消息或状态记录。执行者是具有持久身份的具名 profile，而不是父 Agent 的一次匿名函数调用。

### 5.2 依赖边由程序推进

`parents` 表示“这些父任务完成后，子任务才可开始”。代码会校验未知父任务与循环依赖，并计算哪些任务可以进入 ready：

- 图校验与分解：`/Users/yuweikang/dev/ykcode/ref-agent/hermes-agent/hermes_cli/kanban_db_graph.py:25`；
- 工具读取任务时同时返回 parents、children 与未满足依赖：`/Users/yuweikang/dev/ykcode/ref-agent/hermes-agent/tools/kanban_tools.py:639`；
- 父依赖未满足时，完成子任务也会被拒绝，而不是只在前端置灰：`.../tools/kanban_tools.py:755`。

这解决的是“提示词写了顺序，但模型仍然提前执行”的问题：顺序不仅写在说明书里，还由存储和状态转换执行。

### 5.3 调度器负责启动、限流与回收

调度器识别 ready 工作、按受让人启动 worker，并处理并发上限、运行超时、崩溃回收和连续失败熔断。代码集中在：

`/Users/yuweikang/dev/ykcode/ref-agent/hermes-agent/hermes_cli/kanban_db_dispatch.py:1`

其中崩溃路径不是看到 PID 不在就简单再启动：它还检查认领者、运行代次和旧 worker 是否仍存活，避免旧执行者旁边再跑一个重复执行者。示例见同文件 `:1296`。

### 5.4 完成与审查是明确交接

Worker 可提交完成、请求审查或报告阻塞；reviewer 可接受或退回。状态变化和结构化 summary／metadata 留档，后续 worker 能读到同一事实，而不是依赖上一个 Agent 的私有记忆。

### 5.5 不照搬的部分

Hermes Kanban 以本地 SQLite 与 OS 进程为重要运行边界，产品设计包含单主机假设。tako 的目标是多副本 Go＋PostgreSQL／Redis，因此只摄取任务语义、状态约束和调度责任，不把 SQLite、PID 管理或本地 worktree 布局照搬过来。

此外，状态机只能证明“系统按规定推进”，不能证明模型报告写得对；结果质量仍需要独立验证与 doc/45 的场景化 Eval。

## 6. 对 tako 的最终摄取分工

| 方向 | 主要参照 | 落到方案里的动作 |
|---|---|---|
| 持久委派 | Comma | Task＋首条命令原子创建；独立执行 run；持久通知；幂等与中断边界 |
| 同伴发现与后台调用 | Octop | 只保留为后续可选入口，不进第一期 |
| 依赖与调度 | Hermes | `parents` 依赖边；ready 计算；原子领取；并发上限；失败与取消传播 |
| 结果汇合 | Hermes＋Comma | 结构化结果与文件路径进入下游 Task；协调 Agent 负责最终交付 |
| 质量验证 | tako 自身 doc/45 | 独立检查最终产物，不采信“Agent 说完成” |

## 7. 调研结论

tako 不应把目标写成“做一个和某项目一样的 swarm”。可验证的目标是：

> 一个协调 Agent 创建 A、B、C 三件持久 Task；A、B 可并行，C 依赖 A、B；调度器只启动满足依赖的工作；结果通过结构化记录交接；一个执行者中断后，状态仍可解释、可恢复，最终只产生一份综合交付。

这就是后续方案的完成线。
