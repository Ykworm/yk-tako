## 1. 为什么是一个方案集、两个方向

tako 当前已有主 Agent 委派 coder／researcher：子代理有独立上下文、工具权限、持久档案和完整档案 resume。但要把“调用一个子代理”推进到“多个 Agent 按依赖完成一个目标”，中间缺两层不同机制：

1. **Task 方向**：一件工作怎样脱离一次工具调用，拥有独立身份、输入、执行 run、状态、结果和通知；
2. **多 Agent 编排方向**：多件 Task 之间怎样表达依赖、取得执行权、控制并发、交接结果和响应失败。

如果只做 Task，得到的是可靠的异步委派；如果跳过 Task 直接画任务图，图上的节点仍没有独立执行与恢复语义。两条线因此共用一套 V1 方案，但施工顺序不是并列：**Task 是底座，多 Agent 编排消费 Task。**

## 3. 调研形成的参照分工

- **Comma**：学习持久 Task、创建幂等、独立执行 Session、结果通知与两类沉默监控。其当前版本一个 Task 一个 Worker，旧 Task Graph 已退役，因此不是依赖调度的主参照。
- **Hermes Kanban**：学习任务依赖、ready 推进、原子领取、具名执行者、审查与故障回收。其 SQLite／本机进程形态不照搬到 tako 的多副本 Go／PostgreSQL 目标栈。
- **Octop／harness-agent TeamManager**：学习具名 Agent 发现、同步／后台同伴调用与 inbox；作为后续可选能力，不是 V1 前提。
- **Eino**：继续负责 Task 内部的 Agent 与模型／工具执行；外层业务 Task、依赖、通知和交付事实由 PostgreSQL 保存。

## 4. V1 最小完成线

先让一件 Task 独立跑完并能恢复，再完成下面这一场：

```text
用户目标
  → 协调 Agent 一次创建 A、B、C 三件 Task 与两条依赖边
  → researcher 分别执行 A、B
  → C 声明 parents=[A,B]，只有两者成功才 ready
  → writer 读取 A、B 的结构化结果与文件路径，生成汇总
  → 一个执行者中途崩溃：C 不提前启动，恢复后只产生一个 C
  → 协调 Agent 交付一份可独立检查的 final 文件
```

这条链同时证明“有多个 Agent”和“系统确实在编排它们”。只看到多个角色名、没有依赖与结果交接，不算本方案达成。

V1 的图创建后不修改工作内容、执行者或依赖边。下一版可以讨论 Goal 驱动的动态计划修订，但不把动态改图、Agent 自由群聊或无限共享历史塞进 V1。

## 5. 与现行文档的边界

- doc/25、doc/39：现有同步子代理委派与 wire 档案仍是当前实现真源；本方案集未改变它们。
- doc/41：现有 `run_tasks` 是一次 run 内的看板，不是可调度 Task；两者不能混名。
- doc/30：现有 run 的租约、执行代次、journal 与显式 resume 是恢复底座；本方案集不承诺外部副作用 exactly-once。
- doc/43：租户并发容量仍在数据库裁决；编排组不能绕过它。
- doc/45：任务是否真正做对由独立场景评测证明，不由 Agent 自报成功。
- doc/71：文件写入竞争与长任务 worktree 有独立方案边界，V1 不顺带实现并行仓库合并。
