## 3. 项目介绍：约 3 分钟

### 3.1 先讲用户为什么需要它

> 用户想让 AI 完成一个需要多步骤的任务，例如阅读项目文件、整理资料并生成文件。一次模型回复未必够用：模型先决定调用工具，工具返回后再继续判断，必要时委派子代理，直到形成最终结果。
>
> 这条链路可能持续很久。浏览器断线、模型拒收过长输入、worker 退出，都可能发生在任务已经完成一部分以后。如果只写一个“请求模型然后返回文本”的接口，失败时就很难知道哪些步骤已经做过、哪些结果还在。
>
> tako 的定位是管理这段执行过程的 Agent 运行时，不是以知识库问答为主体的产品。检索和记忆是执行过程需要时使用的支撑能力。

### 3.2 连起来讲一条业务链

```text
用户提交消息
  → HTTP API 校验身份、会话与工作区访问权限
  → 存储层创建 run，记录用户消息并取得执行权
  → worker 装配模型输入，交给 Eino 的 Agent 循环
  → 模型返回文本或工具调用
  → 工具执行，结果进入下一次模型输入
  → 浏览器通过 SSE 或 frames 拉取观看过程
  → 成功收尾时提交定稿历史及后续模型需要的历史
  → 浏览器读取定稿结果，用户取得回复与生成文件
```

run 指一次任务执行，session 指它所属的会话。一次 run 内可能有多次模型调用和多次工具调用。

Eino 提供 Agent 循环和中间件接入能力；项目代码承担身份、数据归属、运行状态、存储、帧接口、恢复及上下文处理等工作。不要把框架已有能力都说成自己从零实现，也不要把调用框架等同于没有工程工作。

### 3.3 解释为什么这样分存储

PostgreSQL 保存需要长期保留或决定执行权的数据，例如 run 状态、租约、执行账本和历史。Redis 保存带过期时间的实时帧及执行代次标识。

用户看到的定稿历史，与下一次发给模型的历史不是同一份用途：前者保留已完成的交流和工具活动；后者要服从模型窗口限制，可能被摘要替代。如果直接压缩用户历史，用户回头查看的原始结果也会被改掉。

SSE 用来及时显示进度，但断线不能等于任务结果丢失。页面还能通过状态、frames 和定稿历史接口重新取得需要的数据。不能把 SSE 说成可靠消息队列。

### 3.4 主动交代边界

> 这是个人工程实践项目。已有相关机制和测试代码，但我不会把它说成已经经历大规模生产流量。目前需要进一步补充的是固定版本下的故障实验、任务效果评测和性能数据。崩溃续跑的回归收口状态也需要按当前索引确认。

真源入口：[文档索引](../README.md)。入口实现：[server.go](../../yk-tako-eino/internal/runengine/server.go)、[worker.go](../../yk-tako-eino/internal/runengine/worker.go)。

## 4. 工程故事一：worker 死了，恢复不能变成盲目重做

### 4.1 先演失败场景

用户让 Agent 修改文件。工具已经写完文件，进程却在记录工具结果之前退出。用户点击继续执行，新 worker 只看到“计划调用工具”，不知道外部写入有没有发生。

如果它直接重跑，追加写入或外部请求可能发生两次。如果它当成成功，又可能把没做完的步骤说成完成。恢复的核心问题不是“重新启动函数”，而是辨认已知结果和未知结果。

### 4.2 当前实现如何处理

1. **工具执行前先记调用意图。** 主 Agent 工具包装器将工具名、参数和调用 ID 写入 `run_journal`。写入失败就不执行工具，避免工具发生了而系统连调用记录都没有。
2. **工具返回后再记结果。** 下一步重放读取这些记录，按调用 ID 配对，而不是假定并行工具的返回顺序就是发起顺序。
3. **worker 定期续租。** 租约是数据库里的到期时间。进程退出后无人续约，状态读取可以将过期的 running 显示为 interrupted；它不需要先等后台任务改状态。
4. **恢复先抢执行权。** `/resume` 在数据库事务内锁住 run 行，检查状态、租约和次数，再将 `lease_epoch` 加一。这个数字是执行代次，新 worker 带新值，旧 worker 仍带旧值。
5. **拿账本构造模型输入。** 已有结果直接回放；缺少结果的调用回注“中断、没有拿到结果、引擎不会自动重跑”的说明。然后重建 Redis 实时现场，启动续跑。

上一拍记录下来的调用和结果，是恢复输入的来源；取得的新代次，是后续写入能否被接受的依据。

### 4.3 为什么租约还需要执行代次

旧 worker 不一定真的死了，也可能只是暂停太久。租约过期、新 worker 接管后，旧 worker 又开始运行。

因此续约、账本写入、定稿写入和 Redis 帧写入需要识别执行代次。旧代次不能继续提交到新执行者负责的状态里。仅有“到期时间”不足以告诉存储层这次写入来自谁。

这里阻止的是受守卫保护的状态写入，**不是撤销已经开始的外部工具副作用**。文件系统或第三方接口是否接受旧执行者的操作，要另外设计。

### 4.4 必须承认的边界

- 重放不会自动重做缺结果的旧调用，但模型仍可能新发起同类调用。
- 工具副作用与账本不是一个跨系统原子事务；“工具已执行、结果未记下”的窗口仍存在。
- 不能因此承诺业务操作 exactly-once，即“整个业务动作严格发生一次”。付款、发信等场景还需要业务幂等键、结果查询或人工确认。
- 这段主线程账本逻辑不是子代理全部内部执行的无缝恢复。子代理档案与 resume 应单独按当前实现解释。
- 多副本恢复还需要能访问原文件。数据库可接管不等于本地工作区文件自动共享。

**90 秒练习稿：**

> 我把恢复分成执行权和已完成工作两件事。数据库租约过期后，恢复请求锁住 run 行并增加执行代次，新 worker 据此接管；旧 worker 即使恢复运行，也不能继续写受守卫保护的状态。工作进度来自执行账本：工具前记调用，工具后记结果。重放时复用已有结果，缺结果的调用明确标为未知，不直接重做。我不把这称为业务严格一次，因为工具副作用与账本之间仍有失败窗口，模型也可能重新发起同类动作。

证据：[journal.go](../../yk-tako-eino/internal/runengine/journal.go) 的 `InvokableRun`、`replayJournal`；[store.go](../../yk-tako-eino/internal/runengine/store.go) 的 `ClaimResume`、`RenewLease`、`EndRun`；[redisstore.go](../../yk-tako-eino/internal/runengine/redisstore.go) 的代次校验脚本。

所以，这解决的是“能依据已记录的工作继续，并挡住旧执行者覆盖新状态”，不是“所有外部动作都能无损恢复”。

## 5. 工程故事二：身份合法，不代表路径合法

### 5.1 先演失败场景

一个已登录用户有权访问工作区 A，提交媒体路径：

```text
workspaces/A/../B/.media/example.png
```

如果程序先认出 A 并放行，再由文件系统解释 `..`，最终读到的却是 B。登录检查成功，仍可能发生越权。

### 5.2 当前媒体读取链

```text
用户请求 /api/media?path=...
  → 路径解析先 Clean，得到实际工作区 ID 与内部相对路径
  → VisibleWorkspace 用当前身份检查这个工作区是否可见
  → 用服务端身份中的租户 ID 构造工作区根目录
  → resolveInWorkspace 检查最终路径是否仍在这个目录内
  → 通过后才打开文件并返回媒体字节
```

顺序很重要：规范化后的 ID 是鉴权的输入；鉴权通过后确定的根目录，是文件读取的边界。不先规范化，就可能检查 A 却读取 B。

会话接口另外检查租户、属主和可见性。同租户成员能读取共享会话，不代表能写它；项目目录是工作区级资源，也不能笼统说所有文件都按私人会话隔离。

**90 秒练习稿：**

> 我不会把多租户隔离理解成加一个 tenant_id 字段。数据接口要检查对象归属，文件接口还要检查程序最终会打开哪个路径。媒体读取先规范化路径，再检查实际工作区可见性，最后用服务端身份确定租户目录并检查目录边界。否则合法工作区前缀后面加一个 ../，就可能绕过前缀检查。这个机制解决路径归属问题，但不等于任意 bash 或 MCP 工具都天然安全，它们还需要自己的执行边界。

证据：[media.go](../../yk-tako-eino/internal/runengine/media.go) 的 `parseSessionMediaPath`；[server.go](../../yk-tako-eino/internal/runengine/server.go) 的 `getMedia`；[session_access.go](../../yk-tako-eino/internal/runengine/session_access.go) 的 `decideAccess`。

所以，这解决的是“检查的资源与实际读取的资源一致”，不是“JWT 有效就允许读文件”。

## 6. 工程故事三：上下文压小一次，下一轮为什么又超了

### 6.1 先演失败场景

Agent 已经读了多个文件，准备把工具结果送给模型。发送前的 token 估算认为装得下，但模型厂商拒收：输入超过窗口。

一味重试同一份输入不会变短；从整个 Agent 任务开头重跑，则可能再次执行已经做过的工具。即使临时压小这次请求，如果循环内部还保存着旧历史，下一次调用又会超限。

### 6.2 当前实现如何处理

1. **先分类错误。** `IsOverflowError` 先排除限流、服务不可用等报文，再匹配上下文超限。否则一次限流可能被误当成历史太长，导致无谓摘要。
2. **区分起手与中途。** 起手尚未产生相关帧时，外层有单独救援路径；中途拒收由模型包装器处理，缩小重试范围，只重试被拒的模型调用，不重跑此前工具。
3. **构造更短输入。** 将历史转换成可摘要的形式，计算目标预算，摘要旧内容并保留所需消息，再用折后输入重试。摘要也可能失败，因此救援不是无限循环。
4. **把折后历史写回循环状态。** 包装器把折后消息及救援时的输入长度保存下来；下一轮中间件用它替换旧历史，并接回救援后新增的回复和工具结果。只改变重试请求、不改变循环状态，会在下一轮回到原来的超长输入。
5. **限制救援次数。** 同一次 run 的相关救援路径共用一次性标记，避免反复摘要、重试和消耗成本。

**90 秒练习稿：**

> 上下文管理不能只有发送前计数，因为本地分词估算与实际厂商输入仍可能有差异。我增加了实际拒收后的救援，但关键不是简单删几条消息。中途拒收只重试模型调用，不能重跑已经发生副作用的工具；折后历史还要回写到 Agent 循环状态，否则下一轮又拿旧历史超限。另外错误要先分类，限流不能当成超限处理，救援也必须有次数上限。

证据：[overflow.go](../../yk-tako-eino/internal/runengine/overflow.go)、[guard.go](../../yk-tako-eino/internal/runengine/guard.go)、[midfold.go](../../yk-tako-eino/internal/runengine/midfold.go) 的 `BeforeModelRewriteState`。

边界：错误文本匹配不等于所有厂商行为都已实测；从报文提取窗口值属于有局限的规则。摘要会丢信息，“请求能被模型接受”也不等于“任务结果仍然正确”，后者需要任务评测。

所以，这解决的是“拒收后缩小正确的调用范围，并让后续循环继续使用新历史”。

## 7. 高频追问：回答到哪里才算够

| 追问 | 回答应包含的内容 |
|---|---|
| 为什么用 Eino，不直接手写循环？ | 框架提供什么；项目自己承担什么；中间件能接入哪里；框架边界造成过什么实际约束。不要只说“生态好”。 |
| 为什么执行权放数据库？ | 两个副本各自的 mutex 看不见对方；数据库部分唯一索引限制同会话 running 行；租约处理失联，代次处理旧执行者回来。 |
| 数据库和 Redis 能一起原子提交吗？ | 不能用 PostgreSQL 事务包住 Redis 就声称跨库原子。逐个说明写入顺序、失败补偿、剩余窗口和读侧如何处理。 |
| 相同 messageId 重发能去重吗？ | 不应默认能。当前契约不承诺 messageId 去重；并发忙闸也不等于重试幂等。若岗位需要，继续讨论唯一约束、请求内容校验与返回原结果。 |
| 页面断线任务会停止吗？ | 分清浏览器连接和任务生命周期；通过状态与历史重建显示；说明实时帧会过期，不能只依赖断线前的 SSE。 |
| PostgreSQL 挂了，还能执行工具吗？ | 主线程工具调用意图写账失败会阻止该工具执行；其他步骤按具体路径分析，不把局部机制推广成所有工具的全局保证。 |
| 模型被提示注入后怎么办？ | 模型决定不作为授权依据；工具在执行端做权限与参数检查，高风险动作要受限制。当前是否有审批必须查实现，不能当已有能力。 |
| 多副本是不是已经部署验证？ | 设计目标、代码守卫、双实例实测、生产部署是四件事。只承诺手头确有证据的层级，并说明文件共享与沙箱条件。 |
| 如何衡量 Agent 好不好？ | 固定任务及验收结果，记录成功率、错误类型、耗时和用量；模型或提示词变更后重跑。没有评测数据就明确还没建立。 |
| 这个项目比调用模型 API 多了什么？ | 用“工具已执行但进程退出”的场景说明状态、记录、恢复、权限和观察过程为什么需要程序负责。 |

这些问题必须与后端基本功连起来练：事务和行锁、部分唯一索引、外部副作用幂等、重试分类、请求取消、可观测性。不要只记项目函数名。

## 8. 如何回答“这是 AI 写的吧”

不要否认实际使用的辅助工具，也不要笼统说每行代码都是自己写的。

可按真实情况改写：

> 我使用了 AI 辅助研究和编码。我的具体工作是 [本人实际负责的需求拆解、方案选择、代码实现或验收工作]。我区分框架提供的能力、参考项目借鉴的机制和这个项目需要处理的业务问题。你可以选一条链路追问，我会说明输入输出、为什么这样实现、失败时发生什么，以及哪部分目前没有验证。

准备时挑一个 AI 建议被你否决或修正的真实例子，展示原建议、失败场景、你的判断和验证结果。没有实际例子就不要编。阅读代码能证明理解，不自动证明作者身份或职责归属。

## 9. 十分钟演示：先成功，再解释失败

演示使用专用账号、工作区和实例，不在已有用户数据上做破坏操作。模型结果不确定，所以提前录好一段真实成功过程作为备用。

| 时间 | 操作 | 希望面试官看到什么 |
|---|---|---|
| 0:00-1:00 | 讲用户任务与项目定位 | 是完成多步骤任务，不是功能菜单展示 |
| 1:00-4:00 | 提交一个可验证的小任务，例如生成一个短文件并读回 | 模型调用、工具执行、最终交付连成完整链 |
| 4:00-6:00 | 刷新页面或重开连接，查看状态与定稿历史 | 浏览器连接不是任务结果唯一来源 |
| 6:00-8:00 | 展示已提前完成的中断恢复实验记录 | 记录工具结果、执行代次与恢复结果，不临场赌模型行为 |
| 8:00-10:00 | 打开一段关键实现并解释边界 | 能接受深入追问，不只是能运行界面 |

下面仅用于核对基础 API，**本次未执行**。先按根 README 启动隔离环境并登录，在当前 shell 设好 `BASE` 和专用账号的 `TOKEN`，不要把令牌录进截图或提交到仓库。

```bash
curl -i -X POST "$BASE/api/runs" \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"messageId":"interview-demo-001","text":"请只回复 interview-ready"}'
```

成功预期为 HTTP 202，返回 `sessionId`、`runId`、`messageId`。将前两个值设为 `SESSION_ID`、`RUN_ID` 后读取：

```bash
curl -sS "$BASE/api/runs/$RUN_ID/frames?eventOffset=0" \
  -H "Authorization: Bearer $TOKEN"

curl -sS "$BASE/api/sessions/$SESSION_ID/log?runlogOffset=0" \
  -H "Authorization: Bearer $TOKEN"
```

frames 预期包含 `frames`、`nextOffset`、`status`；运行期间可见生成帧，完成后可见 terminal，过期后可能为 gone。log 包含 `rows`、`nextOffset`，成功定稿后应能找到 assistant 结果。不要把某一瞬间没有结果误判成失败，也不要要求模型严格输出固定字节来判断接口正确性。

详细字节以现行契约与实现为准；旧 runs 接口未统一换成新 JSON 信封。不要在面试材料里声称所有接口已经采用同一种响应格式。

## 11. 过去工作：准备两个业务故事
