# 20 · 会话级并发：从 409 到收件箱

> **性质**：设计草稿，未实施。诊断部分是**已验证的事实**（附代码位置）；设计部分是提案。
> **起因**：两次独立的追问，指向同一个空洞。第一次是纸上推演「同 session 两个标签页会怎样」，
> 第二次是用 Kimi 的 APP + 网页做实测反证。
> **一句话结论**：409 不是缺一个错误处理，是 `POST /api/chat` 的语义把「输入」和「执行」绑死了。
> 修法是解耦，不是打补丁。解耦之后，409、不变量 6、多标签页画面分裂三个问题一起消失。
>
> 路径约定：同 doc/19，`internal/webui/...` 省略 `yk-tako-eino/` 前缀。

## 1. 现状：409 守住了什么，没守住什么

### 1.1 数据层是安全的

会话闸 `session.live` 由 `s.mu` 保护，每会话最多存在一个 run：

```go
// session.go:96
if s.live != nil {
    return 0, nil, nil, false, nil   // → 调用方回 409
}
```

所有写路径都在事务里，且各有额外校验：

| 写操作 | 保护措施 |
|---|---|
| `beginTurn` | 持 `s.mu`，占闸与装档案原子完成（session.go:93-111） |
| `BeginRun` | 事务内插 run_archive 行 + seq=1 start 帧 |
| `Finish` / `FinishWithPatch` | 事务内写终局帧 + 改 status；之后 `Append` 直接拒绝（不变量 5） |
| `RestoreMessage` | 事务内校验 status ≠ running、owner == sessionID、seq == max+1（logdb.go:248-273）。⚠️ **但这个方法没有任何调用方**——见下方「一处更正」 |
| `modelMsgs` | 只在持锁时改，且改它的只有唯一 live run 的 driveRun |

**一处更正（核实过代码）**：本文早期草稿把 `RestoreMessage` 列为「崩溃窗口的兜底」。
**它兜不住，因为浏览器那一半已经不在代码里了。**

- 路由 `POST /api/chat/restore`（server.go:67）、handler（:456-485）、DB 方法（logdb.go:243）、
  测试 `TestRestoreCompletedMessage`（server_test.go:1092）**都在**
- 但 `internal/webui/static/` 下**只有 index.html 一个文件**，其中 `restore` 出现 **0 次**
- 全仓 grep `/api/chat/restore`，除路由注册外**无任何调用方**
- 浏览器 localStorage 只存 sessionId（index.html:562-563、:1110），**不存任何对话内容**
- 那个测试直接调 `d.RestoreMessage(...)`，`d` 是 DB 结构体——**不经过 HTTP，也不经过浏览器**

所以真实情况是：进程死在「流结束」与 `AppendSealed`（session.go:303-304）之间时，
全文只在 `eventMem` 里，而 **`eventMem` 也是进程内存，一起没了**。
那条 assistant 正文从 event_log 和 run_archive **同时消失**，下一轮模型上下文缺这一条。
**这不是表现层问题，是真实的（虽然窄的）数据丢失。**

**但这不是「忘了接线」，是「有计划地悬空」。** doc/15:252 明写：

> `RestoreMessage` 和 `handleRestore` **暂时保留，等 MQ 落地后再删**

即：浏览器备份那一半**曾经有过，是被主动移除的**（因为「页面从 event_log 读对话」之后
浏览器不再是真源，让它补发正文在架构上就是倒退）；服务端那一半故意留着当占位，
等 MQ 同步写入（doc/16 #8c）落地后一起删。**MQ 里会有完整正文，窗口从根上消失，
不需要任何补发协议。** 所以正确的措辞是「兜底被拆了一半、另一半在等 MQ」，
而不是「兜底没写完」。

（这也说明「数据层安全」这个结论要限定范围：**并发写是安全的，崩溃恢复有一处未接线的洞**。
两者不是一回事，面试时不能混着说。）

**结论**：不可能有两个 run 并发写同一会话的档案。后开的 run 一定能通过
`completedMessagesLocked()` 读到先前所有已完成轮次（session.go:115-139），
**模型上下文永远是对的**。库里是一条完整、线性的历史。

### 1.2 表现层是分裂的

订阅是 **run 级**的：`GET /api/chat/stream?run=<runID>&from=<seq>`。
系统里**没有会话级事件通道**。这导致一个具体后果：

> A 连 runID 都无从得知，因此不可能订阅到 B 开的那场 run。

前端也没有任何兜底——无 `setInterval`、无轮询、无 `BroadcastChannel`、无 `storage` 监听。
唯一的历史触发是滚到顶，而它只朝**更早**翻（index.html:1018）。

**精确区分：数据一致，画面不一致。** 每个标签页停在它最后一次成功订阅的时刻。

**一个同源的具体漏洞（顺手查出来的，单用户也会踩）**：
「新会话」按钮的实现是 `const run = state.runID; if (run) { POST /api/stop }`（index.html:1092-1104）。
而 `state.runID` **只在收到第一帧 SSE 时才被赋值**（:1215），`send()` 开头还会把它清空（:1139）。
所以从「按下发送」到「第一帧到达」之间它是空的——**这段窗口覆盖了模型首 token 之前的全部思考时间，
通常有好几秒，不窄**。此时点「新会话」，`if (run)` 为假，**stop 根本没发出去**，
旧 run 在后台跑到底，帧继续写进一个用户以为已经不存在的会话。

它与「没有会话级通道」是同一个根：**客户端要负责告诉服务端停哪个 run**，
而客户端在那一刻还不知道 runID。修法是让停止以 sessionID 为键、无条件取消
（`Engine.Delete`，doc/19-v3 §5.5），而不是让前端补一个 runID 的兜底查询。

## 2. 发现过程

### 2.1 第一轮：纸上推演 A/B 双标签页

先划清场景边界。sessionId 来自 `localStorage.yktakoSession`（index.html:563）：

- 两个不同浏览器 / 隐身窗 → 不同 sessionId → 完全不相干，零影响
- **同一浏览器两个标签页 → 同一个 sessionId** → 这才是真实碰撞场景

推演「A 一句、B 两句」的时序，得到：

| 时刻 | 发生什么 | A 看到 | B 看到 |
|---|---|---|---|
| t0 | A 发 a1 → run r1 | a1 + 输出 | — |
| t1 | B 打开页面，`attachLive` 挂上 r1 | 同上 | a1 + 输出 ✅ |
| t2 | r1 完成，两边 busy=false | 完整 | 完整 ✅ **此刻一致** |
| t3 | B 发 b1 → r2 | **停在 t2** ❌ | b1 + 输出 |
| t4 | B 发 b2 → r3 | **停在 t2** ❌ | b1、b2 + 输出 |
| t5 | A 发 a2 | **409 红字** ❌ | 正常 |

三个附带发现：

1. **A/B 无法真正并发输入**。两层拦截：UI 层 `attachLive` 会 `setBusy(true)`（index.html:1293），
   而 `send()` 首行即 `if (!message || state.busy) return`（index.html:1132）；
   服务端层则是闸。**「交替输入」只能串行成多场 run。**
2. **B 吃 409 后变瞎子且不自愈**。前端只 `appendError` 就 return（index.html:1152-1156）。
   讽刺的是能力全都现成——`attachLive()`（index.html:1276-1307）干的正是「查 liveRun → pullStream(0) →
   history.runs.add 防重」，但它**只在页面加载时调一次**（index.html:1309）。
   于是「B 后打开」能同步，「B 早就开着」永远同步不到。
3. **一个窄竞态**：`liveID()` 在占闸那刻就有值（session.go:100），而档案行要等 `BeginRun` 才写
   （server.go:138）。这个窗口内 attach 会吃 404（handleStream 的 lookupArchive 查不到，server.go:223）。

顺带排除一个误判：409 分支的 `return` 会走 `finally`（index.html:1180）→ `setBusy(false)`，
**输入框不会卡死**。

### 2.2 第二轮：Kimi 实测反证

纸上推演只能说明「tako 有这个空洞」，不能说明「这个空洞值得填」。
于是用 Kimi 做了实测：APP 与网页登录同一账号、同一对话（同 session），APP 发消息后 2 秒内在网页发。

**观察到的行为**：

- APP 发出消息，**网页端立刻看到该消息**，状态转为「等待 LLM 回复」
- 手速够快时，网页端的发送按钮**可以点**，消息发出后进入**排队**状态——**不是被拒**

**这两条观察各自证明一个机制存在**：

| 观察 | 证明的机制 |
|---|---|
| 网页立刻看到 APP 的消息 | **控制面通道存在**。run 级订阅做不到——它要求先知道 runID |
| 消息排队而非被拒 | **投递永远成功**。语义是「进收件箱」，不是「开一场 run」 |
| B 的会话列表新增条目；B 删掉它 → A 的任务被停、A 的列表同步删除 | 通道粒度比会话更高一层：**账号级** |
| Chrome Network 里看不到长连接，SharedWorker 里也没有 | 控制面连接不在页面上下文里，或用了 DevTools 不记录的载体 |
| 抓到 `wss://notilo.kimi.com/im/v1/subscribe/ws?encoding=proto&ticket=<ticket>` | 控制面 = **WS + Protobuf + 多路复用 + 短时 ticket** |
| 逐字输出不走 WS，走 `POST .../kimi.gateway.chat.v1.ChatService/Chat` | 数据面 = **流式 POST**，与控制面物理分离 |

即两个平面：

```
控制面  wss://notilo.kimi.com/im/v1/subscribe/ws        常驻，per 账号，多路复用所有会话
数据面  POST .../kimi.gateway.chat.v1.ChatService/Chat  per 一次 Chat 调用，流式
```

两个工程细节值得记（面试时能体现「不只是看了行为，还想清楚了为什么」）：

- 控制面挂在**独立子域** `notilo`——IM 基础设施复用，且是独立的扩缩容域
- ticket 走 **URL 参数**，因为浏览器 JS 无法给 WS 设自定义 header；
  而 URL 会进日志，所以 ticket 必须是短时的

外部产品的实际行为，把「这是不是过度设计」的疑问直接消掉了：
**会话级同步 + 输入排队是产品级必需，不是多用户边缘场景。**

### 2.3 第三轮：帧级抓包（意外收获，与 409 无关但更有价值）

拿到数据面 URL 后抓了响应流。一次「真的吗」→「1+1」的短对话，33 帧：

```
{op:"set",    mask:"message",            eventOffset:2,  message:{role:"user",      status:"MESSAGE_STATUS_COMPLETED",  blocks:[{text:{content:"真的吗"}}]}}
{op:"set",    mask:"message",            eventOffset:3,  message:{role:"assistant", status:"MESSAGE_STATUS_GENERATING"}}
{             heartbeat{},               eventOffset:3}
{op:"set",    mask:"chat.name",          eventOffset:4,  chat:{name:"1+1算式验证"}}
{op:"set",    mask:"block.text",         eventOffset:5,  block:{id:"1", text:{content:"是的"}}}
{op:"append", mask:"block.text.content", eventOffset:6..31, block:{id:"1", text:{content:"，"/"1"/" +"…}}}
{op:"set",    mask:"message.status",     eventOffset:32, message:{status:"MESSAGE_STATUS_COMPLETED"}}
{             done{},                    eventOffset:33}
```

实体是一棵树 `chat → message → block`。帧的含义不是「发生了一件事」，
而是「**某实体的某字段变成了这个值**」：`mask` 是字段路径，`op` 是应用方式
（`set` 覆盖 / `append` 尾部追加），`eventOffset` 是**跨实体类型全局单调**的游标。

这个建模差异，直接暴露了我们自己设计里三块「本可以不存在」的复杂度：

| 我们的做法 | 增量协议的做法 | 差在哪 |
|---|---|---|
| Partial 帧**反复推全文**，n 个字 = 1+2+…+n | `append` 只推增量 | **O(n²) vs O(n)** 带宽 |
| 「流式中→定稿」= 预留号 + `AppendSealed` + `ErrSealConflict` + `dropPartialTail` + 游标不前移 + `gen` 防忙等 | `op:"set" mask:"message.status"` 一次普通字段变更 | 前者是**把「正在输出」建成事件**的产物；后者把它建成**实体的状态字段**，问题不成立 |
| Partial 不落库 → 进程死在流结束与 seal 之间，全文只在 `eventMem`（进程内存），一起没了。设计了 `RestoreMessage` 让前端补发，**但浏览器那一半已被主动移除，服务端那半按 doc/15:252 留着等 MQ**（§1.1 更正） | message 实体在 offset 3 就已存在，append 累积到哪儿库里就是哪儿 | **崩溃窗口不存在**，补发机制整个不需要 |
| 前端 `appendUser` 本地回显（`state.localEcho`） | 服务端从流里回显用户消息（offset 2） | 后者下**多客户端同步是免费的**——A 和 B 画的气泡来自同一个 offset 序列 |
| seq 是 per-run，`chat.name` 这类元数据无处安放 | `mask:"chat.name"` 与内容帧共用 offset 序列 | run 中途的会话元数据变更**可表达** |
| 无心跳 | `heartbeat` **带 eventOffset** | 客户端能区分「服务端卡住」与「在等 LLM」 |
| 靠查 `run_archive.status` 判断流是否该结束（衍生出 liveID-有值-档案-未写的 404 竞态） | `done:{}` 显式终止符，且语义是「**这条流**完了」不是「这个会话完了」 | 不需要查库，也就没有竞态 |

**这一段在面试里的用法**：它证明能力不止「修好一个 409」，而是能从一个外部实现的
线协议反推出自己设计里的建模问题。判断是——**这套增量协议值得采纳，但不该和 v3 捆在一起做**：
它要重写数据面（Event/EventLog/Subscription/前端渲染/大部分测试），量级不小于 v3 本身，
而 v3 要解决的三个问题（409、排队、多客户端同步）**一个都不依赖它**。
捆在一起会让 v3 失去最好的性质：执行与档案两个最难的部分完全复用现有设计和测试。
所以是 v4，或 v3 落地后的独立一步。（详见 doc/19-v3 §12）

### 2.4 第四轮：溯源——我们的设计是从哪抄来的

前三轮都在问「应该怎么做」。这一轮问「**当初为什么这么做**」。
答案是 `ref-agent/WeKnora`（腾讯，Go + Gin）——tako 现行传输层设计的直接来源。

**逐条对上**：

| tako | WeKnora | 位置 |
|---|---|---|
| `POST /api/chat` → `text/event-stream` | `POST /knowledge-chat/:session_id` → `@Produce text/event-stream` | `routes_chat.go:119-128`；`qa.go:890,920` |
| **不变量 6**：409 必须在写 SSE header 之前 | 注释原文：「**SetLiveRun happens before SSE headers: a 409/503 after text/event-stream has started cannot change the status**, and the client would sit on a stream nobody will write to」 | `qa.go:710-712` |
| `session.live != nil` → 409 | `rejectIfOtherAgentRunLive` → `NewConflictError("another turn is already running in this session")` | `qa.go:1049-1065` |
| 订阅是 run 级，要先知道 runID | `GET /sessions/continue-stream/:session_id?message_id=...` | `routes_chat.go:87` |
| **没有会话级推送通道** | **也没有**（全仓唯一的 WS 是 sandbox 终端中继，与对话无关） | `routes_chat.go:137-157` |
| 前端只存 sessionId | 同样，localStorage 只有 session ID / 模型选择 / 分组模式 | `frontend/src/api/embed/index.ts:143` |

连不变量 6 的论证文字都同理同辞。**这不是巧合，是继承。**

**但接下来是关键转折**：WeKnora 自己**已经走出了这条路**。`routes_chat.go:72-79`：

```
POST   /sessions/:session_id/steer                  投递一条消息
GET    /sessions/:id/steer                           列出排队中的
DELETE /sessions/:id/steer/:steer_id                 撤回
POST   /sessions/:session_id/steer/:steer_id/inject  手动提升到正在跑的那一轮
```

路由注释：「Mid-run message injection … **Accepts even when no run is live**」——
这就是**投递永不因状态冲突失败**，即 v3 的不变量 7。四个端点与 v3 §5.7 的设计
**一一对应**，它还多一个 v3 没想到的「提升」。

`steer.go:18-27` 更狠，投递有**两种模式**：

```go
steerDeliveryInject = "inject"  // 在下一个 round boundary 排进正在跑的这一轮
steerDeliveryAfter  = "after"   // 默认。等当前 run 退出，成为下一场 run 的 query
```

`after` == v3 的收件箱。`inject` == **插话进正在跑的 run**，v3 原先完全没考虑这一维。
它是严格更强的能力：用户看到 agent 走错方向想说「不对，看另一个文件」，
`after` 要等它跑完（可能几分钟），`inject` 立刻生效。

**这条我当时标了「前置未知项：eino 有没有这个 hook，尚未查证」。后来查了，答案是「有，而且不止一个」**（详见 doc/19-v3 §11 问题 11）：

| 钩子 | 位置 | 语义 |
|---|---|---|
| `BeforeModelRewriteState` | `eino/adk/handler.go:160-171` | 「called before **each model invocation** … The returned state is **persisted** … **This is the recommended place to modify messages** … reflected in subsequent iterations」——就是 round boundary，而且 **tako 自己的 compact / mediaoffload 已经在用它重写 `state.Messages`** |
| `WithAfterToolCallsHook` | `eino/adk/chatmodel.go:125-134` | 「fires synchronously after all tool calls in a react iteration complete, before the next ChatModel call. **This is suitable for TurnLoop Push+Preempt patterns**」——注释直接点名了这个用法 |
| `adk.TurnLoop[T,M]` | `eino/adk/turn_loop.go:879` 起 | **eino 原生的「收件箱 + 调度器」**：`Push(item, WithPreempt())`、`GenInput(ctx, loop, items)` 决定 `Consumed`/`Remaining`（**就是合并窗口**）、`PrepareAgent(consumed)`、`Stop(UntilIdleFor)`、`Store`+`GenResume`（未处理消息持久化后重新缓冲） |

**`WithPreempt` 比 WeKnora 的 inject 更强**：WeKnora 只能等下一个 round boundary，
TurnLoop 能**打断当前正在跑的 agent turn**（`turn_loop.go:1452`），
并在 `TurnContext` 上直接给 `tc.Preempted` / `tc.Stopped` 信号。

**结论（面试里可以直接讲的一个判断）**：v3 用 middleware 那条路（改动小、不动 `adkrun`），
TurnLoop 留给 v4。**不是因为它不好，恰恰因为它太好**——它同时重写了收件箱、合并窗口、
抢占和 checkpoint-resume，在 v3 的语义层还没站稳时换底座，等于同时改两层，
而 v3 的全部风险预算应该花在语义层。

还有三处直接改进了 v3 的待定问题：

| WeKnora | 改进 |
|---|---|
| `maxSteerQueueDepth = 10`，注释「past that the run is clearly ignoring its user and **the honest answer is to refuse instead of queueing silently**」 | 我原来倾向「软上限 5、超出延后」——**错了**。静默延后是不诚实的，应该拒绝 |
| 客户端提供 `SteerID`（「so a consume event may precede the HTTP response」） | messageID 改客户端生成 → 前端能立刻画 pending 气泡、帧到达按同一 ID 对齐，**RTT 延迟感消失且不需要 localEcho** |
| 客户端提供 `ExpectedAssistantMessageID`（fencing token） | 服务端能判断「你说的那场已经不是现在这场了」，比 v3 不变量 9 更强 |

**所以准确的结论不是「被 WeKnora 带歪了」，而是：抄了它的止血层，没抄它的治疗层。**

而 WeKnora 只能止血是有原因的——它是**多副本部署**（Redis-backed StreamManager）。
`steer.go:29-33` 的注释说明了这个约束：

> `steerDataConsumed` … lives on the event itself (**not in process memory**)
> so **every replica agrees** on what is still pending

多副本下不能重写入口（会破坏其他副本上正在跑的 run），只能挂在旧协议旁边。

**两处自我更正（这一轮里被追问出来的，比结论本身更有价值）**：

**① 「tako 是单进程 SQLite，所以有条件做治疗」——这句是错的。**
doc/03:42 记的目标栈是 `Go + Gin + PostgreSQL/pgvector + Redis（asynq 任务队列）+ MCP + 沙箱 + Vue`。
asynq 是分布式任务队列 → 多 worker。**SQLite 只是测试替身，公测都不会用。**
所以多副本约束对 tako **一样适用**。

正确的理由换一个：**窗口是「未上线」，不是「单进程」。**
WeKnora 不能重写入口，是因为旧路径上有生产流量、跨着多个副本；
tako 能重写，是因为 v2/v3 **都还只是「设计草稿，未实施」，一行都没上线**。

> **这不是持久优势，是一个正在关闭的窗口。**
> 公测之后 tako 就会处在 WeKnora 今天的位置：旧入口上有真实用户，
> 重写变成破坏性变更，只能挂 steer 式补丁，
> 然后花几年解释「为什么我们有两套并存的输入语义」。

**② 「steer 是没看见」——也不对，是看见了并明确划掉了。**
doc/10:190-197 那张「写下来是为了防止实现时被 WeKnora 带跑」的排除清单里，
第 4 条就是 **`❌ steer 运行中插话`**（同列还有 `❌ 跨实例、Redis`）。

而**同一份 doc/10 的第 99 行**，对 WeKnora 的 409 是这么写的：

> 特别注意它**在写 `text/event-stream` header 之前先做冲突检查**（409/503…）——
> 流一旦开了就没法回头报错，**这个顺序是踩坑换来的，照学。**

于是真正的错误是**分类错了**：

| WeKnora 的东西 | 它的实际性质 | doc/10 把它归成 |
|---|---|---|
| 「SetLiveRun 在 SSE header 之前」+ 409 | **历史遗留**——被多副本 + 生产流量锁死 | **定律**（「踩坑换来的，照学」）→ 升格为不变量 6 |
| steer（投递永不失败） | **演进方向**——正在逃离上面那条遗留 | **可选功能**（「❌ 第一期不做」） |

**把别人的遗留当定律抄进不变量，把别人的演进当可选功能划掉。**

排除清单本身没错——第一期不做 steer 是合理的范围控制。
错在**同时**把 409 提升成了不变量：于是「暂不做 steer」从一个可撤销的范围决定，
变成了有约束力、要在 `server_test.go` 里守护的架构法律。
范围决定随时能改；不变量改起来要动测试、动文档、动心智模型。

**这一轮的方法论收获（面试里最值钱的部分）**：

> **第一条**：借鉴参考实现时，要区分它的**当前态**与**演进方向**。
> 可操作的检查方法是 grep「挂在旧协议旁边的新端点」——它们通常是演进的足迹。
> 本例中 `steer` 就是：它不接受「会话忙」的拒绝，
> 与同一仓库里 20 行之外的 409 逻辑**语义矛盾**。那个矛盾本身就是信号。
>
> **第二条（配套，更容易漏）**：找到那个「遗留」之后，追问一句
> **「它是因为什么约束才不得不存在的？」**
> 本例答案是「多副本 + 生产流量」。
> 如果那个约束**在你这里也成立**（tako 的目标栈是 Postgres + Redis + asynq，成立），
> 它对你就是**未来的债**，不是可照抄的定律；
> 如果**不成立**，它是纯包袱，更不该抄。
> **两种情况下「照学」都是错的**——这才是 doc/10:99 那句「照学」真正的问题。

**多副本目标会不会推翻这个提案？不会，反而是它的一个论据**（详见 doc/19-v3 §13.5）：

- v3 新增的 `inbox` 与 `session_log` **都是 DB 表**，不是进程内存——
  与 WeKnora `steerDataConsumed` 那条教训是同一个答案，v3 独立走到了同一处
- `beginRunAtomic` 的同事务原子性是**数据库级**的，跨副本天然成立，不需要分布式锁
- 会被打断的三处**全是从 v2 继承的进程内机制**（闸用 mutex、审批用 Go channel、
  事件缓冲在内存），与 v3 的新增部分无关。其中审批最严重：
  副本 A 阻塞在 channel 上、用户的 POST 落到副本 B → B 的 `pending` 没这个 id →
  **404，审批永久卡死**
- 闸的改法已给出：Postgres 部分唯一索引
  `... ON run_archive(session_id) WHERE status='running'`——**插入失败本身就是闸**，
  比 WeKnora 的 Redis `SetLiveRun` 更强（闸的判定与 run 的创建在同一事务，不可能不一致）

即：**v3 相对 v2 的改动，恰好是多副本方向上的改动。**
这不是设计时预料到的（v3 的全部动机是 409 与多标签页），但结果是对的。

（详见 doc/19-v3 §13）

## 3. 根因：POST 的语义错了

对照两套语义：

| | tako 现在 | Kimi |
|---|---|---|
| 上行请求的含义 | **开一场 run** | **投递一条消息 / 发起一次 Chat**（可先排队后执行） |
| 输入与执行 | **同一个动作** | **解耦** |
| 冲突时 | 409（拒绝） | 排队（接受，延后执行） |
| 上行请求的响应 | SSE 流，**绑定一个 runID** | 流式响应，**绑定一次 Chat 调用**（跨越排队与执行两阶段） |

> ⚠️ **一处修正**：本文早期草稿写过「Kimi 的 POST 返回普通 JSON」，**这是错的**。
> 抓包确认它的数据面就是流式 POST：
> `POST www.kimi.com/apiv2/kimi.gateway.chat.v1.ChatService/Chat`。
> 所以根因**不是**「POST 返回了流」。返回流本身无罪。
>
> 真正的差别是**流绑定什么**：tako 的 SSE 绑一个 runID（run 不存在→404，结束→关流），
> Kimi 的流绑一次 Chat 调用——调用可以先排队后执行，流一直开着，
> 客户端从流里得知 runID。于是「正忙」不需要用状态码表达，它是流内的一个状态。

tako 的 `POST /api/chat` **既开 run 又是第一个读者**（server.go:152-157）。
doc/19-v2:748 是这么描述它的：

> `POST /api/chat` … **开一轮新 run**（`engine.Start`）并让本请求**降级**成第一个读者

「降级」这个词就是耦合的味道。而这个耦合，**正是不变量 6 存在的全部理由**：

> **不变量 6**：响应三态不得跨越：未提交 / 已提交 / 已结束。
> 冲突检查（409）与 `BeginRun` 必须在写 SSE header 之前。
> —— doc/19-v2:41

因为 HTTP 状态码只能提交一次。一旦写了 `Content-Type: text/event-stream` 并 flush，
这次请求就永久是 200 的流，之后再发现冲突也回不了 409，只能往流里塞错误帧——
语义从「请求被拒」降级成「流内错误」。于是所有可能失败的判断都必须挤在「未提交」阶段做完，
于是 `Start` 必须同步完成占闸 + BeginRun、只把 drive 丢进 goroutine（doc/19-v2:566）。

**一整套约束，都是为了让一个本该独立的「输入」动作，去承担「执行」的失败语义。**

约束链完整写出来（注意第一环）：

```
POST 的含义是「开一场 run」
  → 会话正忙时这个含义无法兑现
    → 只能用状态码拒绝（409）
      → 而 POST 又返回流，状态码只能提交一次
        → 409 必须赶在写 header 前
          → Start 必须同步占闸 + BeginRun
            → 输入与执行绑死
```

改掉第一环（含义变成「投递」），后面五环全部失去理由。
**只改第四环（让它不返回流）是没用的**——「开 run」这个含义还在，冲突还得表达，
只是换个地方表达。这是本提案最容易被误读的一点。

## 4. 设计：收件箱 + 会话级订阅

### 4.1 三个概念

```
       POST /api/message（永远 2xx）
              │
              ▼
    ┌──────────────────┐
    │  inbox（每会话）  │  持久化。用户打的字，丢了比丢一帧输出严重
    └────────┬─────────┘
             │ 闸空时，调度器取空收件箱
             ▼
    ┌──────────────────┐
    │  scheduler       │  = 现在的 beginTurn + driveRun，但不再由 HTTP 请求驱动
    └────────┬─────────┘
             │ 开 run
             ▼
    ┌──────────────────┐        ┌──────────────────────────┐
    │  run（不变）      │───────▶│ GET /api/chat/stream     │ run 级：给内容
    └──────────────────┘        └──────────────────────────┘
             │
             │ 所有状态变化
             ▼
    ┌──────────────────────────────┐
    │ GET /api/session/stream      │ 会话级：告诉你发生了什么
    └──────────────────────────────┘
```

**两层订阅，职责分离**：会话级流只负责「通知」，run 级流负责「内容」。
客户端收到 `run.started` 后，自己去挂 `GET /api/chat/stream?run=<runId>`。

### 4.2 API 变化

| 现在 | 改成 |
|---|---|
| `POST /api/chat` → **SSE 流**（含义：开一场 run） | `POST /api/message` → **JSON** `{messageId}`（含义：投递） |
| `GET /api/chat/stream?run=&from=` | 保留，run 级续传，语义不变 |
| — | **新增** `GET /api/session/stream?id=&from=`（常驻控制面） |
| `GET /api/session?id=` → liveRunID | 保留，退化成会话级流的快照版 |
| `POST /api/stop` | 保留；另加 `DELETE /api/message/{id}` 撤回排队消息 |
| 前端 `startNewSession()` 只 POST /api/stop | **新增** `DELETE /api/session/{id}`，级联停 run + 清四张表 |

会话级流推的事件：

```
message.queued    {messageId, text}
run.started       {runId, messageIds[]}     ← 客户端据此去挂 run 级订阅
run.terminal      {runId, kind}
message.cancelled {messageId}
```

### 4.3 合并窗口：run 启动瞬间清空收件箱

**不用时间 debounce。** debounce 引入延迟，用户会疑惑「我发了怎么没反应」。

改成：调度器启动一场 run 时，在一个事务里把收件箱**取空**，多条合并成一个 user turn：

```
b1

b2
```

这个规则有个漂亮的性质——**天然退化成正确行为**：

| 场景 | 收件箱内容 | 行为 |
|---|---|---|
| 单用户单条 | 1 条 | 与现在**完全相同**，零回归 |
| 用户连打两句（都很快） | 第 1 条立刻开跑；第 2 条排队 | 第 2 条单独成一场 run |
| run 期间攒了多条（B 两句） | 2 条 | 下一场 run 一次性吃掉，合并成一个 turn |

**永远不会为了等合并而延迟第一条消息。**

合并成一个 user turn 而不是两场 run 的理由：模型看到的是「用户连说了两句」，
这与人类在 IM 里的行为一致，是最自然的表达。分成两场则会出现
「b1 的回复在 b2 说完之后才出来」的割裂感，而且回 b1 时模型看不到 b2。

### 4.4 落库：新增 inbox 表，不污染 event_log

不变量 3「先落库，再推浏览器」必须延伸到排队消息——
**排队消息是用户打的字，进程崩了不能丢**。

有个设计张力：`event_log` 是 **per-run** 的（`run_id` + `seq`），而排队消息**还不属于任何 run**。
硬塞进去要么提前假定 run_id，要么引入特殊值，两者都破坏「per-run 只追加」的纯净语义。

所以新增一张表：

```sql
CREATE TABLE inbox (
    session_id TEXT NOT NULL,
    message_id TEXT NOT NULL PRIMARY KEY,
    text       TEXT NOT NULL,
    created_at INTEGER NOT NULL,
    seq        INTEGER NOT NULL   -- 会话级流的续传坐标
);
CREATE INDEX idx_inbox_session ON inbox(session_id, seq);
```

run 启动时在一个事务里：`SELECT` 该会话所有行 → `DELETE` → 写 start 帧。
撤回就是 `DELETE` 一行，天然支持。

### 4.5 状态机

```
message:  queued ──▶ consumed（被某场 run 取走，不可撤回）
                └──▶ cancelled（用户撤回）

run:      running ──▶ complete / stop / error      （不变）

session:  idle ◀──▶ running                        （闸，不变）
```

前端要区分 `queued` 与 `consumed`：只有前者能撤回。

## 5. 连带收益：不变量 6 自然解除

这是整个提案最值的部分——**不是修好一个 bug，是让一类约束不再必要**。

| | 现在 | 改后 |
|---|---|---|
| 上行请求的含义 | 「开一场 run」，忙时无法兑现 | 「投递」，永远能兑现 |
| POST 的响应 | SSE 流，状态码只能提交一次 | 普通 JSON（**不返回流是结果，不是手段**，见 §3 修正） |
| 冲突表达 | 409（必须在写 header 前判定） | **不存在冲突**——投递永不失败 |
| `BeginRun` 失败 | 500（必须赶在 header 前） | 写一帧 error 进 run，推给订阅者 |
| 不变量 6 | 三态不得跨越，约束整条链路 | **两态坍缩成一态，约束解除** |
| `Start` 必须同步 | 为了给 409 留窗口 | 不需要，调度器在后台 |

关键的架构洞察：

> **当有了一条常开的会话级通道，单次请求就不再需要承载错误语义。**
> 错误从「HTTP 状态码」降级成「流内事件」——这在有会话级订阅之后完全合理，
> 因为客户端本来就在监听。

## 6. 取舍与未决

### 6.1 代价（要诚实列出）

1. **复杂度上升**：多一张表、多一条流、多一个调度器。
2. **客户端要管两层订阅**：会话级流断了期间发生的事件会丢，
   所以它**也需要 seq + 续传**，不是可选的。重连逻辑比现在复杂。
3. **撤回有语义边界**：消息一旦被 run 消费就不能撤回，前端必须区分两态。
4. **合并让对应关系变模糊**：「我发的那句」与「模型回复」不再一对一，
   UI 需要能表达「这两句被一起回答了」。

### 6.2 未决问题

- **会话级 seq 怎么编**？与 `event_log` 共用一套，还是独立递增？
  共用会让 run 级续传坐标失去意义；独立则客户端要维护两个游标。倾向独立。
- **进程重启后 inbox 里的消息怎么办**？
  直接继续调度（符合「run 的命不属于任何连接」的精神），还是等用户确认？
  倾向继续，但要在 UI 上明示「这条是重启前排队的」。
- **与 doc/19-v2 的 Engine 如何对齐**？v2 的 `Engine.live` 就是这里的闸，
  `Start` 要拆成 `Enqueue`（同步、永不失败）+ `schedule`（后台）。
  收件箱归 Engine 所有，会话级订阅由 EventLog 提供。

### 6.3 优先级判断

**排队这件事，理由不是多客户端。** tako 是本地单用户工具，两个标签页同时打字是边缘场景。
但有一个痛点与客户端数量无关、天天撞：

> **agent 跑工具的那几分钟里，你想说的下一句话没法先说。**

看现在的代码：`setBusy(true)` 把发送键**换成**停止键（index.html:967-971），
而 `send()` 首行 `state.busy` 直接 return（index.html:1132）。
run 期间**连排队的入口都不存在**——能打字，但按 Enter 什么都不发生，发送按钮根本不在屏幕上。

所以实施顺序：

1. **先做收件箱 + 调度**（POST/SSE 解耦）——单用户立刻受益，且顺手简化掉不变量 6
2. **会话级通道作为副产品出现**——「消息已排队」「run 已开始」本来就得广播，多标签页同步自动有了
3. `BroadcastChannel` 那个纯前端小补丁**可以不做了**——它只治症状，治不到根

顺序上是「先改协议，前端跟着变」，比「先补前端」重，但方向对，且适合放进 v2 Engine 重写一起做。

## 7. 面试叙事

### 7.1 两分钟版本

> 我在读自己写的运行引擎设计文档时，卡在一条不变量上：「409 必须赶在写 SSE header 之前」。
> 这条约束是为了保证 HTTP 状态码只提交一次，但它逼着整个开轮流程必须同步完成。
>
> 我先推演了一个场景：同一个会话开两个标签页会怎样。结论是**数据层完全安全**——
> 会话闸由互斥锁保护，所有写路径都在事务里，模型上下文永远是对的。
> 但**表现层会分裂**：订阅是 run 级的，而「别人开了一场新 run」是会话级事件，
> 系统里没有这个概念，所以先打开的那个页面永远看不到对方新开的 run，除非刷新。
>
> 推演只能说明「有这个空洞」，不能说明「值得填」。所以我去实测了 Kimi：
> APP 和网页登同一对话，APP 发消息后网页**立刻**看到，而且网页手速快时能点发送，
> 消息进入**排队**而不是被拒。再往下抓包，摸清了它是两个平面：
> 控制面一条常驻 WS（`notilo.kimi.com/im/v1/subscribe/ws`，Protobuf，多路复用所有会话），
> 数据面是流式 POST（`kimi.gateway.chat.v1.ChatService/Chat`）。
>
> 对照之下根因就清楚了：**不是「POST 返回了流」有问题**——Kimi 的数据面就是流式 POST。
> 问题是我们的 POST 含义是「开一场 run」，输入和执行是同一个动作，
> 所以「你输入的时机不对」只能暴露成 HTTP 层的 409；
> 而它的流又绑死在一个 runID 上，run 不存在就 404、结束就关，
> 承载不了「排队中」这种跨阶段状态。
>
> 我的提案是把两者解耦：上行变成「投递到持久化收件箱」，永远 2xx；
> 调度器在闸空时取空收件箱开 run，多条合并成一个 user turn；
> 另加一条常驻会话级通道只负责通知，内容仍走 run 级订阅。
>
> 最值的收益不是修好了多标签页，而是**那条不变量自然解除了**——
> 没有冲突需要表达，就没有「必须赶在写 header 前判完」的约束，409 这个概念消失。
> 背后的判断是：**当有了一条常开的控制面通道，单次请求就不需要承载状态语义。**

**如果面试官追问「那你为什么不像 Kimi 一样用 WS」**——这是个好问题，答案是成本与阶段：
WS 多路复用能省连接（见 7.3），但需要引入 WS 库、鉴权 ticket、topic 协议三样东西。
tako 是单用户单会话视图，两条 SSE 就够；
**关键是接口按可互换设计**（存储层 `SessionFeed` 与传输分离），将来换传输不动存储。

### 7.2 这个故事展示什么

| 能力 | 具体体现 |
|---|---|
| **不变量思维** | 先问「什么情况下数据会错」，确认数据层安全后才谈表现层。**不夸大成「有 bug」** |
| **精确分层** | 「数据一致，画面不一致」——一句话把问题域切干净，避免误修 |
| **用外部产品反证推演** | 不是「我觉得应该这样」，而是「我实测了 Kimi，它的行为证明这是产品级必需」 |
| **根因定位到语义层** | 409 不是缺一个错误处理，是 POST 语义把输入与执行绑死。修法是解耦，不是打补丁 |
| **敢于删约束** | 提案的落点是「让一类约束不再必要」，而非「满足现有约束」 |
| **诚实列代价** | 主动写出复杂度上升、两层订阅的重连、撤回的语义边界 |
| **抓包验证到帧级** | 不停在「Kimi 能排队」的行为层，摸到了两个平面的 URL、编码、鉴权方式，以及数据面的帧协议 |
| **溯源自己的设计** | 追查「409 这套是从哪来的」→ 定位到参考实现 WeKnora，并发现**它自己已经用 steer 走出了这条路**，而我们只抄了它的遗留路径（§2.4） |
| **敢推翻自己的结论** | 四次：① 曾判定「POST 不该返回流」，抓到流式 POST 后窄化结论（§3 修正框）；② 曾把 `RestoreMessage` 当作已有兜底，查代码发现浏览器那一半**曾有过、被主动移除**，服务端那半是 doc/15:252 明写「留着等 MQ」的故意悬空（§1.1 更正）；③ 队列上限从「软上限延后」改成「超限拒绝」，因为 WeKnora 的理由更硬（§2.4）；④ 曾用「tako 是单进程 SQLite 所以有条件做治疗」论证，被指出目标栈是 Postgres + Redis/asynq，理由换成「**窗口是未上线，不是单进程**」（§2.4） |
| **前置假设去源码里验，不靠印象** | inject 模式的前置是「引擎循环有 drain point」，原先标「尚未查证」。后来在 `$GOMODCACHE/eino@v0.9.21/adk/` 里查到三处钩子，还发现 `adk.TurnLoop` 就是框架原生的收件箱+调度器——**结论因此从「v3 最大缺口」变成「v3 用 middleware、TurnLoop 留 v4」**（§2.3 后的表格） |

### 7.3 可能的追问

**Q：为什么用 SSE 不用 WebSocket？**
诚实答：**这是成本选择，不是技术优越性判断。** Kimi 用的就是 WS。

- SSE 的优势：基于 HTTP、`EventSource` 自动重连、过代理友好、不需要额外的连接管理、
  不需要鉴权 ticket（复用 cookie）。会话级通道是服务端→客户端**单向**，WS 的双向能力用不上。
- SSE 的**真实代价**：浏览器对同一 host 的 HTTP/1.1 并发上限是 6，SSE 会长期占坑。
  2 个标签页 × 2 条 SSE（会话级 + run 级）= 4 个坑，只剩 2 个给普通请求。
  **这个缺陷只在多标签页下暴露，而多标签页正是本次要修的场景**——所以它不是理论问题。
- Kimi 的解法是**一条 WS 多路复用所有会话**，连接数与标签页数无关。

所以我的方案里，存储层与传输层是分开的（`SessionFeed` 接口：`Since` 拉 / `Subscribe` 推 /
`Notify` 只发信号）。SSE、轮询、WS 多路复用三种传输都能建在同一份 `session_log` 上，
换传输不动存储。**先用 SSE 起步，把演进路径保住。**

**Q：合并窗口会不会让模型困惑？**
合并成一个 user turn、换行分隔，模型看到的就是「用户连说了两句」——
这与人类在 IM 里的实际行为一致，反而是最自然的表达。分成两场才会出问题：
回第一句时模型看不到第二句。

**Q：run 启动瞬间清空收件箱，那之后 1ms 发的消息呢？**
进下一场。这正是「零延迟」的含义：**永远不会为了等合并而延迟第一条消息**。
debounce 方案则会，那是它被否掉的原因。

**Q：inbox 表会不会成为瓶颈？**
每会话几行的量级，且天然按 session 分区，SQLite 完全够。
真正的写压力在 event_log（每帧一次），那张表的设计已经在 doc/19 里论证过了。

**Q：这个设计的失败模式是什么？**
会话级长连接断开期间的事件会丢。所以**会话级流也需要 seq + 续传**，
断线重连时补齐——这是必须做的，不是可选的。这也是复杂度上升的主要来源。

**Q：为什么不先用 BroadcastChannel 快速修一下前端？**
可以，几十行、零服务端改动，能治「B 吃 409 变瞎子」和「A 看不到 B」。
但它治不到根：POST 依然返回 SSE、依然有 409、依然没法排队。
而且它只在**同源标签页**间有效，跨设备（APP + 网页，也就是 Kimi 那个场景）完全无效。
所以它是止血，不是治疗——如果 v2 重写就在眼前，不值得先做止血。

**Q：数据层既然安全，这算 bug 吗？**
不算。这是一个**能力缺失**，不是**正确性缺陷**。区分这两者很重要：
正确性缺陷必须立刻修，能力缺失要按产品价值排期。
我把它排进 v2 重写，而不是当 hotfix，就是这个判断的结果。
