# 37 · 删除项目连带删会话

> 性质：**方案草稿**（待点头）。2026-10-20 起草，2026-10-21 补拍 D3（单场删除，仅属主本人可删）并细化 D3 文件清理（按所有权分层：系统档案随删会话清、产出保留）。
> 代码落点：`yk-tako-eino/internal/runengine/pgstore.go`、`product_api.go`、`session_access.go`、`store.go`、`server.go`（D3 路由）。
> 真源关系：项目目录真源是 [doc/35](35-项目目录.md)。本篇只改它 A6 拍好的「删除只删空项目」语义——[doc/35](35-项目目录.md) 第 0 节第 3 条写明「连带删会话另立拍」，本篇就是那独立的一拍。
> 不在本篇：已删会话的恢复与彻底清理（独立方案）、前端页面（删除按钮、确认弹窗属前端 loop，doc/35 前端另立）、清理架构的其余件（原子写 / 写路径清单 / scratch TTL / 子代理保留窗口，见 §9）。

## 0. 本篇做什么

两件事：

1. 把 `DELETE /api/workspaces/:id` 的语义从「项目里还有会话就拒绝（409 `114002`），请先挪走」改成「连带把挂载的会话一起删掉」。
2. **新增 `DELETE /api/sessions/:id`**（D3，2026-10-21 补拍）：删除单场会话。门槛 = 仅会话属主本人，tenant owner/admin 均不能删别人的会话。文件清理按所有权分层：**系统档案（会话目录的 `.tako/`、`.media/`）随删会话清掉；agent 写进会话目录的产出是用户资产，保留不动**。

连带删 = 同一笔事务里：检查项目下没有正在跑的 run → 软删所有挂载会话 → 删项目行；事务提交后：删项目目录、删各挂载会话的会话目录。有活 run 时拒绝删除（新码 409 `114006`）。

## 1. 背景与动机：一场真实的删除

用户「Q4 调研」项目做完要收尾。这个项目下挂了 12 场会话——自己开的 8 场，团队成员挂上来的 4 场（doc/35 A7b）。现在想把这个项目删掉：

按 doc/35 A6 的语义，`DELETE /api/workspaces/:id` 回 `409 {"code":114002,"message":"项目里还有会话，先挪走再删"}`。用户得先对 12 场会话逐一 `PATCH /api/sessions/:id {"workspaceId":""}` 解绑——这是 12 次手打 curl 或未来页面上的 12 次确认，而且其中 4 场根本不是他自己的会话，解绑别人的会话还得逐个确认（A7c 特意为创建者开了这个口，但口开得越宽，操作越繁琐）。做完这些才能删项目。

实际后果是用户不删了：项目越积越多，列表里永远躺着一堆做完不用的「Q4 调研」「Q3 复盘」，真正的活跃项目混在里面找不到。删除的门槛高到形同虚设，等于没有删除。

连带的问题是：单场会话也删不掉。`DELETE /api/sessions/:id` 端点在 doc/28 的权限表里只有一行设计（「owner/admin；软删」），从没排期实现——会话只能建、看、改可见性、挪项目，永远删不掉。写方案时核实过 server.go 全部路由，确认它不存在。

## 2. 名词

- **软删**：给 `sessions` 加一列 `deleted_at`（timestamptz，可空，默认 NULL）。删会话 = 写上删除时刻；没删 = NULL。本篇之前这列不存在（pgstore.go:28-37 的 Session 结构体只有 8 列），会话在系统里从来没有「被删除」这种状态。
- **活 run**：`runs` 表里 `status='running' AND lease_until > now()` 的行。lease 是 worker 的续约租约，lease 未过期的 running run 真有一个进程在跑；lease 已死的 running 行只是还没被清扫的僵尸，不算活。
- **连带删的范围**：哪些东西跟着项目一起没了、哪些留在库里。明细见 §4 的表。
- **属主**：`sessions.user_id` 那一列指向的用户。删单场会话的唯一门槛（§5.4）。
- **系统档案**：会话目录里系统自己生成的字节。今天只有 `.tako/`（搜索截断落盘，search.go:187 写 `<作业根>/.tako/search/<runId>_<n>.md`）和可能残留的 `.media/`（A8c 前的旧媒体；启动清理已删，删它算兜底）。系统拥有，**删会话时自动清**。
- **产出**：agent 通过文件工具 / bash 写进作业根的文件，用户可见资产。**删会话不碰**；只有删项目（容器销毁）才随目录一起清。

## 3. 现状（代码事实）

`DELETE /api/workspaces/:id` 今天的完整路径：

1. handler `deleteWorkspace`（product_api.go:200-233）调 store，成功后**事务提交之后** `os.RemoveAll` 项目目录（删目录在事务外，避免库回滚了目录已经没了）。
2. store `DeleteWorkspace`（pgstore.go:292-320）单事务三步：`lockOwnedWorkspace` 锁项目行（FOR UPDATE）→ 查 `is_default`（默认工作区回 `ErrWorkspaceDefault` → 409 `114005`）→ `SELECT COUNT(*) FROM sessions WHERE workspace_id = ?`（只有这一个条件）→ 大于 0 回 `ErrWorkspaceNotEmpty`（409 `114002`），等于 0 才 `DELETE FROM workspaces`。

数会话的条件只有 `workspace_id = ?` 一列——这是本篇要动的核心查询。

互斥现状（删除 vs 运行）有两层是现成的：删除事务锁 `workspaces` 行，而「新会话挂这个项目」在 `AcquireRun` 里也锁同一行（`lockVisibleWorkspace`），两边互等；`one_live_run_per_workspace` 部分唯一索引（pgstore.go:428-432）保证同一项目同时最多一场活 run。

没有的一层：删除与「已有挂载会话继续发消息」之间没有直接互斥——那条路径锁的是 `sessions` 行（`AcquireRun` 的 `SELECT ... FOR UPDATE WHERE id = ?`），不锁项目行。本篇软删会话时的 `UPDATE sessions WHERE workspace_id = ?` 恰好也锁这些行，互斥是顺带成立的（§5 时序图）。

## 4. 待拍决策与推荐

| # | 决策点 | 推荐 | 理由 |
|---|---|---|---|
| D-a | 会话删除语义：软删还是硬删 | **软删**（新增 `deleted_at` 列） | doc/28 里 `DELETE /api/sessions/:id` 的设计就是「软删；保留审计」，本篇先把软删的语义和过滤做出来，§5.4 的 D3 直接复用；硬删要顺手清 5 张 `session_id` 关联表（runs / run_model_messages / runlog_entries / dialogue_chunks / memory_jobs，全库无外键无级联，product_api 与 store 逐张清），动作大且掐断审计线 |
| D-b | 连带删的范围 | **见下表** | 原则是：表行软删保审计、磁盘字节删掉、计费/记忆数据不动 |
| D-c | 项目下有活 run 时 | **拒绝删除**，409 `114006` | 删除是不可逆的破坏性操作，活 run 说明项目正在用；让用户等 run 跑完再删，比「自动 stop 再删」安全——后者会误杀用户正等着结果的 run，且 stop 要等 worker 收尸，语义复杂 |
| D-d | 成员挂在项目下的会话（A7b） | **无差别连带软删** | 项目 owner 对项目内容本就有处置权（A7c 已定创建者可解绑成员会话）；软删不是抹除，runlog 仍在库里；给成员留副本/做通知的复杂度不值 |
| D-e | `114002` 的去向 | **退役**（本篇起 DELETE 不再返回它） | 新语义下「有会话」不再是拒绝理由；想保留会话的用户仍走老路径——先解绑（A5）再删，那正是空项目删除 |
| D-f | 单场删除的门槛（2026-10-21 拍） | **仅会话属主本人**；tenant owner/admin 不豁免 | doc/28 表格里「owner/admin」的口径作废。会话正文是私人对话，属主之外的人（哪怕 tenant owner）删除都越权；与 A5 挪挂的门槛一致（`sessions.user_id` 等于当前用户），错误响应也复用 A5 的双轨：看不见 → 旧体 404，看得见非本人 → 403 `111204` |
| D-g | 删会话时产出怎么办（2026-10-21 拍） | **产出保留，只清系统档案** | 借鉴 Kimi/dsh/opencode 梳理的口径：所有权决定清理方式。系统档案（`.tako/` 搜索落盘、`.media/`）按会话生命周期自动清；agent 写的产出是用户可见资产，不能因为删对话记录就没收。删项目（D-b）才是容器销毁，产出随之清 |

连带删的范围明细（D-b）：

| 对象 | 处置 | 说明 |
|---|---|---|
| `workspaces` 行 | 硬删（不变） | 项目是真删，doc/35 A6 已拍 |
| 挂载的 `sessions` 行 | **软删**：`deleted_at = now()` | 新增列；过滤点见 §6 |
| 项目目录 `tenants/<tid>/workspaces/<wid>/` | `RemoveAll`（不变） | 含 `.media/` 附件与全部产出（doc/35 A8b 后附件挂工作区）。**删项目 = 容器销毁，产出随之清**——这是 D-g 的例外 |
| 各挂载会话目录 `tenants/<tid>/sessions/<sid>/` | `RemoveAll`（新增） | 挂过又挪走的会话的游离期残留；删项目时容器已销毁，残留一并清 |
| `runs` / `run_model_messages` / `runlog_entries` | 不动 | 审计线；软删会话后这些行变成「查不到的关联数据」，DBA 手查可及 |
| `usage` / `tenant_usage_daily` | 不动 | 计费线 |
| `dialogue_chunks` / `memory_jobs` | 不动 | 记忆线，随会话死但保留 |
| Redis 事件键（runlive/draft） | 不动 | 只在活 run 期存在；活 run 已被 D-c 挡在删除之外 |
| 默认工作区 | 不受影响 | 游离会话的 `workspace_id` 是 NULL，不挂默认工作区；`is_default` 的 409 `114005` 逻辑不变 |

D3 的范围补充（D-g）：删单场会话只软删会话行；文件层面**只清会话目录的系统档案子目录**（`.tako/`、`.media/`，`RemoveAll` 各一次，不存在算成功），**产出全部保留**；项目目录不动。已删会话的产出残留在 `sessions/<sid>/` 里是刻意的——后续回收靠未来的文件管理入口，或整库清理时处理，不由删除动作没收。

## 5. 新 DELETE 语义

### 5.1 请求响应

路由、鉴权、成功响应全不变：`DELETE /api/workspaces/:id`，仅创建者（`lockOwnedWorkspace` 锁不到别人的行），成功仍是 `200 {"code":0,"message":"","data":{"status":"deleted"}}`。

变化的只有失败分支：

| 场景 | 旧语义 | 新语义 |
|---|---|---|
| 项目下有会话 | 409 `114002` | **200 `deleted`，会话连带软删** |
| 项目下有活 run | （撞项目闸 409 `114004`，仅发生在新建 run） | 409 `114006`「项目里有正在运行的会话，等它跑完再删」 |
| 默认工作区 | 409 `114005` | 不变 |
| 别人的/不存在的项目 | 404 `114001` | 不变 |
| 未登录 | 401 `111102` | 不变 |

### 5.2 事务时序（store 层新方法 `DeleteWorkspaceCascade`）

```text
BEGIN
  1. lockOwnedWorkspace(id, tenantID, userID)     -- FOR UPDATE 锁项目行；没有 → 114001
  2. is_default? → ErrWorkspaceDefault            -- 114005（不变）
  3. SELECT COUNT(*) FROM runs
     WHERE workspace_id = :id AND status='running' AND lease_until > now()
     → > 0 回 ErrWorkspaceBusy（新错误 → 114006）
  4. SELECT id FROM sessions WHERE workspace_id = :id
     → 记下 id 列表（删目录用）
  5. UPDATE sessions SET deleted_at = now()
     WHERE workspace_id = :id                      -- 软删全部挂载会话
  6. DELETE FROM workspaces WHERE id = :id
COMMIT
```

handler：拿到 store 返回的会话 id 列表后（沿用「事务外删目录」的现状结构）：先 `RemoveAll` 项目目录（现状），再对列表逐个 `RemoveAll` 会话目录。目录删除失败照旧只记日志、不改响应。

### 5.3 时序竞争为什么安全

所有并发路径都在抢同两把锁中的一把，且活 run 检查在锁保护之内：

- **新会话挂这个项目**（`AcquireRun` 的 `lockVisibleWorkspace`）锁项目行：删除事务持锁期间它等着；删除提交后行没了，预检回 114001，不建行。反之它先提交，删除的计数能看到新会话（步骤 4/5 照常软删它）。
- **已有挂载会话发消息**（`AcquireRun` 锁 `sessions` 行）不锁项目行：但步骤 5 的 `UPDATE sessions WHERE workspace_id = ?` 锁全部挂载会话行，两边互等。若发消息方先提交，步骤 3 的活 run 检查能看到它刚插入的 running 行 → 整个删除回滚，回 114006；若删除先提交，发消息方的 `SELECT ... FOR UPDATE` 带上软删过滤后查无此行 → 按「未登记会话」回旧体 404 `{"error":"session_not_found"}`，不建行。

所以不会出现「会话已删、run 还在跑」或「run 在跑、项目没了」的孤儿态。

### 5.4 单场删除：DELETE /api/sessions/:id（D3，2026-10-21 补拍）

端点至今不存在（§1），本篇新增。D1 铺好软删基础设施后，本端点的增量 = 路由 + handler + store 一个方法。

- **路由**：`DELETE /api/sessions/:id`，挂 `RequireAuth`。仓库里 sessions 相关路由只有 GET/PATCH（server.go:78-84），新增不冲突。
- **门槛**：`sessions.user_id = 当前用户`。tenant 的 owner/admin **不豁免**（D-f）。错误双轨对齐 A5 挪挂：
  - 看不见这场会话（跨租户、private 且非本人）→ 旧体 404 `{"error":"session_not_found"}`，不泄露存在性；
  - 同租户 `visibility=tenant` 看得见、但不是本人 → HTTP 403 `{"code":111204,"message":"只有本人能修改","data":null}`。
- **活 run**：会话有活 run 时拒绝，409 `114007`「这场会话正在运行，等它跑完再删」（D-c 同一逻辑，不自动 stop）。
- **事务**（store 新方法 `DeleteSession`）：`SELECT ... FROM sessions WHERE id = ? FOR UPDATE`（D1 的软删过滤在这里生效：查无 → 旧体 404）→ 属主校验（不通过 → 403）→ 活 run 检查 → `UPDATE sessions SET deleted_at = now()`。
- **文件清理**（D-g，事务提交后，失败仅记日志）：
  - `RemoveAll(<会话目录>/.tako/)`——搜索截断落盘（`.tako/search/<runId>_*.md`）等系统档案；
  - `RemoveAll(<会话目录>/.media/)`——A8c 前旧媒体的兜底清理；
  - **产出不删**：会话目录其余文件（agent 写的）原样留在盘上；项目目录不动。残留是刻意的（§4 D3 补充）。
- **成功**：`200 {"code":0,"message":"","data":{"status":"deleted"}}`，对齐项目删除。幂等：再删一次 → 旧体 404（已删会话视同不存在，§2）。
- **并发**：与 §5.3 同款——删除锁 `sessions` 行 ↔ `AcquireRun` 锁同一行互等；发消息方先提交则活 run 检查挡住（114007），删除先提交则对方查无此行（404 不建行）。

## 6. 软删对全站查询的影响

软删列一旦存在，所有按 `id` 或列表查会话的地方都要补 `deleted_at IS NULL`，否则已删会话照常收发消息。代码里要动的查询点（2026-10-20 实读）：

| 查询点 | 位置 | 不加的后果 |
|---|---|---|
| `SessionAccess`（按 id 取会话，一切会话读写的总闸） | session_access.go:43-57 | 已删会话的发消息 / 详情 / log / media 全放开——最大洞 |
| `AcquireRun` 的 `SELECT ... FOR UPDATE` | store.go:146-148 | 已删会话继续建 run |
| `ListSessions` | session_access.go:76-97 | 列表里诈尸 |
| `SetSessionVisibility` 的 FOR UPDATE | session_access.go:106 | 已删会话还能改可见性 |
| `SetSessionWorkspace` 的 FOR UPDATE（A5 挪进挪出） | session_access.go:135 | 已删会话还能挪挂 |
| `Exists` | pgstore.go:448-454 | 按调用点逐个核；凡是「会话还在不在」的语义都要过滤 |
| `POST /api/runs/:runId/resume` 的鉴权路径 | server.go（resume handler） | 实现时核：已删会话的 run 不许复活 |

`SessionStatus` 里的 `EXISTS(SELECT 1 FROM sessions WHERE id=?)`（pgstore.go:492）**不用改**——它只组装 `liveRunId`，真正拦人的是它前面的 `SessionAccess`。

配套：加部分索引对齐项目闸的现有建法，如 `CREATE INDEX ... ON sessions (tenant_id, user_id) WHERE deleted_at IS NULL`，让列表查询不为过滤付全表扫描。

## 7. 错误码

| code | 场景 | HTTP | 从哪拍开始用 |
|---|---|---|---|
| `114006` | 项目下有活 run，拒绝删除项目 | 409 | D1 |

## 8. 分拍与验收

| 拍 | 做什么 | 怎么验收 |
|---|---|---|
| D1 | §5.2 全链路：`sessions.deleted_at` 列 + `DeleteWorkspaceCascade` + `deleteWorkspace` 换用新 store 方法（114006、目录连带删）+ §6 前三个过滤点（SessionAccess / AcquireRun / ListSessions） | curl 主链路（见下） |
| D2 | §6 剩余过滤点（两个 SET、Exists 各调用点、resume 核）+ 软删部分索引 + 单测 | curl 边角 + `go test ./internal/runengine` |
| D3 | §5.4：`DELETE /api/sessions/:id`（路由 + handler + store `DeleteSession`：锁行 → 属主校验 → 活 run 检查 → 软删；事务后清 `.tako/`、`.media/`，产出保留） | curl 主链路（见下） |

D1 验收（引擎起来后，两个用户 A、B，一个 `visibility=tenant` 共享项目）：

```bash
# 1. 项目下挂两场会话（A 一场、B 挂上来一场），目录里各写得到文件
# 2. 有会话时删除——旧语义是 409，现在：
curl -X DELETE -H "Authorization: Bearer $A_TOKEN" 127.0.0.1:8905/api/workspaces/$WS
# → 200 {"code":0,"message":"","data":{"status":"deleted"}}
# 3. 项目没了：
curl -H "Authorization: Bearer $A_TOKEN" '127.0.0.1:8905/api/sessions?workspaceId='$WS
# → 404 {"code":114001,"message":"找不到这个项目","data":null}
# 4. 已删会话按 id 取详情、发消息：
curl -H "Authorization: Bearer $A_TOKEN" 127.0.0.1:8905/api/sessions/$SID_A
# → 404 {"error":"session_not_found"}（旧体，SessionAccess 出口）
curl -X POST -H "Authorization: Bearer $B_TOKEN" -d '{"text":"hi","sessionId":"'$SID_B'"}' 127.0.0.1:8905/api/runs
# → 404 {"error":"session_not_found"}，runs 行数不增
# 5. 目录没了：项目目录、两场会话目录都不在盘上；游离会话目录不受影响
# 6. 审计线在（psql 断言）：runs / runlog_entries 行数与删除前相同，sessions 行数也不变（软删是 UPDATE 不是 DELETE）
# 7. 活 run 拒绝：挂一场会话、发一条长消息让 run running、趁 running DELETE

#    项目行、会话行、目录都还在；run 跑完后重发 DELETE → 200 deleted
```

## 9. 不在本篇

- **清理架构的其余件**（2026-10-21 借鉴 Kimi / dsh / opencode 梳理后明确另立，与本篇是姊妹件）：
  - write_file 原子写（临时文件 + rename，防 kill -9 留半截文件）；
  - 每 run「写过的路径清单」（崩后页面列出可疑文件，用户显式回退，不自动恢复）；
  - `.tako/scratch/<runId>/` 中间产物目录 + TTL 自动清（交付物仍留工作区）；
  - 子代理逐字记录的保留窗口（终态压摘要进 runlog 后删逐字，保留窗口 = 恢复承诺）。
  本篇 D3 补上了这些件共同缺的「会话生命周期」清理单位；各件独立成案，不在本篇混做。
- **已删会话的恢复与彻底清理（purge）**：软删留着 `deleted_at`，产品上没有恢复入口，也没有 purge 任务；哪天要做是独立方案。
- **前端**：项目删除按钮、单场删除按钮、确认弹窗（「将连带删除 N 场会话」「删除后对话不可恢复，但工作区文件保留」）属前端 loop（doc/35 前端另立）。
- **游离会话的批量清理**：和删除无关，以后有需求再立。

## 10. 闭环

**所以这解决了什么。** 项目从「删不掉」变成「删得掉」：删除一个做完的项目从 12 次解绑 + 1 次删除变成 1 次删除；单场会话从「永远删不掉」变成属主本人一条 DELETE（D3），且 tenant owner/admin 都不能越权删别人的私人对话（D-f）。文件清理按所有权分层（D-g）：系统档案（`.tako/` 落盘、`.media/`）随删会话自动回收，agent 写的产出作为用户资产保留——删对话记录不没收工作区文件，只有删项目这个容器销毁动作才清产出。会话数据不因删除而灭失（软删 + 审计线保留），删除时正跑着的 run 被 114006/114007 挡住，删完之后的并发安全靠现有锁和索引兜住，不需要新通信机制。D3 同时补上了清理架构（原子写 / 清单 / scratch / 保留窗口）赖以挂接的「会话生命周期」入口。

**仍不解决的：** 已删会话的恢复、删除前的用户确认 UI、半截文件的自动处理（原子写/清单是另案）——都在 §9 明说。
