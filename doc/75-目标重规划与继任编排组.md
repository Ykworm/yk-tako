## 1. 要解决的不是“失败后重试”，而是“下一步还该不该执行”

一场真实失败：

```text
原方案要求从数据源 X 收集资料并生成报告
→ 抓取 Task 确认 X 已下线
→ 原 DAG 的后续节点无法按原样完成
→ 但数据源 Y 可能仍能提供同样资料
```

这时系统不该机械重跑抓取，也不该只报告 Task failed。它应让 mAgent 判断：原目标是否仍可行、哪些结果仍有效、是修订当前组还是另起继任组。

另一个场景：

```text
用户要求提供一份不存在且无法合法取得的数据
→ 更换 DAG 不改变事实
→ 不应创建继任组
→ 应告诉用户证据与原因，必要时请用户调整目标
```

因此，本篇的核心是**目标可行性判断 + 有依据的计划选择**，不是自动重试。

## 2. 范围与非目标

### 2.1 本期完成线

1. 在原方案失败、阻断、检查点或用户明确要求换方案时，给 mAgent 提供完整决策输入。
2. 先判断目标可行性，再决定同组修订、创建继任组、补充调查或告知用户。
3. 同组修订继续走 doc/72，不另写一套改图协议。
4. 继任组通过 `replanOf`、决策原因和结果引用写 handoff 文件。
5. 复用旧组中已经接受的不可变结果，不复制仍在变化的工作现场。
6. 继任组启动前原组必须终态或被停止，避免两个方案同时执行和发布。
7. 重规划次数与深度有上限，不能通过新建组重置预算。
8. 页面能展示重规划原因、继任关系、复用结果与原组状态。

### 2.2 不做

- 不在每次 Task error 后自动重试或自动新建组；
- 不根据模型一句“做不到”判定目标不可行，必须展示支撑事实；
- 不重新打开已终态的原组，不修改 running／succeeded Task 的历史；
- 不建立跨组调度依赖边；
- 不自动重放结果未知的外部动作；
- 不做无限重规划、自由群聊或多个继任组竞争同一目标；
- 不把 Git 引用、目录哈希或 Provider 路径写进 PG；
- 不在本篇实现用户级 skill／plugin。

## 3. 两个决策必须分开

### 3.1 第一问：目标是否仍可行

mAgent 的输入必须包含：

- 原始目标与用户附加约束；
- 当前 DAG、各 Task 状态与错误；
- 已有结果的摘要、产物和 `(taskId, resultRevision)`；
- 已发生外部动作的提示；
- 已有 handoff 链与重规划次数。

输出不是简单布尔值，而是：

| 判断 | 含义 | 下一步 |
|---|---|---|
| `feasible` | 现有事实下仍有可执行方案 | 进入第二问 |
| `infeasible` | 当前约束下没有可达成目标的方案 | 告知用户原因，不创建组 |
| `uncertain` | 现有证据不足以判断 | 先补充调查或问用户，不盲目重建 |

模型负责语义判断，程序负责把判断对应的写操作限制在合法状态内。模型说 feasible 不等于程序必须接受一张违法图。

### 3.2 第二问：修订当前组还是创建继任组

**默认优先同组修订。**必须同时满足：

1. 原组 active，最终 Task 尚未开始；
2. doc/72 的修订规则与预算允许；
3. 不改写 running／succeeded Task 的历史；
4. 目标、最终交付物、项目与通用工作区配置不变；
5. 变化只涉及未来工作；
6. 保留同组身份有助于理解，而不是掩盖一次已经结束的尝试。

满足时调用现有 `revise_orchestration`，新增节点可直接依赖原组已经成功的工作。

**以下情况才创建继任组：**

- 原组已经 failed／cancelled／succeeded；
- 最终 Task 已开始，当前规则不允许继续改图；
- 新方案需要替换大量未来节点，继续作为同一张计划会误导审计；
- 最终交付物、项目或通用工作区配置改变；
- 需要把上一轮明确收口，作为一次独立尝试重新开始。

继任组不是绕过修订预算的方法。原组与继任组的关系、重规划深度和累计次数必须进入 handoff。

## 4. 完整业务链

```text
原组出现 Task 失败／阻断、计划检查点，或用户要求换方案
→ 现有协调通知把事实带回来源会话
→ mAgent 读取原目标、DAG、错误、已有结果与 handoff 历史
→ 判断目标可行性
   ├─ infeasible：向用户说明原因，不创建组
   ├─ uncertain：补充调查或 ask_user
   └─ feasible：进入方案选择
      ├─ 当前组仍可修订：doc/72 追加／替换未来工作
      └─ 当前组应收口：停止或确认原组终态
          → 生成继任组与新 DAG
          → 写 handoff（replanOf、原因、复用结果、预算、禁止重放事项）
          → 引擎校验 handoff 与结果引用
          → 继任组才可被调度
→ Provider 按引用读取旧结果，带入需要它们的 Task
→ 新 DAG 执行、验证、发布与交付
```

新旧组不并行争抢同一目标。若原组还有活 run，先走现有停止链；不能仅写一条继任关系就放任两边同时执行。

## 5. handoff.md：机器可读关联与人读原因放在一起

继任组目录中必须有：

```text
<继任编排组目录>/handoff.md
```

示例：

```markdown
---
kind: orchestration-replan
orchestrationId: or_new
replanOf: or_old
replanDepth: 1
reuse:
  - taskId: at_B
    resultRevision: 2
  - taskId: at_D
    resultRevision: 1
---

# 为什么重规划

数据源 X 已下线，原抓取步骤无法继续；Y 能提供同一资料。

# 为什么创建继任组

原组已 failed，且最终交付物从单一报告改为报告加数据附件。

# 目标可行性证据

Y 能提供与 X 同一口径的原始资料，原目标仍可达成。

# 哪些结果仍有效

B 的统计结果不依赖 X，可以继续使用；D 的历史数据已完成清洗。

# 不得重放的动作

原组已经发送的外部通知不得再次发送。
```

规则：

- frontmatter 是程序读取的机器字段；正文是给人看的决策说明；
- 程序不通过解析自由文本正文提取 `replanOf` 或结果引用；
- 文件使用现有锁内重读、临时文件和原子 rename；
- 继任组在 handoff 成功落盘前保持不可调度；
- handoff 缺失或引用无效时明确失败，不伪造关联；
- 不因 handoff 是 Markdown 就把正文当机器契约。

PG 不需要复制 `replanOf`、结果内部引用或 Provider 路径。PG 继续保存通用编排组、Task、结果版本、run 与状态；需要展示继任原因时从 handoff 读取。

## 6. 结果复用是输入快照，不是跨组依赖边

继任组创建请求中的 `reuse` 只包含通用引用：

```json
[
  {"taskId": "at_B", "resultRevision": 2},
  {"taskId": "at_D", "resultRevision": 1}
]
```

引擎校验：

- 引用指向同一来源会话可见的旧组 Task；
- Task 已有成功接受的该版本结果；
- 结果仍可由 Provider 读取；
- 不把失败、未提交或仍在变化的结果当成有效输入。

Provider 在准备继任组 Task 时读取这些结果：

- Git：解析旧组结果引用对应的确切提交；
- Directory：读取旧组结果目录中的清单与文件字节；
- 只读结果摘要和声明产物，不继承旧组完整聊天与工具历史。

跨组不建立 parent link。旧组已经终态，结果已经是输入快照；若让新组等待旧组状态，会把继任关系误成执行依赖。

## 7. 触发、工具与 API 草案

### 7.1 触发来源

- 现有 `task_failed`／`task_interrupted` 通知；
- doc/72 的 `plan_review_required` 检查点；
- 最终 Task 被显式标为检查点时，对最终目标做一次复核；
- 用户在来源会话明确要求换方案。

程序只提供事实与触发，不试图用固定规则理解“目标有没有达成”。不确定目标是否需要复核时，由 LLM 在计划阶段选择检查点；不为每组强制增加一次模型调用。

### 7.2 模型工具

建议增加一个继任创建工具，而不是让 mAgent 手写 handoff 文件：

```text
create_successor_orchestration(
  orchestrationId,
  goalAssessment,
  reason,
  successorReason,
  reuse[],
  goal,
  tasks[],
  links[],
  workspaceMode?,
  verifyCommand?
)
```

它只提交意图。程序负责：

1. 校验原组可见性、状态与当前无竞争继任者；
2. 校验目标判断、结果引用、DAG 与预算；
3. 停止尚未终态的原组；
4. 创建继任组记录与通用配置；
5. 写 handoff；
6. 原子发布继任组的调度资格；
7. 发既有编排组事件与调度唤醒。

模型不直接写路径、handoff 文件或 Git 引用。

### 7.3 产品 API

建议同一服务增加：

```text
POST /api/orchestrations/:id/successors
GET  /api/orchestrations/:id/handoff
```

- 创建继任组写面 member + 来源会话属主；
- handoff 读面沿用编排组属主链；
- 响应使用统一信封；
- 真实请求／响应与错误码在施工包中先 curl 钉死，不在本稿冒充已验收字节。

同组修订仍使用 doc/72 的既有端点，不把两种操作合并成一个含义模糊的“更新计划”。

## 8. 并发、预算与副作用边界

1. 同一原组最多一个正在创建或执行中的继任组；创建条件在原组锁与当前状态检查下成立。
2. 原组已有活 run 时，先持久化停止并等其收口；继任组不能提前执行。
3. 原组与继任组不得同时持有同一目标的发布资格；发布仍走 doc/74 的项目准入。
4. 重规划深度与累计次数从 handoff 链读取并校验；超过上限后必须问用户，不能另开组重置。
5. 结果复用不证明外部副作用可以重放；handoff 必须列出已知不可重放动作。
6. 交付失败仍走 doc/73；它不重跑 DAG，也不触发自动重规划。
7. 用户停止、删除项目或改变权限后，当前创建与执行资格立即失效。

## 9. 页面与观测

- 编排组详情显示“由哪个编排组重规划而来”、目标可行性判断、原因与复用结果；
- handoff 正文可展开，机器字段由程序渲染，不依赖模型 Markdown 画按钮；
- 原组显示已停止／已结束事实；继任组创建后通过现有事件刷新；
- 不可行时页面只显示原因与用户可选的补充动作，不显示空的新组；
- trace 记录原／新 orchestrationId、replanDepth、reuse 数量与决策结果；不记录敏感结果正文。

## 10. 验收与完成线

至少真跑：

1. **同组修订**：原组 active 且只需追加未来工作，走 doc/72，不创建继任组；成功结果不重跑。
2. **继任组复用**：原组失败后收口，新组通过引用读到两个旧结果，DAG 正常执行，旧组不再发布。
3. **目标不可行**：mAgent 给出证据与原因，不创建组、不写空 handoff。
4. **目标不确定**：先调查或问用户，不盲目重建。
5. **并发创建**：两个通知／两个副本同时创建继任者，只成功一个，原组不会继续执行。
6. **预算**：通过继任链不能重置重规划次数；超限后进入人工处理。
7. **结果边界**：失败／未提交／不可读结果被拒绝；复用产物字节与原版本一致。
8. **副作用**：handoff 标明不得重放的动作没有被继任组自动重复。
9. **崩溃**：继任组已建但 handoff 未固化时不可调度；handoff 完成后崩溃可恢复且不重复建组。
10. **回归**：doc/70／72／73／74 的现有场景全绿。

完成不是“多一个创建继任组端点”，而是：**目标可行时知道该修订还是继任，目标不可行时不再制造新组，旧结果可复用，历史可解释，故障与副作用有边界。**

## 12. 所以这解决了什么

doc/75 把“原方案失败”变成一次有证据的决策：先判断目标是否仍可行，再决定修订还是继任；继任组有 handoff、有结果复用、有预算，也不会与原组竞争执行。

它同时守住两端：该继续时不重做已有工作，不该继续时能明确告诉用户为什么，而不是用更多 DAG 掩盖无法达成的目标。
