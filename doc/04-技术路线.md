## 1. 当时摆在桌上的两个问题

项目从"照着 Octop 复刻一个 AI 工作伙伴"起步时，有两个必须先答的问题：

1. Octop 的**记忆**能力，要不要连同腾讯的 T-Mem 算法一起整合？
2. 复刻的**技术栈**选 LangGraph.js（贴近 Octop 的 Python LangGraph 血统）还是 Eino（Go）？

两个问题的答案都不是"第一直觉"，两个都反转过。

## 2. 问题一：是否整合 T-Mem？

**结论：值得，但不要第一天就整合——把它藏在 Memory 接口后面，分两期走。**

### 2.1 T-Mem 是什么

- 定位：对话式 Agent 的**长时记忆架构**（arXiv:2606.15405，腾讯 + 港科广），LoCoMo / LoCoMo-Plus 双基准 SOTA
- 核心思想："**记忆应当预判，而非归档**"——写入时由 LLM 为每条记忆预演两类触发器：
  - 描述性触发器（措辞/实体相似就能召回）
  - 联想性触发器（与记忆无表面特征重叠、靠潜在语义弧关联的查询也能召回）
- 结构：Scene → Topic → Item 三层图 + 级联检索（RRF 融合 BM25 + 稠密向量 + 硬余弦门控）
- 参考实现：Python（`github.com/Sherlockwz/T-Mem`），构建期 LLM 调用密集

### 2.2 两期方案

| 阶段 | 方案 | 理由 |
|---|---|---|
| 一期 | pgvector + 简单情景记忆表（session 摘要 + 事实抽取） | 先跑通 Agent 主循环，**记忆接口先行**；接口不钉死，二期才换得动 |
| 二期 | 实现 T-Mem 算法 | 触发器预演 + 三层级联检索是算法层面的东西，**不绑定 Python**，可以用 Go 重写；也可先跑 Python 参考实现做 sidecar 验证效果 |

注意点：

- T-Mem 写入成本高（每段对话多次 LLM 调用：边界判定、主题分配、触发器实例化）→ 需要**异步写入管线**
  （可借鉴 WeKnora 的 asynq 任务队列）。
- WeKnora 已有"跨会话长时记忆"实现，可对照参考。
- Octop 自带的记忆系统较简单，T-Mem 是差异化竞争力的候选。

> 现状（2026-09-26）：记忆还没开工（排在能力路线靠后位置），上表仍是待执行的计划，不是实现记录。

## 3. 问题二：LangGraph.js 还是 Eino？

### 3.1 对比

| 维度 | LangGraph.js (Node/TS) | Eino (Go) |
|---|---|---|
| 移植工作量 | ⭐ API 与 Python LangGraph 几乎一一对应，接近"逐行翻译" | 概念一一对应（Graph/Node/Edge/State/Checkpoint），但 API 需重写 |
| 与 Octop 现有后端 | 引入第三种运行时（Go + Python + Node），或被迫砍掉 Go 部分 | ⭐ 收敛为**纯 Go 单语言**，gRPC 边界最终可整个删掉 |
| DeepAgents 对应物 | deepagents 有 JS 版，生态跟随紧密 | Eino ADK（多智能体/supervisor），较新但在快速迭代 |
| 桌面 Agent 形态 | Node 守护进程部署重 | ⭐ Go 单二进制，天然适合本地数字员工 |
| MCP / 流式 | LangChain 生态成熟 | Eino 官方支持 MCP，流式基于 callback 机制完善 |
| 技术资产一致性 | 新增 TS 栈 | ⭐ 与 WeKnora（Go）一脉相承，架构经验直接复用 |

### 3.2 结论：选 Eino

决定性理由不是"Eino 比 LangGraph.js 强"，而是**系统拓扑**：

1. Octop 自己是"Python 应用 + Python Agent 芯"；用 LangGraph.js 复刻只是换一种双语双进程，
   复杂度没降下来；用 Eino 则收敛为纯 Go 单语言，少一种运行时。
2. 目标是本地数字员工形态，Go 单二进制部署是硬优势。
3. 参考系（WeKnora）全是 Go，遇到问题有两个大型 Go 项目（WeKnora + Eino 自身）可抄。

代价：复刻不是"翻译"而是"重写"，需要先建立 LangGraph → Eino 的概念映射表。

### 3.3 LangGraph → Eino 概念映射（移植手册）

| LangGraph (Python) | Eino (Go) |
|---|---|
| `StateGraph` | `compose.Graph` / `compose.NewChain` |
| `add_node` / `add_edge` | `AddNode` / `AddEdge` |
| 条件边 `add_conditional_edges` | `AddBranch`（`GraphBranch`） |
| State（TypedDict + reducer） | 泛型 State + `WithStatePostHandler` / `GenLocalState` |
| `Checkpointer`（PostgresSaver） | Checkpoint 接口（`compose.CheckPointStore`），需自实现存储 |
| `interrupt` / 人机协同 | Eino Interrupt & Resume（`compose.StatefulInterrupt` + `Runner.ResumeWithParams`） |
| ReAct Agent（prebuilt） | `react.Agent` / ADK `ChatModelAgent` |
| 多智能体 supervisor | Eino ADK 的多 Agent 组合（`flowAgent` 等） |
| 工具节点 ToolNode | `compose.ToolsNode` + MCP 工具适配 |
| 流式 `astream_events` | Callbacks + `StreamReader` |

这张表在后续每层都用得上：读 Octop/harness 的 Python 实现时，先用它把"这个概念在 Eino 里叫什么"定位出来，
再决定是"照抄语义"还是"用 Eino 的正式做法重做"（后者更多，见《05》§翻译原则）。

## 4. 反转记（2026-09-23 → 2026-09-24）

路线来回走了两圈，两次反转都有具体原因，记下来避免重复踩：

### 4.1 第一圈：定全栈 TypeScript（2026-09-23）

理由不是技术对比，而是**人的连续性**：owner 曾用 TS 和 Go 各复刻过一遍 pi agent（双语言对照实验），
实测体感 TS 更适合；生长式路线下"学习连续性"权重最高；且 harness-agent 的中间件矩阵在 JS 版 deepagents
上有官方对应物，翻译最直接。技术栈定为 LangGraph.js + deepagents(JS) + Node 后端。

### 4.2 实地验证推翻前提（同日晚）

clone 下 `ref-agent/Octop` 实际代码（v0.9.33）后发现：**不存在"可保留的 Go 后端"**——
Octop 主进程是 Python 3.12+ 单进程（FastAPI + uvicorn，src 约 13.1 万行），Go 只存在于 `desktop/` 桌面外壳（约 2.6k 行）；
Agent 核心在外部 pip 包 `orcakit-harness-agent` 里。两条路线都是全量重写，谁也不占存量便宜。

### 4.3 第二圈：回到 Eino（2026-09-24）——终版

爬完 L2（任务规划）后做了一轮 Eino 专题调研，暴露的核心问题是**规划与执行的时序保证**：
在 LangGraph 系里，这类约束只有 middleware 一层可做文章（`afterModel` 之类），用软机制模拟硬约束；
Eino 却把分界写死——**Graph 管确定性、Agent 管自主性，不要用静态编排去假装动态决策**，
要硬保证时直接编图（Workflow Agents / Plan-Execute 节点图）。

即："对确定性有正式的一等公民答案"这件事，Eino 有，LangGraph 系没有。这正是后续层级
（子代理、断点恢复、多入口）会反复碰到的问题。调研全文见《08》。

**决策**：

- 只保留 `yk-tako-eino/` 作为唯一主线，后续能力全部在 Go/Eino 里生长；
- 复刻方针：**功能翻译，按 Eino 的思想写**（细则见《05》§翻译原则）；
- TypeScript 实现全部删除；`maf/`（.NET 对照）冻结为存档，不再推进。
