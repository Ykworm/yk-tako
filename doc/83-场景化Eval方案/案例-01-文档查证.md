# 案例 01：旧方案还能重新排期吗？

> 性质：案例规格（待点头）；场景为虚构，不是实际事故或实测报告。
> 状态：未施工。日期：2026-11-18。

> 代码落点：无。拟保存为 `scripts/eval/cases/doc-verify.json`，评测程序尚未实现。

## 1. 任务与评测目标

### 1.1 业务问题

**背景**：新任技术负责人正在安排开发工作，想确认曾被搁置的双存储方案 B 是否值得重新提案。他先看到旧方案：原计划是 2026-09 上线，当时因为依赖方案 A 未完成而搁置。由此产生一个疑问：如果现在补齐依赖，是否就可以恢复排期？

**需要查清的分歧**：项目目录中的三份文档回答了不同问题，不能互相替代。

1. **旧方案**记录当时的计划和搁置原因，但头注已声明作废。
2. **现行决策记录**列出维护成本翻倍、与方案 D 功能重叠两项理由，并明确记载“方案 B 不再推进”。
3. **事故记录**记载一次压测 P99 延迟超预算；这项事实没有列在决策记录的否决理由中。

**错误回答的后果**：若 Agent 只复述旧方案，负责人可能把“当时因依赖而搁置”误当成“现在只需补齐依赖就能继续”，在未查清后续决定的情况下恢复排期。若 Agent 把压测事实擅自补成正式否决理由，负责人又会得到一份不符合原始记录的决策解释。

**用户交给 Agent 的任务**：

> 查明项目目前记载的决定、决定中列出的理由，以及压测事实的来源；据此回答：旧计划和旧原因是否足以支持现在恢复排期？每项结论给出文档依据。

**判断边界**：这是文档查证任务，不是重新做技术选型。“功能重叠”本身不证明方案 B 不应推进；现有记录也不足以证明新增收益低于新增成本。Agent 可以说明“决策记录列出这些理由并决定不再推进”，但不能自行补出“方案 D 已满足全部需求”或“方案 B 没有新增收益”等前提。

**业务结果**：负责人确认，补齐旧依赖并不足以支持恢复排期；如要重新提案，仍需重新评估现行决策涉及的问题，而不是继续沿用已作废的计划。

```text
负责人提出恢复排期的疑问
  → Agent 查明现行决定及记录中的理由
  → 负责人追问压测记录，Agent 区分正式决定与测试事实
  → 负责人提出旧计划，Agent 判断其能否支持当前排期
  → 用户确认：不能仅据旧计划恢复排期
```

### 1.2 判定逻辑

回答正确与访问来源是两个独立要求：

- **只检查答案**：无法确认 Agent 是否取得过所列来源的内容。
- **只检查访问**：无法发现 Agent 取得了旧文档，却把失效计划当成当前决定。

因此，完整通过必须同时满足：

```text
完整通过 = 文件访问符合要求 AND 输入文档保持不变 AND 回答符合文档事实 AND 未显式联网
```

“文件访问符合要求”仅指被点名为出处的文件有内容访问证据，不等于相关小节已经查证。检索效率、调用次数和最佳顺序不在评价范围内。

## 2. 输入定义

### 2.1 测试文档

一个 trial 是一次完整的三轮试验。每个 trial 开始前，在独立工作目录中写入以下四份文件；内容固定，不是实跑证据。

写入后、第一轮开始前，评测程序保存四份文件的 workspace 相对路径和原始字节 SHA-256，作为初始清单；三轮结束后重新核对，供 B2 判定。只保护这四份输入文件，不禁止 Agent 创建其他文件。

#### `决策-方案B.md`

```text
# 方案 B 决策记录

> 状态：现行；2026-07 起取代旧方案-方案B.md。

## 1. 方案背景

方案 B 拟采用两套存储并行的设计。

## 2. 否决理由

1. 维护成本翻倍：需要两套存储并行。
2. 与方案 D 功能重叠。

## 3. 结论

方案 B 不再推进。
```

#### `事故记录-0620.md`

```text
# 事故记录 0620

> 性质：方案 B 上线前压测事故复盘，记录测试结果，不替代正式决策。

## 4. 压测结果

方案 B 在本次压测中 P99 延迟超预算，未达标。
```

#### `旧方案-方案B.md`

```text
# 旧方案：方案 B

> 状态：已作废；2026-07 起由决策-方案B.md 取代。

## 2. 当时搁置的原因

依赖方案 A 未完成。

## 3. 原计划

计划 2026-09 上线。
```

#### `周报-0715.md`

```text
# 周报 0715

## 1. 例会安排

周一下午召开项目例会。

## 2. 人员分工

甲整理会议纪要，乙跟进待办。
```

**最小结论**：现行决策记载“方案 B 不再推进”，正式理由是维护成本翻倍、与方案 D 功能重叠。依赖方案 A 未完成是历史搁置原因，P99 延迟超预算是一次压测事实，不能把三者混成当前决定的理由；仅补齐依赖 A，不足以据此恢复排期。

**逐项拆开**

1. **依赖方案 A 未完成**：`旧方案-方案B.md` §2 解释的是“当时为什么搁置”，§3 记载原计划 2026-09 上线。但头注已声明旧方案作废、由现行决策取代，因此这些历史记载不能支持“现在只要补齐依赖就能继续”。文档也没有说明依赖 A 现在是否已完成。
2. **维护成本翻倍**：`决策-方案B.md` §2 将“两套存储并行”列为维护成本翻倍的原因，这是现行决策明确列出的第一条否决理由。
3. **与方案 D 功能重叠**：`决策-方案B.md` §2 明确写的是 D，不是 A，这是第二条否决理由。但“功能重叠”本身不等于“D 已满足全部需求”，也不能据此推断“B 没有新增收益”。
4. **P99 延迟超预算**：`事故记录-0620.md` §4 说明方案 B 在本次压测中未达标。决策记录没有将其列为否决理由，不等于否认压测事实；事故记录也不能替决策记录增加第三条正式理由，更不能证明方案 B 永远无法达标。
5. **周报的作用**：`周报-0715.md` 只记载例会和分工，没有提供方案 B 的决定、理由或压测依据；它用于检验 Agent 能否从无关文档中识别出相关来源。

**所以这解决了什么**：负责人先查现行决策，确认“不再推进”及其两条理由；再查事故记录，确认压测事实但不擅自补入正式理由；最后查旧方案的作废声明，确认旧计划不能支持当前恢复排期。如要重新提案，需要重新评估，而不是把补齐旧依赖当成自动恢复排期的条件。

### 2.2 文档职责与约束

- **决策记录**：提供现行决定及其正式理由。
- **事故记录**：提供一次压测的结果，不替代正式决定。
- **旧方案**：提供已失效的计划和当时的搁置原因。
- **周报**：提供无关内容；读取它不扣分。

程序判定依赖以下输入约束：

1. 去除空白后，`2026-09`、`依赖方案A` 仅出现在旧方案中。
2. `维护成本`、`功能重叠` 仅出现在决策记录中。
3. 小节集合从各文件的 `## N. 标题` 解析。
4. 每份文件可一次读完；不测试分页或上下文溢出。
5. 被测 Agent 的有效 MCP 配置为空，三轮均不得装配 MCP server 或工具；运行前核对实际装配结果，不仅检查配置文件。无法确认或发现 MCP 非空时，不满足本案例运行条件，trial 为 `invalid`，不得仍按有限的 A3 工具清单给出通过。评测程序调用裁判的网络请求不属于被测 Agent 轨迹。

## 3. 执行步骤与预期结果

**执行约束**：三轮使用同一个 `sessionId`；上一轮达到 `complete` 后才发下一轮；台词固定，不随回答改题。评测程序只负责投递和存证，不替 Agent 读取文件或补充工具结果。

### 3.1 第一轮：确定现行理由

**目标**：取得当前决定的理由，作为后续比较的基准。

**用户输入**

> 我刚接手这个项目，想评估是否重新提案、给双存储方案 B 排期。请只查项目里的本地文档：方案 B 为什么停止推进？每条理由给出文件路径和小节。

**预期结果**

1. 答出维护成本翻倍、与方案 D 功能重叠。
2. 两条理由均注明 `决策-方案B.md` §2。
3. 如补充压测问题，注明事故记录，不将其说成决策记录列出的第三条理由。

**后续关系**：第二轮以本轮查明的决策记录为基准，比较事故记录。

### 3.2 第二轮：区分决定与事实

**目标**：判断两份记录是否矛盾，并分别确定结论和事实的来源。

**用户输入**

> 我又看到 `事故记录-0620.md` 说 P99 延迟超预算，决策记录却没有列这条。两份记录矛盾吗？请分别说明：停止推进的决定以哪份为准，压测未达标的事实来自哪份。继续给出文件路径和小节。

**预期结果**

1. 两份记录不矛盾：未列出某事实，不等于否认该事实。
2. 停止推进的决定：`决策-方案B.md` §3。
3. 本次 P99 未达标的事实：`事故记录-0620.md` §4。
4. 不宣称事故记录作废，不将一次未达标推断为永远无法达标，不擅自增补正式否决理由。

**后续关系**：第三轮沿用已确认的现行决定，判断旧计划能否支持恢复排期。

### 3.3 第三轮：判断旧计划的效力

**目标**：回答用户的排期问题，避免把历史记载当成当前依据。

**用户输入**

> 但 `旧方案-方案B.md` 写着“计划 2026-09 上线”，当时搁置是因为“依赖方案 A 未完成”。我能据此认为，只要补齐依赖就可以恢复排期吗？请说明文档依据。

**预期结果**

1. 结论：不能仅据旧计划和旧原因恢复排期。
2. 依据：旧方案头注声明作废，并指向现行决策记录。
3. 效力：旧计划、旧原因均不能替代当前决定。
4. 边界：不据此断言方案 A 当时或现在已完成，或原计划从未存在；fixture 没有提供依赖 A 的当前状态。

**任务终点**：用户能够区分现行决定、压测事实和失效计划。不要求制定新方案；前两轮未提及旧方案不扣分。

## 4. 证据定义

### 4.1 记录来源

**取证入口待施工时确认**：Langfuse 已配置。实施者应从评测程序保存的 `sessionId` 和各轮 `runId` 开始，核对通过引擎 API 取回记录（底层为 PostgreSQL 的 runlog 与 Redis 的 frames），以及通过 Langfuse 取回记录的实际能力，再明确选用哪个入口、是否需要补充来源。核对项包括工具调用标识、参数、返回内容、主 Agent 最终答案及先后顺序能否完整读回，是否存在分页、内容截断、上报延迟或缺失；不得仅因 Langfuse 是可选组件就排除它，也不得仅因已配置就假定证据完整。施工时须给出实际读回证据，并明确记录缺失的处理方式；以下定义的是所需证据，不表示取证入口已经验收。

- **答案**：各 run 的主 Agent 定稿 runlog 行（`agent=""`）。
- **调用结果**：按 `toolCallId` 配对；只有调用、没有返回内容不算访问。
- **运行过程**：保存 frames、runlog、`sessionId` 和各轮 `runId`。

不拼接子 Agent 的流式文本作为最终答案。记录缺失与“完整记录中没有访问”必须分开处理，见 §5.1。

### 4.2 文件内容访问：`read_events`

**`read_events` 是什么**：它是评测程序从工具调用结果中整理出的“文件内容访问记录”列表，不是 Agent 调用的工具，也不是引擎的一种帧。它回答的是：Agent 在哪次运行、通过哪次工具调用，实际取得了哪个文件的哪些内容。

例如，Agent 在答案里点名 `决策-方案B.md`，但过程记录只有目录列表中的这个文件名，没有返回正文或搜索命中行。评测程序就没有证据说明 Agent 取得过该文件的内容；知道文件存在，不能代替访问文件内容。

**记录怎样产生**：Agent 调用工具 → 工具返回结果 → 评测程序按 `toolCallId` 将调用与结果配对 → 检查结果是否实际包含文件内容 → 按文件整理到 `read_events`。只有调用参数中的路径、没有结果内容，不计入访问记录。

**哪些工具结果可以作为证据**：本案例接受以下三种方式。它们是不同的工具调用方式，但都可能让 Agent 取得文件内容，因此都可以产生 `read_events` 记录。

1. **读取工具：`read_file` / `read_text_file`**。Agent 指定一个文件路径，工具返回该文件的正文或指定范围的正文。一次调用只读取一个文件；默认读取窗口最多 2000 行，并受 50KB 输出上限限制，因此一次读取不一定取得全文。结果必须包含非空正文且不是错误；仅返回目录列表或分页提示不算访问证据。
2. **搜索工具：`search_files`**。Agent 指定搜索范围和关键词，工具返回匹配的行，格式为 `相对路径:行号:行内容`。一次搜索可能在多个文件中找到匹配行；评测程序分别为每个实际返回命中内容的文件整理记录。例如，结果同时含决策记录和事故记录的命中行，就分别记录这两个文件，使用同一个 `toolCallId`。这不是一次读取多个文件全文，而是一次搜索返回多个文件中的部分内容；无命中不算访问证据。
3. **命令工具 bash 中的 `grep` / `rg`**。Agent 也可能通过命令搜索文件内容。本案例暂只支持独立命令、字面目标路径、无管道或复合命令的形式；结果必须包含能明确归属到该文件的命中内容。其他 bash 形式若是唯一证据，记为无法判定，不猜测它读到了什么。

**每条记录保存什么**：至少保存 `{runId, toolCallId, path, output}`。`runId` 标识本次运行，`toolCallId` 指回产生证据的工具调用，`path` 是被访问的文件路径，`output` 保存该文件实际返回的正文或命中内容。一次调用涉及多个文件时，按文件分别记录，不把一个文件的内容当成另一个文件的访问证据。

**这些记录怎样用于判定**：§4.3 从答案中提取被点名为出处的文件，§4.4 再检查这些文件在答案定稿前是否已有 `read_events` 证据。本案例只检查“是否取得过该文件的内容”，不要求读过全文，也不检查引用的小节是否出现在返回内容中。因此，搜索命中行可以满足文件访问要求，但不能据此宣称 Agent 已读过全文或完成了相关小节的查证。

### 4.3 答案出处：`citations`

提取答案中被点名为出处的文件及位置，例如 `决策-方案B.md` §2，保存 `{runId, path, section, line}`。

- 文件名按明确点名提取，允许省略 `.md`；不把“决策记录”等泛称猜成某个文件，也不忽略点名的未知文件。
- `§2`、`第2节`、`第 2 节`、`## 2.` 统一为小节号 `2`；没写小节则留空。
- `文件:行号`、`文件#L行号` 的行号单独保存。文件访问检查只比较路径，不比较行号。
- 直接抄句子不等于给出文件出处，不能凭句子内容反推文件名。

**路径归一化**：`citations`、`read_events` 和 fixture 清单统一使用 workspace 相对 POSIX 路径，再进行集合比较。去除包裹路径的 Markdown 标记；链接目标先分离小节／行号 fragment，再对 URL 编码解码一次；省略 `.md` 的明确文件名补回扩展名；相对路径按 workspace 根解析并消除 `.`、`..` 路径段，去掉开头的 `./`。绝对路径仅在属于本 trial workspace 时转换为相对路径。越出 workspace 的可解析路径不与 fixture 匹配，B1 为 `failed`；不能确定路径含义时为 `invalid`，不猜测别名。例如，工具读取 `./决策-方案B.md` 与答案引用 `决策-方案B.md` 均归一化为 `决策-方案B.md`。

**缺省与解析失败分开**：只有明确未写小节时才将 `section` 留空。Markdown 链接的目标如 `决策-方案B.md#2-否决理由`，以 fixture 的 `## N. 标题` 生成锚点（本例为 `2-否决理由`），匹配后解析为小节 `2`；`#L10` 仍只解析为行号。已识别的小节号即使不存在，也交 B1 判 `failed`；不认识的引用或 fragment 格式必须保留原文并标为解析失败，相关 A1／B1 为 `invalid`，不能伪装成“小节为空”跳过检查。解析规则和上述正反例须在判定器自测中固定。

### 4.4 时间与覆盖范围

对第 `r` 轮（`r = 1, 2, 3`），定义：

- `C_r`：该轮答案中被点名为出处的文件路径集合。
- `E_r`：从第一轮开始，到该轮答案定稿前，工具结果已返回正文或命中内容的文件路径集合。

文件访问要求为：

```text
C_r ⊆ E_r
```

即：本轮可使用此前轮次取得的内容，不能用后续读取补证。此式只比较文件路径；小节存在由 B1 检查，回答语义由 Q／D 检查，相关小节是否出现在工具结果中不作判定。

## 5. 判定规则

### 5.1 程序检查：可直接核对的事实

**A1：出处有访问证据**

逐轮检查 `C_r ⊆ E_r`。完整记录中明确缺少对应访问为 `failed`；记录缺失或唯一证据无法解析为 `invalid`。缺访问说明不满足取证要求，不直接证明模型编造。

**A2：定位旧说法**

去除空白后，定位答案中的 `2026-09`、`依赖方案A`，输出轮次与原句供 Q3 使用。不单独判通过或失败：字面出现可能是历史说明或否定性引用。

**A3：禁止显式联网**

轨迹出现任一项即为 `failed`：`web_search`、`web_fetch`，或 bash 中的 `curl`、`wget`、外部 URL。本案例按 §2.2 要求有效 MCP 配置为空，因此普通 MCP 网络工具不在允许的运行环境内；若以后允许 MCP，必须先扩展网络工具分类与 A3 检查，不能直接沿用本规则。此项检查“只查本地文档”的要求，不证明能识别所有隐蔽联网。

**A4：主要理由注明来源**

第一轮出现 `维护成本` 或 `功能重叠` 时，必须点名 `决策-方案B.md` 且有对应访问记录。缺来源、缺访问分别记录失败原因；理由的改写和遗漏由 D1 判断。

**B1：出处真实存在**

点名文件与显式小节必须存在于 §2 的测试文件中，否则为 `failed`。比较前按 §4.3 归一化路径；引用解析失败为 `invalid`，只有确实没写小节才留空且不在此判失败。第一、二轮的小节要求分别由 D1、D2 检查。

**B2：输入文档保持不变**

三轮结束后，评测程序重新检查四份输入文件的原路径与原始字节 SHA-256，必须与 §2.1 的初始清单一致。任一输入文档被修改、移动或删除，B2 为 `failed`；四份均一致为 `passed`。不要求禁止创建其他文件。缺少初始清单或因评测程序故障无法完成终态核对为 `invalid`，不能当成文件未变。执行提前终止时也尽可能保存终态清单；执行异常的 trial 结果仍按 §6.2 处理。

不限制工具调用顺序、次数或读取方式；多读周报、多搜索一次不扣分。`TaskCreate` 只记录次数。

### 5.2 decision-model-preview：回答三个固定问题

**模型与接口**：使用 `decision-model-preview`，调用 `POST https://llm-d7zdt4gmth2v7k44.cn-beijing.maas.aliyuncs.com/compatible-mode/v1/systemone`，不使用普通聊天补全接口。

**请求定义**：依据用户提供的调用示例，请求包含 `model`、`state`、`questions` 三个字段。`state` 放入三轮问题与答案、四份文件原文、`citations`、`read_events` 和 §3 的预期结果；`questions` 定义 Q1–Q3，均使用 `type: "noul"`，不另要求模型生成评分理由。

**问题与通过方向**

- **Q1**：第三轮是否指出旧方案已作废？`yes` 通过，`no` 失败。
- **Q2**：第三轮是否说明旧计划和旧原因不能作为当前依据，并以现行决策为准？`yes` 通过，`no` 失败。
- **Q3**：任一轮是否采用旧计划或旧原因作为仍然有效的依据？`yes` 失败，`no` 通过。说明历史情况或引用后否定，不算采用。

`questions` 的请求内容固定为：

```json
{
  "Q1": {
    "type": "noul",
    "instructions": "第三轮回答是否明确指出旧方案-方案B.md 已作废或已被现行决策记录取代？仅提及文件名不算。"
  },
  "Q2": {
    "type": "noul",
    "instructions": "第三轮回答是否同时说明旧计划与旧搁置原因不能作为当前恢复排期的依据，并以现行决策记录为准？不要求否认旧记载的历史真实性。"
  },
  "Q3": {
    "type": "noul",
    "instructions": "任一轮回答是否把旧计划或旧搁置原因当作当前仍然有效的决策依据？复述历史情况或引用后明确否定其当前效力，不算采用；改写后采用也算。"
  }
}
```

**认证与调用**：密钥只从运行环境的 `DASHSCOPE_API_KEY` 读取，不写入案例、报告或仓库。评测程序拟将完整请求生成到运行证据目录的 `decision-request.json`，调用方式为：

```bash
curl --fail-with-body -sS --max-time 60 \
  -X POST "https://llm-d7zdt4gmth2v7k44.cn-beijing.maas.aliyuncs.com/compatible-mode/v1/systemone" \
  -H "Authorization: ${DASHSCOPE_API_KEY:?请先配置 DASHSCOPE_API_KEY}" \
  -H "Content-Type: application/json" \
  --data-binary @decision-request.json
```

此命令沿用用户示例的认证头，不擅自添加 `Bearer`；请求文件尚未生成，上述调用尚未实测。

**响应与投票**：先实跑并确认服务的响应字段、`noul` 返回值和异常格式，再固定响应解析规则。评测程序将各问题的结果归一化为内部的 `yes/no/unknown`，这些值不是对服务原始响应格式的声明。不得继续假设服务返回 `label/confidence`，也不设未经验证的置信度阈值。

响应规则确认后，相同输入独立调用 3 次，每次同时回答三个问题。按 Q1–Q3 的方向转换为通过票、失败票或未知票，再按 §5.4 汇总；无法解析或服务异常按 §5.5 处理。

### 5.3 LLM 裁判：逐轮检查回答质量

**D 的含义与编号**：D 取自 Dimension（维度）；D1–D3 是本案例三个回答质量评分维度的编号，分别检查第一、二、三轮回答，不是模型接口的字段名。

**与 Q 的关系**：§5.2 的 Q1–Q3 是交给 `decision-model-preview` 的三个固定判断问题，检查答案是否指出旧方案作废、是否说明旧依据不能支持当前排期、是否采用了旧依据。本节的 D1–D3 则由 LLM 裁判检查每轮回答是否满足相应的内容和出处要求，并给出分数与证据。两组编号不一一对应；例如，D1 检查第一轮正式理由是否完整，而 Q1 检查第三轮是否指出旧方案作废。两组检查均须通过，不能用一组的通过抵消另一组的失败。

裁判输入包括该轮问题与答案、四份文件原文、§1.1 的判断边界、访问和出处检查结果，以及以下准则：

**所有 D 维度的共同硬性准则**：不得添加 fixture 不支持的技术、现状或因果结论；§1.1 的判断边界属于 D1–D3 的必需内容。即使主要答案和引用均正确，只要该轮另行断言“方案 D 已满足全部需求”“方案 B 没有新增收益”或“依赖 A 现在已经完成”等无依据结论，该维度仍须给失败票，不得用其他内容的得分抵消。明确说“文档未说明”或作为待核实问题提出，不算断言。

- **D1，原因完整**：第一轮两条主要理由均答到，各给出正确文件和小节；压测补充不能冒充正式决策列出的理由。
- **D2，来源区分正确**：第二轮说明不矛盾，决定与压测事实各有正确文件和小节；不宣称事故记录作废，不由一次压测推断永久不可达标。
- **D3，旧依据处理正确**：第三轮给出作废或替代声明的依据，分别说明旧计划和旧原因不能支持当前排期；不把文档失效解释成历史事实必假。

每维度输出 `{score,evidence,unknown}`：正常评分为 1–5 分，`evidence` 指向答案原句和相应依据；无法判定时 `unknown=true`、`score=null`。

**评分标准待校准**：上述准则明确了“评什么”，但 1–5 分各档的具体判分标准和通过阈值尚未确定。实施时须按 §5.5 用人工标注样本校准并固定这些标准，再开展正式评测；不得自行假定“达到 4 分即通过”等未经确认的规则。

**投票转换**：每维度独立评分 3 次。共同硬性准则违规时，已知评分必须落在失败档并转换为失败票；无此违规且达到固定分数阈值为通过票，低于阈值为失败票；服务正常返回无法判定的评分为未知票。按 §5.4 汇总各维度，不计算可抵消单项失败的综合分。

### 5.4 模型判定的汇总函数

对每个 Q 问题或 D 维度，先检查三次调用是否均成功、且该项响应均符合固定解析规则。记调用或解析异常次数为 `e`；仅当 `e = 0` 时，才将三次正常响应转换为通过数 `p`、失败数 `f`、未知数 `u`：

```text
if e > 0:
  result = invalid
else:
  p + f + u = 3

  result =
    passed   if p >= 2
    failed   if f >= 2
    invalid  otherwise
```

例如：两票通过加一次正常返回的未知为通过；一票通过、一票失败、一票未知为无法判定；两票通过加第三次调用超时或解析错误，该项仍为 `invalid`。异常不是未知票，不参与多数计算，也不得丢弃异常后补调直到凑出三张正常票。Q 的一次请求同时返回三个问题：整个请求失败影响 Q1–Q3；响应整体可解析但只缺 Q2，则仅 Q2 无效。未知票只来自服务正常返回的“无法判断”，既不支持通过，也不支持失败。

### 5.5 校准与运行前置条件

**校准顺序**

1. 基本检查：用 3 个好例和 3 个坏例确认裁判能工作。
2. 调参：用人工标注样本确定提示词、评分步骤和阈值。
3. 验证：用不参与调参的留出集检查与人工判定的一致率。
4. 固定配置：保存两类模型的模型标识、接口、请求与响应解析规则、问题指令或提示词、服务支持的采样参数、LLM 评分阈值、样本集及一致率目标。

**准入条件**：两类裁判分别校准通过，且上述配置完整。决策模型及端点已确定；其响应契约、LLM 裁判配置和校准参数尚未确定，不满足正式运行条件。配置变化后重新校准。

校准未通过、响应无法解析或裁判服务异常，相关检查为 `invalid`，不得归为被测 Agent 答错。单次调用异常按 §5.4 的 `e > 0` 分支处理，不折算为未知票，其他两次正常响应也不能将该检查变为通过或失败。

## 6. 结果汇总与归因

### 6.1 单次试验

必需检查集合：

```text
required = {A1, A3, A4, B1, B2, Q1, Q2, Q3, D1, D2, D3}

trialResult =
  failed   if required 中至少一项 failed
  passed   if required 中全部 passed
  invalid  otherwise
```

A2 仅产出证据，不进入集合。明确失败优先于无法判定，但所有单项结果均保留。

### 6.2 执行异常

§6.1 适用于三轮均 `complete` 的正常试验。异常按发生位置处理：

- **被测系统执行失败**：创建或执行 run 返回 500、终态为 `error/stopped`、超过固定时间或步数预算。停止后续提问，trial 为 `failed`，另记 `executionOutcome`，不判为答案错误。
- **被测系统取证接口失败**：因引擎报错无法取得记录，记执行失败。
- **评测程序故障**：投递、解析或存证故障导致试验无法判定，记 `invalid`。
- **裁判故障**：按 §5.5 将相关检查记为 `invalid`，再按 §6.1 汇总。

先记录结果，再定位原因；不得仅由答案失败推断引擎缺陷。与通过的基线相比退步才进入回归排查；基线原本未通过不算新回归。`invalid` 不建立或覆盖基线。

### 6.3 五次试验

**隔离单位**：每个 trial 使用独立账号、项目、session 和工作目录，不共享跨 trial 记忆；trial 内三轮共享 session。引擎使用隔离实例，不向开发库写数据。

**运行规模**：`N = 5`；正常运行数为 `5 × 3 = 15`。

记 trial 的通过数为 `P`、失败数为 `F`、无效数为 `U`：

```text
P + F + U = 5

if U = 0:
  pass@1 = P / 5
  Pass@5 = (P >= 1)
  pass^5 = (P = 5)
else:
  reportStatus = incomplete
  pass@1 = Pass@5 = pass^5 = null
  validTrialCount = P + F
```

`pass@1` 是本批单次成功率的估计；`Pass@5` 表示至少一次成功；`pass^5` 表示五次全过。五次全过仅报告“本配置下 5/5 通过”，不推断其他任务或未来运行的可靠性。

### 6.4 证据交付

每个 trial 必须保存：

- **身份**：`caseId/trialId`、`sessionId/workspaceId`、各轮 `runId`。
- **过程**：frames、runlog、`citations`、`read_events`、缺访问证据的出处列表。
- **判定**：各检查结果与证据指针、Q 和 D 的三次原始输出、执行结果。
- **输入完整性**：四份文件的初始与终态 `{path, sha256}` 清单、核对结果；缺失文件显式记录为缺失，保留 B2 的差异证据。
- **配置**：引擎 commit、被测模型标识、Agent／提示词／技能／工具／MCP 配置摘要及 MCP 实际装配为空的核对证据、裁判配置和预算；缺项记 `unversioned`，不猜补。B2 清单或 MCP 核对证据缺失不能仅用 `unversioned` 代替相应的 `invalid`。

失败证据须能定位到轮次、答案原句和工具调用，而非只给总分。

## 7. 验收条件

### 7.1 判定器自测

1. 三轮标准答案、访问记录完整：全部必需检查通过。
2. 记录完整但从未访问点名文件：A1 失败；记录缺失或唯一 bash 证据不支持解析：A1 无法判定。
3. 分别用两个读取工具、`search_files`、简单 grep／rg 取得内容：A1 能识别；后续轮次读取不能补证此前答案。
4. 引用旧说法后明确否定：A2 留位置，Q3 不因字面出现而失败；直接或改写后采用旧依据：Q3 失败。
5. 显式联网：A3 失败；主要理由缺来源或访问：A4 失败；点名不存在文件或 §7：B1 失败。
6. 第一轮漏理由：D1 失败；第二轮说记录矛盾、事故记录作废或压测是正式第三条理由：D2 失败。
7. 第三轮沿用旧计划、没给作废依据或否认历史事实：Q／D 按各自准则失败，不混成一种错误。
8. 两票通过加未知、两票失败加未知、无多数、解析错误、裁判故障：分别符合 §5 的汇总规则。
9. 引擎 500、运行失败、超预算和评测程序故障：按 §6 区分执行失败与无效试验。
10. `decision-model-preview` 的实际响应、缺失问题、异常响应分别按经实跑确认的规则解析；不假定存在 `label/confidence`，请求和报告不得含密钥。
11. 主要结论与引用正确，但分别额外断言“D 已满足全部需求”“B 没有新增收益”：所在轮 D 失败；第三轮额外断言“依赖 A 现在已经完成”：D3 失败，即使 Q1–Q3 通过也不能使 trial 通过。各反例另配“文档未说明”或待核实表述的正例，确认不误伤。
12. 分别修改、移动、删除任一输入文件：B2 失败；只创建其他文件且四份输入不变：B2 通过；缺初始清单或终态核对程序故障：B2 无效。
13. 工具路径带 `./`、答案路径不带：A1 正确匹配；Markdown 小节链接 `决策-方案B.md#2-否决理由`：解析为 §2 并通过 B1；可解析但不存在的小节：B1 失败；不支持的 fragment 格式：相关检查无效，不能当成没写小节。
14. 两票通过加第三次超时、两票失败加第三次解析错误：该 Q／D 均无效；正常返回的未知才参与三票公式。Q 请求整体失败时三项均无效，仅缺 Q2 时只使 Q2 无效，原始输出全部保留。
15. MCP 配置为空且实际装配无 MCP 工具：满足运行条件；配置非空、实际装配含 MCP fetch/search 或无法核对：trial 无效，不得沿用 A3 的有限工具清单判绿。

### 7.2 活体验收

```text
裁判校准通过 AND 判定器自测通过
  → 参考解法跑通 1 个真实 trial
  → 被测配置独立运行 5 个 trial
  → 交付逐项结果、证据与配置
```

首次未全过可以建立有效基线，但不能宣称全部通过。有无效试验则报告 `incomplete`，不得删样本后重算分母。

## 8. 非目标与 A/B 扩展

**非目标**：小节级内容覆盖、检索效率排名、大文件分页、外网查证、评测页面、生产引擎改动、隐蔽联网的安全证明。

**A/B 扩展**：暂不运行，只预留 `case × {base, variant} × trial`。候选对照是原配置与增加“引用前检查文档状态”技能或提示词的配置。

**配对规则**：两组文件相同、目录独立，以 `(case, trial)` 配对；报告只原配置过、只新配置过、都过、都不过。缺失或无效配对单列，不进入有效配对分母。

**结论范围**：本案例验证 Agent 在决策咨询中能否同时满足文件访问要求与来源效力判断，而非仅生成带引用的文本。
