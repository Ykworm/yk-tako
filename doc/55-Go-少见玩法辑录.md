## 1. 并发与互斥

### 1.1 不用第三方库的 `flock`：哈希桶 + 排序取锁 + 非阻塞轮询

**病灶。** 两个 agent 同时改同一个文件：A 读了 v1，B 也读了 v1；A 写 v2，B 基于 v1 算出内容写 v3——v2 被覆盖，两边都报成功。只在内存里放互斥量挡不住另一个进程/另一个副本；要对**文件**本身加排它锁。

**写法**（`filefp.go:191-280`）：

```go
// 锁文件按路径哈希分 256 桶，桶数恒定
const lockBuckets = 256

func lockPathFor(lockDir, absPath string) string {
	sum := sha256.Sum256([]byte(absPath))
	return filepath.Join(lockDir, fmt.Sprintf("%02x.lock", int(sum[0])%lockBuckets))
}
```

取锁的三条规则（缺一就死锁），对应 `lockPaths`：

1. **路径去重**：`flock` 挂在 open file description 上，同一进程两次 `open` 同一文件是两个不同的 open file description，第二次会阻塞在**自己**的第一次上。
2. **按字典序取**：防 A 拿 L1→L2、B 拿 L2→L1 的 AB-BA 死锁。
3. **逐把取，失败全释放**：任一把失败就把已拿到的全部 `LOCK_UN`，再返回错误。

等待方式不是阻塞式 `LOCK_EX`：

```go
for {
	err = syscall.Flock(int(fd.Fd()), syscall.LOCK_EX|syscall.LOCK_NB)
	if err == nil { break }
	if !errors.Is(err, syscall.EWOULDBLOCK) { ... }
	if time.Now().After(deadline) { ... return nil, errLockTimeout }
	time.Sleep(lockWaitInterval) // 20ms 轮询，30s 上限
}
```

**为什么不阻塞。** 阻塞式 `flock` 会占住一个 OS 线程，而且没有内建超时；`LOCK_NB` + 轮询才能给调用方一个「30 秒拿不到就告诉模型稍后重试」的出口。

**少见在哪。** Go 标准库没有文件锁；大多数服务直接上 Redis/etcd 分布式锁，或者引第三方库。这里直接 `syscall.Flock`，并用「桶」把锁文件数量钉死在 256——否则一个项目写几千个文件，锁目录就堆几千个空文件，而**清理锁文件本身又很危险**：`unlink` 一个正被持有的锁文件，后来者会 `open` 到新 inode，两边同时以为自己独占。

**代价 / 前提。**
- `flock` 是 advisory 的：`bash` 里的 `rm`、`sed -i`、`>` 重定向完全不守这把锁，由人审兜底。
- 注释口径是「同机跨进程跨副本都串」，前提是这些副本看到的是**同一个文件系统**；本地磁盘上的 `flock` 不跨机器。
- 不同路径可能撞同一桶（1/256），结果是「假串行」——多等一会儿，没有正确性问题。

### 1.2 Redis `INCR`/`EXPIRE` 当跨副本信号量

**病灶。** 委派子代理要限并发。用 Go 的 `chan struct{}` 信号量，只能限制**本进程**：A 副本占满自己的 8 个槽，B 副本即使租户总额度还有空，也会在本进程排队。额度属于租户，不属于进程。

**写法**（`scope.go:218-248`）：

```go
key := "tk:subagents:" + p.TenantID
n, err := s.rdb.Incr(ctx, key).Result()
...
_ = s.rdb.Expire(ctx, key, 30*time.Minute).Err()
if int(n) > maxSub {
	_ = s.rdb.Decr(ctx, key).Err()
	return false, nil
}
return true, nil
```

释放就是 `Decr`；调用方用 `defer store.releaseSubagentSlot(context.WithoutCancel(ctx))`。

**少见在哪。** 不是「Redis 计数」本身，而是**没有 Redis 时自动退回进程内信号量**：

```go
useProcessSem := store == nil || store.rdb == nil
if store != nil { /* Redis 槽 */ }
if useProcessSem {
	select { case sem <- struct{}{}: ...; case <-ctx.Done(): ... }
}
```

单测没有 Redis，仍然能测并发语义；生产有多副本，闸自然落到 Redis。

**代价。** `Incr` 与 `Expire` 是两条命令，不是原子的；进程恰好死在两者之间，会留下一个没有 TTL 的计数键。实现接受这个极小窗口，用 30 分钟的 TTL 兜底（但兜不住「EXPIRE 根本没执行」的那一次）。要绝对干净就得像下面的 Lua 脚本一样合并成一条。

### 1.3 `sync.Map.CompareAndDelete` 按指针身份清理「上一代」

**病灶。** 一场 run 的取消把柄放在进程内注册表 `runID → *runCancel`。崩溃续跑后，新执行者接管同一个 run，注册表里换成了新一代的值。旧 `Run` 的 `defer` 这时才退出——如果它按 key 直接 `Delete(runID)`，会把**新执行者**的取消把柄删掉，之后用户点停止就停不掉。

**写法**（`worker.go:145-150, 493-494`）：

```go
type runCancel struct {
	epoch  int64
	cancel context.CancelFunc
}

rc := &runCancel{epoch: epoch, cancel: cancelRun}
w.runCancels.Store(runID, rc)
defer w.runCancels.CompareAndDelete(runID, rc)
```

`CompareAndDelete(key, value)` 比较的是值相等；这里是 `*runCancel` 指针，所以等于**指针身份**：只有注册表里还是我当时存进去的那个对象，才删得掉。watchdog 判死时也要再核对一次 epoch：

```go
if c, hit := w.runCancels.Load(runID); hit {
	if rc := c.(*runCancel); rc.epoch == epoch {
		rc.cancel()
	}
}
```

**少见在哪。** `CompareAndDelete` 是 Go 1.20 才加的方法，日常代码里很少用；把「指针身份」当**代际令牌**用，比额外维护一个 `map[runID]epoch` 更省。

### 1.4 手写流式 stall 检测：goroutine + done 通道 + timer 手动 Stop

**病灶。** 摘要模型流式返回，provider 卡住时 `stream.Recv()` 会一直阻塞。`context` 的超时不一定能穿透第三方 SDK 的 `Recv`；需要的是「**等不到下一帧**就失败」，而不是「总时长超了」。

**写法**（`compact.go:1002-1060`）：

```go
ch := make(chan recvResult, 1)
done := make(chan struct{})
defer close(done)
go func() {
	for {
		chunk, err := stream.Recv()
		select {
		case ch <- recvResult{chunk: chunk, err: err}:
		case <-done:
			return // 调用方已超时退出：带走 goroutine，不泄漏
		}
		if err != nil { return }
	}
}()

timer := time.NewTimer(firstToken)
defer timer.Stop()
for {
	select {
	case r := <-ch:
		...
		chunks = append(chunks, r.chunk)
		if !timer.Stop() {
			select { case <-timer.C: default: }
		}
		timer.Reset(chunkGap)
	case <-timer.C:
		return nil, errStall
	case <-ctx.Done():
		return nil, ctx.Err()
	}
}
```

**少见在哪。** `Timer.Stop` 之后要**非阻塞地 drain** `timer.C`，否则下一次 `Reset` 可能读到上一次的过期信号——这是 `time.Timer` 的经典坑，很多人只会 `Stop` 不会 drain。另一个细节是 `done` 通道：调用方一旦超时返回，接收 goroutine 必须能被收走，不能永远卡在 `ch <-` 上。

### 1.5 `defer` LIFO 当收尾顺序契约

**病灶。** run 收尾有两件事必须按顺序：先停 watchdog（续租 goroutine），再 `EndRun` 放闸。反过来的话，watchdog 可能在 `EndRun` 把 `runlive` 的 TTL 设成 300s 之后又续回 30s，把已定稿的帧重新变成「可能还活着」。

**写法**（`worker.go:547-579`）：

```go
defer func() {
	_, _, ok, err := w.store.EndRun(context.WithoutCancel(ctx), ...)
	...
}()

leaseCtx, cancelLease := context.WithCancel(ctx)
var wg sync.WaitGroup
wg.Add(1)
go func() { defer wg.Done(); w.watchdog(leaseCtx, sessionID, runID, epoch) }()
defer func() { cancelLease(); wg.Wait() }()
```

`defer` 是 LIFO：后注册的先跑。`EndRun` 先注册，所以最后跑；停 watchdog 的 defer 后注册，所以先跑。`wg.Wait()` 再保证续租 goroutine **完全退出**，而不是「收到 cancel 但还没跑完」。

**少见在哪。** 用 `defer` 的注册顺序表达「收尾依赖图」，而不是写一个显式的 `shutdown()` 函数。代价是读代码时必须记住 LIFO——所以这里必须配注释，否则下一个人重排两行就破坏契约。

## 2. HTTP 与子进程

### 2.1 手写 SSE：`http.Flusher` + `Last-Event-ID` + 注释心跳帧

**病灶。** 前端要边生成边显示，但拉模式（轮询 `frames`）有一拍延迟。SSE 是「同一帧面的第二种运输方式」：不新增帧形状，只换运输。

**写法**（`server.go:1112-1180`）：

```go
w.Header().Set("Content-Type", "text/event-stream")
w.Header().Set("Cache-Control", "no-cache")

write := func(block string) bool {
	if _, err := w.WriteString(block); err != nil {
		return false // 客户端已断开，SSE 无错误语义，直接退出
	}
	w.Flush()
	return true
}

write(fmt.Sprintf("id: %d\nevent: frame\ndata: %s\n\n", f.EventOffset, b))
```

- `id:` 就是轮询路的 `eventOffset`，断线重连带 `Last-Event-ID: N` 从 `N` 之后续读——**不是流另认一套游标，是同一游标的第二种读法**。
- 静默期每 15 秒写一行 `: ping`。冒号开头是 SSE 注释帧，`EventSource` 自动忽略，但能防止中间层把空闲连接掐掉。
- run 结束发一条 `event: terminal` 后关闭；`runlive` 键不存在（从没存在或 TTL 过期，故意不区分）发一条 `event: gone` 后关闭。SSE 没有错误语义，客户端靠「断了且没收到 terminal」知道该重连。

**少见在哪。** 没有引 SSE 库，直接用 `w.WriteString` + `w.Flush` 拼帧；并且把「流」和「拉」的游标统一成同一个整数。另一个细节是心跳间隔用 `var` 而不是 `const`：

```go
var (
	sseTailInterval      = 150 * time.Millisecond
	sseHeartbeatInterval = 15 * time.Second
)
```

单测可以调小它验证心跳，生产值不动。

**代价。** `write` 一旦返回 `false` 就退出；但 SSE 无法告诉客户端「服务端内部错了」，只能断流。另外循环里 `time.After(sseTailInterval)` 每次分配一个 timer（见 §5.1）。

### 2.2 Redis Stream `XREAD BLOCK` 当长轮询

**病灶。** 变更事件（会话被删、工作区改名）要推给在线客户端。WebSocket 要额外协议和连接管理；纯轮询又浪费。

**写法**（`events.go:114-150`）：

```go
lastID := strings.TrimSpace(c.GetHeader("Last-Event-ID"))
if lastID == "" {
	lastID = "$" // 只推新事件
}
for {
	res, err := s.store.rdb.XRead(ctx, &redis.XReadArgs{
		Streams: []string{key, lastID},
		Count:   100,
		Block:   10 * time.Second,
	}).Result()
	if err != nil {
		if errors.Is(err, context.Canceled) || errors.Is(err, context.DeadlineExceeded) {
			return // 客户端断开 / 请求收尾
		}
		if errors.Is(err, redis.Nil) {
			continue // BLOCK 超时：本轮无事件，继续挂读
		}
		...
	}
	for _, msg := range res {
		for _, e := range msg.Messages {
			fmt.Fprintf(w, "id: %s\ndata: %s\n\n", e.ID, b)
			lastID = e.ID
		}
	}
	flusher.Flush()
}
```

**少见在哪。**
- 没有 `Last-Event-ID` 时用 Redis 的 `$` 游标——只收「从现在开始」的新事件，历史对刚 reconcile 完的客户端没有意义。
- `XREAD BLOCK` 超时返回的是 `redis.Nil`，不是错误；把它当「继续挂读」。
- 写入端用 `MaxLen: 1000, Approx: true` 做近似截断：流是有界的易失通知设施，不是真源；丢了就靠客户端全量重拉。
- 多副本下任何副本写的事件，任何副本的连接都读得到，因为共享同一个 Redis。

### 2.3 `io.Writer` 截断仍返回 `len(p)`；`exec.Cmd.WaitDelay` 收尸

**病灶一：管道写满/对端退出。** `bash` 输出可能是几百 MB。如果直接把 `cmd.Stdout` 接到一个「超过 32KB 就返回 error」的 writer，`os/exec` 会关掉管道，子进程收到 `SIGPIPE` 提前死掉——我们只是想截断展示，不想杀命令。

**写法**（`bash.go:37-56`）：

```go
func (w *capWriter) Write(p []byte) (int, error) {
	if w.buf.Len() >= w.cap {
		w.truncated = true
		return len(p), nil // 丢弃，但报告「全收」
	}
	room := w.cap - w.buf.Len()
	if len(p) > room {
		w.buf.Write(p[:room])
		w.truncated = true
		return len(p), nil
	}
	return w.buf.Write(p)
}
```

超过帽子的字节丢掉、置 `truncated`，但 `Write` 返回 `len(p), nil`：对 `os/exec` 来说「写成功了」，管道继续流动，命令继续跑。最后在结果文本里补一句「超 32 KB 已截断，把内容写进文件再读」。

**病灶二：孙进程占着 stdout。** `exec.CommandContext` 在 context 取消后会 kill 直接子进程，但如果有孙进程继承了 stdout/stderr，`cmd.Wait()` 会一直等 I/O 管道关闭，迟迟不返回。

**写法**（`bash.go:104`）：

```go
cmd.WaitDelay = 3 * time.Second
```

Go 1.20 加的字段：context 取消后，等这么久还收不干净 I/O，就强制关闭管道并返回 `ErrWaitDelay`。

**少见在哪。** 两个都是「知道契约边界」的写法：`io.Writer` 的返回值语义、`os/exec` 的收尸语义。大多数代码只写 `capWriter` 的截断，不会处理 SIGPIPE；也不会用 `WaitDelay`。

### 2.4 把 `PATH` 按真实路径过滤成安全边界

**病灶。** 引擎把宿主 `PATH` 原样传给 `bash`。宿主里有 `~/.pyenv/shims/python3`，`exec` 找得到，但 seatbelt 围栏不允许读 `~` → 执行时 `Operation not permitted`。模型会把它当成路径写错，换着路径重试，浪费一轮上下文。

**写法**（`subprocesspath.go:84-118`）：

```go
for _, seg := range strings.Split(raw, sep) {
	seg = strings.TrimSpace(seg)
	if seg == "" { continue }
	if _, err := filepath.EvalSymlinks(seg); err != nil {
		continue // 目录不存在 / 悬空链接：它指向的可执行文件本来也跑不了
	}
	real := sandboxRealPath(seg)
	allowed := false
	for _, root := range realRoots {
		if pathWithin(root, real) { allowed = true; break }
	}
	if !allowed || seen[real] { continue }
	seen[real] = true
	out = append(out, real)
}
```

同时把租户工具根 `<tenant>/tools/*/bin` 放在 `PATH` 最前面，让「租户装的东西」抢过宿主同名命令。围栏读根与 `PATH` 过滤**共用同一份** `sandboxReadRoots`——抄两份就会漂，漂回去又是「PATH 里有、围栏读不到」。

**少见在哪。** 大多数人把 `PATH` 当环境变量；这里把它当**安全边界**的一部分，且用真实路径（`EvalSymlinks`）对齐 seatbelt 的 `subpath` 匹配。`/bin` 在 macOS 上是指向 `/usr/bin` 的符号链接，两者都放行不会放宽权限，但去重时会被解析成同一段。

## 3. 抽象与装配

### 3.1 编译期接口锚 + 故意不嵌 Base

**写法一：普通锚。** 每个装饰器后面都有一行：

```go
var _ adk.ChatModelAgentMiddleware = (*overflowGuard)(nil)
var _ model.BaseChatModel = (*guardModel)(nil)
```

接口一缺方法，编译不过。这是常见写法，真正少见的是**故意不嵌 Base**。

**写法二：绊线**（`agentlog.go:22-23`）：

```go
// 编译期锚：接口九方法缺一不可。
var _ adk.ChatModelAgentMiddleware = (*AgentLogHandler)(nil)

type AgentLogHandler struct {
	seq atomic.Int64
}
```

`adk.ChatModelAgentMiddleware` 有一个 `*adk.BaseChatModelAgentMiddleware` 可以嵌入，嵌了就自动获得所有方法的空实现——将来接口加一个新方法，代码照样编译，新钩子被**静默漏掉**。这里九个方法全部手写、**不嵌 Base**：接口一长新方法，编译失败，逼人当场补观测。这是把「编译期锚」从「检查我实现了」变成「检查我没漏实现」——方向反过来。

**代价。** 接口每加一个方法，这个文件就要多一个样板方法（哪怕只打一行日志）。对一个观测架来说，这是有意用样板换「不漏」。

### 3.2 在 `BeforeAgent` 里替换 `Tools` 切片，用注册顺序拼装饰器栈

**病灶。** 要在工具执行前后加账本、加计划模式拒绝、加错误回注、加 PII 打码，但不能改每个工具的实现，也不能漏掉运行时才追加的 MCP 工具和委派工具。

**写法。** 中间件在 `BeforeAgent` 里原地替换 `runCtx.Tools`：

```go
func (h *planGuardHandler) BeforeAgent(ctx context.Context, runCtx *adk.ChatModelAgentContext) (context.Context, *adk.ChatModelAgentContext, error) {
	for i, t := range runCtx.Tools {
		if inner, ok := t.(tool.InvokableTool); ok {
			runCtx.Tools[i] = &planGuardTool{inner: inner}
		}
	}
	return ctx, runCtx, nil
}
```

`planGuardTool` 只覆写 `InvokableRun`，`Info` 透传。账本层同理：`journalTool` 把整个池换成记账壳。

**顺序语义是最容易看漏的部分。** eino 按注册顺序应用 `BeforeAgent`，**后注册的包在更外层**。所以：

- `planGuardHandler` 必须 append 在 `journalWrapHandler` **之后** → 运行时是 `guard(journal(tool))`，拒绝发生在记账与执行之前（被拒的调用不该留 intent）。
- `journalWrapHandler` 注册在链尾 → 它看到的 `runCtx.Tools` 已经包含一手池、MCP 工具、委派工具，一次遍历包全。
- 子代理入口快照在更早的 handler 里做，拿到的是**未包壳**工具——子代理内部调用天然不记账；`callerNameFrom` 是第二道闸。

**少见在哪。** 不是「装饰器」本身，而是用**注册顺序**表达嵌套顺序，并用「谁必须在谁之后」的注释把这条隐含契约钉住。框架没有显式 `Use(outer, inner)` API 时，这是最省事的做法，也最容易在重构时被排错。

### 3.3 `context` 当依赖注入容器 + `context.WithoutCancel` 做收尾写入

**写法一：私有空 struct 当 key。** 项目里有 22 处 `context.WithValue`，key 全是未导出的空 struct：

```go
type planGateKey struct{}

func withPlanGate(ctx context.Context, g *planGate) context.Context {
	return context.WithValue(ctx, planGateKey{}, g)
}

func planGateFrom(ctx context.Context) *planGate {
	g, _ := ctx.Value(planGateKey{}).(*planGate)
	return g
}
```

同样的还有 `journalTarget`、`fileBaseline`、`subagentWire`、`foldBox`、`skillBox`、`taskBox`、`noteBox`、`workspaceRef`。它们都是**一场 run 的生命周期**：run 起手塞进去，工具/中间件从 ctx 取，run 结束自然消失，不落库、不跨 run 共享、无清理负担。

**写法二：`context.WithoutCancel`。** 用户点停止后，run 的 ctx 被 cancel；但收尾还要写 PG/Redis——「已配对的工具行」不能因为取消而丢。于是：

```go
_, _, ok, err := w.store.EndRun(context.WithoutCancel(ctx), sessionID, runID, epoch, status, ...)
```

`WithoutCancel` 保留 ctx 上的所有 value，但去掉 deadline 和 cancel 信号。项目里有 10 处，集中在收尾写入：`EndRun`、`AbandonClaim`、`releaseSubagentSlot`、预留额度释放。

**少见在哪。** `context.WithValue` 本身很常见；不常见的是**把它当 run 级 DI 容器**，塞的是可变对象（`foldBox`、`fileBaseline`、`noteBox`），不是只读配置。另一个是 `context.WithoutCancel`（Go 1.21 加）——很多人遇到「收尾写不进去」的第一反应是 `context.Background()`，那会丢掉 run 作用域里的所有值；`WithoutCancel` 才是正解。

**代价。** ctx 里的东西没有编译期类型检查，取不到就是 nil；所以每个 `xxxFrom` 都要处理 nil。ctx 也容易被当成「什么都能塞」的袋子，项目用私有 key + 成对的 `withXxx`/`xxxFrom` 把它约束住。

### 3.4 `//go:embed` + 包级 `var` 初始化时 `panic`

**写法**（`internal/config/catalog.go:13-14, 86-96`）：

```go
//go:embed provider-catalog.json
var catalogJSON []byte

var providerPresets = mustPresets()

func mustPresets() []ProviderPreset {
	presets, err := loadPresets()
	if err != nil {
		panic(err) // 目录坏了直接 panic，不留到运行期
	}
	return presets
}
```

厂商目录在编译时打进二进制，运行时零文件依赖；包初始化时解析一次，失败就 `panic`，进程起不来。这和项目里 `log.Fatalf` 的 fail-fast 口径一致：配置手误应该在启动时炸，而不是等第一个请求才 500。

**少见在哪。** `go:embed` 本身不罕见；把它和「包级 `var` + 初始化 panic」组合成「编译期资产 + 启动期校验」的写法，在业务代码里不算多。注意这不适合会热更新的数据——热更新要走文件/DB，不能嵌。

## 4. 存储与一致性

### 4.1 `RowsAffected == 0` 当围栏；Redis Lua 脚本做多键原子 CAS

这是全仓库最值得看的一组「多副本一致性」写法，核心思想一句话：**闸放数据库/Redis，不放进程**；进程内只留快照。

#### 4.1.1 DB 行的 `UPDATE ... WHERE epoch` 就是 CAS

**病灶。** 多副本下，一场 run 同一时刻只能有一个执行者。用进程内互斥量只能管本进程；用「先 SELECT 再判断再 UPDATE」又有检查与写之间的缝。

**写法**（`plangate.go:157-166`）：

```go
res := s.db.WithContext(ctx).Exec(
	`UPDATE runs SET plan_mode = ? WHERE id = ? AND lease_epoch = ?`, on, runID, epoch)
if res.Error != nil { return res.Error }
if res.RowsAffected == 0 {
	return errJournalGateLost // 本执行者已不是当前令牌持有者
}
return nil
```

`RowsAffected == 0` 不是错误，是**「我这一代已经失效」**的信号。续约同理（`store.go:835-842`）：

```sql
UPDATE runs SET lease_until = now() + make_interval(secs => ?)
 WHERE id = ? AND session_id = ? AND status = 'running' AND lease_until > now()
   AND lease_epoch = ?
```

其中 `lease_until > now()` 是「过期不可复活」：少了它，一个「已过期但还没被清扫」的 run 会被迟到的续约救活，旧执行者手里的 turn 会被定稿。

接管（`ClaimResume`，`store.go:874`）在**一笔事务**里 `SELECT ... FOR UPDATE` → 四态判定 → `epoch+1` → 续租约 → 读账本。提交即「获得这一代令牌」。

#### 4.1.2 Redis 帧写口用 Lua 脚本校验令牌

**病灶。** 帧写进 Redis list。旧执行者在被接管后如果还能 `RPUSH`，就会把上一代的 delta 混进新执行者的现场。

**写法**（`redisstore.go:66-72`）：

```lua
if redis.call('GET', KEYS[2]) ~= ARGV[2] then  -- KEYS[2]=tk:runepoch，ARGV[2]=本执行者 epoch
  return 0
end
redis.call('RPUSH', KEYS[1], ARGV[1])          -- KEYS[1]=tk:runlive，ARGV[1]=帧 JSON
return redis.call('LLEN', KEYS[1])             -- 返回新帧的 eventOffset
```

Go 侧：

```go
var appendFrameScript = redis.NewScript(`...`)

n, err := appendFrameScript.Run(ctx, s.rdb,
	[]string{keyRunlive(runID), keyRunepoch(runID)}, string(frameJSON), epoch).Int64()
```

四个脚本各管一段：`acquire`（建两键 + start 帧 + 出生令牌，一条 Lua = 原子，不会留半个键）、`renew`（先验令牌再 `PEXPIRE` 两键）、`appendFrame`（验令牌 + `RPUSH` + 返回 `LLEN` 当 offset）、`seedResume`（换新令牌 + 丢掉旧 runlive + 压 resume 帧）。

**少见在哪。** 两点：

1. **`RowsAffected == 0` 当布尔 CAS 结果**，而不是「先查再改」。这把「检查 + 写」压成一条 SQL，检查与写在同一个原子步骤里。
2. **在 Go 代码里内嵌 Lua**，把「多键一起改」变成原子操作；并且 Lua 脚本自己承担令牌校验——不是 Go 先 GET 再 RPUSH，那中间又有缝。

**代价。** 逻辑分散在 SQL / Lua / Go 三处，读代码必须同时看三边；`RowsAffected == 0` 的语义要靠命名（`errJournalGateLost`）和注释说清，否则下一个人会把它当「没找到行」处理。

### 4.2 ULID 当可排序主键（以及它不保证同毫秒单调）

**写法**（`pgstore.go:565-566`）：

```go
func newRowID(prefix string) (string, error) {
	id, err := ulid.New(ulid.Now(), rand.Reader)
	if err != nil { return "", err }
	return prefix + id.String(), nil
}
```

主键形如 `s_01M5...`、`r_01M5...`、`m_01M5...`。ULID 前 48 位是毫秒时间戳，后 80 位是随机数，字符串字典序≈时间序。所以查询可以直接：

```sql
ORDER BY run_id, seq
```

不用额外 `created_at` 列也能按时间排；`run_id` 是 ULID，字典序即 run 时序；`seq` 在同一 run 内再排序（`0` = 摘要行排最前）。笔记同理：`ORDER BY kind, id`——agent 笔记先于 user 笔记，各自按 ULID 创建序。

**少见在哪。** 用「字符串主键的字典序」承担时间排序，省一列索引；B-tree 插入也更局部（新 ID 总在末尾）。

**必须注意的边界。** 这里用的是 `ulid.New(ulid.Now(), rand.Reader)`，**不是** `ulid.Make()`。`ulid.Make()` 用带单调熵的全局源，同一毫秒内也严格递增；显式传 `rand.Reader` 的版本在同一毫秒内是**随机序**。所以：

- 跨 run 的排序只保证**毫秒级**；同一毫秒创建的两个 run，先后是随机的。
- 同一 run 内的行序靠 `seq`，不靠 `run_id` 的尾部随机位。
- 如果哪天需要「同一毫秒内也严格有序」，要换 `ulid.Make()` 或加自增列——不要假设现在的主键有这个性质。

### 4.3 预留额度事务 + 延迟测量回调

**病灶。** 上传/写文件前要判租户存储配额。两个并发上传各自看到「目录还差 100MB」，都放行，结果一起超帽。而且「数目录大小」很贵，不能每次请求都walk 一遍。

**写法**（`storage_reserve.go:20-48`）：

```go
func (s *Store) ReserveStorage(ctx context.Context, tenantID string, adding, maxBytes int64, used func() int64) (func(), error) {
	err := s.db.WithContext(ctx).Transaction(func(tx *gorm.DB) error {
		tx.Exec(`INSERT INTO tenant_storage (tenant_id, reserved) VALUES (?, 0) ON CONFLICT (tenant_id) DO NOTHING`, tenantID)

		var reserved int64
		tx.Raw(`SELECT reserved FROM tenant_storage WHERE tenant_id = ? FOR UPDATE`, tenantID).Scan(&reserved)

		var have int64
		if used != nil { have = used() } // 在行锁内才数目录
		if reserved+adding+have > maxBytes { return errStorageQuota }

		return tx.Exec(`UPDATE tenant_storage SET reserved = ? WHERE tenant_id = ?`, reserved+adding, tenantID).Error
	})
	...
	return func() {
		_ = s.db.WithContext(context.WithoutCancel(ctx)).Exec(
			`UPDATE tenant_storage SET reserved = GREATEST(reserved - ?, 0) WHERE tenant_id = ?`, adding, tenantID).Error
	}, nil
}
```

三个细节：

1. `INSERT ... ON CONFLICT DO NOTHING` 先保证行存在，再 `SELECT ... FOR UPDATE` 拿行锁——否则第一次预留时没有行可锁。
2. **`used()` 在行锁内调用**。数目录很贵，但必须和「读 reserved」在同一个临界区里，否则两次测量之间别人又写入了。
3. 释放用 `GREATEST(reserved - ?, 0)`，防止并发/重复释放把计数打成负数；并且用 `WithoutCancel`，保证 run 取消后预留也能放开。

**少见在哪。** 把「昂贵的外部测量」做成回调参数，延迟到锁内才执行——而不是在外面先算好再传进来（那会有一整段窗口）。同时用「预留 + 释放」两段式，把「还没落盘的字节」也算进配额。

## 5. 安全与沙箱

### 5.1 多版本 AES-GCM 封存 + 密钥轮换

**病灶。** 租户的模型 API key 要落库，不能明文。用 `TAKO_JWT_SECRET` 派生密钥加密，听起来可以；但**轮换登录密钥**会把所有已存的租户密钥变成解不开的乱码。

**写法**（`secretseal.go`）：

```go
const (
	seal1Prefix = "seal1:" // 用 TAKO_JWT_SECRET 派生
	seal2Prefix = "seal2:" // 用独立的 TAKO_DATA_KEY 派生
)

func keyFromEnv(name string) ([]byte, bool) {
	raw := os.Getenv(name)
	if len(raw) < 32 { return nil, false }
	sum := sha256.Sum256([]byte(raw))
	return sum[:], true // AES-256 要 32 字节
}

func encryptSecret(prefix string, key []byte, plain string) (string, error) {
	block, _ := aes.NewCipher(key)
	gcm, _ := cipher.NewGCM(block)
	nonce := make([]byte, gcm.NonceSize())
	io.ReadFull(rand.Reader, nonce)
	return prefix + base64.RawStdEncoding.EncodeToString(
		gcm.Seal(nonce, nonce, []byte(plain), nil)), nil
}
```

解密按前缀选密钥族，再依次试当前密钥和 `*_PREVIOUS`：

```go
case strings.HasPrefix(stored, seal2Prefix):
	return unsealWith(stored, seal2Prefix, "TAKO_DATA_KEY", "TAKO_DATA_KEY_PREVIOUS")
case strings.HasPrefix(stored, seal1Prefix):
	return unsealWith(stored, seal1Prefix, "TAKO_JWT_SECRET", "TAKO_JWT_SECRET_PREVIOUS")
```

**少见在哪。**
- **密文自带版本前缀**：`seal2:` 告诉解密方「用 DATA_KEY 这一族」，而不是靠调用方记得这是哪一代密钥。轮换时只需要换 `TAKO_DATA_KEY`，旧的 `seal2:` 密文因为 `..._PREVIOUS` 还在，仍然打得开。
- **`base64.RawStdEncoding`**（无 padding）而不是 `StdEncoding`：密文更短，且不会出现 `=` 在 URL/日志里被转义的问题。
- **`nonce || ciphertext` 拼成一个串**，取的时候按 `gcm.NonceSize()` 切开；没有单独的 nonce 列。
- **密钥是 `sha256(env)`**：允许运维填任意长度的口令，统一派生到 32 字节，不要求正好是 32 字节的十六进制。

**代价。** 没有 KMS/信封加密，密钥在进程环境里；能读进程环境的人能解密所有租户密钥。这是「开发期够用、上线要换 KMS」的形态。

### 5.2 `sync.Once` 真跑一次沙箱探测 + 手写 seatbelt S 表达式

**病灶一：`LookPath` 成功 ≠ 沙箱可用。** macOS 上 `sandbox-exec` 存在，但 seatbelt 可能拒绝 apply。这时命令会以普通非零退出结束，调用方却以为「已经隔离」——最危险的静默失败。

**写法**（`sandbox.go:23-39`）：

```go
func sandboxAvailable() bool {
	sandboxProbe.once.Do(func() {
		path, err := exec.LookPath("sandbox-exec")
		if err != nil { return }
		cmd := exec.Command(path, "-p", "(version 1)(allow default)", "/bin/echo", "ok")
		out, err := cmd.CombinedOutput()
		sandboxProbe.ok = err == nil && strings.Contains(string(out), "ok")
	})
	return sandboxProbe.ok
}
```

不是「看文件在不在」，而是**真的 apply 一次**一个最小 profile、跑 `/bin/echo ok`，看输出。`sync.Once` 保证只跑一次，结果缓存到进程退出。探测失败时，需要沙箱的调用方直接拒绝启动（fail closed），不退回裸 bash。

**病灶二：围栏 profile 的路径匹配。** seatbelt 的 `subpath` 走**真实路径**，而 macOS 的 `/tmp` 是指向 `/private/tmp` 的符号链接。如果围栏根写成 `/tmp/xxx`，`(subpath "/tmp/xxx")` 匹配不上真实路径，agent 会连自己项目里的文件都读不到。

**写法**（`sandbox.go:62-90`）：

```go
root = sandboxRealPath(root) // EvalSymlinks + Abs

return fmt.Sprintf(`(version 1)
(deny default)
(allow process-exec)
(allow process-fork)
(allow signal (target same-sandbox))
(allow sysctl-read)
(allow mach-lookup)
(allow file-ioctl)
(allow file-read-metadata)
(allow network-outbound)
(allow file-read* (literal "/"))
(allow file-read*%s)
(allow file-read* (subpath "/private/etc/ssl"))
%s(allow file-read* file-write* (subpath %q))
(deny file-read-data (literal "/etc/passwd") (literal "/private/etc/passwd"))
`, system.String(), extra.String(), root)
```

读是「系统白名单 + 项目根 + 已 `use_skill` 的技能根」，写只在项目根；`/etc/passwd` 显式拒绝；出站网络开、入站不开。

**少见在哪。** 在 Go 里动态拼 macOS seatbelt 的 S 表达式，本身就是小众技能；更少见的是「探测要真跑」这条纪律——大多数 `LookPath` 式探测都会把「存在」当「可用」。

**一个使用时序的坑。** `sandboxWrap` 是重建命令：

```go
func sandboxWrap(cmd *exec.Cmd, root string) *exec.Cmd {
	if root == "" { return cmd }
	args := append([]string{"-p", sandboxProfile(root, nil)}, cmd.Args...)
	return exec.Command("sandbox-exec", args...)
}
```

它只保留 `Args`；`Dir`、`Env`、`Stdin` 等都是新的空值。所以必须在 wrap **之后**再设 `cmd.Env`/`cmd.Dir`——项目里的 MCP 调用正是这么做的（`mcp.go:118` 之后才 `cmd.Env = ...`）。

## 6. 契约与数据形状

### 6.1 struct 字段顺序 = JSON 字节序契约

**写法**（`auth.go:42-46`）：

```go
type envelope struct {
	Code    int    `json:"code"`
	Message string `json:"message"`
	Data    any    `json:"data"`
}
```

`encoding/json` 按 struct 字段声明顺序输出，所以响应字节恒为 `{"code":...,"message":...,"data":...}`。这不是风格问题，是**契约**：前端拦截器、契约测试、验收脚本都按这个字节序断言。字段顺序一改，`contract_test.go` 和 `scripts/acceptance/expected.json` 会红。

同样的写法出现在事件帧（`streamEvent` 的 `Seq/Type/ID/At`）、各种响应体里。项目把「字段顺序」写进 doc/40 和 19v6-01，再用测试钉住——**隐式契约显式化**。

### 6.2 `*bool` 区分「没传」与 `false`

**病灶。** 一个 JSON 开关，客户端可能不传（用服务端默认）、也可能显式传 `false`。用 `bool` 接，两者都是 `false`，分不开。

**写法**（`plangate.go:174-185`）：

```go
var req struct {
	Tool     string `json:"tool"`
	PlanMode *bool  `json:"planMode"`
}
...
planMode := true // 缺省值
if req.PlanMode != nil {
	planMode = *req.PlanMode
}
```

指针为 `nil` = 字段没出现；非 `nil` = 客户端显式给了值（可能是 `false`）。这是 Go JSON 里表示「三态」最轻的做法；更重的做法是 `json.RawMessage` 或自定义 `UnmarshalJSON`。

## 7. 测试里的小把戏

### 7.1 全仓库唯一一处泛型

```go
func mustSearchToolInfo[T any](t *testing.T, name, desc string) *schema.ToolInfo {
```

在 4.8 万行非测试 + 测试代码里，这是唯一一个带类型参数的函数（`grep` 过 `func X[T ...]` 与 `type X[T ...]`）。它不是框架代码，是测试辅助：给不同输入类型造同一个 `*schema.ToolInfo`，省掉每个测试各写一遍。

这说明一件事：**这个项目基本不用泛型**。业务代码靠接口 + `any` + 具体类型；泛型只在「测试工厂」这种纯重复劳动的地方出现。不是不能用，是没有非它不可的场景。

### 7.2 `reflect` 比函数指针、查字段是否存在

**比函数身份**（`agents_test.go:87, 513`）：

```go
if reflect.ValueOf(inherit).Pointer() == reflect.ValueOf(base).Pointer() {
	t.Fatal("...")
}
```

用来断言「继承后的工具池不是同一个函数对象」——如果装配代码偷懒直接返回了 `base`，指针相同，测试红。比比较输出内容更直接。

**查字段是否存在**（`skills_test.go:210`）：

```go
field, ok := reflect.TypeOf(SkillRow{}).FieldByName("Valid")
```

用来断言某个字段**已经被删掉**。普通测试只能断言「值是多少」；要断言「这个字段不该存在」，就得靠反射查类型。

**调小间隔的 `var`**（`server.go:1082-1084`）：

```go
var (
	sseTailInterval      = 150 * time.Millisecond
	sseHeartbeatInterval = 15 * time.Second
)
```

不是 `const`，单测可以临时改小，验证心跳与 tail 行为。这是「给测试留缝」的常见做法，但值得记一笔：生产代码里出现非 `const` 的时间间隔，多半是为了可测性。

## 8. 看着常见、但这里用得很讲究的几处

这几处不算「少见语法」，但用法值得对照：

- **`min` 内建函数**（Go 1.21）：`window - min(window/5, 16384)`（`compact.go:142`）。项目直接用它算压缩触发线，没有自己写 `if a < b`。
- **`strings.CutPrefix`**（Go 1.20）：`bearer()` 里解析 `Bearer ` 前缀（`auth.go:655`）。比 `HasPrefix` + `TrimPrefix` 少一次扫描。
- **`errors.Is` 哨兵错误跨层**：`errJournalGateLost`、`errLockTimeout`、`ErrSessionNotFound`、`ErrSweepNotClaimed`。上层按哨兵分支，不拆错误字符串。
- **`time.NewTicker` + `defer t.Stop()`**：watchdog（`worker.go:1067`）与清扫器（`archive_sweep.go:297`）都是这个形状。ticker 不能泄漏，`Stop` 必须在 defer。
- **`exec.CommandContext` + `cmd.WaitDelay` + 输出帽**：见 §2.3，三个一起才完整。

## 9. 不建议照抄的三处

这一节是「仓库里存在、但有代价」的写法。照抄前先看代价。

### 9.1 循环里的 `time.After`

`server.go:1167`：

```go
select {
case <-ctx.Done():
	return
case <-time.After(sseTailInterval):
}
```

每次循环分配一个 timer。Go 1.23 起未触发的 timer 可以被 GC，不再是经典意义的「泄漏到触发为止」，但仍有分配开销。150ms 的 tail 无所谓；如果间隔是分钟级、循环又高频，应该用 `time.NewTimer` + `Reset`，或者在外面复用一个 timer。

### 9.2 对第三方错误文本做字符串手术

`tools.go:69-83` 剥掉 eino 的外壳：

```go
for _, prefix := range []string{"[LocalFunc] ", "[EnhancedLocalFunc] "} {
	if strings.HasPrefix(msg, prefix) {
		if i := strings.Index(msg, ", err="); i >= 0 {
			msg = msg[i+len(", err="):]
		}
		break
	}
}
```

它依赖 eino v0.9.21 的固定错误格式；库升级改了格式，皮就剥不掉。代码里有兜底（剥不出来原文照发，不误伤），也有 fixture 测试钉住。**可以学「剥之前先想好剥不掉的兜底」，不要学「依赖库的错误字符串格式」**——能改库就用结构化错误，改不了才做字符串手术。

### 9.3 `sandboxWrap` 重建命令会丢字段

见 §5.2 末尾。它只保留 `Args`，`Env`/`Dir`/`Stdin` 都不继承。当前调用方在 wrap 之后才设 `Env`，所以没事；如果哪天有人在 wrap 之前设了 `Dir`，会静默丢失。用这种「重建 `exec.Cmd`」的包装时，要么显式拷贝所有字段，要么在注释里钉死「wrap 后设」。

## 10. 一句话收口

这份仓库的 Go 风格不是「炫技型」，而是**约束型**：能用标准库就不引库（`flock`、SSE、AES-GCM、ULID），能用数据库原子性就不靠进程内状态（`RowsAffected`、Lua 脚本、行锁），能用编译期检查就不靠人记（接口锚、`go:embed` + 启动 panic），能用真实路径就不靠字符串前缀（seatbelt、`PATH` 过滤）。

所以「少见」的不是语法，而是这些约束被写成了**可执行的检查**：编译失败、测试红、启动 panic、`RowsAffected == 0`、`sync.Once` 探测失败——每一种都把「下一个人可能忘」变成了「机器不会忘」。
