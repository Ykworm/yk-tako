**2026-10-02 二次修订（改纯拉模型）**：推翻「一条 message 所有 delta 同号」→ 每个 delta 独占 `eventOffset`；据此**删掉 SSE `stream` 端点，改为纯轮询拉取**（`runlive` 拉生成中的帧 + `runlog` 拉定稿历史）。理由：每 delta 独占号后 `eventOffset` 的唯一归宿就是续传游标，与其让流认游标或维护「挂流+拉取双路合并」，不如让 `runlive` 直接成为拉取端点、删掉流。无长连接、无推送、无 heartbeat。
> **【2026-10-18 翻案，doc/31】**SSE 回来了，但**只翻半边**：b2 的核心论证（`eventOffset` 只有一个归宿、不新增游标抽象、不搞两路状态合并）全部继续成立——流端点的 `id` 就是同一 `eventOffset`，消费逻辑（reconcile）只有一份。翻掉的只是「删掉流」这个结论：流被重新定位为**同一帧面的第二种运输方式**（动机：API 面通用流式，外部消费方不该各自抄轮询样板），拉是正确性、流是优化，四 API 零改动。心跳随流回来（纯拉无连接可掐，流有）。

**2026-10-02 三次修订（单批上限 + 初始游标窗口化）**：`runlog` 永久增长（compact 压的是 `model_history`，不动 `runlog`），所以「新 tab 游标 = 0 = 全量重拉」在长会话下是**无界请求**。改法**不加端点、不加索引、不加请求参数**：两个拉取端点统一加**单批上限 `W`**（`LRANGE key N N+W-1`），客户端初始游标改取 `max(0, 高水位 - 窗口)`——高水位本来就由 session 状态端点返回。又因 `runlogOffset` **永久有效**，往回拨游标翻更早的历史同样合法。

**2026-10-03 四次修订（REST 化端点形状）**：四个 API 的**路径**重排为资源式——
