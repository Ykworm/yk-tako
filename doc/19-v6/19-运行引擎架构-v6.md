> **本文只写第一步**：跑通最小闭环所需的四个 API 的最简契约。骨架、组件、用例全集——不在本文，后续 loop 各自成文。**没有「明确不做」清单**：范围只在 §0 正面声明，其余一律「需要时照本文通道扩、不预留字段」。
>
> **2026-10-02 二次修订（改纯拉模型）**：推翻「一条 message 所有 delta 同号」→ 每个 delta 独占 `eventOffset`；据此**删掉 SSE `stream` 端点，改为纯轮询拉取**（`runlive` 拉生成中的帧 + `runlog` 拉定稿历史）。理由：每 delta 独占号后 `eventOffset` 的唯一归宿就是续传游标，与其让流认游标或维护「挂流+拉取双路合并」，不如让 `runlive` 直接成为拉取端点、删掉流。无长连接、无推送、无 heartbeat。
>
> **2026-10-02 三次修订（单批上限 + 初始游标窗口化）**：`runlog` 永久增长（compact 压的是 `model_history`，不动 `runlog`），所以「新 tab 游标 = 0 = 全量重拉」在长会话下是**无界请求**。改法**不加端点、不加索引、不加请求参数**：两个拉取端点统一加**单批上限 `W`**（`LRANGE key N N+W-1`），客户端初始游标改取 `max(0, 高水位 - 窗口)`——高水位本来就由 `GET /api/session` 返回。又因 `runlogOffset` **永久有效**，往回拨游标翻更早的历史同样合法。
>
> 术语：**message** = 一条对话消息（`role=user`/`assistant`）；**run** = 一次执行，消费一条 user message、产出一条 assistant message；**session** = 服务端登记的资源。没有合并语义，没有 inbox，没有跨 client 同步。

## 概念解释

全文反复出现的词，先在这里钉死：

| 概念 | 是什么 |
|---|---|
| **session（会话）** | 服务端登记的资源。首条消息投递时含铸；未登记一律 404。没有跨 client 同步。 |
| **message** | 一条对话消息，`role` 区分：用户投递的是 `user`，模型产出的是 `assistant`。`messageId` 仅 user 消息有、客户端生成、请求前就有，不参与排序。 |
| **run** | 一次执行。本步：消费一条 user message、产出一条 assistant message。同一 session 同时最多一场（闸保证）。 |
| **帧（frame）** | `runlive` 列表里的一项（一个 JSON），描述一场 run 的一个事件。本步三种：`start` / `delta` / `terminal`。**不是 SSE `data:`，是拉取响应里的数组元素**。 |
| **eventOffset** | `runlive` 的游标：**run 内序号**，`start`=1、每 delta +1、`terminal` 占末。拉 runlive 用它（`LRANGE runlive:{run} N N+W-1`）。定稿、runlive 过期后即失效，**不是历史地址**。 |
| **runlogOffset** | `runlog` 的游标：**session 内全局序号**，跨 run 单调，每条定稿记录占一个，永久有效。`GET /api/session` 返回它的高水位、`GET /api/runlog` 拿它当游标。**永久有效 ⇒ 双向合法**：往前拨补新、往回拨翻旧。初始值取 `max(0, 高水位 - 窗口)`，**不是 0**。 |
| **W（单批上限）** | 服务端对两个拉取端点的单批返回条数上限（dev 默认 200，可配）。实现即 `LRANGE key N N+W-1`。被截断时 `nextOffset` = 本批末条 offset，客户端从它续拉即补齐——**没有「一次拿全部」**。 |
| **runlive** | Redis LIST，键 `runlive:{run}`：一场 run 的**生成过程帧序列**。开跑建、每 delta 追加、定稿压 `terminal` 并设 TTL（到期自动清）。客户端**轮询它**看正在生成的回复。 |
| **runlog** | Redis LIST，键 `runlog:{session}`：session 的**定稿记录序列**（`role:user`/`assistant`，带 `run`+`role`+`text`），**index+1** 即 runlogOffset。**永久，历史真源**（未来搬 DB、Redis 作缓存）。 |
| **delta** | `kind:delta` 帧的 `text` 是增量片段（非累计全文）。客户端按 `eventOffset` 顺序**追加**进该 run 的气泡。 |
| **定稿** | worker 收完 LLM 输出，一个 `MULTI`：`runlive` 压 `terminal` 帧 + 设 TTL + `runlog` 追加 `assistant` 全文记录。此后该回复的权威内容以 `runlog` 为准。 |
| **收口** | 客户端见 `runlive` 的 `terminal`（或 `liveRunId` 变化 / runlive 已 `gone`）→ 拉 `runlog` 拿那条 `assistant` 全文，按 `run` **替换**用 delta 拼的半截气泡。 |
| **闸** | `model_history` 上的 `one_live_run_per_session` 部分唯一索引：插入活行成功 = 抢到 run；失败 = 409 `session_busy`。 |
| **liveRunId** | `GET /api/session` 返回的当前活 run id；`""` = 会话闲着（无 running run）。 |
| **reconcile（对账）** | refresh / reconnect 共用的**纯轮询**流程：查 session → 拉 runlog 补历史 → 有活 run 则轮询 runlive → 见 terminal 收口。无长连接、无挂流。 |

## 0. 第一步的范围

客户端要跑通的最小循环只有一件事：**投一条消息，轮询看着回复一点点生成、定稿**。
支撑它需要且仅需要四个 API：

| # | API | 干什么 | 游标 |
|---|---|---|---|
| 1 | `POST /api/message` | 投递（含首条消息懒创建会话） | — |
| 2 | `GET /api/session` | 状态查询：有没有活 run + runlog 高水位 | — |
| 3 | `GET /api/runlive` | 拉某场活 run 的**生成中帧** | `eventOffset`（run 内） |
| 4 | `GET /api/runlog` | 拉 **定稿历史**记录 | `runlogOffset`（全局） |

**纯拉模型**：无 SSE、无长连接、无推送、无 heartbeat。实时性 = 客户端轮询节奏（dev 建议 300–500 ms，服务端不管频率）。没有 inbox / 合并 / 跨 client 同步 / Stop / Delete / approval / 会话级帧——需要时后续 loop 照此扩，不预留。

**拉取一律有界**：两个拉取端点都受**单批上限 W** 约束（dev 默认 200，`-batch-window` 可调），实现即 `LRANGE key N N+W-1`；客户端初始游标取「高水位 − 窗口」而**不是 0**。理由：`runlog` 永久增长（compact 不动它），「从 0 全量重拉」在长会话下是无界请求。这不加端点、不加索引、不加请求参数——高水位本来就由 `GET /api/session` 返回。

## 1. `POST /api/message`

请求体三个字段，按情形发：

**情形 1 · 首条消息（本地还没有 sessionId）**——不带 `sessionId`：

```
POST /api/message
Content-Type: application/json

{"messageId":"m_1","text":"hi"}
```

→ `202 {"sessionId":"s_01","messageId":"m_1"}`。服务端在投递事务内含铸会话（`s_<ULID>`）；**客户端要把 `sessionId` 存下来**，之后所有请求都带着它。

**情形 2 · 会话里的后续消息**——带 `sessionId`：

```
POST /api/message
Content-Type: application/json

{"sessionId":"s_01","messageId":"m_2","text":"读一下 doc/19"}
```

→ 带 = 准入检查：未登记一律 404，**不隐式创建**。

**情形 3 · 超时重发**——和情形 2 一模一样地重发（同 `messageId`、同 `text`）：`messageId` 请求前就得生成好（绑本地气泡），重发不换 id；服务端**不承诺按 `messageId` 去重**，本步幂等语义仅限「闸」层面。

字段约定：`sessionId` 可省（不带=懒建会话，带=只认登记过的）；`messageId` 客户端生成、不参与排序。

响应与错误：

```
202 {"sessionId":"s_01","messageId":"m_1"}
404 {"error":"session_not_found"}     ← 只带未知 sessionId 时
409 {"error":"session_busy"}          ← 会话有活 run；什么都不写，客户端本地排队、本轮收口后补投
500 {"error":"internal"}
```

服务端行为（一笔事务，同生同灭）：闸检查（`one_live_run_per_session` 部分唯一索引）+ `run` 行 + **把用户消息追加为 `runlog` 一条 `role:user` 记录**（占一个 runlogOffset）+ **建 `runlive:{run}` 并压入 `start` 帧**（eventOffset=1）。要么整笔成功（消息开跑），要么整笔回滚（409）。不存在「入队待调度」的中间态。

> 事务成功后，客户端并不知道 run 会回什么——它靠 §5 reconcile 轮询 `runlive` / `runlog` 观测。POST 本身不返回任何生成内容。

## 2. `GET /api/runlive` —— 拉生成中的帧

```
GET /api/runlive?run=r_1&eventOffset=N        ← LRANGE runlive:{run} N N+W-1（**index+1** 即 eventOffset；W = 单批上限）

200 {"frames":[
  {"eventOffset":1,"kind":"start","messageId":"m_1"},
  {"eventOffset":2,"kind":"delta","text":"好的"},
  {"eventOffset":3,"kind":"delta","text":"，我来读"},
  {"eventOffset":4,"kind":"terminal","status":"complete"}
],"nextOffset":4,"status":"done"}
```

- `eventOffset=N` 返回该 run 中 offset > N 的帧，升序，**单批最多 W 条**；缺省或 `=0` 即从 `start` 起（新客户端从零看到整段生成，超长回复分几批拉完）。
- `nextOffset` = 本批最大 offset；**空则 = N**（客户端直接拿它当下次的 `eventOffset`）。被 W 截断时它就是本批末帧的 offset，续拉即补齐。
- **W 与 `runlog` 共用同一条规则**，不做特例：`runlive` 本身有界于单条回复长度，上限对它只是防「超长回复把一次响应撑爆」。
- `status` ∈ `generating`（还没 terminal）/ `done`（本批或已含 terminal）/ `gone`（`runlive` 键已过期删除）：
  - `generating` → 客户端按轮询间隔继续拉 `nextOffset` 之后；
  - `done` → 见 terminal，**收口**（§5 第 4 步）；
  - `gone` → 该 run 早已定稿清走，**转拉 `runlog`**。
- **`terminal` 是这一场 run 的最后一个事件**：本步只 `status:complete`；Stop / error 是后续 loop。
- 帧里的 `delta.text` 是**增量片段**，客户端按 `eventOffset` 顺序追加进气泡；地址↔内容一对一，去重 = 「见过的 eventOffset 跳过」。

## 3. `GET /api/runlog` —— 拉定稿历史

```
GET /api/runlog?id=s_01&runlogOffset=N        ← LRANGE runlog:{id} N N+W-1（**index+1** 即 runlogOffset；W = 单批上限）

200 {"rows":[
  {"runlogOffset":1,"run":"r_1","role":"user","messageId":"m_1","text":"读一下 doc/19"},
  {"runlogOffset":2,"run":"r_1","role":"assistant","text":"好的，我来读……"}
],"nextOffset":2}
404 {"error":"session_not_found"}
```

- `runlogOffset=N` 返回 offset > N 的记录，升序，**单批最多 W 条**；缺省或 `=0` = 从头**分批**拉（要拉 ⌈总条数 / W⌉ 次），不是「一次拿全部」。
- **初始游标不是 0**：新客户端先 `GET /api/session` 拿高水位 `H`，取 `runlogOffset = max(0, H - 窗口)` 只拉尾巴；要更早的历史就把游标**往回拨**再拉一次。理由：`runlog` 永久增长（compact 压的是 `model_history`，不动 `runlog`），「从 0 全量」在长会话下是无界请求。窗口大小由客户端定，服务端的 W 兜底。
- **只有定稿记录**：`runlog` 里永远只有已定稿的 message（§1 的 user 记录、§定稿 的 assistant 记录），没有半截——生成中的半截在 `runlive`（§2）。
- `nextOffset` = 本批最大 offset；**空则 = N**。被 W 截断时它就是本批末条记录的 offset，客户端从它继续拉即补齐。
- 记录带 `run`：客户端按 `run` 把定稿的 `assistant` 记录对上「正在生成」气泡**替换**（收口）。

## 4. `GET /api/session` —— 状态查询

```
GET /api/session?id=s_01

200 {"liveRunId":"r_1","runlogOffset":1}   ← run 正在跑，runlog 已有 1 条（用户消息）
200 {"liveRunId":"","runlogOffset":2}      ← run 结束，助手全文已进 runlog
404 {"error":"session_not_found"}
```

- `liveRunId`：读 `model_history` 活行（`WHERE status='running'` 的一行），`""` = 会话闲着。决定客户端要不要拉 runlive。
- `runlogOffset`：`runlog:{session}` 的高水位（`LLEN`）。客户端据此判断有没有新定稿要补。

## 5. reconcile —— 客户端纯轮询总流程（refresh / reconnect 共用）

本步只要求语义、不要求实现：

1. **查状态** `GET /api/session` → `{liveRunId, runlogOffset=高水位}`；
2. **补历史** `GET /api/runlog?runlogOffset=本地值`（新 tab 本地值 = `max(0, 第 1 步的高水位 - 窗口)`，**不是 0**）→ 渲染这批定稿记录；本地 `runlogOffset` 推进到返回的 `nextOffset`；**若 `nextOffset` 仍小于第 1 步的高水位，说明本批被 W 截断，重复拉直到追平**；用户往上滚要更早的历史时，用更小的 offset **临时**拉一批（见下「两种游标」）；
3. **观测生成** 若 `liveRunId` 非空 → `GET /api/runlive?run=liveRunId&eventOffset=本地值`（新 tab = 0）→ 按 `eventOffset` 追加 delta 成「正在生成」气泡；按轮询间隔重复拉 `nextOffset` 之后；
4. **收口** 见 runlive `status:done`（terminal）或 `status:gone`，或状态查询发现 `liveRunId` 变 `""` / 变了 → 回第 2 步拉一次 `runlog`，把那条 `assistant` 全文按 `run` **替换**半截气泡；停止轮询该 runlive。

关键不变量：**两个对齐游标各自只在自己的端点前进**——本地 `runlogOffset` 只在拉 runlog 时 +，本地 `eventOffset` 只在拉 runlive 时 +。所以在线的、断线重连的、run 结束后才开的新 tab，都靠「拉 runlog 补齐 + 有活 run 就拉 runlive」这一条路径对齐，不需要「当时在场」。terminal 帧、`liveRunId` 变化、runlive `gone` 三者任一都能触发收口，互为冗余，不押注单一信号。

**两种游标别混（窗口化引入的区分）**：

- **对齐游标**（本地 `runlogOffset` / `eventOffset`）：表示「我已经对齐到哪」，**只前进**，就是上面那条不变量说的游标。
- **翻页游标**（往上滚翻旧历史时用的 offset）：**临时值，只用于那一次请求**，拉完渲染即可，**不回退对齐游标**。

之所以能这么拆，是因为 `runlogOffset` 永久有效：往回拨拉旧数据不破坏任何东西，服务端也不需要知道客户端翻到哪。窗口化因此**不削弱**「不需要当时在场」——恢复只要求「拿得到高水位 + 一段尾巴 + 之后能续」，从来不要求「拿到全部」。

## 6. 验收（curl 手打）

```
# 用例 1：投递 → 轮询看生成 → 定稿看历史
curl -X POST localhost:8080/api/message -d '{"messageId":"m_1","text":"hi"}'
→ 202 {"sessionId":"s_01","messageId":"m_1"}

curl localhost:8080/api/session?id=s_01
→ 200 {"liveRunId":"r_1","runlogOffset":1}          （刚开跑，user 已进 runlog）

curl 'localhost:8080/api/runlive?run=r_1&eventOffset=0'   （反复轮询，frames 逐次变长）
→ frames: [start] → [start,delta,delta] → [...,terminal], status: generating→done

curl localhost:8080/api/session?id=s_01
→ 200 {"liveRunId":"","runlogOffset":2}             （定稿后）

curl 'localhost:8080/api/runlog?id=s_01&runlogOffset=0'
→ rows:[{1,user,"hi"},{2,assistant,"…全文"}], nextOffset:2

# 用例 2：游标增量 & 越界
curl 'localhost:8080/api/runlog?id=s_01&runlogOffset=1'   → 只 offset>1
curl 'localhost:8080/api/runlive?run=r_1&eventOffset=999' → {"frames":[],"nextOffset":999,...}
curl 'localhost:8080/api/runlog?id=s_01&runlogOffset=999' → {"rows":[],"nextOffset":999}

# 用例 3：带未知 sessionId
curl -X POST localhost:8080/api/message -d '{"sessionId":"s_nope","messageId":"m_9","text":"hi"}'
→ 404 {"error":"session_not_found"}

# 用例 4：忙时诚实拒绝
（会话有活 run 时）curl -X POST localhost:8080/api/message -d '{"sessionId":"s_01","messageId":"m_2","text":"急"}'
→ 409 {"error":"session_busy"}，且 runlog/runlive 里没有 m_2 的任何痕迹

# 用例 5：单批上限 W（W=200 时造不出截断，dev 起服务把它调小：-batch-window 3）
（runlog 已有 5 条时）
curl 'localhost:8080/api/runlog?id=s_01&runlogOffset=0'  → 只返回 offset 1..3，nextOffset:3
curl 'localhost:8080/api/runlog?id=s_01&runlogOffset=3'  → 返回 offset 4..5，nextOffset:5
curl 'localhost:8080/api/runlog?id=s_01&runlogOffset=5'  → {"rows":[],"nextOffset":5}
# 往回拨（翻页游标）同样合法：
curl 'localhost:8080/api/runlog?id=s_01&runlogOffset=1'  → 返回 offset 2..4（受 W=3 限），nextOffset:4
```

## 7. 存储最简形态（只为这四个 API 服务）

四类结构，先内存 / Redis、后落库（loop 内决定）：

- `session`（登记：只插入 / 只删除）；
- `model_history`（每 run 一行：闸 + 状态 + 模型侧消息；本步只有 `status='running'` 活行，`AddRun` / 压缩后续 loop 才来）；
- **`runlog:{session}`**（Redis LIST，**index+1**=runlogOffset，只追加，永久/历史真源）。永久 ⇒ **无界增长**（compact 压的是 `model_history`，不动 runlog），所以读取一律分批：`LRANGE key N N+W-1`，见 §0「拉取一律有界」；
- **`runlive:{run}`**（Redis LIST，**index+1**=eventOffset，生成中追加，定稿压 terminal + 设 TTL 自动清）。读取同一条 `LRANGE key N N+W-1` 规则，有界于单条回复长度。

> 「一条记录 / 一帧」= DB 的一行 row，不是文本的一行 line。`text` 里的 `\n` 原样保留，客户端按 markdown 渲染，排版不受影响。

**生命周期**：
- POST 事务：`runlog` RPUSH user 记录 + 建 `runlive` RPUSH start 帧（同笔）。
- worker：每收一个 LLM delta → `runlive` RPUSH delta（eventOffset 自增）。
- 定稿：一个 `MULTI` —— `runlive` RPUSH terminal + `EXPIRE`（TTL）+ `runlog` RPUSH assistant 全文记录（runlogOffset 自增）。

真源划分：**`runlog` 记「产出了什么」（历史展示只读它）；`model_history` 记「模型现在该看到什么」；`runlive` 是「正在生成的临时态」，TTL 到即清——清掉后那条回复的权威在 `runlog`，`runlive` 过期不影响历史正确性。**

**多副本**：`session`/`model_history`/`runlog`/`runlive` 全在 Redis/DB。客户端轮询打到任意副本都从 Redis 读；执行 run 的 worker 往 `runlive` 写。删掉 SSE 后不再有「持有长连接的副本 = 执行副本」的亲和问题。
