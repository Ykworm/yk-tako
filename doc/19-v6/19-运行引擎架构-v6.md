## 概要

第一步只跑一件事：**投一条消息，轮询看着回复一点点生成、定稿**。四个 API 就是全部契约面：

- `POST /api/runs` —— 创建 run（= 投递消息；含首条消息懒建会话）——字节真源 19v6-01 §1
- `GET /api/sessions/{sessionId}` —— 状态查询（活 run + runlog 高水位），reconcile 的唯一入口 —— 19v6-01 §4
- `GET /api/runs/{runId}/frames` —— 拉生成中帧（`eventOffset`，run 内）—— 19v6-01 §2
- `GET /api/sessions/{sessionId}/log` —— 拉定稿历史（`runlogOffset`，全局）—— 19v6-01 §3

心智模型一条循环：投递拿 `runId` → 轮询 frames 看生成 → terminal / `gone` / `liveRunId` 变空任一触发收口 →
拉 log 用 assistant 全文替换半截气泡（总流程见 19v6-02）。

## 概念表

全文反复出现的词，先在这里钉死：

| 概念 | 是什么 |
|---|---|
| **session（会话）** | 服务端登记的资源。首条消息投递时含铸；未登记一律 404。没有跨 client 同步。 |
| **message** | 一条对话消息，`role` 区分：用户投递的是 `user`，模型产出的是 `assistant`。`messageId` 仅 user 消息有、客户端生成、请求前就有，不参与排序。 |
| **run** | 一次执行。本步：消费一条 user message、产出一条 assistant message。同一 session 同时最多一场（闸保证）。 |
| **帧（frame）** | `runlive` 列表里的一项（一个 JSON），描述一场 run 的一个事件。本步三种：`start` / `delta` / `terminal`。**不是 SSE `data:`，是拉取响应里的数组元素**。 |
| **eventOffset** | `runlive` 的游标：**run 内序号**，`start`=1、每 delta +1、`terminal` 占末。拉 frames 用它（`GET /api/runs/{runId}/frames` = `LRANGE runlive:{runId} N N+W-1`）。定稿、runlive 过期后即失效，**不是历史地址**。 |
| **runlogOffset** | `runlog` 的游标：**session 内全局序号**，跨 run 单调，每条定稿记录占一个，永久有效。`GET /api/sessions/{sessionId}` 返回它的高水位、`GET /api/sessions/{sessionId}/log` 拿它当游标。**永久有效 ⇒ 双向合法**：往前拨补新、往回拨翻旧。初始值取 `max(0, 高水位 - 窗口)`，**不是 0**。 |
| **W（单批上限）** | 服务端对两个拉取端点的单批返回条数上限（dev 默认 200，可配）。被截断时 `nextOffset` = 本批末条 offset，客户端从它续拉即补齐——**没有「一次拿全部」**。 |
| **runlive** | Redis LIST，键 `runlive:{runId}`：一场 run 的**生成过程帧序列**。开跑建、每 delta 追加、定稿压 `terminal` 并设 TTL（到期自动清）。客户端经 `GET /api/runs/{runId}/frames` 轮询它看正在生成的回复。 |
| **runlog** | PG 表 `runlog_entries`（序号列 `seq`）：session 的**定稿记录序列**（`role:user`/`assistant`，带 `runId`+`role`+`text`），**`seq` 即 runlogOffset**。**永久，历史真源**，经 `GET /api/sessions/{sessionId}/log` 有界读（`seq > N ORDER BY seq LIMIT W`）。 |
| **delta** | `kind:delta` 帧的 `text` 是增量片段（非累计全文）。客户端按 `eventOffset` 顺序**追加**进该 run 的气泡。 |
| **run 结束** | run 侧收尾：`running` → 终态 `status`（本步 `complete`/`error`；`stopped` 后续 loop）。压 `terminal` 帧、给 `runlive` 设 TTL、放闸、删 `draft`——**无条件**，不管结局如何闸必放。入口 `endRun(sessionId, runId, status)`。 |
| **定稿** | message 侧收尾：assistant 碎片 → 一条完整 message 记录（`runlog` 追加 `assistant` 全文记录）。**只有 `status=complete` 那一次发生**；此后该回复的权威内容以 `runlog` 为准。run 结束与定稿**同一笔原子写**——拆名不拆原子性，否则客户端能观察到「闸已放、历史还没那行」的窗口。`error` 结局不进历史（runlog 永远只有定稿记录），残缺 `draft` 随删。 |
| **收口** | 客户端见 frames 的 `terminal`（或 `liveRunId` 变化 / frames 已 `gone`）→ 拉 log 拿那条 `assistant` 全文，按 `runId` **替换**用 delta 拼的半截气泡。 |
| **闸** | `runs` 表上的 `one_live_run_per_session` 部分唯一索引（`UNIQUE (session_id) WHERE status='running'`）：插入活行成功 = 抢到 run；失败 = 409 `session_busy`。进程死亡由租约列 `lease_until` 判死（watchdog 续约；租约过期读侧即不算活）。 |
| **liveRunId** | `GET /api/sessions/{sessionId}` 返回的当前活 run id；`""` = 会话闲着（无 running run）。 |
| **reconcile（对账）** | refresh / reconnect 共用的**纯轮询**流程：查 session → 拉 log 补历史 → 有活 run 则轮询 frames → 见 terminal 收口。无长连接、无挂流。 |

没有合并语义，没有 inbox，没有跨 client 同步。

## 注意事项（跨切面不变量，改哪篇都适用）

- **纯拉模型**：无 SSE / 长连接 / 推送 / heartbeat（19v6-01 §0）。
- **拉取一律有界**：单批上限 W 管两个拉取端点；**没有「一次拿全部」**（19v6-01 §0）。
- **两种游标别混**：对齐游标只前进；翻页游标是临时值、不回退对齐游标（19v6-02）。
- **闸在共享存储不在进程**：`runs` 表 `one_live_run_per_session` 部分唯一索引（`WHERE status='running'`）——插入失败本身就是 409；进程死亡由租约列 `lease_until` 兜底（watchdog 续约、租约过期读侧即判死）（概念表「闸」、19v6-03）。
- **runlog 只增不删**：只追加、永久、历史真源；任何失败路径都不删行（19v6-03）。
- **run 结束与定稿同一笔原子写**；`error` 结局不进历史（概念表「run 结束」「定稿」、19v6-03 生命周期）。
- **帧的头尾是应用层造的生命周期标记**：`start` 由投递事务压、`terminal` 由 `endRun` 造；provider 的 done 事件不产生帧（实现裁定见 `tmp/19-v6/planning.md` §5 第 8 条）。
- **「从未存在」与「已过期删除」不区分**：frames 对未知 run 回 200 `gone` 而非 404（19v6-01 §0）。
- **没有用例逼出的端点不进契约**；需要时照既有通道扩，不预留字段（19v6-90 四修）。
