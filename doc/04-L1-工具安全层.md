# 04 · L1 工具安全层

> L0 回答了"agent 循环是什么"，L1 回答一个更现实的问题：**agent 有了手（shell、文件读写）之后，怎么防止它闯祸？**
> 复刻对象：harness-agent 的 `security/tool_guard/` + `middleware/tool_guard.py`、`middleware/filesystem_guard.py`、`middleware/pii.py`。

> 实现注记（2026-09-24）：本层最初用 TypeScript（LangGraph.js）实现，TS 版已随路线定案删除，
> 唯一实现现为 `yk-tako-eino/`（Go）。文中的机制分析（三态裁决、规则引擎、审批回路、守卫分层）与语言无关，全部照旧成立；
> Go 侧的对应关系：挂载点是 ADK middleware 的 `WrapInvokableToolCall`，
> 审批是 `compose.StatefulInterrupt` + `Runner.ResumeWithParams`（resume 值同样是 `"approve"` / `"reject"`）。
> "中断审批的回路"一节按 LangGraph.js API 写成，留作机制对照；踩坑记录 2–4 是 TS 专属，仅作历史保留。

## 本层目标

给 L0 的 agent 循环加一圈"安检"，三件套各管一件事：

```
用户输入 ──→ [PII 脱敏] ──→ 模型 ──→ 决定调工具
                                    │
        ┌───────────────────────────┤
        ▼                           ▼
[ToolGuard 查命令参数]      [FilesystemGuard 查文件路径]
        │                           │
 放行/警告/拦截/审批           放行/拦截/问人
        └──────────→ 工具执行 ←──────┘
                      │
            [PII 脱敏工具结果] ──→ 回到模型
```

两个守卫都是**三态**：`allow` 直接放行、`deny` 用错误 ToolMessage 挡回给模型、`ask` 暂停整张图等人裁决（`interrupt` + `Command({ resume })`）。

## 从 harness 读到了什么

### tool_guard（约 620 行，本次精读）

语义骨架其实很小，大的是规则库：

- **引擎** `ToolGuardEngine.guard(tool_name, params)` → 返回 findings 列表，空 = 安全。
- **三模式 × 严重度阈值**决定拦不拦：

| 模式 | 拦截的严重度 | 语义 |
| --- | --- | --- |
| `block` | CRITICAL / HIGH | 硬拦，工具不执行 |
| `require_approval` | + MEDIUM | 暂停，等人裁决 |
| `warn` | 无 | 亮黄牌但放行 |

- **规则**是 YAML 里的正则签名表（`dangerous_shell_commands.yaml`，约 300 行）：rm/mv、mkfs/dd 写裸设备、fork 炸弹、`curl|bash`、反弹 shell、Unicode 空白、`/proc/*/environ`、jq system()、zsh 危险内建……每条带 severity、remediation、exclude_patterns（比如注释行不报警）。
- **审批**用 `langgraph.types.interrupt`：图整个暂停，人批准后从断点继续。

### filesystem_guard

当 deepagents 自带的权限机制不可用时（sandbox backend），在工具调用边界补一层路径策略：有序规则表先命中先生效，路径要展开 realpath（macOS `/etc` → `/private/etc` 的符号链接坑），`/etc/**` 这种模式也要匹配 `/etc` 本身。

**重要：这层是 deny-only 的降级版。** deepagents 上游的 permissions 本来是三态（含 `interrupt` 审批），但因为 shell backend 下会抛 `NotImplementedError` 被整个禁用；harness 只在工具边界补回了 deny 半边，`interrupt` 只剩一个抄来的注解（详见下面「溯源纠错」）。

### pii

它自己也不是从零写的：框架自带 `PIIMiddleware` 检测 email/信用卡/IP，但**不认识 API Key**。harness 补了一个自定义检测器，专抓 `sk-...`、`sk-ant-...`、`AKIA...`、`AIzaSy...`、`hf_...` 和 `api_key=...` 赋值形式，配 `mask` 策略（留头尾、中间打星）。

## 三态裁决：区外访问先问人（对齐 Codex / deepagents）

FilesystemGuard 不是"区外一律拒"，而是和 ToolGuard 一样的**三态**：`allow` / `deny` / `ask`。这个 `ask` 态对齐的是 Codex 的 `workspace-write` + 提权审批——**区外不是不能去，是去了要先问用户**。

### 溯源纠错（一开始我写错了）

我最初在本文档里写过"harness 原版也有这一态"，**这是错的**，核对源码后更正（核对的版本：`orcakit_harness_agent-1.0.14`，deepagents 0.7.18 / GitHub main，两者一致）：

| | harness 自研 fs guard | deepagents 上游 | 我们 |
| --- | --- | --- | --- |
| 规则 mode 类型 | `Literal["allow","deny"]`（`security/models.py:40`） | `Literal["allow","deny","interrupt"]` | `allow \| deny \| ask` |
| `interrupt` 态实现 | **无**。`_check_fs_permission` 的返回注解里有 `"interrupt"`，但它是从 deepagents 私有函数抄来的签名（文件头注释自己写明）；全树 grep 只有这一处，中间件无分支、无 `interrupt` 导入 | 完整：`_fs_interrupt.py` 把 interrupt 规则转成 HITL 的 `interrupt_on` 配置（含 `when` 谓词），审批人有 4 个决策 `approve/edit/reject/respond` | `interrupt()` 内联在中间件里，审批只有批准/拒绝 |
| 死签名的后果 | 配置里写 `mode: interrupt` → 加载时被**静默丢弃**（`models.py:197` 只放行 allow/deny）；程序内直接构造则 `"interrupt" != "deny"` → **放过（fail-open）** | —— | —— |
| 为什么 harness 这么弱 | deepagents 在 backend 支持命令执行时**直接抛 NotImplementedError**（"Tool-level permissions for the execute tool are not implemented"），整套 permissions 机制（含审批）被禁用；harness 只好在工具边界重做一个**只留 deny 的降级版** | —— | —— |

**这本身是个教训**：一个三态的类型注解，配上一个两态的实现，比没有更危险——它给人"这里有审批"的错觉，实际是静默丢弃或静默放行。读上游代码时要顺注解一路查到 `return` 语句，别信签名。

顺带记下 deepagents 上游两个值得抄的设计点（我们暂时没抄）：
1. **策略与审批解耦**：fs 守卫只做纯策略判定，interrupt 规则由 `_build_interrupt_on_from_permissions` 映射成 HITL 配置，审批逻辑不污染守卫。
2. **批量工具的锚定问题**：`ls`/`glob`/`grep` 的中断按"搜索子树是否与规则锚定前缀重叠"触发；全通配（`/**/secrets`）会收敛到 `/`，保守过度触发。我们目前只有 `read_file`/`write_file`（单路径），还没这个问题；以后加批量工具就必须补。

**这一态为什么在两代项目里都没用上**（三道闸门 + 一个后端限制，全部静默）：

1. **UI 层**：Octop 仪表盘的 TS 类型就是两态 —— `dashboard/src/api/modules/security.ts:12` `mode: "allow" | "deny"`。用户在界面上根本表达不出 interrupt。
2. **策略模型层**：`harness_agent/security/models.py:40` `FilesystemMode = Literal["allow","deny"]`。
3. **反序列化层**：`models.py:197` `if mode not in ("allow","deny") or not paths: continue` —— 手改 settings JSON（key `security_policy`，经 Octop 的 `policy_store.py` 落库）写 `mode: interrupt` 也会被**静默丢弃，连 warning 都没有**。
4. **后端限制**：deepagents 的 `FilesystemMiddleware.__init__` 里 `if _permissions and supports_execution(self.backend) ...: raise NotImplementedError("Tool-level permissions for the execute tool are not implemented")`；Octop 自己把这原因写进了 `src/octop/infra/backend/resolver.py:202-206` 的 `backend_spec_supports_execution()`（`local_shell`/`docker`/`opensandbox` 都算执行类）。所以执行类后端下 deepagents 那整套 permissions（含 interrupt 审批）整个不可用，harness 才在工具边界自研了 deny-only 的兜底版。

**一个精确化**：并不是说 Octop 完全没有审批——它有的是**工具级** HITL，不是**路径级**审批。`resolve_interrupt_on()`（`models.py:258-303`）默认把 `bash`/`execute`/`write_file`/`edit_file`/`delete` 纳入审批，还专门给 fs 工具装了 `when` 谓词，但谓词语义是"路径没被 deny 就照样弹审批"（`return not bool(filesystem_guard_block_reason(...))`），跟规则 mode 无关。deepagents 上游那条"规则 mode=interrupt → 生成 `interrupt_on` 条目"的路径（`_fs_interrupt.py`）在 harness 里根本没有对应实现。

所以三方的能力边界是：

| | 工具级审批 | 路径级审批（按目录/文件问） |
| --- | --- | --- |
| deepagents 上游 | ✅ HITL | ✅ permission mode=interrupt（执行类后端除外） |
| Octop / harness | ✅ dashboard 可配 | ❌ 被三道闸门砍掉 |
| yk-tako | ✅ `require_approval` 模式 | ✅ `ask` 三态（我们补的就是这一格） |

### 分界线怎么划

| 场景 | 裁决 | 理由 |
| --- | --- | --- |
| 工作区内读写 | allow | 常态，不打扰 |
| 工作区外任意路径 | **ask**（默认） | 可能合理（读系统日志、写 /tmp），交给人判断 |
| `**/.env`、`**/.git/**`、`**/.ssh/**`、`**/id_rsa*` | deny | 密钥不该问，问了也不好答应 |
| `/etc/**`、`/usr/**`、`/System/**` 等系统目录**写** | deny | 没有"合法"的写理由 |
| `/etc/passwd` 这类系统文件**读** | ask | 读本身无破坏性，人来判断 |

关键设计取舍：**能问的不拒，该拒的不问**。全用 ask 会把审批弹窗变成噪音，人就会无脑点 y；全用 deny 会逼 agent 绕道（自己去 bash 里 `cat`），反而丧失可观测性。

配置：`outsideWorkspace: "ask" | "deny"`（默认 `ask`，设成 `deny` 即回到旧行为）。规则级裁决是硬编码的，不受该开关影响。

## 中断审批的回路（本层最核心的新机制）

LangGraph.js 的 HITL 不需要 Web 服务，REPL 就能演完整流程：

```
中间件里 interrupt(payload)          REPL 里：
   │ 图暂停，状态进 checkpointer         state = await agent.getState(config)
   │                                   interrupts = state.tasks[].interrupts
   │                                   人输入 y/n
   └────────── resume 值 ◄── agent.stream(new Command({ resume }), config)
        interrupt() 原地"返回"resume 值，中间件继续走完剩下的分支
```

两个前置条件：必须有 checkpointer（`MemorySaver` 即可）；interrupt 的恢复值**不能是 falsy**（见下面的坑 1）。

## 中间件模式在 agent 场景的真实代价

中间件不止放 guard：官方自带的就有 summarization（压缩历史）、modelRetry / toolRetry（重试）、modelCallLimit / toolCallLimit（限流）、todoList（能力增强）等十几种。和 Gin 的中间件类比很准，但有个关键差异：**Gin 包的是一次请求-响应（几百毫秒、进栈出栈）；agent 中间件包的是一个多轮循环**——一次用户输入可能触发 N 轮"模型→工具→模型"，每个钩子每轮都触发，消息历史在循环里持续累积。HTTP 请求不会"聊着聊着上下文爆了"，agent 会；HTTP handler 不会"失败了自己决定重试"，模型调用会抖。所以需要照顾的方面天然就多，"杂"是场景决定的。

但杂有真实的代价，三条：

1. **顺序变成语义**。PII 脱敏放在 summarization 前还是后，结果不同；中间件数组的顺序就是执行顺序，不再是无关紧要的清单。本层三个守卫顺序无关是运气好（互相独立），不是普遍规律。
2. **隐式交互**。两个中间件各自单测都过，组合起来可能互相干扰——例如 retry 重试时把审批又触发一遍，人要看两次弹窗。
3. **调试变难**。行为分散在 N 个中间件里，出问题要沿链条逐个排查，不像单文件函数那样一目了然。

应对办法不是"少放"，是**约定 + 可见性**：

- 顺序约定：安全类最前、压缩类靠后（官方文档的建议）。
- trace 可见：LangSmith 里每个中间件的进出都可见，所以中间件的注册名要起得能认出身份（`api_key_pii` 而不是 `api_key`）。
- 保持互相独立：本层三个守卫互不依赖、判断逻辑抽成纯函数（`filesystemGuardDecision` 不碰 `interrupt` 和工具，可脱离 agent 单测），把"组合爆炸"的基数压小。

## 踩坑记录

1. **`resume: false` 会炸**。LangGraph 对 falsy 的 resume 值判定为"空 Command"，报 `Received empty Command input`，而且图状态会停在"assistant 有 tool_calls 但没有对应 ToolMessage"的烂摊子，下一轮直接被 API 400 拒。解法：resume 用 `"approve" / "reject"` 字符串，不用布尔。
2. **`createAgent` 的 tools 重载推断很娇气**。`tools` 传数组变量（联合类型）+ 混合新工具时泛型推断塌缩，报一个风马牛不相及的 `responseFormat is missing`。解法：tools 用数组字面量（推成 tuple）；`model` 的联合类型收窄成 `BaseChatModel`。
3. **块注释里不能写 `**/.env`**。`*/` 序列会提前终结注释，喜提一排 TS1131。
4. **TS 正则字面量里别粘不可见 Unicode 字符**，用 `\u00a0` 转义写（YAML 里的 `\\u00a0` 到了 TS 就是 `/[\u00a0...]/`，语义一致）。

## 实测记录（`go run ./cmd/l1guard`，原 TS 版为 `pnpm l1:guard`）

| 输入 | 结果 |
| --- | --- |
| `用 bash 执行 echo hello-l1` | 无命中，直接放行，输出 `hello-l1` |
| `用 bash 执行 rm -rf /tmp/l1test` | 命中 `TOOL_CMD_DANGEROUS_RM:HIGH` → 图暂停 → 审批 UI → 输入 n → 工具不执行，模型收到"用户拒绝"并主动给出替代方案 |
| `用 read_file 读取 /etc/passwd 的第一行` | 区外 → 暂停问人 → 输入 y → 工具真的执行，读到 `/etc/passwd` 全文（模型随后还自己说明"read_file 不支持只读前 N 行，要精确用 bash head"） |
| `用 read_file 读取 .env` | 规则级 deny，不弹窗，直接返回"敏感文件"拒绝理由 |

外加 13 条引擎/守卫/检测器的单元冒烟全过（rm、curl|bash、sudo、/etc/passwd、.env、sk- key、api_key= 赋值等）。

### 一个值得记录的观察

第三轮里模型被文件守卫拦下后，**自己指出**了防御缺口：`bash cat /etc/passwd` 可以绕过 read_file 的工作区边界——并主动声明不这么做。这说明两点：

1. **逐工具的守卫 ≠ 沙箱**。bash 能读任意路径，文件守卫只管文件工具。这一点即使改成 ask 态也没变：Codex 的 `workspace-write` 是 **seatbelt/landlock 在系统调用层**兜底，agent 无论从哪个工具发起都逃不掉；我们的守卫只在工具调用边界生效，属于"可观测、可协商"的软约束。harness 的解法是纵深防御：文件守卫拦路径、命令守卫拦 `/proc/environ` 这类高危路径、更上层还有沙箱 backend。守卫分层，每层都有自己看得见和看不见的东西。
2. **把拦截原因写清楚，模型会配合**。ToolMessage 里带了拒绝理由（"超出工作区"），模型不仅理解了，还内化了策略意图。模糊的错误只会让模型乱试。

顺带一个副产物：`ask` 态把"区外访问"这条信息**升格成了用户可见事件**。以前 agent 用 bash 绕道读系统文件，我们永远不知道；现在只要它走文件工具，就会弹出来问一句。软约束的收益不在拦截率，在于让越界行为变得可见。

## 与 harness 的差距（有意留下的）

- 规则只有 10 条代表性规则，harness 有 ~25 条 + YAML 热加载 + 用户自定义 rules_dir。知识补齐是体力活，随时可做。
- 审批是 REPL y/n，harness 是 HITLRequest 结构（action_requests / review_configs），为 Web 审批 UI 预留。等 L7 多入口时再对齐。
- harness 的 guardian 接口支持插件化（规则 guardian 之外还能接 LLM guardian），我们只留了 `rules` 数组注入。
- 没有系统调用层沙箱（Codex 有 seatbelt/landlock）。要真堵 bash 绕道，得等 L6 沙箱 backend，或者把 bash 本身也纳入"参数级路径解析"——后者不可靠，不划算。

## 有意偏离 harness 的一处语义（exclude_patterns）

harness 原版：`exclude_patterns` 任何一条命中**整段参数**，整条规则放弃。副作用是 `# 注释\nrm -rf /` 这类"注释行 + 危险命令"的多行输入会绕过所有带注释排除的规则（漏报）。

我们的版本（`textForRule`）：`/^\s*#/` 这类注释行模式只**剥掉注释行**后继续扫剩余文本；其它排除模式才保持整段排除。已验证 5 个边界场景（注释+rm、纯注释、行尾注释、引号内 #、普通危险命令）。

已知脆弱点：`isCommentLineExclude` 靠正则源码逐字符相等（`^\s*#` + 无 flags）来识别注释行模式，改写法（如 `/^ *#/`）会静默退化为整段排除。若规则表扩大，应改成规则上的显式开关（如 `stripCommentLines: true`）。
