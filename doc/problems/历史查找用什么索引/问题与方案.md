# 历史查找用什么索引

> 模块：同会话历史查找（`internal/runengine/search.go`）｜ 状态：已落地（`dd63b8e` / `38a230f`）｜ 证据：`doc/21-同会话历史查找.md`

## 1. 场景与病灶

用户在同一个会话的下一场问：「上次那个错误码是什么？就是 `E_DECK_17` 那个。」

模型需要一个工具去翻本会话的历史。看起来最标准的做法是 PostgreSQL 全文检索，但实测：

- PG 默认的 `pg_catalog.english` 把中文整段切成一个词，把 `E_DECK_17` 拆成 `e`、`deck`、`17，deck`；
- `plainto_tsquery` 查「错误码」和 `E_DECK_17` 都不命中；
- 开发库没有 `pg_search`，也没有中文分词扩展。

也就是说，**在「中文 + 代码标识符」这个真实语料上，默认全文索引的召回是零**。

## 2. 候选与代价

| 候选 | 做法 | 好处 | 代价 |
|---|---|---|---|
| A `ILIKE` 子串 | 按词做大小写无关的子串匹配 | 中文与错误码都命中；零新索引、零新扩展 | 扫本会话本场之前的行；语义近义查不到 |
| B `to_tsvector` | 标准全文检索 | 索引快、标准 | 实测中文/错误码不命中 |
| C ParadeDB / BM25 / 向量 | 换库或加扩展 | 召回强 | 换库或新依赖，超出本篇；与 doc/29 的对话召回是两条不同语料 |

**裁定：A。** 本篇不换 ParadeDB，也不走 `to_tsvector`。用 `ILIKE` 而不是 `LIKE`：库里是 `E_DECK_17`，问句写成 `e_deck_17` 时 `LIKE` 落空，`ILIKE` 仍中。

## 3. 同族小裁定

| 小问题 | 裁定 | 代价 / 备注 |
|---|---|---|
| 结果超长怎么办？ | 4000 字上限；**发生截断时**把完整结果落 `.tako/search/`，未被截断则一个字节不变 | 上限是为了避免一次工具结果把刚折掉的正文原样灌回窗口；落盘让丢掉的命中仍可再读。写失败退化为纯截断、不报错 |
| 落盘要不要登记 `file_effect`？ | 要，登记为 write | 否则清理与审计看不到这些文件 |
| 子代理拿真工具还是拒绝壳？ | 拿同一个真工具对象，不设壳 | 拒绝壳会让查询逐轮落回主线程历史，mid-run 折叠被提前触发，子代理独立窗口形同虚设（2026-10-12 当日由壳改为真工具） |
| 查询包含本场 run 吗？ | 排除本场 `run_id` | 本场 user 行在抢闸时已进 `runlog_entries`，按 seq 从新到旧取，最新一行会是问句自己，把真正结果挤出 `limit` |
| 读未提交内存吗？ | 不读，只读已提交的 `runlog_entries` | 否则会看见可能被丢弃的半截生成 |
| 跨会话能查吗？ | 不能，只查同一会话 | 跨会话找结论是 doc/29 的两条召回线，不是这把工具 |
