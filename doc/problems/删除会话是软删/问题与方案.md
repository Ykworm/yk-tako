# 删除会话是软删

> 模块：删除与档案清理（`internal/runengine/pgstore.go` / `archive_sweep.go`）｜ 状态：已落地（`0fd15c5`）｜ 证据：`doc/37-删除与档案清理.md`、`tmp/37-删除连带删/planning.md`

## 1. 场景与病灶

用户误删一场重要会话，或者删完立刻想撤回；同时，逐字档案不能无限膨胀。

硬删的后果：无法恢复、审计链断裂、后续「恢复入口」没地方挂。更麻烦的是**删除的连带范围**：

- 会话有一场活 run 正在跑，删了它，run 怎么办？
- 会话产出了 `report.md`，删对话是不是连产出一起没收？
- 子代理的逐字档案在 `run_model_messages` 里，要不要另建 `subagent_runs` 表？
- 多副本各跑一个清扫 ticker，同时到点物理删同一批行？

## 2. 候选与代价

| 问题 | 候选 | 好处 | 代价 |
|---|---|---|---|
| 删还是软删 | A 硬删 | 干净 | 不可恢复、审计断 |
| | B `deleted_at` 软删，过滤语义 =「视同不存在」（404 不是 403）（定案） | 可恢复、留审计 | 所有查询要带过滤 |
| 活 run 时 | A 自动 stop 再删 | 一键完成 | 误杀正在产出的任务；已删会话的 run 还要收尸 |
| | B 拒绝，回 409 `114006/114007`，等跑完再删（定案） | 不误杀 | 用户多一步 |
| 删会话的目录 | A 整个目录删 | 彻底 | 没收用户产出 |
| | B 产出保留，只清 `.tako/`、`.media/` 等系统档案（定案） | 资产安全 | 目录可能留半空 |
| 子代理档案建新表吗 | A `subagent_runs` | 查询直观、对齐 Kimi 独立 wire | 第二真源、双写 |
| | B 不建，用现有 compacted 行 + `run_id → runs.finished_at` 推导（定案） | 单一真源 | 查询要 join |
| 清扫器互斥 | A 进程内 mutex | 简单 | 多副本失效 |
| | B PG 租约表 + DELETE 幂等 + 水印推进（定案） | 跨副本互斥、可续跑 | 多一张表与租约逻辑 |
| 软删档案留多久 | A 永久 | 恢复无上限 | 库无限膨胀 |
| | B 与全局档案同一个窗口（默认 168h，`-archive-ttl` 可配），过窗物理清（定案） | 恢复承诺与清理一致 | 窗口外不可恢复 |

**裁定：B / B / B / B / B / B。**

## 3. 同族小裁定

| 小问题 | 裁定 | 代价 / 备注 |
|---|---|---|
| 谁能删？ | 仅属主本人，tenant owner/admin 不豁免 | 详见 `doc/problems/会话默认私有` |
| 看不见的会话回 404 还是 403？ | 404 | 403 等于确认 id 存在 |
| 删除是事务吗？ | 先删 DB 行（软删），事务后再清系统档案 | 文件操作不进 DB 事务；清失败留待清扫器 |
| 会话删除后 run 还能续吗？ | 不能；resume 入口按 `deleted_at IS NULL` 校验 | 删会话是用户的明确意图 |
