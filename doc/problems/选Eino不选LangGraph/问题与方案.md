# 选 Eino 不选 LangGraph：选的是系统拓扑，不是框架能力

> 模块：技术路线 · 运行时选型（doc/04）｜状态：**已定案**（2026-09-24，仍有效）｜证据：`doc/04-技术路线.md`、`doc/08-Eino规划机制调研.md`、`yk-tako-eino/go.mod`、`yk-tako-eino/cmd/yktako`

## 1. 场景与病灶

项目起步于「照着 Octop 复刻一个 AI 工作伙伴」。第一个必须回答的问题是：**Agent 核心用什么技术栈写。** 桌上两个候选：

- **LangGraph.js（Node/TS）**：与 Octop 的 Python LangGraph 血统几乎一一对应，接近逐行翻译；owner 之前用 TS 与 Go 各复刻过一遍 pi agent，实测体感 TS 更顺手。
- **Eino（Go）**：概念一一对应（Graph / Node / Edge / State / Checkpoint），但 API 要重写。

第一直觉选了 LangGraph.js，理由是「人的连续性」——生长式路线下，学习连续性权重最高；deepagents 的中间件矩阵在 JS 版有官方对应物，翻译最直接（doc/04 §4.1）。

**然后实地 clone 了 Octop（v0.9.33）**，前提当场塌了：**不存在「可保留的 Go 后端」**。Octop 主进程是 Python 3.12+ 单进程（FastAPI + uvicorn，`src` 约 13.1 万行），Go 只存在于 `desktop/` 桌面外壳（约 2.6k 行），Agent 核心在外部 pip 包 `orcakit-harness-agent` 里。

这一下把选项重排了：

| 路线 | 实际含义 |
|---|---|
| 用 LangGraph.js 复刻 | 得到一个 **Python + Node** 双语双进程系统：Octop 原有的 Python 应用还在，Agent 芯换成 JS。**复杂度没有下降**，只是换了一种双语 |
| 用 Eino 复刻 | 收敛为**纯 Go 单语言**，只需一种运行时；gRPC 边界最终可整个删掉 |

「翻译省力」这个好处，只在「有存量代码可翻译」时成立；存量不存在时，两条路都是全量重写，谁也没有便宜可占。

第二圈反转（同两天内）来自更深的一层：**规划与执行的时序保证**。L2（任务规划）调研暴露的问题是——在 LangGraph 系里，这类约束只有 middleware 一层可做文章（`afterModel` 之类），等于用软钩子模拟硬约束；Eino 把分界写死：**Graph 管确定性、Agent 管自主性**，不要用静态编排假装动态决策，要硬保证时直接编图（Workflow Agents / Plan-Execute 节点图）。后续的子代理、断点恢复、多入口都会反复碰到这条线。

## 2. 候选与代价

| 候选 | 做法 | 好处 | 代价 |
|---|---|---|---|
| A LangGraph.js | Octop 的 Python 图逻辑逐行翻成 TS；deepagents JS 版 | 与参考实现最贴；owner TS 手感好 | **多一种运行时**（Go + Python + Node）或被迫砍掉 Go 部分；桌面/本地部署重；确定性约束只能靠 middleware 软钩子 |
| B Eino（选定） | 概念映射后按 Eino 思想重写 | 纯 Go 单语言；单二进制部署；Graph/Agent 分界是一等公民；WeKnora 同为 Go 可抄 | 不是翻译而是重写；Eino 生态较新、文档要自己读源码；先要建映射表 |
| C 保留 Octop 原栈（Python） | 直接在 Octop 上改 | 与参考实现零距离 | 主进程 13.1 万行 + 外部 pip 包，改造成本高；部署是 Python 应用形态，与「本地数字员工单二进制」目标冲突 |
| D 自研最小 loop | 不用框架，自己写 ReAct 循环 | 完全可控、依赖少 | 断点恢复、流式、子代理、MCP 适配都要自己造；这些正是框架的活 |

选 B。**决定性理由不是「Eino 比 LangGraph.js 强」，而是系统拓扑**：

1. 目标形态是本地数字员工，Go 单二进制是硬优势；
2. 收敛为一种运行时，少一条进程边界、少一套依赖与部署；
3. 参考系（WeKnora）是 Go，遇到问题有两个大型 Go 项目可抄；
4. 确定性 vs 自主性有正式答案，不用把约束伪装成 middleware。

代价也写清楚：**复刻不是翻译，是重写**；移植时先用映射表把「这个概念在 Eino 里叫什么」定位出来，再决定照抄语义还是按 Eino 正式做法重做。

## 3. 概念映射（移植手册）

| LangGraph (Python) | Eino (Go) |
|---|---|
| `StateGraph` | `compose.Graph` / `compose.NewChain` |
| `add_node` / `add_edge` | `AddNode` / `AddEdge` |
| 条件边 `add_conditional_edges` | `AddBranch`（`GraphBranch`） |
| State（TypedDict + reducer） | 泛型 State + `WithStatePostHandler` / `GenLocalState` |
| `Checkpointer`（PostgresSaver） | `compose.CheckPointStore` 接口，需自实现存储 |
| `interrupt` / 人机协同 | `compose.StatefulInterrupt` + `Runner.ResumeWithParams` |
| ReAct Agent（prebuilt） | `react.Agent` / ADK `ChatModelAgent` |
| 多智能体 supervisor | Eino ADK 的多 Agent 组合 |
| 工具节点 ToolNode | `compose.ToolsNode` + MCP 工具适配 |
| 流式 `astream_events` | Callbacks + `StreamReader` |

这张表的用法是**定位，不是翻译**：读 Octop / harness 的 Python 实现时，先查出对应概念，再按 Eino 的做法重写（doc/05 §翻译原则）。

## 4. 同族小裁定

| 小问题 | 裁定 | 代价 / 备注 |
|---|---|---|
| 唯一主线 | **`yk-tako-eino/` 一个** | 旧 L0–L2 五个入口与 `internal/planexec` 已删；TS 实现全删；`maf/`（.NET 对照）冻结为存档 |
| 复刻方针 | **功能翻译，按 Eino 思想写** | 不逐行搬 Python 结构；先映射再重写 |
| 记忆方案（T-Mem） | **接口先行、两期走**：一期 pgvector + 简明情景表，二期再上 T-Mem | 写入成本高（多次 LLM 调用），须异步管线；接口不钉死才换得动 |
| 要不要为了省事引 TS 工具链 | **不引** | 前端是 Vue（Node 只用于构建），运行时不引第二种语言 |
| 版本基线 | `go.mod` = Go 1.27.0 + Eino v0.9.21 | **doc/04 §5 写的「Go 1.25」已过期**，以 `go.mod` 为准 |
| 参考实现可信度 | **先 clone 读真代码，再判断** | Octop 案例：`desktop/` 的 Go 只有 2.6k 行，不足以撑「保留 Go 后端」的论据 |
| 反转怎么记 | **保留反转记录与原因** | doc/04 §4 记了两圈反转；避免下一轮重复踩同一个前提 |
