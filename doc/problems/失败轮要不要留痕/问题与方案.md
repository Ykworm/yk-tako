# 失败轮要不要留痕：区分「没产出」与「做了一半」

> 模块：运行引擎 · run 终态与历史（`tmp/失败留痕` 台账，commit `d74bf91`）｜状态：**已落地**（2026-10-22）｜证据：`tmp/失败留痕/planning.md`、`internal/runengine/store.go`、`worker.go`

## 1. 场景与病灶

一场 run 失败时，它已经说过的话、已经做过的工具调用，现在**什么都不留**。三个会真实发生的戏：

**戏一：用户刷新页面，半截回答消失。** 模型说了三段话，正说到一半，provider 报 500，run 走 error 出口。页面上半截回答还在（浏览器内存里），用户一刷新 → 页面从 runlog 重建历史 → **runlog 里没有这场 run 的 assistant 行** → 半截回答消失，只剩用户那条提问。五分钟后帧也过期（`tk:runlive` 终态 `EXPIRE 300s`）→ 连现场都没了。

**戏二：模型下一枪看到一条没人回答的用户消息。** `AcquireRun` 在同一笔事务里把本轮 user 行写进 mh 和 runlog；`EndRun` 的 complete 分支才写 assistant / tool 行，error / stopped 走 `else` 分支**一行不写**。于是下一场 run 的 `prepareInput` 读到的是 `[…历史…, user: 帮我把 X 改一下]`——这条 user 消息永远没有配对的 assistant 行。用户重发「刚才改到哪了？」，模型看到两条没有回答的 user 消息，既不知道上一轮说了什么，也不知道上一轮已经动过手。

**戏三：工具的副作用没人记得。** 崩溃账本 `run_journal` 是这一轮最完整的记录（每次工具调用的 intent 与 result、每次 assistant 轮）。但终态时账本被无条件删掉——于是「这一轮改过哪些文件、跑过什么命令、结果是什么」只剩 Redis 里 300 秒的帧，之后归零。

**病根**：`error` / `stopped` 这一档同时意味着「这一轮没发生」和「这一轮做了一半」，而现在的实现只认前一种。

## 2. 候选与代价

| 候选 | 做法 | 好处 | 代价 |
|---|---|---|---|
| A 全不留（现状） | error/stopped 一行不写 | 语义简单：有 assistant 行 ≈ 成功 | 戏一、戏二、戏三全部发生 |
| B 全留 | 失败轮一律写 mh + runlog | 不丢任何东西 | 「失败且无产出」也写 → 库里多出一堆空 assistant 行；页面刷新后每个失败都显示一个空气泡 |
| C 区分「失败无产出」与「失败有产出」（选定） | 判据：`len(turn) > 0` 即算有产出 | 该留的留、该干净的干净；一行代码就能判 | mh 里会出现半截 assistant 行，Provider 协议要求 tool_calls 有配对结果，需要配平 |

选 C。「这一轮说没说话」是现成、无歧义、不依赖模型的判据——`turn` 里有没有条目，机械可判。

改后落什么：

| 终态 | turn | 改后落什么 |
|---|---|---|
| complete | 有 | mh + runlog（现状不动） |
| error | 空 | 只有 user 行（与改造前一致） |
| error | 非空 | mh + runlog（**新增**） |
| stopped | 空 | 只有 user 行 |
| stopped | 非空 | mh + runlog（**新增**） |
| 闸失（已被接管） | 任意 | 零写入（接管者负责） |

## 3. 同族小裁定

| 小问题 | 裁定 | 代价 / 备注 |
|---|---|---|
| stopped 与 error 是否同待遇 | **同待遇** | 两者同构（用户主动停 = 这一轮做了一半）；分开处理只多一个特例。stopped 天然多是无产出——流被掐断时 turn 里没有 assistant 条目，规则自动落成「一行不写」 |
| 失败轮的半截 assistant 行要不要进 mh | **要** | 不落 → 模型下一枪看到一条没人回答的 user 消息，接不上 |
| mh 里 tool_calls 没有配对结果怎么办 | `balanceToolResults` 补一条合成结果行（「没拿到结果」），**不编造结果** | OpenAI 协议要求 tool_calls 后紧跟对应结果，否则下一枪被拒。配平规则复用 `replayJournal` 已在做的事 |
| 记忆抽取线要不要放开到失败轮 | **不放开** | 记忆要可信的完整事实；失败轮虽落 runlog，但**不登记抽取任务**（outbox 仍只在 complete 分支）。`failtrace_test.go` 有断言钉住 |
| 闸失分支 | **仍零写入** | 接管者负责；旧进程的每次写都自然失败（doc/30 §7） |
| 账本删除时机 | **不变**（终态照旧删） | 账本的职责是续跑；续跑完了就没用了，内容已转进 mh / runlog |
| complete 分支 | **一行不改** | 用既有回归 + 契约矩阵重放兜底 |
| 用量记账 | 三个终态都记 | 2026-10-22 从「只在 complete 记」改成三终态都记——失败那轮也花了 token |
| 前端收口 | `error` / `stopped` 也拉 log 渲染 | 气泡以 log 为准，状态保留 error/stopped |
| runlog 语义变化 | 「有 assistant 行」不再 ≈「run 成功」 | 凡是拿它当成功判据的地方都要复查：前端已改；记忆线靠「不放开」这条不变量挡住 |

**活体验收（台账 §10 记录，2026-10-22 全部落地）**：

- 停止场景（B）：投一条会让 agent 先调 bash、说几句的消息 → 8 秒后 `POST /api/runs/{id}/stop` → 拉会话历史 → 至少两行（user + assistant 非空）。改前只有 user 一行。
- 反向用例（A）：模型一个字没说就报错 → log 里仍只有 user 一行，不该凭空多出 assistant 行。
- 模型接得上（C）：承 B 再发一条消息 → 新一轮模型输入里带着上一轮的半截回答与工具结果。
- 记忆不进（E）：承 B 等抽取线跑完 → `memory_items` 里没有这场 run 的产物。

## 5. 现状

- **仍有效**：`turn` 非空即留痕；stopped 与 error 同待遇；配平规则；记忆线只在 complete；闸失零写入；账本终态删除。
- **已知小瑕疵**：`web/src/chat.ts:838` 的注释仍写着「停止/失败在 log 里都不留 assistant 行」——这句话在 `d74bf91` 之后已过期（closeOut 已改为拉 log）。行为正确（reconcile 先查气泡是否已存在），注释待顺手清。
