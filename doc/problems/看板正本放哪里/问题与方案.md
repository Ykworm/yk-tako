# 看板正本放哪里：内存 Store 复活成 PG 表

> 模块：运行引擎 · 任务看板（doc/41 C 线 + doc/52 D32/D34/D35）｜状态：**已落地**（2026-10-23，`fd6a489`；B5/B6 2026-10-28 追加）｜证据：`doc/41-任务看板与人工审批.md` §3.3/§5.1、`doc/52-技能.md` D32/D34/D35、`internal/runengine/tasktools.go`

## 1. 场景与病灶

用户发了一条「把这三个接口改造成异步，顺便补测试」的长任务，run 跑了二十分钟。页面上只有一段段 tool_call 帧在滚——哪步做完了、卡在哪、还剩几件，全在模型脑子里。用户看不出整体进展。

旧线的任务看板（doc/01）本来解决这个，但它的正本是**进程内内存 Store**（doc/01 §3 原文：「进程退出即清空」）。随 v1–v5 旧线一起删掉后，v6 至今空着。

第二个病灶来自同一根：run 会崩。如果看板还是内存里的那张表，`kill -9` 一下，之前建的任务全部消失，续跑的模型面对一个空白看板，只能重新规划——而它重新规划的结果未必和原来一致。

病根不是「没有看板 UI」，是**看板的状态归谁持有**。归进程，崩溃即丢、多副本看不见、续跑接不上；归 PG，这三件事同时解决。

## 2. 候选与代价

| 候选 | 做法 | 好处 | 代价 |
|---|---|---|---|
| A 内存 Store（旧线 doc/01） | 进程内 map + eino session 镜像 | 零 I/O、实现最简单 | 进程退出即清空；多副本下各看各的；崩溃续跑全丢。旧线正是死在这里 |
| B PG 正本 + 四工具（选定） | `run_tasks` 表为唯一真源，工具 handler 直写行 | 崩得掉、续得上、多副本共享；会话内跨 run 可续做 | 每次工具调用一次 DB 写；需要 run 内自增序号 |
| C 从帧/running 内存重建 | 看板不落库，每次从 runlive 帧回放 | 不新增表 | 帧只活 300 秒；多副本读不到别人的帧；等于没存 |
| D 落在 mh 里当一条消息 | 把看板当普通 assistant 文本存进模型消息 | 复用现有存储 | 看板会参与折叠、被压缩截断——任务一多就丢行 |

选 B。与 v6 的整条存储哲学一致：**凡要长期存在的状态，先问多副本下它在哪**。看板行在 PG，续跑和崩溃接管天然兼容——续跑时 `TaskList` 读到的就是真相，不需要任何重建动作。

## 3. 对外协议：逐字继承旧线已验证的部分

四把工具、一个状态词表，不重新发明：

| 工具 | 签名 | 干什么 |
|---|---|---|
| `TaskCreate` | `(subject, description?, activeForm?) → taskId` | 建一行，返回 `task_no` |
| `TaskUpdate` | `(taskId, status?, …)` | 改状态 / 字段 |
| `TaskList` | `()` | 当前看板紧凑视图（+ 上一场未完成段） |
| `TaskGet` | `(taskId)` | 单行详情 |

状态词表：`pending → in_progress → completed`，不再需要时 `deleted`（`TaskList` 不列出）。

**约束写在 tool description，不写状态机**：≥3 步或用户列了多件事才建表；一步任务不建；动手前标 `in_progress`，同时尽量一条；做完立刻 `completed`；测试红 / 做了一半 / 未解报错不准 `completed`；卡住就 Create 一条 blocker。

**每个工具输出 = 操作回执 + 当前看板紧凑视图 + 催更块**。模型的眼睛始终能自校准——这条在跨进程续跑里更关键：被中断未执行的调用按 doc/30 默认不回放，模型靠 `TaskList` 自己对齐进度。

## 4. 同族小裁定

| 小问题 | 裁定 | 代价 / 备注 |
|---|---|---|
| 注入方式 | **静态注册**进一手工具池，不走旧线的动态 middleware | v6 没有「只在有看板语义下才有意义」的状态——每个 run 都是干活 run。子代理通过既有 `tools:`/`exclude_tools:` 自行裁剪 |
| Plan 层要不要重建 | **不重建**。Plan 只是提示词约定的口述方案 | doc/01 既定；v1 没有人审 gate。`enter_plan_mode`/`submit_plan` 是 doc/47 另起的一拍，不是看板的一部分 |
| 要不要 Action↔Task 双射 | **不做** | 「要硬进度：收窄执行模型，不要在开放 ReAct 上做语义对齐」（doc/01 §6） |
| 模型漏 Update 时自动勾选 | **不做** | 同上；语义对齐不可靠，宁可显式漏 |
| Graph 拓扑强制顺序 | **不做** | 同上 |
| 前端怎么渲染 | tool_result 文本带紧凑视图（给模型），另发 `kind=task` 帧（给前端） | 前端解析自然语言文本一换措辞就渲染错；帧是结构，文本是给人和模型的。词表 7→8 |
| 用户说的「第 N 步」指什么 | 页面看到的 `task_no`（`#%d [%s] %s`），**不是**技能正文的步骤编号 | 两者不保证对齐，必须在文档里说清 |
| 上一场的看板在新 run 里看不见怎么办 | `TaskList` 额外带「上一场」段：同租户同会话、最近一个**有任务**的 run、只列未完成行 | D34（2026-10-28）。取「最近一个有任务的」而非「最近一个 run」——后者就是当前这场，等于取空。全完成只回一行提示 |
| 写操作回执带不带上一场 | **不带**，只有显式 `TaskList` 才有 | 否则每建/改一条任务就把上一场的说明重付一遍 token |
| 「上一场」靠什么续上 | `description` 语义升级为「**这一步具体做什么**」 | 这是 schema 文案 + 提示词约定，**靠模型自觉、不是结构闸**；兜底是重读技能正文 |
| 任务归哪个技能 | `run_tasks.skill_name` 列，唯一写入点是 `TaskCreate`，按本 run 最近一次成功 `use_skill` 盖戳 | D32。不用 `Subject` 前缀编码（前缀脆、与序号挤在一起）；程序不代建任务 |
| 行的生命周期 | 完成不删（只改 `status`）；删除单位是**会话**不是 run | 全仓 `DELETE FROM` 没有一条指向 `run_tasks`。**今天的缺口**：`sweepDeletedSessionBatch` 只清 `run_model_messages`，`run_tasks`/`run_questions` 都没进清单 |
