# 崩溃前那半句要不要存

> 模块：运行生命周期 / Redis 临时态（`internal/runengine/`）｜ 状态：已落地（`6e4de68`，2026-10-20）｜ 证据：`doc/38-删除draft键.md`、`tmp/38-删除draft键/planning.md`、commit `6e4de68`

## 1. 场景与病灶

一场 3000 字的回答，最后一个 delta 已经推到了浏览器上。`EndRun` 开始收尾，此时 Redis 正在做主从切换。

旧实现里 `EndRun` 的第一件事是 `GET tk:draft`——把流式过程中缓存的正文读出来，再写进 `runlog_entries`。连接错误时它直接在开 PG 事务之前返回。结果：**PG 里 run 仍是 running，租约过期后读侧判「已中断」，下一次 POST 把它清扫成 error。用户屏幕上明明看到了完整回答，刷新后却变成一个失败气泡**——模型已经写完、PG 也健康，但这场回答永远不会进 runlog。

`tk:draft` 同时干着两件事，这是问题的根：

1. **定稿正文的缓存**（EndRun 从这里拿文本）；
2. **run 是否还活着的哨兵**（append 前 `EXISTS draft`，不在了就停止推流）。

两个职责都绑在一个易失键上，于是「缓存被 `maxmemory` 逐出」被误读成「执行者死了」，「最后一枪后 draft 消失」被写成「complete 但空回复」。

## 2. 候选与代价

要换的是「正文从哪拿」和「活判看什么」两件事。

| 问题 | 候选 | 好处 | 代价 |
|---|---|---|---|
| EndRun 正文源 | A `GET tk:draft` | 零改动 | 定稿依赖 Redis 可用性；Redis 故障即丢整场回答 |
| | B 参数里现成的 `pending[""]`（内存 turn 累计） | 与 draft 逐字节同源；PG 事务照常提交 | 依赖「turn 累计」这一约定 |
| | C 读 `run_journal` 拼正文 | PG 真源 | 多一次读、多一个失败面，而 turn 已经在参数里 |
| 活判哨兵 | A `EXISTS draft` | 简单 | 缓存被逐出 = 判死；最后一枪后写空回复 |
| | B `EXISTS runlive` | 键一定在 | terminal 后还有 300s TTL，旧执行者能在收尾后继续追加；把帧流契约与判活绑死 |
| | C `runepoch == epoch` | 回答「我还是不是这一代的执行者」 | 要改名、改测试 |
| 删法 | A 先换正文源、再换哨兵 | 可逐字节对照 | 两个不可发布的中间态：A1 后 draft 只写不读，A2 后 APPEND 可能重建无 TTL 的孤儿键 |
| | B 一次性删干净 | 无中间态 | A1 diff 约 195 行，超过 80 行目标 |

**裁定：正文取 `pending[""]`（B），哨兵换 `runepoch == epoch`（C），draft 一次性删干净。** `pending[""]` 正是 `Σ root assistant turn Text`，写进 runlog 的字节与旧路完全相同；`runepoch` 回答的是执行者身份，不是「某个缓存键在不在」。

## 3. 同族小裁定

| 小问题 | 裁定 | 代价 / 备注 |
|---|---|---|
| 拒写出口顺手把 status 改成 error 吗？ | 只改名 `live`→`accepted`，不改行为 | 四个 `!accepted` 出口仍直接 return；「被逐出算失败还是可接受的部分定稿」是产品判断，另案 |
| 崩溃前那半截 delta 持久化吗？ | 不存，随 resume 丢弃 | 每个 delta 写 PG 会把 at-most-once 改成 at-least-once，需要新持久化层与幂等语义；doc/30 已裁 at-most-once |
| 保留 draft 只当缓存 / 加 `TAKO_DRAFT` 开关？ | 不做 | 「要不要一个缓存」不是运维选择，是结构决定 |
| 正文写入的字节怎么保证不变？ | 用单测与活体对账替代过渡态 | 一次性删除的风险由「逐字节等价证明 + 六件单测 + 五场活体」吸收 |
