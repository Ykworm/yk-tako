# 租户从第一天就在

> 模块：多租户与身份（`internal/runengine/product_store.go` / `auth.go`）｜ 状态：已落地（`9c21b66`，2026-10-19）｜ 证据：`doc/28-多租户.md`、`tmp/28-多租户/planning.md`

## 1. 场景与病灶

产品先服务个人用户，团队功能「几个月后再上」。这几个月里，`sessions`、文件目录、`notes` 都已经按「用户」落了盘。

等团队功能上线，要补的东西是：给每张表加 `tenant_id`、把所有文件从用户根搬到租户根、把每条查询改成「团队内可见/个人可见」两套。如果当时为了快，用的是可空 `team_id`，那么每条查询永久分叉成「有团队 / 无团队」两条路径——**漏一条就是跨租户读**。

这是典型的「先快后返工」：省下的是建表时的一列，付出的是全量数据搬迁加永久双路径。

## 2. 候选与代价

| 候选 | 做法 | 好处 | 代价 |
|---|---|---|---|
| A 用户直挂资源，`team_id` 以后加 | 个人版先跑起来 | 起步快 | sessions / 文件根 / notes 全量加列并搬目录；查询双路径永久化 |
| B tenant 第一天就在，个人只是单成员 tenant | 所有表和查询从一开始就带 `tenant_id` | 以后加团队只多一行 membership，资源不搬家 | 从第一行代码起就要处理租户上下文 |

**裁定：B。** 「加团队」变成一个纯数据动作：`tenant_members` 插一行，资源一条都不动。

## 3. 同族小裁定

| 小问题 | 裁定 | 代价 / 备注 |
|---|---|---|
| 角色写进 JWT 还是每次查库？ | JWT 只带 `sub` / `tid`，角色每次从 `tenant_members` 解析 | 降级/移除立即生效；同一 user 在 A 是 owner、B 是 member，单值 claim 根本表达不了。代价是每请求一次查询 |
| `runs` / `messages` / `runlog` 要不要冗余 `tenant_id`？ | 不加；`tenant_id` 只在 `sessions` 上，其余回查 | 每表冗余会造多个事实源，某条写入路径漏填一次就出现「run 属于 A、session 属于 B」的串租户数据 |
| 归属校验只放 handler 吗？ | handler 之外，**store 每个入口在同一笔事务里**再回查 tenant/user/visibility | 内部调用方（worker、清扫器、子代理工具）会绕过 handler；只在 handler 查等于给新入口留裸奔口 |
| 没有归属模型的全局端点（media / memory / mcp）先放所有登录用户吗？ | 不放；没有归属前只放 `system_admin`，随各条线做正后逐个开放 | 「先加 auth 放所有人」等于把全局 media 根、全局 MCP 配置、别人记忆暴露给任意新注册用户。保守闸不是最终产品语义，是过渡 |
| 系统管理员是什么角色？ | `users.is_system_admin` 与租户角色正交 | 平台运维不该靠「混进某个租户当 owner」获得权限 |
