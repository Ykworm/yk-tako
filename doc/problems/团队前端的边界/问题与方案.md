# 团队前端的边界

> 模块：前端 / 团队与邀请（`web/src/MembersView.vue` 等 + `product_api.go`）｜ 状态：已落地｜ 证据：`doc/36-团队前端.md`、`tmp/36-团队前端/planning.md`

## 1. 场景与病灶

团队页面要处理四个真实动作：拉人、发邀请、按角色显隐按钮、被邀请人落地注册。

四个地方各自有一个「看起来更顺」的做法，但都会把语义弄坏：

1. **直接添加成员**：填邮箱点「添加」。后端对未注册邮箱回 404 `111201`，文案却是成员语义，页面显示成「成员不存在」——用户以为系统坏了。
2. **服务端发邀请邮件**：要引入发信设施、退信、垃圾箱、域名信誉。在还没有邮件基础设施时，邀请链接会卡在「怎么发出去」。
3. **前端藏按钮当权限**：viewer 看不到「移除成员」按钮，但可以直接调 API。任何会用 devtools 的人都能越权。
4. **注册成功直接发 token**：把注册与登录流程耦合，安全面扩大；而后端成功体本来只有 `{userId, status:"accepted"}`，前端若假装登录，与真实会话状态不一致。

## 2. 候选与代价

| 问题 | 候选 | 好处 | 代价 |
|---|---|---|---|
| 拉人入口 | A 做「直接添加成员」 | 少一步 | 未注册邮箱文案错位、误导 |
| | B 不做入口，只走邀请流（定案） | 语义一致 | 拉未注册者要发链接。接口保留给 curl/运维 |
| 邀请怎么送达 | A 服务端发邮件 | 体验完整 | 邮件设施与运维 |
| | B owner 复制 `<origin>/invite/<token>` 自己转发，7 天过期（定案） | 零设施 | 手动转发 |
| 前端显隐算不算权限 | A 是 | 省后端 | 可绕过；矩阵与后端漂移 |
| | B 只做显隐，后端每个路由自己查角色（定案） | 安全边界在后端 | 两处维护矩阵 |
| 邀请注册后 | A 直接发 token 进团队 | 顺滑 | 注册与登录耦合、安全面扩大 |
| | B 不发 token，前端明示「注册成功，请登录」（定案） | 流程诚实 | 多一步 |

**裁定：B / B / B / B。**

## 3. 同族小裁定

| 小问题 | 裁定 | 代价 / 备注 |
|---|---|---|
| 角色矩阵写在哪？ | 后端 `RequireTenantRole` 是唯一判定；前端只按角色藏按钮 | 前端的矩阵是「体验」，不是「权限」 |
| 邀请 token 过期多久？ | 7 天 | 过期由服务端判，前端只在落地页显示错误 |
| 待处理邀请在哪儿处理？ | 顶栏 `PendingInvites` 展开；落地页 `InviteLanding` 负责未注册/已注册两条路 | 两条路都不自动切换身份 |
| 租户切换怎么做？ | `auth.ts` 存 active tenant，切换后重拉全部列表 | token 带 `tid`，切换要换 token |
