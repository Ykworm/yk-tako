## 0. 为什么三件事捆成一份方案

**背景**：doc/16 §5.1 把「人工审批 + PII 脱敏」排为当前待做第 1 项（原话：agent 能写文件、能跑 bash，没有闸等于让租户数据裸奔），「v6 任务看板」排第 2 项；§2 表 #7 行还挂着一个 ⬜ 的「内存 checkpoint + interrupt 审批」。用户要求出一份结合现行代码状况的独立方案，本文就是。

先讲三个会真实发生的病灶故事：

**病灶一（看板）**：用户发了条「把这三个接口改造成异步，顺便补测试」的长任务，run 跑了二十分钟。页面上只有一段段 tool_call 帧在滚，用户看不出整体进展——哪步做完了、卡在哪、还剩几件，全在模型脑子里。旧线的任务看板（doc/01）本来解决这个，但它的正本是**进程内内存 Store**（doc/01 §3：「进程退出即清空」），随 v1–v5 旧线一起删了，v6 至今空着。

**病灶二（PII 与审批）**：租户 A 的 agent 跑 `cat .env`——bash 工具今天零守卫（`bash.go:3-4` 明文写着「不做危险命令表」），`.env` 里的厂商 API Key 原样进 tool_result 帧、进 mh（模型消息表）、进 runlog（历史真源），再被记忆抽取带进 memory_items 长期保存。多租户已经能区分人和组织（doc/28），但数据在 agent 工具链里是裸奔的。密钥之外，用户消息里的身份证号、手机号也一路原样喂给模型、抽进记忆。

**病灶三（interrupt 审批）**：就算定出「危险命令要拦下来问人」的规则，v6 的 run 也只有三种活法：complete / error / stopped（`worker.go` 收尾三态）。引擎里**没有任何「暂停等人」的生命周期**——`interrupted` 存在，但那是崩溃后的读侧派生视图（`server.go:864-872`：status 仍 'running'、租约过期），语义是「执行者死了」，不是「挂起等人」。旧线用过 eino 的 `compose.StatefulInterrupt` + gob checkpoint（doc/06、doc/blog），v6 翻篇时明确不做 eino checkpoint 接入（doc/30 §15），这条技术路线没有随代码留下来。

三个病灶共用同一副地基：**把 run 停在工具调用前、问人、按人的决定继续**。PII 的「拒收／打码」要挂在同一处工具链上才能全覆盖；看板的「任务进度」挂在 PG 上之后才天然活得过崩溃续跑。分开做，等于三次重造同一套帧、端点、表和前端卡片。所以：一份方案，三个 loop（§6），**人审回路只做一次**。

**端到端链路**（每环可点名，机制在链路中的位置见 §3）：

```
用户发消息 → POST /api/runs 起 run（会话闸：runs 行部分唯一索引）
  → worker 主循环 agent.Run（worker.go:620-774）
  → 模型决策 → tool_call 帧（AppendFrame 进 tk:runlive）
  → journalWrapHandler 先记意图（run_journal 表，intent 写失败不执行）
  → 审批闸 gateMW 判定：allow / deny / ask
       deny  → 解释文本当 tool_result 回给模型（不调工具、不打扰人）
       ask   → run_approvals 表落一行 + approval 帧 + 阻塞轮询该行
             → 人看帧/审批卡 → POST /api/approvals/:id/decide（PG CAS 一裁终裁）
             → 批准：真执行，结果照常回模型；拒绝：拒绝文本当 tool_result
  → PII 打码贴在真工具内侧：工具返回先打码再往外流（模型/mh/帧/runlog 全干净）
  → 模型继续或定稿 → terminal 帧 → EndRun 事务（mh + runlog 一笔落库）
  → 挂起期间进程死了：租约过期 → 派生 interrupted → 客户端 resume（doc/30 通路）
  → 重放 journal 时对到 run_approvals 行：pending → 重新挂起；approved → 补执行；rejected → 补拒绝文本
```

## 1. 名词准入（操作定义，后文不再重复解释）

- **人审回路**：工具调用执行前的一道闸 + 一次等人。闸判 allow/deny/ask 三态；ask 时 run 挂起，人的决定回来后 run 继续。三态语义逐字继承 doc/06：allow 直接放行；deny 把解释性 string 当结果挡回给模型（**不抛 error**）；ask 暂停问人。
- **审批行（run_approvals 表一行）**：一次 ask 的持久态。字段见 §5.1；状态机只有 `pending → approved/rejected`（外加终态 run 死亡后清扫的 `stale`）。它是多副本下「人在另一个入口裁决、worker 在本进程等」的共享阵地——裁决不是进程间消息，是** UPDATE 这一行**。
- **挂起**：worker goroutine 阻塞在审批轮询上（SELECT 该行，1–2s 间隔），run 不结束、租约照续、不烧 token、不消耗迭代数。与之相对的 `interrupted` 是**死了**，挂起是**活着在等**。
- **裁决**：人对一条审批行做出的 approve/reject。端点里用 PG 条件更新实现一裁终裁：`UPDATE run_approvals SET status=$2 WHERE id=$1 AND status='pending' RETURNING`——影响 0 行就是被别人裁过了，回 409。没有「第二个副本一起判」的窗口。
- **打码**：正则命中后把敏感串换成保留头尾的掩码（旧线口径：头尾各 4 位；证件类中间位全掩）。打码不是删除原文的唯一策略——三处挂载点策略不同，见 §3.2。
- **tasktracker**：任务看板在 v6 的统称（命名已裁定，doc/XX handoff，仓库零落点）。对外是 TaskCreate/TaskUpdate/TaskList/TaskGet 四把工具，状态词表 `pending/in_progress/completed/deleted`。
- **checkpoint（v6 语义）**：本文**不重建**旧线意义的 eino gob checkpoint。v6 的等价物已经存在：mh（`run_model_messages`，模型输入唯一读源）+ run_journal（意图账本）+ runs 行的租约/令牌。interrupt 审批新增的持久态只有 run_approvals 一行。理由见 §3.1 第四段。

## 2. 现状锚点（方案就建立在这些事实上）

结合现行代码（2026-10-22，main @ 7ef004e）逐条锚定：

1. **工具链零守卫**。一手工具池在 `worker.go:192-245` 逐个 append，执行链 = ADK `ToolsNode` 直执行；唯一的包装是 `wrapToolErrors`（错误回注）和 `journalWrapHandler`（记账）。`bash.go:3-4` 明文不做危险命令表。`tools.go:47` 留了一句注释「interrupt 类错误原样透传，不挡未来 HITL」——eino 的错误通道是预留未用的出口。
2. **middleware 挂点现成**。`journalWrapHandler` 就是 `adk.ChatModelAgentMiddleware`，覆写 `WrapInvokableToolCall`（`journal.go:55-65`），在 handler 链最内位。审批闸和 PII 打码用同一个钩子类再包两层即可。**顺序即语义**（doc/blog §3：handlers[0] 最外层），本方案的执行序：gate（外）→ journal（中，既有）→ pii（内，贴真工具）。
3. **帧只有 7 种**。`contract_test.go:148-158` 用生产代码字面量钉死词表：`start/delta/tool_call/tool_result/usage/terminal/resume`。写帧唯一口 `AppendFrame`（Redis RPUSH 进 `tk:runlive`），轮询与 SSE 两条运输都原样透传 kind——加第 8、9 种 kind 传输层无障碍，但词表测试会立刻红，**这是显式的同步点，不是隐患**。
4. **journal 意图先行，这就是挂起现场的半边**。`journal.go:79-121`：intent 写失败不执行工具；result 写失败 run 走 error。崩溃恢复 `replayJournal`（`journal.go:141-255`）按 call id 归组重放，缺结果的调用回注固定文本 `interruptedResultText`（at-most-once，不重跑）。**审批挂起天然借这层**：挂起时 intent 已在账本里，进程死了重放也对得上。
5. **interrupted 是派生视图，不是存储状态**（doc/30 §2.3 的选择原文）：runs 行保持 `status='running'` + 租约过期，读侧派生。部分唯一索引 `one_live_run_per_session` 不放闸。本方案的挂起**沿用同一哲学**：不加第四种存储状态，挂起 = running + 存在 pending 审批行（读侧可派生「等审批」）。
6. **恢复通路现成且已验收**。`POST /api/runs/:id/resume`（`server.go:579-645`）：claim 用 PG `FOR UPDATE` CAS、epoch+1、三个 409（112102/112103/112104）；`seedResume` 丢 runlive 重建；`RunResume` 与 Run 共用主体（`worker.go:428-430`）。审批恢复是它的一个分支，不新造通路。
7. **PII 是彻底空白**。记忆条目 `MemoryItem`（`memory.go:65-77`）只有 kind 词表（fact/preference/decision/episode），无敏感分级；抽取只有提示词劝阻「不抽密钥」（`memory.go` 抽取提示词），无程序拦截；写入校验只查隐形字符与伪造块。全仓唯一带 mask 字样的是 `maskSecrets`（`product_store.go:874`，租户配置密钥出 API 打 `***`），与 PII 无关。`bash.go:24-26` 的 env 白名单是唯一「密钥不进历史」的现役机制。
8. **旧线的两份设计档案还在**。doc/06 记录了三态守卫（allow/deny/ask）、命令/文件守卫规则（`.env/.git/.ssh` deny、工作区外 ask）、7 条密钥正则打码（`sk-proj-`/`AKIA`/`AIza` 等，头尾各 4 位）、两个挂载点；`docs/superpowers/` 的 MAF 设计记录了消息级请求-回执协议（框架替你把调用换成审批请求，人回执后按 call id 重入）。**两者代码都已出仓，本文只继承结论，不继承实现**。
9. **eino StatefulInterrupt 这次不用**。旧线博客（doc/blog）记过它的真实成本：信号树、地址链、gob 序列化全链、文档与实现互斥的坑。更硬的理由是 v6 的 run 循环是 worker 直驱动（`agent.Run` 单调用 + 事件消费），没有可重入的执行图，StatefulInterrupt 的恢复语义（checkpoint + 地址重入）无用武之地；而「阻塞在工具包装里 + 决定落 PG 行」在多副本目标栈下天然正确——gob checkpoint 是进程内字节，DB 行是共享阵地。
10. **tasktracker 是空位**。名字已裁定（doc/XX），代码零落点；旧方案的对外协议（四工具、四状态、约束写 tool description、明确不做三件）是重建时唯一的体内参照。

## 3. 总设计

### 3.1 人审回路（底座，只做一次）

**闸的判定**（纯函数，金样单测钉死）：

```
gate(toolName, argsJSON, workspaceCtx) → allow | deny(理由) | ask(理由)
```

- **deny 规则**（硬拦，解释文本当 tool_result 回模型，不问人）：写类文件工具目标命中 `.env`/`.git`/`.ssh`/`id_rsa*`；写系统目录（`/etc`、`/usr`、根）；bash 命中危险命令正则一级表（`rm -rf /`、`mkfs`、`dd of=/dev/sd*`、fork bomb、`chmod -R 777 /` 等，逐条金样）。继承 doc/06 口径：「能问的不拒，该拒的不问」，全 ask 会把审批弹窗变成噪音。
- **ask 规则**（挂起问人）：**bash 一律 ask**（v1，对齐 doc/26 §9 登记的「主代理 bash 加确认闸/HITL 后话」；deny 表优先）；写类文件工具目标在工作区外；**MCP 工具（`mcp__*` 前缀）一律 ask**——第三方 server 不可信，且它们本就走 deferred 档、调用低频，噪音可接受。
- **allow**：其余（读类文件工具在工作区内、memory、search_history、get_time 等）。
- 策略表一期硬编码在 `gate.go` + 金样测试；租户级可配（挂 tenant_settings）登记为后续拍，不做进 v1。

**ask 的三拍**（每步四问齐全）：

1. **落行**：`INSERT run_approvals`（tenant_id/run_id/session_id/tool_name/args/reason/status=pending）。不做会怎样：进程死了解释不清在等什么。
2. **发帧**：`AppendFrame` 一条 `kind=approval` 的帧（字段映射见 §5.2）。不做会怎样：前端不知道在等人，页面死寂。
3. **阻塞等**：goroutine 内 1–2s 轮询该行，直到 `status != pending`；全程尊重 ctx（stopRun 能打断，run 走 stopped，行留 pending，裁决端点后补 409）。批准 → 调真 endpoint（原参数，不换）；拒绝 → 返回拒绝文案（「用户拒绝了这次调用。不要重试相同命令；需要的话先跟用户商量替代方案。」语义继承 doc/06）。

**挂起现场 = 账本 intent + 审批行，不新造 checkpoint**。挂起期间 worker 活着：watchdog 照续租约（`worker.go:519-526`），帧流静止，agent loop 不消耗迭代数。这解决什么：一次 ask 不需要把内存里的消息列表、循环进度序列化到任何地方——模型输入的下一次装配本来就从 mh 全序 + 账本重放出发（`prepareInput`），中断 run 的行本就未进 mh（EndRun 才落），journal 已经记了 intent。**没这层会怎样**：要么退回旧线 gob checkpoint（多副本下是进程内字节，裁决端点在别的副本够不着），要么挂起期间进程一死现场全丢。

**崩溃兼容是 journal 重放的一个分支**。挂起中进程死 → 租约过期 → 派生 interrupted（既有）；客户端 resume（既有 claim CAS）→ `replayJournal` 重放到这条 intent 时查 run_approvals：

| 账本 intent 对到的审批行 | 重放行为（对齐 doc/30 两个恢复分支的新第三分支） |
|---|---|
| 无行 | 维持现状：`interruptedResultText` 回注，不重跑（at-most-once） |
| `pending` | **重新挂起**：重发 approval 帧（seedResume 已清空 runlive，天然幂等），继续轮询 |
| `approved` | **补执行**：此刻真调 endpoint，结果落账本 |
| `rejected` | 拒绝文案回注 |

**没这个分支会怎样**：批准了的调用在 resume 后被当成「结果未知」跳过——人白批了，且模型拿到的文本与批准语义矛盾。**resumeCount 语义不变**：挂起不消耗次数（lease_epoch 不动），只有崩溃接管才 +1（doc/30 既有语义）。

### 3.2 PII 脱敏（三个挂载点，三种策略）

PII 在本方案指两类：**密钥类**（API Key、token、密码——旧线 7 条正则口径，直接继承并扩到 `AKIA`/`AIza`/`hf_`/`sk-` 家族与赋值形式）与**证件类**（身份证号、手机号、邮箱、银行卡）。打码掩码规则：密钥类头尾各 4 位（旧线口径）；证件类保留可人工核对的头尾、掩掉可直接利用的中段——逐条金样钉死。

| 挂载点 | 位置（执行序） | 策略 | 没它会怎样 |
|---|---|---|---|
| ① 工具返回 | piiMW 贴真工具内侧，wrapper 的返回路径上 | **打码后返回**：模型、mh、runlog、tool_result 帧全部只见过干净文本（打码即焚，原文不进任何持久层） | `cat .env` 的密钥落帧落库，被记忆抽走，多租户数据裸奔 |
| ② 模型输入装配 | `prepareInput`（`worker.go:1043-1049`）出口 | **喂模型前打码**：mh/runlog 保留原文（页面要显示用户原话），模型侧只见掩码 | 用户消息里的身份证号被模型复述进终稿、带进记忆 |
| ③ 记忆抽取入库 | `memory.go` 抽取管线 parseExtraction 之后、入库之前 | **密钥类拒收**（整条丢弃，提示词劝阻变成程序拦截）；**证件类打码后入库**（记忆要复用，拒收会把可用信息一起扔掉） | memory_items 慢慢攒成 PII 库，召回一次带一次 |

三个点共用同一个扫描函数（`pii.go` 纯函数 + 金样单测 + dev 探针端点）。①与②策略不同是刻意的：工具输出夹带的密钥没有「用户想在页面上看到原文」的需求，焚掉最干净；用户消息原文要留在 runlog 里给页面回放，模型侧出口打码就足够。③的拒收/打码分档是开放问题第 2 条。

**本期不做**：落库加密（at-rest）、向量库侧的 PII、对外 API 返回体的 PII 审查（记忆端点本来就是 dev 观测口）。这些是数据安全另案，不是 agent 工具链的闸。

### 3.3 任务看板（tasktracker）

**对外协议逐字继承 doc/01**（旧线被验证过的部分，不重新发明）：

- 四把工具：`TaskCreate(subject, description?, activeForm?) → taskId`、`TaskUpdate(taskId, status?, ...)`、`TaskList()`、`TaskGet(taskId)`。
- 状态词表：`pending → in_progress → completed`，不再需要时 `deleted`（TaskList 不列出）。
- **约束写在 tool description，不写状态机**：≥3 步或用户列了多件事才建表；一步任务不建；动手前标 in_progress，同时尽量一条；做完立刻 completed；测试红/做了一半/未解报错不准 completed；卡住就 Create 一条 blocker。
- **每个工具输出 = 操作回执 + 当前看板紧凑视图 + 催更块**（模型的眼睛始终能自校准）。
- **Plan 层不重建**：doc/01 既定——Plan 是给人审的文档，v1 没有人审 gate、没有 ExitPlanMode 式 interrupt，仅以提示词约定的口述方案形态存在。看板使用约定（什么时候建表）静态拼进系统提示——doc/blog 的同款答案：「提示词和工具，一个都不能少」。
- **明确不做三件**（继承 doc/01 §6）：Action↔Task 双射、模型漏 Update 时自动勾选、Graph 拓扑强制执行顺序。「要硬进度：收窄执行模型，不要在开放 ReAct 上做语义对齐。」

**存储改掉旧线的死因**：正本从「进程内内存 Store + eino session 镜像」（doc/01 §3，进程退出即清空）改成 **PG 表 `run_tasks`**（字段见 §5.1）。每个操作四问：做什么——工具 handler 直写一行；不做的后果——回到进程内存就是回到「崩溃即丢」；输入——TaskCreate/TaskUpdate 的参数（handler 拿到 args）；输出——该行 + 回执文本。崩溃续跑兼容性免费获得：已执行的 TaskCreate 行在 PG 里活着，resume 后 `TaskList` 读到的就是真相；被中断未执行的调用按 doc/30 默认不回放，模型从 TaskList 自校准（这正是旧线「回执带紧凑视图」的跨进程版）。

**注入方式从旧线的动态 middleware 改为静态注册**：v6 没有「只在有看板语义下才有意义」的状态——每个 run 都是干活 run。四把工具直接 append 进一手池（`worker.go:192-245` 那段），子代理通过既有的 `tools:`/`exclude_tools:` 四态自行裁剪（对齐 doc/26 四态表，金样测试 `TestShippedAgentSpecToolGuards` 需要同步——出厂规格的 effective 名单会多四把工具，金样行逐条更新）。

**帧**：tool_result 文本始终带紧凑视图（模型的眼睛，零契约成本）；另发 `kind=task` 帧给前端结构化渲染看板（契约 +1，见 §5.2）。没 task 帧会怎样：前端要解析自然语言文本才能画看板，换个提示词措辞就渲染错——帧是结构，文本是给人和模型的。

## 4. 顺序即语义：handler 链与装配点

```
一手池工具
  └─ wrapToolErrors（既有，错误回注）
       └─ gateMW（新增，最外）：allow 透传 / deny 返回解释 / ask 三拍
            └─ journalWrapHandler（既有）：intent 记账——挂起前落账，崩溃重放对得上
                 └─ piiMW（新增，贴真工具）：返回路径打码
                      └─ 真工具
```

- gate 在 journal **外**：deny 的调用从未发生，不该有 intent；ask 的调用intent 必须先落（挂起现场的半边）。
- pii 在 journal **内**、贴真工具：打码发生在结果返程上，意图与结果的分工不被打乱。
- MCP 工具与委派工具走同一个 `WrapInvokableToolCall` 链（`mcp.go:274`、`agents.go:507-509` 都在 handler 覆盖范围内）——**审批与打码对 MCP/子代理调用天然生效**，帧进当前 run 的 runlive。v1 验收只覆盖主代理；子代理调用触发审批时帧出现在父 run 帧面，属预期行为（登记为已知形态，不单独立拍）。

## 7. 明确不做（本期）

- **不做 eino checkpoint / gob 快照**：v6 已有等价物（mh + journal + 租约），doc/30 §15 裁断沿用。interrupt 审批的现场 = 账本 intent + 审批行。

- **不做看板三件**：Action↔Task 双射、自动勾选、拓扑强制（doc/01 §6）。
- **不做 server 巡检自动恢复/自动裁决**：挂起期间恢复触发沿用 doc/30 A6 裁断——客户端触发；用户不在场 run 一直挂着，是同一取舍的直接后果，不是缺陷。
- **不做 at-rest 加密、对外 API 的 PII 审查**：数据安全另案。
